# 🤝 贡献 {#contributing}

**帮助构建每个人都值得拥有的 AI 界面。**

Open WebUI 是一个独立项目，由一支小而专注的核心团队开发和维护。测试开发版本、提交清晰的 Bug 报告、在 Discussions 中说明使用场景、改进文档以及翻译 UI，都是最有价值的贡献方式。维护者会在内部评估并开发代码改动；**代码 PR 需要维护者明确提出请求**，仅涉及 i18n/本地化的改动除外。本页面介绍如何参与贡献，以及参与时可以期待什么。

---

## 行为准则 {#code-of-conduct}

所有贡献者和社区参与者都必须遵守 **[行为准则 (Code of Conduct)](https://github.com/open-webui/open-webui/blob/main/CODE_OF_CONDUCT.md)**。我们实行**零容忍政策**：任何不尊重、强求或带有敌意的行为，都将在没有事先警告的情况下受到立即处理。

Open WebUI 由一个专注的核心小团队领导，并得到了来自整个项目贡献者的支持。请以专业和尊重的态度对待每一次互动。

---

## 贡献方式 {#ways-to-contribute}

### 测试开发分支（dev） {#test-the-development-branch}

最有价值的贡献之一完全不需要编写代码。只需运行开发分支，在日常中使用它，并报告出现的问题。

```bash
docker run -d -p 3000:8080 -v open-webui:/app/backend/data --name open-webui ghcr.io/open-webui/open-webui:dev
```

开发分支更新很快，因此请**定期拉取最新更新**。如果你不想使用 Docker，请改为遵循 [开发 Open WebUI](/getting-started/advanced-topics/development) 指南。

在 [GitHub](https://github.com/open-webui/open-webui/issues) 上报告问题时，请提供清晰的复现步骤。社区测试有助于我们交付高质量的发布版本。

### 提交代码 {#submit-code}

我们在内部开发并打磨解决方案，因为外部实现通常需要大量返工才能契合项目。**只有在我们已经明确提出请求，或者改动仅限于 i18n/本地化时，我们才接受代码 PR。** 这一要求涵盖缺陷修复、新功能、重构、依赖变更、界面改动以及仅含测试的改动，无论补丁大小、检查是否通过，也无论代码是手写还是借助 AI 辅助完成。被确认的缺陷或对一个想法的正面回应，都不构成对某个实现的请求。不按此流程提交的 PR **通常会被直接关闭，不予评审**。

**我们会监控并验证每一个 issue**，并且**往往已经在内部有了可用的解决方案**，只是在评估和完善方案期间尚未推送。某个 issue 仍未关闭、也没有公开回应或关联 PR，并不意味着它被忽略了，也不意味着存在可以接手实现的工作。一个可用的修复仍然需要契合项目的架构、既有行为和正在进行的工作。这种评估经常改变解决方案的范围和落点：界面上的一个症状可能源自共享状态、API 契约或特定提供商的行为，而一项新设置可能以牺牲其他工作流为代价来迁就某一个工作流。解决眼前症状只是工作的一部分。公开仓库的动态不会展示每一项正在进行的调查或实现，而主动提交的 PR 往往与已在进行的工作重复，同时还引入了另一种需要调和的方案。维护者需要空间先完成这些评估，再公布结果。

"需要明确请求"这一要求，确立了由谁决定什么样的实现工作进入项目、以及何时进入。主动提交的 PR 带来了既定的范围、设计和一组取舍，而维护者还未就项目是否应采用这些具体选择达成一致。评审它会把一个开放的设计问题，变成针对某个既有实现的讨价还价。作者的投入随之带来保住该方案的压力——即使正确的结果是另一种设计、更小的改动，或者根本不加东西。我们需要基于项目需求来做这些决定。维护者的请求意味着我们已经确认了有价值的外部工作，并且**在有人投入之前就商定了它的目的和范围**。

这正是**该要求同样适用于优秀代码**的原因。如果每个主动提交的 PR 都以"它可能有用"为由获得评审资格，我们就必须先完成评审才能判断该要求是否适用，提交规则也就形同虚设。我们不为自行选择的实现维护一个通用评审队列。我们按项目优先级挑选工作，并在这些工作需要外部贡献时提出请求。干净的 diff、通过的检查或愿意修改的承诺，都无法替代这一决定。即使评审能力充足，这仍然是我们的开发流程。

评审一个外部实现、解释所需的修改，并协调多轮修订，**通常比在内部开发解决方案更费力气**。零散的提交历史、没有 rebase 的分支、未解决的冲突、无关的改动，以及未经验证的 AI 生成解释，都会增加额外工作。维护者仍必须重建其中隐含的假设、评估更广泛的影响，并足够理解最终实现才能为其负责。而这些工作占用的注意力，与回归修复、安全修复和发布所需的是同一份。这条要求可以避免计划外的实现评审挤占这部分注意力。

**代码一旦发布，团队就要在后续版本中为它的行为负责。** 我们必须在必要时保持兼容性、诊断故障、维护文档和回归覆盖，并随着周边系统的演进而调整该改动。每一个新依赖、新设置和新抽象都会增加这份责任，而用户会围绕我们接受的行为构建工作流。事后移除一个不合适的改动，同样会带来兼容性和迁移成本。必须为这些后果负责的人，应当在实现开始之前就决定项目要承担哪些承诺。例外工作由维护者主动提出并评估。贡献者不能因自己看好某个补丁就绕过流程。

**对于新增或重写的自动化测试（包括 fixture、快照和测试基础设施），我们同样要求明确的请求。** 请求实现某个修复，并不包含添加测试套件的请求。当代码和测试基于同一组假设生成时，它们可能彼此一致，却同时对预期行为判断错误。从当前输出推导出的断言会固化错误；mock 可能恰好移除失败发生的那处集成；快照则可能记录下错误的结果。绑定内部函数调用的测试会妨碍一次合理的重构，却检测不到面向用户的回归。**这类测试通过只会制造虚假的安全感**，而更多的断言和更高的覆盖率，几乎不能说明真正该验证的行为是否被验证过。

这些测试本身又变成了一份需要调查、重写和维护的实现。在依赖它们之前，我们必须验证它们的预期结果、隐含假设，以及它们能否检测出最初的那个故障。维护者会在确定预期行为之后，于内部选择持久的回归覆盖，并在有助于该计划时提出外部测试工作的请求。对于被请求的 PR，**请提供来自运行中应用的、可复现的证据**：环境准备、确切步骤、预期行为，以及改动前后的实际结果。附上相关的日志、截图或录屏，运行与该改动相关的既有检查，并报告失败项以及你无法验证的部分。不要为了让某个改动通过而删除、禁用或削弱既有测试。手工验证和通过的测试套件，都不能取代对方案本身及其更广泛影响的评审。

**公开源代码与接收外部贡献是两个彼此独立的项目决策。** [SQLite 自称"开放源代码，但不接收贡献"](https://www.sqlite.org/copyright.html)：它的限制条款保留了其代码的公有领域状态，其文档则说明概念验证补丁可以被从头重写。SQLite 有一套接收贡献代码的正式流程。两者的相似之处在于：有价值的报告和参考实现可以为解决方案提供信息，而维护者保留对最终发布内容的控制权。Open WebUI 的理由关乎开发产能、架构一致性和长期责任归属；SQLite 的公有领域要求则是 SQLite 特有的。

[tldraw 在 2026 年 1 月的政策公告](https://github.com/tldraw/tldraw/issues/7695)中提到关闭外部 PR、只挑选性地重新开启值得考虑的工作，理由包括 AI 生成提交、上下文不完整以及作者跟进有限。它的[贡献指南](https://github.com/tldraw/tldraw/blob/main/CONTRIBUTING.md)把人们引导到 issue 和分支引用，同时声明不接受贡献。[Clojure 的开发政策](https://clojure.org/dev/dev)通过自己的流程接受补丁，但把方向决定权交给核心团队，并要求功能提案先明确问题、比较各种方案，再进入实现阶段。这些是不同的政策，治理和许可安排各不相同。它们说明了社区输入如何影响项目，而维护者决定项目的设计和贡献流程。Open WebUI 为明确被请求的工作和本地化贡献保留着通道。

**如果你真心希望帮助 Open WebUI，就应当以项目的需要以及维护者能否采纳你的贡献来衡量它的价值。** 一份精确的复现步骤、一份经过深入调查的报告，或一段对某个工作流的有用解释，都可以在不产生一个署你名字的已合并 PR 的情况下改进项目。请做好准备：维护者可能以不同方式解决问题、在内部实现方案，或认定某项改动不属于这个项目。**提供帮助意味着即使你的代码没有被采用，你也支持这个结果。** 可复现的缺陷请通过 [Issues](https://github.com/open-webui/open-webui/issues)提交，提案请通过 [Discussions](https://github.com/open-webui/open-webui/discussions/new/choose)提交。请先搜索已有的报告、查看当前发布版本和 `dev` 分支，并提供受影响的工作流、预期与实际结果，以及相关证据。安全问题请通过[私下安全报告流程](https://github.com/open-webui/open-webui/security)报告。当实现说明、本地 diff、补丁或分支引用能帮助澄清问题时，请在相应报告中附上它们；不要为了博取对参考代码的关注而提交 PR。请用有用的证据跟进，并尊重团队的优先级。报告不保证会得到回应、被实现或得到时间承诺；反复催促或重复提交只会挤占工作的时间。

当我们请求某个 PR 时，其目的是完成项目已经认定需要的工作。请把这个目的放在对实现方式的个人偏好、你贡献的规模以及能否被合并之前。请遵循 [PR 模板](https://github.com/open-webui/open-webui/blob/main/.github/pull_request_template.md)，以 `dev` 为目标分支，完成贡献者许可协议（CLA），并在 **Maintainer Request** 一节中链接维护者的请求。遵循既有模式，记录验证过程，并且**严格控制在约定的范围内**。如果方案需要调整，请回到讨论中；也要接受评审的结果可能是重写或决定不继续推进。一次邀请并不授权无关的改动或未经请求的测试，**也不保证一定被接受**。对于 i18n/本地化类 PR，请说明该工作仅限于本地化；这项长期例外承认的是语言知识对现有翻译系统中用户的帮助，它并不延伸到无关的行为改动、重构或随翻译捆绑的依赖。尊重这些边界——包括决定关闭某项提交——本身就是贡献的一部分。重新开启已被否决的 PR，或把它拆成更小的提交以争取另一种结果，都与这个目的背道而驰。

### 改进文档 {#improve-documentation}

通过改进文档、编写教程或创建设置指南，帮助让 Open WebUI 变得更容易上手。文档存放于 [docs 仓库](https://github.com/open-webui/docs) 中。

### 翻译 UI {#translate-the-ui}

仅涉及 i18n/本地化的 PR 不需要维护者事先请求。Open WebUI 在 `src/lib/i18n/locales` 中使用 JSON 格式的翻译文件。每个子目录的命名都遵循 [ISO 639 语言代码](http://www.lingoes.net/en/translator/langcode.htm)（例如 `en-US`, `fr-FR`）。

如果你母语就是 Open WebUI 已支持的语言，那么修正现有翻译和新增翻译同样受欢迎。当某个标签在你的语言中读起来不对、不自然或用词有误时，请在对应语言的 `translation.json` 中修正它，并只提交这些改动的 PR。

要添加一种新语言：

1. 在 `src/lib/i18n/locales` 下创建一个使用相应语言代码命名的新目录
2. 将 `en-US/translation.json`（每个语言环境仅包含这一个文件）复制到新目录中
3. 翻译每个 JSON 文件中的字符串值，同时保留对象结构不变
4. 在 `src/lib/i18n/locales/languages.json` 中注册该语言，然后运行 `npm run i18n:parse`，该命令会根据源字符串重新生成每个已注册语言环境的 `translation.json`，格式化它并检查它

在 `en-US` 中，许多值是空的，因为键本身就是英文文本。对于这类条目，请翻译键，并把译文作为值写入。

### 改进无障碍支持 {#improve-accessibility}

无障碍体验是优秀设计的核心部分。请通过 Issues 报告无障碍问题，并附上复现步骤。在实现维护者请求的 UI 更改时：

| 原则 | 做法 |
|-----------|-----------|
| **语义化 HTML** | 使用 `<button>`, `<label>`, `<nav>` 以及其他语义化元素，而不是通用的 `<div>` 包装器 |
| **键盘导航** | 确保所有交互元素在没有鼠标的情况下也能正常工作 |
| **ARIA 标签** | 当仅靠语义化 HTML 不足时，请添加 [ARIA](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA) 角色和标签 |
| **色彩对比度** | 使用 [WebAIM Contrast Checker](https://webaim.org/resources/contrastchecker/) 验证对比度比例 |
| **替代文本 (Alt text)** | 为有意义的图像提供描述性的 `alt` 属性；对装饰性图像使用 `alt=""` |

使用 Lighthouse 或浏览器的无障碍工具测试你的更改。

## 报告问题 {#reporting-issues}

在开启新 Issue 之前，请先查看 [Issues 选项卡](https://github.com/open-webui/open-webui/issues)。提交时请注意：

- **使用 Issue 模板。** 不遵守模板或缺少所需信息的 Issue 将被关闭。
- **包含复现步骤。** 描述你做了什么、你期望发生什么，以及实际发生了什么。
- **请具体说明。** 模糊的报告（“它不起作用”）无法被有效地调查。

:::warning 支持范围
Open WebUI 支持 Docker 部署，但我们假设你熟悉 Docker 的基本原理。与反向代理配置、容器网络或主机操作系统设置相关的问题，不在本项目的支持范围之内。有关这些主题，请参阅 [Docker 官方文档](https://docs.docker.com/get-started/overview/)。
:::
