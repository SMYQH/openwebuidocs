# 认证时序侧信道 {#authentication-timing-side-channel}

|  |  |
| :--- | :--- |

| **状态** | 已缓解可利用的时序差异；接受亚毫秒级残余差异 |
| **追踪编号** | [GHSA-7rw5-9f7q-xj36](https://github.com/open-webui/open-webui/security/advisories/GHSA-7rw5-9f7q-xj36) |

## 概述 {#summary}

登录端点对已有账户的响应时间明显长于不存在的账户，因为密码哈希仅在账户存在时被验证。差异（约 150 毫秒对比约 5 毫秒）使攻击者可以通过响应时间枚举有效账户，从而为后续密码喷洒攻击提供基础。

## 已采取的缓解措施 {#what-we-mitigated}

此问题已报告给我们，追踪编号为 [GHSA-7rw5-9f7q-xj36](https://github.com/open-webui/open-webui/security/advisories/GHSA-7rw5-9f7q-xj36)。现在，登录时即使找不到用户或有效凭证，认证流程也会用固定的占位哈希执行 bcrypt 比较。因此，无论账户是否存在，每次登录都会产生相同的 bcrypt 开销。

测量结果表明，响应时间之比由约 20-40 倍降至约 1.03 倍（两条路径均执行 bcrypt），已无法与正常的运行波动区分。因此，原先可用于枚举账户的时序信号已消除。

我们接受这一毫秒量级的残余时序差异。这不是投入不足的问题：剩余差异受物理条件和运行环境限制（数据库、Python 解释器、CPU 行为、操作系统调度和网络抖动），继续修改 Open WebUI 代码也不会带来明显改善。详见下方[剩余差异及其无法消除的原因](#what-remains-and-why-it-is-not-fixable)。

## 剩余差异及其无法消除的原因 {#what-remains-and-why-it-is-not-fixable}

完美的恒定时间认证在应用级代码中无法实现。一旦主要的 bcrypt 开销被均等化，剩余差异为亚毫秒级，由 Open WebUI 无法控制的层次产生：

- **数据库查找**（已有电子邮件的索引命中对比不存在电子邮件的未命中），
- **Python 解释器和垃圾收集器**，
- **CPU 行为**：缓存状态、分支预测、推测执行，
- **操作系统调度**，
- **网络抖动**。

Python 无法将这些差异完全消除。固定时间填充（「始终在固定的时间窗口内响应」）也解决不了问题：窗口必须覆盖最慢的情况，使每次正常登录都变慢，而且测量精度足够高的攻击者仍能观察到填充前的处理差异。这样做会带来持续的开销，却不能完全消除时序差异。

残余信号为亚毫秒级，且受网络和调度噪声主导，因此无法在网络中可靠测量。我们因此将其接受为已知限制，而非可修补的缺陷。
