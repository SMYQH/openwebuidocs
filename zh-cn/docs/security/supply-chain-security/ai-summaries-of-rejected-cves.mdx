# 被拒绝 CVE 的 AI 摘要 {#ai-summaries-of-rejected-cves}

给所有在漏洞数据之上构建 AI 层的人的一点说明。

**对已撤回的 CVE 所生成的摘要，会把这个漏洞描述成仿佛它真实存在。** 这不是偶尔发生，也不是因为模型不够强。它源于记录本身的结构：撤回只是一句姗姗来迟的散文，而其周边的一切结构化内容仍然断言该发现是真实的。

我们在自己的记录上就遇到了这个问题，而且这种模式足够普遍，值得单独用一页来说明，而不是把它留在针对某一家厂商的抱怨里。

---

## 为什么会发生 {#why-it-happens}

让模型总结一条漏洞记录，它就会总结出一个漏洞，因为记录本就是为承载漏洞而构建的。当一个标识符被拒绝时，承载语义的字段并不会被清空：

- 标题仍在描述某种攻击；
- 严重性、CVSS 向量和 EPSS 概率依然有值；
- 受影响的产品和版本范围依然列着；
- 弱点分类以及映射的攻击模式依然可以解析；
- 状态字段往往仍然是"当前"或"已接收"之类的取值。

与此同时，撤回是以替换文本的形式出现在描述字段里的。它只是十几个结构化断言中的一个非结构化字符串，也是唯一说明该发现已经消失的元素。

摘要提示词会按数据呈现的样子来衡量这些输入。那些被打过分、带类型、可机读的字段描述的是一个真实存在的漏洞，于是摘要也描述了一个真实存在的漏洞，并以评估报告的那种笃定口吻表达出来。有些系统随后还会叠加一层，生成修复建议，告诉读者升级到某个并不存在的修复版本，去解决一个从未真实存在的缺陷。

这种输出并非通常意义上的幻觉。模型只是在忠实地总结记录仍然在说的内容。

---

## 两个例子 {#two-examples}

两者都可以直接核查。我们最后一次确认 BaseFortify 的例子是在 2026-10-30，Vulners 的例子是在 2026-08-08。

### 与撤回声明并排出现的"执行摘要" {#an-executive-summary-beside-the-withdrawal-notice}

在 [BaseFortify](./vulnerability-databases/basefortify.mdx) 上，被撤回记录的条目带有 Rejected 徽标，描述中有发证 CNA 的拒绝声明，而同一页面上由 AI 生成的"执行摘要"则在解释这个漏洞是如何被利用的。对于 CVE-2024-7959，它声称该缺陷"可以被利用来访问内部服务，并可能通过读取实例密钥来执行命令"。两种说法都没有对彼此隐藏。读者会同时看到正确答案和错误答案，而只有错误答案被写成了一份评估。

在其周围，结构化字段依然描述着一个当前有效的发现：CVSS 基础分为 7.7 HIGH，EPSS 概率位于第 97.6 百分位，一个针对 Open WebUI 0.3.8 的 CPE，以及一张把该记录经由 CWE 映射到 CAPEC 的攻击流程图。

### 生成了"建议升级"的文本 {#generated-text-that-recommends-an-upgrade}

在 [Vulners](./vulnerability-databases/vulners.mdx) 上，被撤回记录的默认描述是机器生成的，并标注为 "AI enhanced"。它声称该端点允许未经身份验证的远程攻击者获取敏感配置数据，引用了其他数据库作为佐证，并在结尾建议受影响组织升级到打了补丁的版本或应用厂商缓解措施。

根本没有什么可升级的，因为从来就没有什么需要修复。同一条目还带有一个生成的风险评分，高于发证 CNA 在撤回该记录之前给出的评级。

---

## 设计要求 {#the-design-requirement}

这只是一项检查，而且它应当发生在生成之前，而不是之后。

**先读取记录的状态。如果它已被拒绝，就不要为该发现生成任何评估。** 要么什么都不生成，要么只生成撤回信息：该标识符被谁拒绝、何时被拒绝。

其余一切都由此推导而来，而且代价都不高：

- **不要为被拒绝的记录打分。** 严重性、基础分、向量和利用概率，全都是在陈述"存在一个漏洞"。已经没有东西需要评级了。
- **不要为它输出修复建议。** 建议升级意味着存在修复，而存在修复意味着存在缺陷。
- **不要让生成的输出比它所依据的记录活得更久。** 如果某段摘要是在该标识符仍然有效时写下的，那么状态一改变它就过时了，此后继续提供它，是系统在每次页面加载时都主动做出的选择。
- **把状态暴露为一个字段，而不只是散文。** 下游使用者——包括构建在你之上的下一层 AI——需要的是可以用来过滤的东西，而不是描述字段里的英文文本。

这个状态非常容易获取。任何使用者都可以直接从记录中读出：

```bash
curl -s https://cveawg.mitre.org/api/cve/CVE-2024-7033 | grep -o '"state":"[A-Z]*"'
```

## 为什么这不只是漏洞数据库的问题 {#why-this-is-not-only-a-vulnerability-database-problem}

只要模型被指向漏洞记录，同样的形态就会出现：回答 CVE 相关问题的安全副驾驶、判定某个发现是否值得关注的 LLM 分诊系统、读取扫描器输出并据此开单的智能体，以及为下游包生成公告文本的依赖管理工具。

它们中的每一个，如果先做总结再检查状态，都会继承同样的失败。而在这些系统中，凡是会把输出发布出来的地方，下一个系统又会把它的输出吞进去——于是一个已撤回的标识符，可能在记录本身早已沉寂很久之后，又获得新的佐证。

关于已撤回标识符在各数据库中的普遍情况，请参见[漏洞数据库中被拒绝的 CVE](./vulnerability-databases/)。
