## 📦 供应链与安全扫描器 {#supply-chain-and-security-scanners}

**我们对自动化供应链扫描器（如 socket.dev）所发标记的立场。**

自动化扫描器会为 Open WebUI 的软件包标注行为风险指标，并给出未经证实的分类。该页面解释了为何这些标记不能证明存在已明确识别的漏洞或恶意代码，也直接回答了常见的「无沙箱代码执行」问题：默认代码引擎在浏览器沙箱中运行，服务端执行须主动启用。

| | |
| :--- | :--- |
| 🔎 **启发式标记，而非已确认的发现** | 为何标出某项能力并不等于发现漏洞 |
| 🧪 **未经证实的分类** | "潜在恶意软件"横幅的解释 |
| 🧰 **默认在沙箱中运行** | 默认使用 Pyodide WASM；服务端执行须主动启用 |

[**阅读供应链与安全扫描器 →**](/security/supply-chain-security)

### 漏洞数据库中被驳回的 CVE {#rejected-cves-in-vulnerability-databases}

部分漏洞数据库和终端安全产品不会在 CVE 被撤回后更新记录。因此，即使发布该编号的 CNA 已正式驳回该 CVE，这些产品仍会将它列为 Open WebUI 的有效安全发现。该页面记录了受影响的数据库、每次联系及其结果，也介绍了如何在几秒内通过 cve.org 核对任何记录的权威状态。

[**阅读漏洞数据库中被驳回的 CVE →**](/security/supply-chain-security/vulnerability-databases)

## 📄 供应商处置 {#vendor-dispositions}

## ⚖️ 已知与已接受风险 {#known--accepted-risks}

**我们已尽可能在技术上缓解、然后正式接受的残余风险。**

某些弱点无法在应用代码中完全消除，因为它们受限于语言、运行时、操作系统、CPU 或网络，而非我们可以修补的缺陷。我们将可利用部分尽可能缩小，并将剩余部分记录在此，附上推理以及它如何符合我们的威胁模型。

| | |
| :--- | :--- |
| 🛠️ **尽可能缓解** | 我们为减少每种风险而做的更改 |
| 🚧 **残余保留的原因** | 语言、操作系统、CPU 或网络限制导致无法完全修复 |
| 📐 **威胁模型背景** | 为何残余被接受而非作为缺陷处理 |

[**查看已接受风险 →**](./accepted-risks)
