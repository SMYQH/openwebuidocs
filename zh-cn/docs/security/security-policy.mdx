**这是 Open WebUI 针对安全漏洞报告的政策：什么算作漏洞、如何报告，以及我们如何处理、认可和发布报告。**

我们的目标是保护 Open WebUI 的用户及其数据，并以清晰、一致且公开记录的方式处理安全报告。我们希望运营一个透明的安全流程，其中已接受的漏洞作为公告公开发布，以便任何人都可以看到发现了什么、如何解决的，以及最重要的是哪个版本包含补丁。

我们的立场：可见的公告历史记录是积极审查和有效披露流程的证据，而非衡量软件脆弱性的标准。

## 支持的版本 {#supported-versions}

| 版本（分支） | 支持 |
| ---------------- | ------------------ |
| main             | :white_check_mark: |
| dev              | :x:                |
| 其他             | :x:                |

**如果某个问题在您提交时已在公开中修复或正在修复中，则该报告将不被接受**。它没有为发现或修复该问题做出贡献，我们不会为其发布公告。修复会列在包含它的版本的变更日志中。无论修复存在于哪个分支（包括 `dev`），也无论它是否在更早版本中已被静默解决，修复都被视为已存在。分支支持状态决定漏洞必须在何处**可重现**，而非修复是否已存在：在支持分支中存在的错误但已在 `dev` 中修复，在此规则下仍属于已修复问题。

这涵盖两种特定模式，我们均拒绝：

- 为**旧版本**中发现的、在当前支持版本发布时已解决的错误提交报告。
- **监控我们的公共提交或拉取请求**并为它们已处理或修复的问题提交报告。我们观察到对我们的公共提交和 PR 的自动化监控，产生了针对其他人已撰写的修复的报告；此规则的存在正是为了拒绝这种模式。

您是否独立发现该问题无关紧要，我们也无法区分独立发现与爬取。根据可证明的事实，您的报告是在修复已经公开之后才提交的。首先发现或修复该问题的人公开披露了它，却没有先保密报告给我们，因此他们也得不到任何认可。公开披露的修复不会给任何人记功。

:::tip

**在报告之前，请确认您的发现是否仍在 `dev` 分支（及任何其他活跃开发分支）上可重现。** 我们公开开发，修复可能在发布前已提交到那里。先确认这一点可以节省您撰写报告的工作，而我们将不得不将其关闭为已修复。

:::

## 并非漏洞的善意报告 {#good-faith-reports-that-arent-vulnerabilities}

**我们真心感谢每一份出于善意的报告，即使按我们的准则它最终并不构成漏洞。** 感谢你抽出时间。一份被我们以“超出范围”关闭的善意报告，绝不会因此对你不利。

如果你发现了某些你明知**并非严格意义上的政策漏洞**、但公开披露仍不负责任的内容（例如因下游漏洞而需要紧急升级依赖版本，或类似情况），你仍然可以通过 [GitHub Security Advisories](https://github.com/open-webui/open-webui/security/advisories/new)**私下报告**。我们会负责任地处理。

按照 CVE 规则，我们**不会**为此发布公告或分配 CVE，但**会**采取行动（例如发布该版本升级），并在处理完成前对报告保密。
<ins>**如果你的报告促成了某个修复，你希望获得署名，我们会尽力致谢（例如列为该改动的共同作者）。**</ins>

## 有效报告您能获得什么 {#what-a-valid-report-gets-you}

如果您的报告描述了本政策下的真实漏洞，以下是您可以从我们这里获得的：

- **在公告中获得认可。** 您将被列为已发布公告的报告者。当多个报告者各自展示了不同的攻击向量时，每位都会获得认可（请参见[报告处理](#report-handling)）。
- **协调披露。** 在您与我们共同处理该问题时，我们不会在您不知情的情况下抢先发布。状态在公告本身上可见地更新，包括 CVE 请求，GitHub 会通知您这些更新，因此您可以全程跟进直至发布。
- **真正的修复，负责任地处理。** 细节在分配 CVE ID 之前保持不公开，目前大约是修补版本发布后四周或更久，以便管理员先行更新（参见[预期时间](#expected-timeframe)）。

我们 _无法_ 支付赏金，也无法保证解决该报告需要多长时间。我们会认真修复问题，准确记录您的贡献，并将您的工作视为一项贡献。

## 与 CVE 计划的协调 {#alignment-with-the-cve-program}

**CVE 计划规则**（和 CNA 操作规则）是此处所有 CVE 处理的**基准**，本政策在其框架内运作。根据这些规则，报告是否构成 Open WebUI 中的安全漏洞由供应商决定；本政策记录了我们行使该决定的标准。在规则未明确说明的地方，它们仍然适用；在本政策指定我们如何将其应用于 Open WebUI 的地方，它是作为供应商发布的处置标准，而非对程序规则的替代或例外。

## 安全漏洞的报告位置和方式 {#where-and-how-to-report-security-vulnerabilities}

:::info

Open WebUI 的社区之所以蓬勃发展，是因为像您这样的人，他们深切关心为每个人制造更安全的软件。

为确保您的发现确实有助于保护用户并迅速解决，请**仅**通过我们的[官方 GitHub 安全页面](https://github.com/open-webui/open-webui/security)提交所有安全漏洞报告。任何其他网站、服务或所谓的"赏金"平台都***不*与我们有关联**，您的重要工作根本无法到达能做出改变的人。

:::

**我们仅通过 [GitHub Security Advisories](https://github.com/open-webui/open-webui/security/advisories/new) 接受漏洞报告。** 通过**任何**其他平台提交的报告，包括但不限于第三方漏洞报告平台、漏洞经纪人、社交媒体、电子邮件、Discord 或 Reddit，将不予处理。

这不是程序性偏好。作为一个由小型核心团队领导的项目，Open WebUI 使用单一、权威的报告渠道进行安全工作，而 GitHub Security Advisories 正是该流程所在。我们不监控也不参与外部报告平台，通过这些平台到达的报告将被关闭且不予审查。

在其他平台上提交的报告在此处**没有效力**：它不赋予任何优先级，不建立提交日期，也不产生任何义务让我们进行分类、发布或以其他方式考虑。只有 GitHub Security Advisory 记录为本政策的目的而存在，包括确定谁先提交。

## 威胁模型 {#threat-model}

Open WebUI 是一个**自托管、单租户、经过身份验证、基于角色**的应用。报告将在这个模型内评估：

- **用户必须先通过身份验证**，然后才能接触任何用户数据或产品功能。浏览器在登录之前需要的端点（登录、注册，以及登录页面读取的公共配置）按设计无需账户即可访问。
- **管理员受到信任**，拥有完整的系统控制权。同一实例的管理员共享同一条信任边界。
- **安全设置处于默认值或更严格的状态。**
- **工具、函数和管道按设计执行任意代码。** 管理员控制谁可以创建它们。

## 报告指南 {#reporting-guidelines}

我们感谢社区对发现潜在漏洞所表现出的关注！
如果您想报告某项内容不符合此处列出的规则和指南，您仍可进行报告，我们将予以处理， [更多信息请参阅我们的“善意报告”部分](#good-faith-reports-that-arent-vulnerabilities)。

我们 **不** 接受敷衍了事的漏洞报告。请确保 **提交的报告具有建设性、可操作、可重现、记录详实，并遵守以下准则**：

**安全边界：** 在本政策中，“安全边界”指我们所认定的五项：保密性、完整性、可用性、真实性及不可否认性。 我们对这些概念的解释较为宽泛：其他安全框架中的等效概念均包含在其中。一个有效的漏洞必须针对除报告者以外的其他方，且至少跨越其中一项安全边界。

1. **报告必须是漏洞：** 安全漏洞是指可被利用的弱点，即系统表现为非预期行为，从而使攻击者能够绕过安全控制、获得未经授权的访问权限、执行任意代码或提升权限。 配置选项、缺失的功能以及预期的协议行为均不属于漏洞。漏洞必须跨越至少一个（如上所述）的安全边界。

2. **禁止提交含糊不清的报告**：诸如“我发现了一个漏洞”但未提供任何详细信息的提交将被视为垃圾信息，且不予受理。

3. **深入理解**：报告必须体现对代码库及Open WebUI使用方式的清晰理解，并提供有关该漏洞的具体细节，包括受影响的组件和潜在影响。

4. **必须提供概念验证（PoC）**：每份提交必须包含一份记录详尽的概念验证（PoC），以证明该漏洞的存在。 如果担心保密问题，建议报告者创建该代码库的私人分叉，并向维护者授予访问权限。缺乏有效证据的报告可能会被忽略。

:::note

PoC（概念验证）是一种 **对漏洞利用的演示**。 您的 PoC 必须展示：

1. 究竟是哪一道安全边界被突破了
2. 该漏洞的触发/利用方式（输入、端点、UI 操作等）
3. 攻击者现在可以执行哪些操作
4. 可复现问题的具体操作步骤和命令（尽量可复制粘贴运行），预期结果与实际结果的对比

:::

5. **默认配置测试**：漏洞报告必须能够使用Open WebUI的开箱即用默认配置进行测试且可重现。 仅在明确弱化安全设置的情况下才会显现的漏洞报告可不予采纳，除非符合以下例外情况：

:::note

如果您认为您发现了一个安全问题，该问题

1. 会影响默认配置， **或**
2. 表示真正绕过了预期的安全控制措施， **或**
3. 仅适用于非默认配置， **但相关配置很可能被用于生产环境部署**， **那么我们非常希望了解这一情况。** 本政策旨在筛选配置问题和部署问题，而非阻碍正当的安全研究。

:::

6. **需理解威胁模型**：报告必须证明已理解Open WebUI的自托管、单租户、经过身份验证、可扩展且基于角色的访问控制架构。 若将 Open WebUI 与安全模型存在根本差异的服务进行比较，却未指出其架构上的差异，可能会导致报告被驳回。

7. **CVSS评分准确性：** 您无需在报告中包含CVSS评分。 如果您将 CVSS 部分留空，我们将在发布前为您填写。如果您在报告中包含 CVSS 评分，该评分必须根据 CVSS 方法论准确反映该漏洞。若 CVSS 评分不准确，我们将调整您报告中的 CVSS 评分。 如果您引用其他 CVE 来支持您的报告，请确保它们在漏洞类型、威胁模型和攻击向量方面 **真正具有可比性** 。

8. **管理员操作不在评估范围内：** 需要管理员主动执行不安全操作的漏洞 **不被视为有效的漏洞**。 **管理员拥有对系统的完全控制权，应了解其操作和配置带来的安全影响**。 这包括但不限于：添加恶意的外部服务器（模型、工具、Webhook、应用程序、函数）、将不可信代码粘贴到函数/工具中，或故意削弱安全设置。 **需要管理员疏忽或对管理员进行社会工程学攻击的报告可能会被拒绝。**

:::note

与“默认配置测试”规则类似：如果您认为发现了一个影响管理员的漏洞，且该漏洞并非由管理员的疏忽或蓄意恶意行为引起，
**那么我们绝对希望了解相关情况。** 该政策旨在过滤针对管理员的社会工程学攻击、管理员部署的恶意插件以及类似的恶意行为，而非旨在阻碍合法的安全研究。

:::

9. **工具与函数的代码执行属于预期行为：** 工具和函数会在服务器上执行用户提供的 Python 代码，其访问权限与 Open WebUI 后端相同。这是核心且预期的功能（参见“威胁模型理解”）。只有管理员才能创建函数。 创建工具需要 `workspace.tools` 权限，该权限对非管理员用户默认处于禁用状态。 <ins>**授予该权限相当于授予对服务器的shell访问权限**</ins>，因此将该权限授予不可信用户属于“管理员操作超出范围”所涵盖的配置错误。 **任何描述通过 Tools 或 Functions 实现的攻击链（代码执行、文件访问、网络请求、环境变量访问、前置信息 `pip install` 等）的报告，均将作为预期行为予以关闭。** 不需要这些功能的部署可以使用 [`ENABLE_PLUGINS`](/reference/env-configuration#enable_plugins) 及相关开关将其关闭。

10. **遗留代码路径不在范围之内：** Open WebUI 保留了一些在官方文档中被明确标记为“遗留”的代码路径，而官方文档是判定何为遗留代码的权威依据。 遗留路径之所以仍然可用（有时仍是默认选项），纯粹是为了向后兼容，而非因为它们是受支持或受维护的功能。受支持的替代方案才是迁移目标，安全与功能相关的工作应在替代方案上进行，而非在遗留路径上。 若报告描述的遗留代码路径上的安全边界问题无法在受支持的替代方案中复现，则通常根据此规则属于范围之外。

:::note

如果您发现一个安全问题，且该问题：

1. 同时存在于旧版代码路径 **和受支持的新版替代方案**中，或者
2. 存在于一个遗留代码路径 **上，且该遗留路径是实现给定功能** 的唯一已记录方法（目前尚无迁移目标）

我们仍然希望听到相关反馈。这条规则旨在过滤那些针对已弃用路径且已有文档记录的现代替代方案的报告，而非阻止用户发现其当前仍在使用路径中存在的真实缺陷。

:::

11. **AI报告透明度：** 请告知我们AI是否在任何方面提供了帮助：发现漏洞、撰写报告或构建概念验证（PoC）。AI辅助生成的报告将与其他所有报告一视同仁；我们只是想了解情况。

12. **自影响问题不属于漏洞：** 漏洞必须跨越安全边界，且影响 **除报告者以外的其他方**。 仅针对报告者自身的数据、账户、会话或环境跨越其中一个安全边界， **不属于漏洞**；这属于程序错误，应提交至 [问题跟踪系统](https://github.com/open-webui/open-webui/issues)，而非安全报告中。

:::note

本规则涉及 **哪个人或方遭受了损害**，而非损害的严重程度。用户修改或删除自身数据、破坏自身会话、查看自身配置，或禁用自身账户上的安全控制措施，均不属于本规则的适用范围，无论其影响如何。

如果同一项操作还会影响其他用户、操作员、主机系统或共享资源，请在概念验证（PoC）中明确指明该相关方，并请向我们反馈相关情况。

:::

不符合这些指南的提交可能会被关闭。只有反复或故意忽视这些指南的报告者可能会被禁止提交报告；无心之失和出于善意的报告绝不会被计入其中。我们的目标是营造一个建设性的报告环境，让高质量的提交为所有用户带来更佳的安全保障。

## 预期时间 {#expected-timeframe}

安全报告会与其它所有项目工作一起排定优先级，而报告量非常大。**请预期需要数周时间**报告才会被查看、分析、分流并修复，其间还会出现一段段的静默。**静默并不意味着你的报告被忽略了**；它只是还没有被处理。如果你认为报告丢失了，可以在公告下留言追问。

修复发布后，我们会向 GitHub 申请 CVE ID，并在分配到后尽快发布公告。GitHub 目前分配 ID **大约需要四周或更久**；我们为何要等待，参见[发布前分配 CVE](#cve-assignment-before-publication)。即使 GitHub 分配得更快，现实影响广泛或严重的发现（无论 CVSS 分数如何）仍会推迟到打补丁的版本发布约两周后才公布，以便管理员完成更新。

**本页所列的所有时长都是估计值。** 一切顺利时报告可能推进得更快，遇到阻碍时也可能更慢。

**我们不接受由报告方施加的发布期限。** 我们按自己的节奏协调披露，并会尽合理可能快地分流、修复和发布。外部强加的硬性时间表不会让事情变快，反而会适得其反：它会把我们的时间从真正修复问题上挪开，去应付时钟，**代价是队列中所有其它报告（甚至可能更严重的那些）以及整个项目**。给你的报告挂上一个期限不会改变它被处理的时间和方式。

## 发布前分配 CVE {#cve-assignment-before-publication}

**只有在 GitHub 分配了 CVE ID 之后，我们才会发布安全公告。** 对于通过 GitHub Security Advisories 申请的 CVE，GitHub 就是 CVE 编号机构（CNA）。当一份公告已修复并准备好时，我们就去申请它的 CVE，而在 ID 分配下来之前，公告一直不予发布。按 GitHub 当前的分配速度，<ins>**这会让每一份 Open WebUI 公告的发布时间推迟大约四周甚至更久。**</ins>

**在这条规则之前**，我们申请 CVE 后会立即发布公告。问题本身已经在某个版本中修复，而发布公告正是告诉管理员哪些版本受影响的方式：公告会汇入 GitHub Advisory Database，并触发 Dependabot 告警。GitHub 之后才会补上 CVE ID。

**当时发生了什么。** 2026 年 9 月 27 日和 28 日，我们以这种方式发布了 19 份公告，而这些 CVE 申请在 GitHub 那边挂了好几周。到了 2026-10-12，另一家 CNA——VulnCheck——为这 19 份公告各自发布了它自己的 CVE 记录，随后 GitHub 以“重复”为由拒绝了我们的申请。我们认为通过 GitHub Security Advisories 由代码所有者提交的 CVE 属于 GitHub 的职责范围；而 GitHub 与 VulnCheck 都认为，只有在没有其他 CNA 的职责范围覆盖时，GitHub 的范围才包含它。无论如何，**在这些记录被分配之前，没有任何一方联系过我们。** 协同披露的前提是 CNA 在分配之前联系厂商，而 VulnCheck 并没有这样做。它的记录把我们公告的标题替换成了它自己的标题（至今仍是如此），并在 19 份中的 16 份上写错了致谢方，还有若干份写错了弱点类型或评分，直到我们就此提出异议后 VulnCheck 才予以更正。进入 GitHub Advisory Database 的那些副本情况更糟：它们是未经审核的条目，标题被截断到半句话，没有生态标识、没有受影响的包、也没有受影响或已修复的版本。它们从未触发过任何一条 Dependabot 告警，因此运行受影响版本的管理员从来没有收到过这类警告。

**我们不接受其他 CNA 为 Open WebUI 生成 CVE**，因为我们无法指望他们把记录做对：我们的[供应商处置](./vendor-dispositions/)页面列出了其他 CNA 生成、最终不得不被驳回的记录，而如上所述，VulnCheck 的那 19 条记录是错的。由 GitHub 分配的 CVE 是基于我们撰写的公告生成的，会以经过审核的条目进入 GitHub Advisory Database，附带受影响的包和版本，因此 Dependabot 能从公告发布的第一天起就提醒每一个受影响的部署。把发布推迟到 GitHub 分配 ID 之后，就不给其他 CNA 抢先生成的机会。公告会晚几周才到达管理员手中，但它是完整的：没有信息缺失，数据和元数据也正确，由我们、报告者以及作为 CNA 的 GitHub 共同撰写并核验。

## 报告处理 {#report-handling}

当多位相互独立的报告者描述了同一类漏洞，**但**每个人都展示了**各不相同且相互独立的利用路径**（例如，同一处缺失的权限检查通过不同端点触达），我们会将它们合并到最早的那份提交中，**并在合并后的公告中向每一位展示了独立路径的报告者致谢**。合并后的公告只会分配一个 CVE。

另一种情况：如果你报告的是一个有效漏洞，而别人此前已经报告过（漏洞相同、利用路径相同），我们会把你的报告作为重复项关闭。最早的那份提交是我们后续会继续处理的，我们不会为同一个漏洞发布多份公告。

### 为什么重复报告不获得认可 {#why-duplicate-reports-dont-receive-credit}

我们仅认可给定漏洞的最早提交者：

1. **第一份报告完成了工作。** 当后续报告到达时，分类和修复已在进行中。后续报告不改变结果或时间线；认可它们会歪曲是什么推动了修复。
2. **为重复提供奖励会鼓励提交泛滥。** 如果相似但较晚的提交也能获得认可，理性的做法是浏览公开公告并提出变体。我们已经看到这种压力：先提交规则正是限制它的原因。
3. **共同发现不同于重复。** 多个报告者**在一份公告上获得认可**当每个贡献了**独特的**发现时——不同的向量、不同的受影响组件、早期提交未覆盖的不同子路径。这是上面的合并规则。提交现有报告的重复不是共同发现。

## 保密披露 {#confidential-disclosure}

通过 GitHub Security Advisories 提交的漏洞报告是**私密和保密的**。在公告**完全发布**之前——不仅仅是分配了 CVE ID 时，而是公告本身公开可见时——**公开披露**与已提交漏洞报告相关的**任何**细节是**严格禁止的**。

该禁令适用于 **所有渠道和所有第三方**，包括但不限于：

- 对拉取请求、问题或讨论的评论，无论是在GitHub上还是其他地方；
- 社交媒体、聊天服务器和论坛（Discord、Reddit、X 或任何其他平台）；
- 博客、文章、演讲、论文和通讯；
- 邮件列表、漏洞数据库、漏洞赏金平台和漏洞中介；
- 任何其他组织，包括向其申请该问题的CVE标识符或任何其他标识符；
- 任何其他网站或服务。

设立这一保密且负责任的披露流程，是为了让我们有时间修复漏洞、发布修复程序，并在修复程序准备就绪后通知用户。负责任披露的根本宗旨在于 **保护用户免受漏洞危害**。 因此，过早披露会损害所有Open WebUI用户的安全，并 **违反了负责任披露流程中固有的信任** 。 **在官方发布前过早公开披露漏洞细节的报告者<ins>将被永久禁止进行未来的报告。</ins>**

## 第三方 CNA 和供应商处置 {#third-party-cnas-and-vendor-disposition}

[基于多个第三方 CNA 在未事先将报告通知我们即生成 CVE，和/或生成经不起审查的 CVE 的先例](./vendor-dispositions)，制定了此规则。

当报告通过 GitHub Security Advisories 提交且维护者根据本政策将其关闭为超出范围时，该关闭是该问题的**供应商处置**。CVE 编号机构（CNA）为此类问题生成 CVE 而未在结果记录中反映该供应商处置的行为，是违反供应商处置的行为。

我们通过以下方式回应此类记录：

1. 向 CVE 计划提交 **REJECT** 请求（以 **DISPUTED** 作为备选）
2. 在我们的[供应商处置](./vendor-dispositions)中公开编录该记录，注明发布 CNA
3. 拒绝提供供应商声明、版本映射、修复参考或任何其他会赋予该记录权威性的协调
4. 将来自单个 CNA 的重复模式上报至 CVE 计划 Root

**渠道合规不赋予 CNA 覆盖供应商处置的权利。** 在供应商处置已发布后，将已关闭的超出范围 GHSA 报告升级至第三方 CNA 的报告者同样被视为违反了供应商处置，并**可能被禁止未来的 GHSA 提交**。如果您不同意某个关闭结论，请在公告下带上新证据回复。我们会在出现新信息时重新评估已关闭的报告，也完全愿意重新开启它。

此规则之所以存在，是因为这些升级的成本并不对称。标识符可以在几天内铸就，而移除一个不准确的标识符则需要发布 CNA、CVE 计划以及每一个镜像它的下游数据库之间数月的通信往来，而这些努力没有一分落在创建该记录的一方身上。我们的处置以及我们与 CNA 的其他争议表明，我们无法指望第三方 CNA 会遵守 CNA 规则，或在分配标识符之前先核实一份报告。完整的推理过程，以及这些升级实际付出的代价，见 [The CVE System and Why This Page Exists](./vendor-dispositions/#the-cve-system-and-why-this-page-exists)。

## 工具、函数和管道安全 {#tools-functions-and-pipelines-security}

**工具、函数和管道在你的服务器上执行任意 Python 代码**，其访问权限与 Open WebUI 后端相同：文件、网络、子进程、环境变量和数据库。这是有意为之。关于它们的报告按[报告指南](#reporting-guidelines)的规则 9 处理。能够写入存放已安装插件的数据卷的攻击者同样在威胁模型之外。如需安全使用，请参阅[插件安全](/features/extensibility/plugin/)警告和[加固指南](/getting-started/advanced-topics/hardening#tools-functions-and-pipelines)。

## 生产部署安全 {#production-deployment-security}

Open WebUI 为私有、受信任的网络设计，默认配置针对易于设置进行了优化。处理敏感数据的生产部署应查阅[加固指南](../getting-started/advanced-topics/hardening.md)以获取完整清单。

一个关键注意事项：**没有 Redis 时，登出并不会撤销该会话的 JWT 令牌。** 它会一直有效直到过期（默认：4 周）。修改密码和管理员的**退出所有设备**都会结束该账户的所有会话，无论是否使用 Redis。对于生产部署，请[配置 Redis](../tutorials/integrations/redis.md)或缩短 `JWT_EXPIRES_IN` 以限制暴露窗口。详情请参阅[令牌撤销](../getting-started/advanced-topics/hardening.md#token-revocation)。
