# 供应商处置 {#vendor-dispositions}

**Open WebUI 对外部报告的 CVE 和安全声明的正式评估。**

当针对 Open WebUI 提交 CVE 时，我们会根据我们的 [安全策略](../security-policy.mdx)、我们记录的 [威胁模型](#threat-model) 和软件的实际行为来评估报告。如果报告不准确、误导性或不代表真正的漏洞，我们会在此发布供应商处置以解释我们的评估。

:::note 自动化扫描器标志
关于自动化供应链扫描器指标（socket.dev 及类似工具）而非特定 CVE 的立场，请参见[供应链与安全扫描器](/security/supply-chain-security)。
:::

:::warning 看到这些 CVE 被当作有效漏洞呈现？
若干漏洞数据库不会重新处理 CVE 撤回，因此签发 CNA 已正式拒绝的标识符仍会向它们的客户显示为有效发现。[漏洞数据库中被拒绝的 CVE](/security/supply-chain-security/vulnerability-databases)一节记录了哪些数据库受影响、我们为此做了什么，以及如何自行对照 cve.org 上的权威状态核查任意记录。
:::

## 什么是供应商处置？ {#what-is-a-vendor-disposition}

**供应商处置**是软件供应商对 CVE 或漏洞报告的官方公开回应。它是协调漏洞披露流程的标准部分，具有多个目的：

- **透明度**：用户和管理员可以确切看到我们如何评估一项声明以及为何得出结论。
- **准确性**：CVE 数据库有时包含错误描述严重程度、误解威胁模型或将预期行为描述为漏洞的报告。处置可以纠正公开记录。
- **指导**：每份处置都包含背景信息，帮助管理员评估报告的问题是否与其特定部署相关。

## 威胁模型 {#threat-model}

Open WebUI 是一个**自托管、单租户、需要认证、基于角色**的应用。它可以公开部署，但需要正确配置（TLS 终止、反向代理、恰当的访问控制）。我们的威胁模型假定：

- 所有用户在访问任何功能之前都**已通过认证**。
- **管理员**是受信任的行为者，拥有对系统的完全控制权。
- **安全设置处于默认值或更严格的状态**：威胁模型并不假定有人故意削弱安全设置。有效的漏洞报告必须在默认或更严格的配置上可复现。
- **工具、函数与管道**按设计就会执行任意代码：这是一项功能，而不是漏洞。管理员控制着谁可以安装和使用它们。

忽略这些架构前提的报告，例如声称某个漏洞需要管理员级别访问权、需要故意削弱的设置或配置错误的部署，可能会被驳回。

如需完整概述，请参阅[安全策略](../security-policy.mdx)。

## CVE 系统与本页存在的原因 {#the-cve-system-and-why-this-page-exists}

我们使用 CVE 系统，也相信它。当针对 Open WebUI 的报告有效时，我们会自行申请标识符，发布包含受影响版本与修复版本的公告，并致谢发现问题的人。CVE 记录让从未听说过我们的运维人员知道他们需要升级，这一点值得保护。本页上的任何内容都不是在反对 CVE 项目。

本页所记录的恰恰是反面：那些违背该系统存在初衷的记录。近年来，针对 Open WebUI 铸造的标识符中有相当一部分未能经受住审视，还有若干的产生方式根本无法与协调披露相调和。这个模式足够一致，可以直截了当地描述出来。

截至 2026-11-07，已有 26 条针对 Open WebUI 提交并随后被拒绝的 CVE 记录发布。按这一口径，Open WebUI 在 CVE 列表的所有产品中排名第三，仅次于 Linux 内核和机器人操作系统（ROS）。这 26 条全部由签发它们的 CNA 撤回，而非由 CVE 项目推翻：其中 23 条是在我们提出异议、签发 CNA 承认之后撤回，另外 3 条由签发 CNA 自行作为第三方依赖中 CVE 的重复项撤回，而我们此前根本不知道它们的存在。

**提交给错误产品的记录。** 不止一个标识符描述的影响发生在 Open WebUI 并未分发、未运行、也不掌控的软件上，却把 Open WebUI 列为受影响产品。确定受影响产品正是 CVE 记录的首要职能。

**描述并不存在的代码的记录。** 若干记录建立在被引用的代码本身已排除的机制之上，就在报告自己引用的那几行里。这些不是需要主观判断的事情——读一读引用的代码就足以推翻它们。

**从未联系我们就发布。** 有些记录在报告从未到达我们的安全渠道的情况下就发布了，换句话说，在 CVE 公开之前的任何时刻都没有人告知过我们。这是六类问题中最严重的一类，因为事先通知厂商正是协调披露的全部前提。为维护者从未见过的问题发布一个发现和一个概念验证（proof of concept），不能保护任何人；它只会把暴露窗口拉到最大而不是收拢。如果这些发现中有任何一条是真的，结果将是一个零日漏洞：一个仍在、尚未修补、带可用概念验证的漏洞，在同一时刻向攻击者和防守者披露，而且是由一个公开宣称其目的正是防止此事的组织发布的。

**以月计的响应时间。** 一旦某条记录被提出异议，更正的责任就落在签发它的 CNA 身上，而没有任何期限迫使它采取行动。异议通常要经过签发 CNA、CVE 项目秘书处和项目 Root 层层流转才会有所进展；在其自身 CNA 已经书面同意应标记为拒绝之后，一条记录仍可能继续发布数月。下面每一页上的时间线都记录了相应异议目前的状态。上一层同理。CNA 操作规则第 1.2.3.1 条规定，严重或反复不遵守规则的情形“必须由适当的 Root 审查”。自 2026 年 8 月以来，我们已依据该条款向 Root 提交了数份合规请求，但都只收到了自动确认。

**不处理拒绝状态的数据库。** 在 cve.org 上的撤回只有在下游数据库采取行动时才有意义。若干数据库不会重新处理“拒绝”状态的转换，或只处理其中一部分，因此签发 CNA 已正式撤回的记录仍会无限期地向它们的客户显示为有效发现。参见[漏洞数据库中被拒绝的 CVE](/security/supply-chain-security/vulnerability-databases)。

**无法就其自身数据取得联系的供应商。** 更正这些条目意味着要联系运营该数据库的人，而有时根本不存在可行的途径。有些机构不公布任何联系方式：没有安全联系地址，没有 `security.txt`，甚至连销售表单都没有，只留下一个电话号码作为唯一的联系方式。另一些公布的安全地址会直接拒收邮件。在确实有人回应的渠道中，往往也是为销售咨询或针对该供应商自身软件的报告而建的，完全没有途径告知他们其已发布的数据有误。这些正是告诉客户该采取哪些行动的机构，而其中若干家并未提供任何方式让人们告知某条发现是错的。

### 问题出在不对称上 {#the-asymmetry-is-the-problem}

一个 CVE 标识可以在几天内被铸造出来。而要让它被正式驳回，则需要在签发 CNA、秘书处、项目 Root 以及每一个镜像了它的下游数据库之间往返沟通数月。这种不平衡是解释本页的唯一事实。把一条不准确的记录放进公开数据源所需的工作量，只是移除它所需工作量的一个零头，而这部分移除工作的全部负担都落在那个什么都没做错的当事方身上。

没有人从中获益。CNA 要花掉审阅人员的时间去为站不住脚的记录辩护。报告者最终既失去了标识符，也失去了与之关联的署名。我们的维护者把数月花在与各方沟通和撰写公开文档上，而不是花在软件本身。最重要的是，这套系统所服务的那些人损失最大：评估 Open WebUI 的运维人员无法一眼分辨真实发现与已撤回的发现，而每一条无效记录都会让真正的公告更难被当真。CVE 项目本身也要付出同样的代价。它的权威完全建立在记录准确之上，而每一个站不住脚的标识符都会消耗掉一点整个系统赖以运转的公信力。

### 这正是我们在此记录一切的原因 {#which-is-why-we-document-everything-here}

我们无法从别人的数据库中删除一条记录。但我们不会做的，是把一项无效的发现当作有效。我们不会为了让事情看起来有个了结而发布一个象征性的修复提交。无效就是无效，花再多时间去争论一条记录也不会改变它的性质。

CVE 项目已经为不该存在的记录提供了机制，而这个机制就是驳回。每一次、每一条本页上的记录我们都走这条路。悄悄修补一个本来就没坏的东西要快得多，也会让这些条目全部消失，但那会把一句虚假陈述写进公开记录，并确认一项我们明知错误的发现。那是形式上的合规与实质上的不诚实，对依赖这些数据的人来说，其价值连零都不如。

这对语料本身同样重要。一条被驳回的记录会退出流通，而数据源的每个使用者都会因此受益。而一条被厂商悄悄修补的记录则永久留在语料中，被标记为有效，被数据库镜像，并被扫描器统计为一个根本不存在的真实漏洞。在这两个选项中，只有驳回无效记录能提升 CVE 数据的质量。假装某个发现是真的，并发布一个与这种假装相匹配的修复，会留下一条糟糕的记录并为它背书。每一个以这种方式处理的记录，都会拉低它周围每一个有效 CVE 的质量，因为防守方所信任的那份数据源，其好坏只取决于其中最糟且无人移除的那条记录。

我们所做的，是针对每一个这样的条目，依据真实代码在公开场合逐一详细回应，并把这些回应留在该记录旁边，供任何前来查证的人查看。

接下来呈现的就是这些内容。我们提出异议的每一个针对 Open WebUI 的外部提交的 CVE，下面都有一页说明，写明该记录声称了什么、软件实际做了什么、适用哪些政策规则，以及目前争议进展如何。

### 我们不是唯一这样解读这些记录的人 {#we-are-not-the-only-ones-who-read-these-records-this-way}

2026-09-02，[GitHub Advisory Database](https://github.com/github/advisory-database/pull/8031#issuecomment-5512489251) 的一位维护者表示，有三条镜像了针对 Open WebUI 提交的 CVE 的公告被有意标记为 `unreviewed`，“因为我和我的一些同事对这些 CVE 记录中所述漏洞的有效性存在疑虑”。由于它们未经审查，因此不会触发 Dependabot 告警。

这三条来自三个不同的签发 CNA：

| 公告 | CVE | 签发 CNA | 我们的评估 |
| :--- | :--- | :--- | :--- |
| [GHSA-vh96-p962-544h](https://github.com/advisories/GHSA-vh96-p962-544h) | CVE-2026-0767 | Zero Day Initiative | [处置](./cve-2026-0767.mdx) |
| [GHSA-2rf6-9rc8-rqch](https://github.com/advisories/GHSA-2rf6-9rc8-rqch) | CVE-2025-15603 | VulDB | [处置](./cve-2025-15603.mdx) |
| [GHSA-cfvq-fj53-j2c7](https://github.com/advisories/GHSA-cfvq-fj53-j2c7) | CVE-2024-7040 | huntr / Protect AI | [处置](./cve-2024-7040.mdx) |

这个决定是独立做出的：由与结果无关、也没有就此与我们联系过的人完成，并且发生在其中任何一条记录被撤回之前。这三条如今都已被各自的签发 CNA 撤回。

我们记录此事，是因为本页最常遇到的质疑是：供应商对某条 CVE 提出异议，无非是供应商不想要这个 CVE。在这里，一位以此为业、无论哪种结果都不获益的第三方，读了同样的记录，得出了与我们相同的结论。

这也是上文所述不对称最清晰的例证。三条记录被怀疑到足以从告警流水线中暂缓，却仍然以已发布 CVE 的形式流通——带着严重程度和受影响的版本区间——直到各自的 CNA 撤回为止。
