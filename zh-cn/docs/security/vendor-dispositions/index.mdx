### 问题出在不对称上 {#the-asymmetry-is-the-problem}

一个 CVE 标识可以在几天内被创建出来。而要让它被正式驳回，则需要在发布 CNA、秘书处、项目根以及每一个镜像了它的下游数据库之间往返沟通数月。这种不平衡是解释本页的唯一事实。把一条不准确的记录放进公开数据源所需的工作量，只是移除它所需工作量的一个零头，而这部分移除工作的全部负担都落在那个什么都没做错的当事方身上。

没有人从中获益。CNA 要花掉审阅人员的时间去为站不住脚的记录辩护。报告者最终既失去了标识符，也失去了与之关联的署名。我们的维护者把数月花在与各方沟通和撰写公开文档上，而不是花在软件本身。最重要的是，这套系统所服务的那些人损失最大：评估 Open WebUI 的运维人员无法一眼分辨真实发现与已撤回的发现，而每一条无效记录都会让真正的公告更难被当真。CVE 项目本身也要付出同样的代价。它的权威完全建立在记录准确之上，而每一个站不住脚的标识符都会消耗掉一点整个系统赖以运转的公信力。

### 这正是我们在此记录一切的原因 {#which-is-why-we-document-everything-here}

我们无法从别人的数据库中删除一条记录。但我们不会做的，是把一项无效的发现当作有效。我们不会为了让事情看起来有个了结而发布一个象征性的修复提交。无效就是无效，花再多时间去争论一条记录也不会改变它的性质。

CVE 项目已经为不该存在的记录提供了机制，而这个机制就是驳回。每一次、每一条本页上的记录我们都走这条路。悄悄修补一个本来就没坏的东西要快得多，也会让这些条目全部消失，但那会把一句虚假陈述写进公开记录，并确认一项我们明知错误的发现。那是形式上的合规与实质上的不诚实，对依赖这些数据的人来说，其价值连零都不如。

这对语料本身同样重要。一条被驳回的记录会退出流通，而数据源的每个使用者都会因此受益。而一条被厂商悄悄修补的记录则永久留在语料中，被标记为有效，被数据库镜像，并被扫描器统计为一个根本不存在的真实漏洞。在这两个选项中，只有驳回无效记录能提升 CVE 数据的质量。假装某个发现是真的，并发布一个与这种假装相匹配的修复，会留下一条糟糕的记录并为它背书。每一个以这种方式处理的记录，都会拉低它周围每一个有效 CVE 的质量，因为防守方所信任的那份数据源，其好坏只取决于其中最糟且无人移除的那条记录。

我们所做的，是针对每一个这样的条目，依据真实代码在公开场合逐一详细回应，并把这些回应留在该记录旁边，供任何前来查证的人查看。

接下来呈现的就是这些内容。我们提出异议的每一个针对 Open WebUI 的外部提交的 CVE，下面都有一页说明，写明该记录声称了什么、软件实际做了什么、适用哪些政策规则，以及目前争议进展如何。


# 供应商处置 {#vendor-dispositions}

**Open WebUI 对外部报告的 CVE 和安全声明的正式评估。**

当针对 Open WebUI 提交 CVE 时，我们会根据我们的 [安全策略](../security-policy.mdx)、我们记录的 [威胁模型](#威胁模型) 和软件的实际行为来评估报告。如果报告不准确、误导性或不代表真正的漏洞，我们会在此发布供应商处置以解释我们的评估。

:::note 自动化扫描器标志
关于自动化供应链扫描器指标（socket.dev 及类似工具）而非特定 CVE 的立场，请参见[供应链与安全扫描器](/security/supply-chain-security)。
:::

## 什么是供应商处置？ {#what-is-a-vendor-disposition}

**供应商处置**是软件供应商对 CVE 或漏洞报告的官方公开回应。它是协调漏洞披露流程的标准部分，具有多个目的：

- **透明度**：用户和管理员可以确切看到我们如何评估一项声明以及为何得出结论。
## 威胁模型 {#threat-model}

Open WebUI 是一个**自托管、单租户、需要认证、基于角色**的应用。它可以公开部署，但需要正确配置（TLS 终止、反向代理、恰当的访问控制）。我们的威胁模型假定：

- 所有用户在访问任何功能之前都**已通过认证**。
- **管理员**是受信任的行为者，拥有对系统的完全控制权。
- **安全设置处于默认值或更严格的状态**：威胁模型并不假定有人故意削弱安全设置。有效的漏洞报告必须在默认或更严格的配置上可复现。
- **工具、函数与管道**按设计就会执行任意代码：这是一项功能，而不是漏洞。管理员控制着谁可以安装和使用它们。

忽略这些架构前提的报告，例如声称某个漏洞需要管理员级别访问权、需要故意削弱的设置或配置错误的部署，可能会被驳回。

完整概览请参见[安全策略](../security-policy.mdx)。

- **准确性**：CVE 数据库有时包含错误描述严重程度、误解威胁模型或将预期行为描述为漏洞的报告。处置可纠正公开记录。
- **指导**：每份处置都包含背景信息，帮助管理员评估报告的问题是否与其特定部署相关。

## 威胁模型

Open WebUI 是一个**自托管、单租户、经过身份验证、基于角色**的应用程序。它可以公开部署，但需要适当配置（TLS 终止、反向代理、适当的访问控制）。我们的威胁模型假设：

- 所有用户在访问任何功能前都经过**身份验证**。
- **管理员**是受信任的行为者，拥有完整的系统控制权。
- **安全设置处于默认值或更严格的配置下**：威胁模型不假设故意削弱安全设置。有效的漏洞报告必须在默认或更严格的配置下可重现。
- **工具、函数和管道**按设计执行任意代码：这是一个功能，而非漏洞。管理员控制谁可以安装和使用它们。

忽略这些架构假设的报告——例如，声称需要管理员级别访问、故意削弱设置或配置错误部署的漏洞——可能会被争议。

如需完整概述，请参阅[安全策略](../security-policy.mdx)。
