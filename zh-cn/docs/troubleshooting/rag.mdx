如果模型在你的文档中找不到答案，请依次检查：文件是否已完成处理、对话是否能访问这些文件，以及模型是否拥有检索其内容所需的工具和上下文。本指南涵盖上传失败、检索设置以及与模型相关的上下文限制。

本页汇总了最常见的 RAG 问题及其处理方法。

## 按场景推荐设置 {#recommended-settings-by-scenario}

RAG 性能很大程度上取决于你的模型配置。默认值较为保守以保证兼容性，但针对具体部署调优后效果会好得多。所有设置均在 **Settings > Documents**（管理员区域）中配置。

:::tip Agentic 检索：启用 kb_exec
如果你的模型使用 **原生函数调用**，设置 [`ENABLE_KB_EXEC=True`](/reference/env-configuration#enable_kb_exec) 会让知识库体验明显更好。它会给模型提供一套类 shell 的接口（`ls`、`tree`、`grep`、`cat`、按行读）来操作知识内容，能力强的模型会以一种比单一搜索工具更可靠的方式把它们串起来。在 Legacy 模式下它没有任何效果。参见 [类文件系统访问](/features/workspace/knowledge#filesystem-style-access-kb_exec)。
:::

### 本地模型，上下文受限（≤ 8K tokens） {#local-models-with-constrained-context--8k-tokens}

适用于在消费级硬件上运行的 Ollama 模型（Qwen 3.5 4B、Gemma 4 12B、Muse Glimmer 30B 等），上下文窗口有限。

| 设置 | 值 | 原因 |
|------|-----|------|
| **Text Splitter** | `token` | 基于实际 token 数的一致分块大小 |
| **Markdown Header Text Splitter** | **开启** | 保留文档结构 |
| **Chunk Size** | `1000` | 较小的分块，使每个检索结果都能舒适地放入上下文 |
| **Chunk Overlap** | `100` | 标准重叠 |
| **Top K** | `3` 到 `5` | 较少分块，避免耗尽有限的上下文预算 |
| **Always Use Full Text** | 关闭 | 无法承担发送完整文档的开销 |

:::tip 上下文预算计算
分块大小为 1000 tokens、Top K 为 5 时，RAG 会注入约 5,000 tokens 的检索内容。开启混合搜索时，**Top K Reranker** 决定有多少个 chunk 会被送进模型，因此要按它来算这笔账。再算上系统提示词和对话历史——如果模型的上下文窗口为 8K，留给对话本身的大约只有 2–3K tokens。如果后续问题被截断，请适当降低 Top K。
:::

### 云模型，大上下文（32K+ tokens） {#cloud-models-with-large-context-32k-tokens}

适用于 OpenAI（GPT-5.6）、Anthropic（Claude）、Google（Gemini）、DeepSeek 及其他 API 提供商，上下文窗口为 32K–1M+ tokens。

| 设置 | 值 | 原因 |
|------|-----|------|
| **Text Splitter** | `token` | 一致的分块大小 |
| **Markdown Header Text Splitter** | **开启** | 保留文档结构 |
| **Chunk Size** | `2000` | 较大的分块，每次命中保留更多上下文 |
| **Chunk Overlap** | `200` | 更多重叠防止句子被切断 |
| **Top K** | `15` 到 `25` | 广撒网——你有足够的上下文预算 |
| **Always Use Full Text** | 小文档可考虑 | 文档不超过约 20K tokens 时，完整上下文通常优于检索。**Full Text Threshold (Characters)** 决定哪些文件会被整份放入上下文 |

:::tip 何时使用全文
如果你处理的是单个中小型文档（不超过约 50 页）并且使用大上下文模型，完整上下文往往比分块检索效果更好，因为模型能看到全部内容而没有检索遗漏。在聊天中点击某个附件并切换到 **Using Entire Document**，即可对单个文件这样处理；也可以在 **Settings** > **Documents**（管理员区域）中打开 **Always Use Full Text**，对所有文件生效。
:::

### 混合环境（本地 + 云端） {#mixed-environment-local--cloud}

如果你同时使用本地和云端模型，按最低公分母配置，并在每个模型或每次对话时覆盖：

| 设置 | 值 | 原因 |
|------|-----|------|
| **Text Splitter** | `token` | 适用于两者 |
| **Markdown Header Text Splitter** | **开启** | 适用于两者 |
| **Chunk Size** | `1500` | 折中——不太大也不太小 |
| **Chunk Overlap** | `200` | 安全默认值 |
| **Top K** | `10` | 适中——混合模型使用的好平衡点 |

## 嵌入模型推荐 {#embedding-model-recommendations}

嵌入模型决定检索质量。正确的选择取决于你的部署场景：

| 场景 | 推荐 | 原因 |
|------|------|------|
| **单用户，入门** | `all-MiniLM-L6-v2`（默认） | 本地运行，无需配置 |
| **多用户，有 Ollama** | 通过 Ollama 使用 `nomic-embed-text` | 卸载到 Ollama，释放 Open WebUI 内存 |
| **生产环境，有 API 预算** | 通过 OpenAI 使用 `text-embedding-3-small` | 性价比最高的检索质量 |
| **离线 / 自托管** | 通过 Ollama 使用 `nomic-embed-text` 或 `mxbai-embed-large` | 无需外部 API 调用 |

更换嵌入模型后，请在 **Settings > Documents**（管理员区域）中**重新索引所有现有文档**，使新嵌入生效。

## 常见 RAG 问题与修复方法 {#common-rag-issues-and-how-to-fix-them}

### 1. 模型“看不到”你的内容 {#1-the-model-cant-see-your-content}

这是最常见的问题，通常发生在内容导入阶段。模型并不是故意胡编，而是它根本没有拿到正确的内容。

**解决方法：** 检查内容提取设置。

- 前往：**Settings > Documents**（管理员区域）
- 确认你使用了可靠的内容提取引擎，例如：
  - Apache Tika
  - Docling
  - 自定义提取器（视你的文档类型而定）

:::tip
尝试上传一个文档并预览提取结果。如果内容为空，或缺少关键段落，就需要调整提取器设置，或改用其他引擎。
:::

---

### 2. 只用了文档中的一小部分内容 {#2-only-a-small-part-of-the-document-is-being-used}

Open WebUI 在设计上默认与上下文窗口有限的模型配合使用。例如，Ollama 会根据可用显存为模型选取默认上下文长度，在显存低于 24 GiB 的 GPU 上这个值是 4096 token（见 [Ollama 的上下文长度文档](https://docs.ollama.com/context-length)），远低于大多数模型本身支持的长度。正因如此，Open WebUI 会积极裁剪检索到的内容，以便把它塞进假定可用的空间里。

**解决方法：**

- 前往 **Settings > Documents**（管理员区域）
- 然后任选其一：
  - **启用 “Bypass Embedding and Retrieval”**——直接发送完整内容，不走检索过滤
  - **打开 “Always Use Full Text”**——把更完整的内容注入模型提示词

:::warning
请留意上下文上限——如果模型本身无法处理更多 token，内容仍然会被截断。
:::

---

### 3. Token 上限太小 {#3-token-limit-is-too-short}

即使检索正常，你的模型也可能无法真正处理收到的全部内容——因为它的上下文窗口根本装不下。

默认情况下，由 Ollama 托管的模型在显存不足 24 GiB 的 GPU 上使用 4096 token 的上下文窗口（Ollama 会根据可用显存选择默认值：低于 24 GiB 为 4096，24 到 48 GiB 为 32768，48 GiB 及以上为 262144）。这意味着你检索到的数据只有一小部分会被真正利用。

**为什么 Web Search 尤其需要更大的上下文窗口：**
网页内容对小上下文模型尤其不友好，因为网页通常比普通文档长得多，常见内容包括：
- 主体内容（你真正想要的信息）
- 导航菜单、页眉、页脚
- 侧边栏与广告
- 评论区和相关链接
- 元数据与嵌入脚本

即使经过提取和清洗，网页也很容易占用 4,000-8,000+ token。若上下文只有 4096 token，通常连一半都装不下，更别说页面后半部分经常还包含更关键的信息。即使 4096 token，对完整分析网页内容来说也往往不够。

**解决方法：**

- **对于 Ollama 模型**：扩大模型上下文长度：
  - 前往：**Settings > Models**（管理员区域），然后点击要修改的模型的铅笔图标（**Edit**）
  - 进入 **Advanced Params**
  - 调整 context length（例如提高到 8192+，如果模型支持，最好 16000 token 以上）

- **对于 OpenAI 和其他集成模型**：这类模型通常有自己的上下文上限，无法通过 Open WebUI 直接改动。请确认你选择的是上下文足够大的模型。

对 Web Search 而言，Ollama 在小显存 GPU 上默认的 4096 token 是非常明显的瓶颈。想获得更好的网页 RAG 效果，至少建议 8192 token，复杂网页则最好 16384+。

**替代方案：** 使用上下文更大的外部 LLM（例如 GPT-5.6、Claude、8k+ 上下文的 Gemini）。如果你想确认瓶颈是否来自上下文窗口，最好的办法之一就是拿一个大上下文模型做对照。

:::tip
在生产场景中做 Web Search 和复杂文档分析时，尽量使用支持 8192+ token 上下文的模型。
:::

### 4. 嵌入模型质量差或不匹配 {#4-embedding-model-is-low-quality-or-mismatched}

嵌入差 = 检索差。如果你的向量表示质量不够，retriever 就拿不到正确内容——无论后面的 LLM 多强都没用。

**解决方法：**

- 切换到更高质量的嵌入模型（例如 all-MiniLM-L6-v2、Instructor X，或 OpenAI embeddings）
- 前往：**Settings > Documents**（管理员区域）
- 更换模型后，**重新索引全部现有文档**，让新的 embeddings 生效。嵌入质量直接影响能检索到哪些内容。

### 5. 400: 'NoneType' object has no attribute 'encode' {#5-400-nonetype-object-has-no-attribute-encode}

这个错误通常表示嵌入模型未正确配置或根本没有可用模型。当 Open WebUI 试图创建 embedding，却没有有效模型可用时，它无法处理文本，于是就会出现这个看似晦涩的错误。

**原因：**
- 嵌入模型没有正确配置
- 模型可能没有下载完整
- 如果你使用的是外部嵌入模型，它可能当前不可访问

**解决方法：**

- 前往：**Settings > Documents > Embedding Model**（管理员区域）
- 即使该模型看起来已经选中，也请再保存一次，以强制重新检查/下载
- 如果你使用的是远程/外部嵌入服务，请确认它正在运行，并且 Open WebUI 能访问它

:::tip
修复配置后，请重新对某个文档执行嵌入，并确认日志中不再出现该错误。
:::

### 6. 上传限制与约束 {#6-upload-limits-and-restrictions}

Open WebUI 提供了多种上传限制，用于保证系统稳定与防止滥用。不同上传方式受限方式不同：

*   **聊天上传：** 受全局文件大小和文件数量限制
    *   **最大文件大小：** 由 `RAG_FILE_MAX_SIZE` 控制（默认不限），可在 **Settings > Documents > Files > Max Upload Size**（管理员区域） 中配置
    *   **Office 与 EPUB 文档**还会额外按其实际内容检查，因为这些格式本质上是压缩包。解压后远大于自身体积的文件会被拒绝，并提示解压后体积过大，即便文件本身很小。真实文档很少触发这一限制；触发的要么是文件损坏，要么是刻意构造以耗尽打开它的程序的内存。
    *   **最大文件数量：** 由 `RAG_FILE_MAX_COUNT` 控制（默认不限），可在 **Settings > Documents > Files > Max Upload Count**（管理员区域） 中配置
    *   **允许的文件扩展名：** 由 `RAG_ALLOWED_FILE_EXTENSIONS` 控制（默认全部允许），可在 **Settings > Documents > Files > Allowed File Extensions**（管理员区域） 中配置
*   **文件夹上传：** 受 `FOLDER_MAX_FILE_COUNT` [environment variable](/reference/env-configuration/#folder_max_file_count) 限制（默认 100），限制的是与文件夹直接关联的文件数
*   **知识库上传：**
    *   **文件大小限制：** 受 `RAG_FILE_MAX_SIZE` 和知识库的[文件大小限制](/features/workspace/knowledge#file-limits)约束
    *   **RAG 行为：** 上传到 Knowledge Base 的所有文件都会自动建立索引。不过与聊天上传类似，Knowledge Base 也可以在聊天中使用 **Using Entire Document**（点击聊天中的附件），它会把完整文档内容直接交给模型，而不使用向量检索。

:::info
这些限制被拆分控制后，管理员就能更精细地管理不同功能的资源占用。例如，你可以允许在精心维护的 Knowledge Base 中上传更大的文件，同时限制临时 Folder 上传的文件数量。
:::

### 7. Chunk 过于碎片化或太小 {#7-fragmented-or-tiny-chunks}

使用 **Markdown Header Text Splitter** 时，文档有时会被切得很碎（例如只剩一条目录项或一个很短的小标题）。这类小 chunk 往往缺乏足够语义上下文，嵌入模型难以准确表示，最终导致 RAG 效果差，而且还带来额外开销。

**解决方法：**

- 前往 **Settings > Documents**（管理员区域）
- 提高 **Chunk Min Size Target**
- 将其设置为 **Chunk Size** 的 50-60% 左右（例如 Chunk Size 为 `2000` 时设置为 `1000`），这样系统会把过小碎片与相邻 chunk 合并，获得更好的语义一致性，也能减少总 chunk 数量

### 8. 追问越来越慢（KV Cache 失效） {#8-slow-follow-up-responses-kv-cache-invalidation}

如果首轮回答很快，但后续追问越来越慢，你大概率遇到了 **KV Cache invalidation**。

**问题根源：** 默认情况下，Open WebUI 会把 RAG 上下文注入到 **user message**。随着对话继续，用户消息位置不断向后移动，这会迫使 Ollama、llama.cpp、vLLM 以及 OpenAI、Vertex AI 等提供商不断重新处理整段上下文。

**解决方法：**
- 设置环境变量 `RAG_SYSTEM_CONTEXT=True`
- 这样 RAG 上下文会被注入到 **system message**，其位置固定在对话开头
- 这能让提供商更有效地利用 **KV prefix caching** 或 **Prompt Caching**，即使文档很大，也能让后续追问接近瞬时返回

---

| 问题 | 修复方式 |
|--------|------|
| 🤔 模型看不到内容 | 检查文档提取器设置 |
| 🧹 只使用了部分内容 | 启用 Always Use Full Text 或 Bypass Embedding |
| ⏱ 受上下文长度限制 | 增大模型上下文长度，或使用大上下文 LLM |
| 📉 检索不准确 | 切换到更好的嵌入模型并重新索引 |
| ❌ 上传限制受阻 | 使用 Folder 上传（配合 `FOLDER_MAX_FILE_COUNT`）；Knowledge Base 限制单独计算 |
| 🧩 Chunk 过碎 / 过小 | 提高 **Chunk Min Size Target** 合并小片段 |
| 🐌 追问越来越慢 | 启用 `RAG_SYSTEM_CONTEXT=True` 修复 KV Cache 失效 |
| 📄 API 返回 “empty content” | 等文件处理完成后再加入知识库 |
| 💥 嵌入时 CUDA OOM | 降低 batch size、隔离 GPU、或重启容器 |
| 📷 PDF 图片无法提取 | 使用 Tika/Docling、启用 OCR、或更新 pypdf |
| 💀 上传时 worker 瞬时死亡 | 在多副本或多 worker 的部署下，不要继续使用默认 ChromaDB（SQLite） |
| 💀 上传时 worker 超时死亡 | 更新 Open WebUI，或提高 `--timeout-worker-healthcheck` |
| 🧠 模型忽略已附加 KB | 启用 Builtin Tools、添加系统提示、或在聊天中以整篇文档模式（Using Entire Document）附加一个小文档 |
| 📄 附加单个文件时没有返回内容 | 重新索引以重建单文件索引 |
| 📄 Docling 引用指向了错误的页码 | [重新索引，或重新上传该文件](/features/chat-conversations/rag/document-extraction/docling#citations-point-to-the-wrong-page) |

### 9. API 文件上传：“The content provided is empty” 错误 {#9-api-file-upload-the-content-provided-is-empty-error}

通过 API 上传文件后立即把它加入知识库时，你可能会遇到：

```
400: The content provided is empty. Please ensure that there is text or data present before proceeding.
```

**问题根源：** 这其实是**竞争条件**，并不是真的空文件。默认情况下，文件上传是异步处理的——上传端点会立即返回文件 ID，而内容提取与 embedding 计算会在后台进行。如果你在处理完成前就把文件加入知识库，系统看到的内容自然还是空的。

✅ **解决方法：等待处理完成**

在把文件加入知识库之前，先轮询状态端点：

```python
import requests
import time

def wait_for_processing(token, file_id, timeout=300):
    url = f'http://localhost:3000/api/v1/files/{file_id}/process/status'
    headers = {'Authorization': f'Bearer {token}'}
    
    start_time = time.time()
    while time.time() - start_time < timeout:
        response = requests.get(url, headers=headers)
        status = response.json().get('status')
        
        if status == 'completed':
            return True
        elif status == 'failed':
            raise Exception(f"Processing failed: {response.json().get('error')}")
        
        time.sleep(2)  # Poll every 2 seconds
    
    raise TimeoutError("File processing timed out")
```

**状态值说明：**
| 状态 | 含义 |
|--------|---------|
| `pending` | 等待处理 |
| `processing` | 内容提取与嵌入正在进行 |
| `completed` | 处理完成，包括知识库关联 |
| `failed` | 处理失败（检查 error 字段） |

:::tip
完整 API 工作流示例（包括正确的状态检查）请参阅 [API 端点文档](/reference/api-endpoints#checking-file-processing-status)。
:::

### 10. 嵌入时 CUDA Out of Memory {#10-cuda-out-of-memory-during-embedding}

在处理大文件或连续处理很多文件时，你可能会遇到如下 CUDA OOM 错误：

```
CUDA out of memory. Tried to allocate X MiB. GPU has a total capacity of Y GiB of which Z MiB is free.
```

**常见原因：**
- 嵌入模型与聊天模型争抢 GPU 显存
- PyTorch 重复小规模分配导致内存碎片化
- 大文档在嵌入阶段造成瞬时内存峰值

✅ **解决方法：**

1. **把嵌入任务隔离到另一张 GPU**（如果有）：
   使用 `CUDA_VISIBLE_DEVICES`，把 embedding 固定到与聊天模型不同的 GPU。
2. **降低 Embedding Batch Size**：
   调低 `RAG_EMBEDDING_BATCH_SIZE`（例如从 32 改到 8 或 4），减少峰值显存占用。
3. **启用 expandable segments**：
   ```
   PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
   ```
4. **大规模导入任务之间重启容器**：
   如果碎片化越来越严重，重启 Open WebUI 容器可清理 CUDA context。
5. **换更小的嵌入模型**：
   批量导入时使用更轻量的 embedding 模型，正式查询再切回高质量模型。
6. **将导入与聊天分离**：
   做大规模导入时，不要同时运行聊天模型。先完成 embeddings，再加载聊天模型。

### 10b. 嵌入阶段的 429 限流错误 {#10b-429-rate-limit-errors-during-embedding}

当你使用**远程/外部嵌入提供商**（OpenAI、Azure OpenAI 等），并启用了 [`ENABLE_ASYNC_EMBEDDING`](/reference/env-configuration#enable_async_embedding) 时，在批量导入文档期间可能会在日志里看到 HTTP 429 “Too Many Requests”：

```
Error generating embeddings: 429 Rate limit reached
```

**问题根源：** 启用异步嵌入后，Open WebUI 会并发发送 embedding 请求。如果一次性导入很多文档或特别大的文档，很容易超过提供商 API 的限流，尤其是在免费层或较低套餐下。

✅ **解决方法：**

1. **限制并发嵌入请求数**：
   通过 [`RAG_EMBEDDING_CONCURRENT_REQUESTS`](/reference/env-configuration#rag_embedding_concurrent_requests) 限制同时进行的 embedding API 调用数，例如设置成 `5` 或 `10`：
   ```yaml
   # docker-compose.yaml
   environment:
     RAG_EMBEDDING_CONCURRENT_REQUESTS: 5
   ```
   也可以在 **Settings > Documents > Embedding Concurrent Requests**（管理员区域） 中设置。默认 `0` 表示不限制并发。
2. **降低 batch size**：
   调低 [`RAG_EMBEDDING_BATCH_SIZE`](/reference/env-configuration#rag_embedding_batch_size)，减少单次 API 调用发送的文本量。
3. **关闭异步嵌入**：
   如果限流问题始终存在，可以把 `ENABLE_ASYNC_EMBEDDING` 设为 `False`，按顺序处理嵌入（更慢，但更稳定）。

### 11. PDF OCR 没有提取出图片中的文字 {#11-pdf-ocr-not-extracting-text-from-images}

如果包含图片文字的 PDF 上传后返回空内容：

**问题根源：** 默认的 "pypdf" 内容提取器对某些 PDF 格式支持有限，尤其是以图片为主的内容。

✅ **解决方法：**

1. **改用其他内容提取引擎**：
   - 前往 **Settings > Documents**（管理员区域）
   - 尝试 **Apache Tika** 或 **Docling**，它们通常有更好的 OCR 支持
2. **启用 PDF 图像提取**：
   - 在 **Settings > Documents**（管理员区域） 中确认 **PDF Extract Images (OCR)** 已开启
   - OCR 每次上传会占用一个处理器线程。如果你的服务器核心很多且处于空闲状态，可以提高 [`RAPIDOCR_PARAMS`](/reference/env-configuration#rapidocr_params) 中的 `intra_op_num_threads`，让单次上传的 OCR 更快完成
3. **更新 pypdf**（如果使用默认引擎）：
   新版本 pypdf（6.0.0+）对各类 PDF 格式处理更好
4. **检查 PDF 是否损坏**：
   上传前先确认该 PDF 能在常规 PDF 阅读器中正常打开

### 12. 文档上传期间 worker 死亡 {#12-worker-dies-during-document-upload}

在拥有多个副本或 worker 的部署中上传文档时，你可能会看到：

```
INFO:     Waiting for child process [12]
INFO:     Child process [12] died
```

原因在于**默认的 ChromaDB** 向量数据库与 `UVICORN_WORKERS > 1` 或多个副本的组合。内嵌式 ChromaDB 把数据保存在本地 SQLite 文件中，而这些文件同一时刻只能由一个进程写入。当多个进程同时写入时，它们就会崩溃。你通常会在同一秒内看到这样的输出：

```
save_docs_to_vector_db:1573 - adding to collection file-id
INFO:     Waiting for child process [pid]
INFO:     Child process [pid] died
```

**解决方案：** 将 `UVICORN_WORKERS=1`，并通过副本进行横向扩展。当副本数多于一个时，请改用非内嵌式的 ChromaDB：
- 把 [`VECTOR_DB`](/reference/env-configuration#vector_db) 设置为 `pgvector`、`mariadb-vector`、`milvus` 或 `qdrant`
- 或者把 ChromaDB 作为独立的 HTTP 服务器运行，并设置 [`CHROMA_HTTP_HOST`](/reference/env-configuration#chroma_http_host) / [`CHROMA_HTTP_PORT`](/reference/env-configuration#chroma_http_port)

完整细节请参见[扩缩容与高可用指南](/troubleshooting/multi-replica#6-worker-crashes-during-document-upload-chromadb--multi-worker)。

### 13. 模型附加的知识库不生效 {#13-knowledge-base-attached-to-model-not-working}

你在 **Settings > Models > Edit**（管理员区域）（自己的模型则用 **Workspace > Models**）中把某个知识库附加到了模型上，但聊天时模型似乎完全不知道知识库里的内容。

**问题根源：** Open WebUI 现在有两种不同的 RAG 模式，而模型附加知识库在这两种模式下的工作方式完全不同：

| 模式 | 知识的工作方式 |
|------|-------------------|
| **Legacy（非 native）** | Open WebUI 会自动执行 RAG：查询附加的知识库、检索相关 chunk，并把它们注入会话上下文。整个过程由系统在幕后完成，模型无需做任何事。 |
| **Native Function Calling** | 知识**不会自动注入**。模型收到的是工具（如 `query_knowledge_bases`），它必须主动决定何时调用。这是 **agentic RAG**——模型自主判断何时需要搜索知识。 |

由于 **Native Function Calling 是默认模式**，模型必须同时具备**使用工具的能力**和**被明确引导去使用工具**。在排查下面的检索配置时，请保持 Native 模式开启。

#### 知识检索行为矩阵 {#knowledge-retrieval-behavior-matrix}

| | **模型附加了知识** | **没有附加知识** |
|---|---|---|
| **Legacy Mode** | Open WebUI 只会自动注入**附加知识**的 RAG 结果 | 不会自动执行 RAG——用户必须通过 `#` 手动把知识库加入聊天 |
| **Native Function Calling** | 模型收到的工具仅限于**附加知识**——仍需主动调用 | 如果启用了 Builtin Tools，模型会收到能访问**所有可访问 KB** 的工具——仍需主动调用 |

关键结论：在 Native Mode 下，模型无论如何都必须使用知识工具；附加知识只会限制*可以搜索的内容*；[范围访问](/features/workspace/knowledge#scoped-access-keeps-things-organized)列出了所有算作已附加的内容。

:::tip 在 Native Mode 下阻止模型访问知识库
如果你想阻止某个模型在 native mode 下访问**任何**知识库，不需要关闭整个 Builtin Tools。你只需在 **Settings > Models > Edit > Builtin Tools**（管理员区域）（自己的模型则用 **Workspace > Models**）中关闭 **Knowledge Base** 这个类别。这样会移除所有知识相关工具，但保留其他内置工具（web search、memory、notes 等）。完整分类请参阅 [细粒度内置工具分类](/features/extensibility/plugin/tools#granular-builtin-tool-categories-per-model)。
:::

![模型编辑器中的 Builtin Tools 分类](/images/features/plugin/tools/builtin_tools.png)

✅ **建议按以下顺序检查：**

1. **先检查全局模型设置：**
   - 前往 **Settings > Models**（管理员区域），打开 **Model Defaults**
   - 展开 **Model Parameters**，确认 **Function Calling** 是否被设为 `native`
   - 没有显式设置自身值的模型会继承这一设置。请让生效值保持为 `native`，并确认所选模型支持工具调用
   - 同时检查模型编辑器中的 **Features**。**Preload files** 控制文件处理，**Builtin Tools** 及其 **Knowledge Base** 类别控制原生知识工具的访问权限

:::info 检查生效的模型设置
**Settings > Models > Edit > Advanced Params**（管理员区域）（自己的模型则用 **Workspace > Models**）中的单模型设置，在显式设置时会覆盖全局默认值。没有自己 `function_calling` 值的模型会继承全局设置。当模型行为与预期不符时，这两处都要检查。
:::

2. **确保该模型已启用 Builtin Tools**：
   - 进入该模型的 **Settings > Models > Edit**（管理员区域）（自己的模型则用 **Workspace > Models**）
   - 在 **Builtin Tools** 下确认 **Knowledge Base** 类别已启用（默认启用）
   - 如果被关闭，模型就没有任何途径去查询附加知识库

3. **加入系统提示词引导：**
   - 有些模型需要明确的工具使用指引，可以加入类似内容：
     > “当用户询问已附加的文档时，先用可用的知识工具搜索这些文档再回答，并引用相关段落。”

4. **检查处理与访问权限：**
   - 确认已上传的文件处理完成，并且当前用户可以访问该知识库
   - 换用一个原生工具调用可靠的模型，然后针对文档中某个你可以核实的事实提问

5. **对于小文档，试试 Using Entire Document：**
   - 在聊天中附加知识库，点击它并打开 **Using Entire Document**，同时开启模型的 **Preload files** 能力。对于模型附加的知识库，该开关只在 Legacy function calling 下才生效
   - 这会发送完整的提取内容，而不是检索选中的片段。请确保文档能放进模型的上下文窗口

:::info 为什么用 agentic RAG？
Open WebUI 使用 **agentic RAG**：由模型决定何时以及如何搜索知识库，并且可以用不同的查询重试。这需要模型能够有效地使用工具。如果所选模型无法可靠地检索出一个已知事实，请改用工具调用能力更强的模型，或用 Using Entire Document 试试一份小文档。
:::

关于知识作用域与检索模式的完整说明，请参阅 [知识文档](/features/workspace/knowledge#agentic-knowledge-tools) 和 [文件上下文与内置工具](/features/chat-conversations/rag#preload-files-vs-builtin-tools)。

### 14. 附加链接或 YouTube 视频失败 {#14-attaching-a-link-or-a-youtube-video-fails}

附加某个网页或 YouTube 视频时返回了错误提示。消息会指出失败的具体环节：链接无法读取会指明是哪个链接，YouTube 字幕被拒绝会给出原因，而提到知识库的消息则表示内容已经读取成功，只是保存失败。

`[ERROR: Could not read content from <url>]` 表示什么都没有附加成功。常见原因有：站点拦截了请求，或只有在 JavaScript 执行后才提供内容——这可以由 [`WEB_LOADER_ENGINE=playwright`](../reference/env-configuration.mdx#web_loader_engine) 处理；Open WebUI 没有被告知要使用的代理，参见 [`WEB_SEARCH_TRUST_ENV`](../reference/env-configuration.mdx#web_search_trust_env)；以及地址被有意拒绝——私有地址、回环地址、云元数据端点以及任何匹配 [`WEB_FETCH_FILTER_LIST`](../reference/env-configuration.mdx#web_fetch_filter_list) 的地址都从不会被请求。

YouTube 附加项就是视频的字幕，因此没有可用字幕的视频根本无法附加。当消息显示 YouTube 阻止了来自你服务器地址的请求时（在云服务商网段中很常见），请通过 [`YOUTUBE_LOADER_PROXY_URL`](../reference/env-configuration.mdx#youtube_loader_proxy_url) 转发。当字幕存在但不是所请求的语言时，把你的语言加入 [`YOUTUBE_LOADER_LANGUAGE`](../reference/env-configuration.mdx#youtube_loader_language)。上传者关闭的字幕、年龄限制以及不可观看的视频则无法绕过。

### 15. 附加单个文件时没有返回来源 {#15-attaching-a-single-file-returns-no-sources}

用 `#` 附加单个文件时检索不到任何内容，而附加包含该文件的知识库则一切正常。

**问题所在**：属于某个知识库的文件会被索引两次，一次随知识库索引，一次单独索引。单独附加它只会检索它自己的那份索引，而在向量数据库迁移、部分重置或直接在向量数据库中删除之后，这份索引可能已经丢失。

**解决方案：**

1. 在 **Settings > Documents > Reindex Knowledge and Memory Vectors**（管理员区域）执行**重新索引**。这会重建每个知识库、其中每个文件的单文件索引，以及每位用户的记忆。它会重新提取并重新嵌入全部内容，因此请预留足够时间；如果使用的是付费嵌入模型，还要考虑相应费用。
2. 如果文件不属于任何知识库，请**重新上传**，因为重新索引只覆盖知识库。
