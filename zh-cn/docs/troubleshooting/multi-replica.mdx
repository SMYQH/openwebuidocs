# 多副本、高可用与并发故障排查 {#multi-replica-high-availability--concurrency-troubleshooting}

本指南说明 **多副本** 部署（Docker Compose、Docker Swarm、Kubernetes）中的常见问题。请通过增加副本来扩容，每个副本跑一个 worker；不推荐把 `UVICORN_WORKERS` 设为大于 `1`，那样会遇到同样的问题。

要搭建扩缩容部署，请遵循[扩展 Open WebUI](/getting-started/advanced-topics/scaling)。单实例调优请参阅[优化、性能与 RAM 占用](/troubleshooting/performance)。

## 核心要求检查清单 {#core-requirements-checklist}

在排查具体错误之前，请先确认你的部署满足以下要求。缺少其中任何一项都会导致不稳定、登录循环或数据丢失。

1.  **共享密钥：** [`WEBUI_SECRET_KEY`](/reference/env-configuration#webui_secret_key) 在所有副本上完全一致。
2.  **PostgreSQL：** [`DATABASE_URL`](/reference/env-configuration#database_url) 指向 PostgreSQL。多实例**不支持** SQLite。参见[第 1 步](/getting-started/advanced-topics/scaling#step-1-switch-to-postgresql)。
3.  **Redis：** 每个副本都设置了 [`REDIS_URL`](/reference/env-configuration#redis_url) 和 [`WEBSOCKET_MANAGER=redis`](/reference/env-configuration#websocket_manager)。参见[第 2 步](/getting-started/advanced-topics/scaling#step-2-add-redis)。
4.  **外部向量数据库：** [`VECTOR_DB`](/reference/env-configuration#vector_db) 指向客户端-服务端数据库，或者 ChromaDB 作为[独立 HTTP 服务](/reference/env-configuration#chroma_http_host)运行。嵌入式 ChromaDB 在多进程写入时会崩溃。参见[第 4 步](/getting-started/advanced-topics/scaling#step-4-switch-to-an-external-vector-database)。
5.  **共享文件存储：** 每个副本都通过对象存储或共享文件系统访问同一批上传文件。参见[第 5 步](/getting-started/advanced-topics/scaling#step-5-share-file-storage-across-instances)。
6.  **单一迁移进程：** 升级时只有一个进程执行数据库迁移。参见[更新与迁移](#updates-and-migrations)。

在这些之外，如需推荐的调优参数，请参阅[扩缩容部署所需的最小环境变量集](/getting-started/advanced-topics/scaling#minimum-environment-variables-for-scaled-deployments)。

## 常见问题 {#common-issues}

### 1. 登录循环 / 401 Unauthorized 错误 {#1-login-loops--401-unauthorized-errors}

**症状：**
- 登录后下一次点击就被登出
- 浏览器控制台在登录后立刻出现 "Unauthorized" 或 "401" 错误
- 日志中出现 "Error decrypting tokens"

**原因：**
各副本使用了不同的 `WEBUI_SECRET_KEY`。副本 B 会拒绝由副本 A 签名的 token。如果不设置 `WEBUI_SECRET_KEY`，每个容器都会在首次启动时各自生成一个密钥。

**解决方法：**
在所有副本上，把 `WEBUI_SECRET_KEY` 设置成**同一个**强随机字符串。如果你另外设置了 `OAUTH_SESSION_TOKEN_ENCRYPTION_KEY`，它也必须在所有地方保持一致。

```yaml
# Example in Kubernetes/Compose
env:
  - name: WEBUI_SECRET_KEY
    value: "your-super-secure-static-key-here"
```

### 2. WebSocket 403 错误 / 连接失败 {#2-websocket-403-errors--connection-failures}

**症状：**
- 聊天停止响应或一直卡住
- 浏览器控制台出现 `WebSocket connection failed: 403 Forbidden` 或 `Connection closed`
- 日志中出现 `https://your-domain.com is not an accepted origin`

**原因：**
- **CORS：** 用户访问 Open WebUI 所用的来源不在允许列表中。
- **缺少 Redis：** 没有设置 `WEBSOCKET_MANAGER=redis` 时，实时更新会停留在产生它的那台副本上，因此连接到其他副本的用户永远看不到响应。

**解决方法：**
1.  **配置 CORS：** 把所有公网来源加入 [`CORS_ALLOW_ORIGIN`](/reference/env-configuration#cors_allow_origin)，这是一个**以分号分隔**的列表：

    ```bash
    CORS_ALLOW_ORIGIN="https://chat.yourdomain.com;http://chat.yourdomain.com;https://yourhostname;http://localhost:3000"
    ```

    请把用户可能使用的所有域名、主机名和 IP 都列进去。
2.  在**所有**副本上**为 WebSocket 启用 Redis**：

    ```bash
    REDIS_URL=redis://your-redis-host:6379/0
    WEBSOCKET_MANAGER=redis
    ```

### 3. “Model Not Found” 或配置不一致 {#3-model-not-found-or-configuration-mismatch}

**症状：**
- 你在 Admin UI 中启用的模型，对部分请求可见、对部分请求不可见
- 聊天间歇性报 “Model not found”

**原因：**
设置保存在共享数据库中，每个副本都从那里读取，因此即使没有 Redis，设置变更也能到达所有副本。但模型列表是按副本各自保存的，除非由 `WEBSOCKET_MANAGER=redis` 共享。没有它时，每个副本只知道自己加载过的模型。

**解决方法：**
在每个副本上设置 `REDIS_URL` 和 `WEBSOCKET_MANAGER=redis`（参见[第 2 步](/getting-started/advanced-topics/scaling#step-2-add-redis)）。

对于 Ollama，当一次对话被发往该副本并不认识的模型时，它会先从 Ollama 服务器重新读取模型列表。在副本持有过期列表期间拉取的模型，会在下一次请求时可用。

### 4. 数据库损坏 / “Locked” 错误 {#4-database-corruption--locked-errors}

**症状：**
- 日志中出现 `database is locked` 或严重 SQL 错误
- 在一个实例上保存的数据，在另一个实例上却看不到
- 短暂预热后，几乎每个请求都出现 `sqlalchemy.exc.TimeoutError: QueuePool limit of size N overflow M reached, connection timed out, timeout 30.00`，而不只是在峰值负载时
- `/api/config`、聊天列表和 OIDC 回调会卡住 10 秒到数分钟
- 日志里出现 `PRAGMA journal_mode=WAL` 开始执行，但始终没有完成

**原因：**
**SQLite** 与多副本搭配使用，或者虽然是单副本但 `webui.db` 位于网络文件系统（NFS、CIFS、CephFS、Azure Files、网络 PVC）上。SQLite 的文件锁在[网络文件系统上并不可靠](https://www.sqlite.org/faq.html#q5)，而缓慢的网络 `fsync` 会长时间占用每个池连接，足以耗尽连接池。机制细节参见[磁盘 I/O 延迟](/troubleshooting/performance#disk-io-latency-sqlite--storage)。

**解决方案（按优先级排列）：**

1. **迁移到 PostgreSQL**（多副本的必需项）。参见[第 1 步](/getting-started/advanced-topics/scaling#step-1-switch-to-postgresql)。
2. **单实例：** 把 `webui.db` 移到本地直连的 SSD/NVMe（宿主机 bind mount、节点本地卷）。上传文件和 RAG 文件仍可放在共享存储上。
3. 迁移期间的**临时手段**：减少连接数并延长锁等待时间，可以降低锁竞争。
   ```bash
   DATABASE_POOL_SIZE=1
   DATABASE_SQLITE_PRAGMA_BUSY_TIMEOUT=30000
   ```

更大的 `DATABASE_POOL_SIZE` 反而会更糟：它会让更多缓慢的 `fsync` 同时压向同一份存储。

### 5. 上传的文件或 RAG 知识不可访问 {#5-uploaded-files-or-rag-knowledge-inaccessible}

**症状：**
- 你在某个实例上上传了文件，但模型稍后却找不到它
- 对话中的图片会间歇性显示**图像不可用**占位符，具体取决于请求由哪个副本处理

**原因：**
上传的文件没有在副本之间共享。上传到副本 1 的文件在副本 2 上并不存在。

**解决方法：**
按[第 5 步](/getting-started/advanced-topics/scaling#step-5-share-file-storage-across-instances)的说明，在每个副本上使用对象存储或共享文件系统。在 Kubernetes 上，共享卷需要 `ReadWriteMany`（RWX）访问权限。

### 6. 文档上传期间 worker 崩溃（ChromaDB + 多 worker） {#6-worker-crashes-during-document-upload-chromadb--multi-worker}

**症状：**
- 日志在同一秒内出现如下序列：
  ```
  save_docs_to_vector_db:1619 - adding to collection file-id
  INFO:     Waiting for child process [pid]
  INFO:     Child process [pid] died
  ```
- RAG 文档导入过程中 worker 立即崩溃（不是超时）

**原因：**
默认 ChromaDB 以嵌入方式运行在每个 Open WebUI 进程中，并把数据存放在本地 SQLite 文件里（`data/vector_db/`）。同一时刻只能有一个进程写入它们。存在多个副本或 worker 时，上传期间的并发写入会让进程崩溃。

**解决方法：**

| 选项 | 调整 | 取舍 |
|--------|--------|----------|
| **保持 1 个 worker** | `UVICORN_WORKERS=1`（默认值），通过增加副本来扩容 | 副本超过一个之后，仍需采用下面某种方案 |
| **使用 ChromaDB HTTP 模式** | 把 [`CHROMA_HTTP_HOST`](/reference/env-configuration#chroma_http_host) / [`CHROMA_HTTP_PORT`](/reference/env-configuration#chroma_http_port) 指向独立的 Chroma 服务 | 每个进程都通过 HTTP 连接同一个服务 |
| **切换向量数据库** | 把 [`VECTOR_DB`](/reference/env-configuration#vector_db) 设为 `pgvector`、`mariadb-vector`、`milvus`、`qdrant` 或其他客户端-服务端数据库 | 天然为大量客户端设计 |

若要继续使用 ChromaDB，请把它作为独立服务运行：

```bash
# Run the Chroma server separately
chroma run --host 0.0.0.0 --port 8000 --path /data/vector_db

# Then point Open WebUI at it
CHROMA_HTTP_HOST=localhost
CHROMA_HTTP_PORT=8000
```

### 7. 云上 Kubernetes 比本地更慢 {#7-slow-performance-in-cloud-vs-local-kubernetes}

**症状：**
- Open WebUI 在本地运行良好，但部署到 AKS、EKS 或 GKE 后性能下降或出现超时。
- 即使资源充足，并发负载下性能也会急剧下降

**原因：**
通常是到数据库的网络延迟，或 SQLite 的磁盘 I/O 延迟——两者在云环境里都比本地 NVMe 和局域网更高。

**解决方法：**
参见[云基础设施延迟](/troubleshooting/performance#cloud-infrastructure-latency)。

### 8. 优化数据库性能 {#8-optimizing-database-performance}

**症状：**
- PostgreSQL 在负载下出现 `QueuePool limit of size N overflow M reached` 错误
- PostgreSQL 以 `too many clients already` 拒绝连接

**原因：**
单个进程的连接池对其负载而言过小，或者所有进程的连接池加起来超过了 PostgreSQL 的 `max_connections`。每个副本都有自己的连接池。

**解决方法：**
按进程设置 `DATABASE_POOL_SIZE` 与 `DATABASE_POOL_MAX_OVERFLOW`，并参照[第 1 步](/getting-started/advanced-topics/scaling#step-1-switch-to-postgresql)核对总和是否超过 `max_connections`。如果出现的是阻塞式任务堆积（应用卡死，但 CPU 和内存看起来正常），则提高 [`THREAD_POOL_SIZE`](/troubleshooting/performance#thread-pool-size)。

### 9. Function/Tool 依赖安装导致崩溃 {#9-functiontool-dependency-installation-crashes}

**症状：**
- worker 在启动时，或首次加载某个 function/tool 时，因 `AssertionError` 崩溃
- 日志中出现 pip 锁冲突或多个 pip 进程竞争

**原因：**
当 function 或 tool 在 frontmatter 中声明 `requirements` 时，Open WebUI 会在运行时执行 `pip install`。当 `UVICORN_WORKERS` 大于 `1` 时，每个 worker 会同时向同一个环境安装依赖。

**解决方法：**
保持 `UVICORN_WORKERS=1`，设置 [`ENABLE_PIP_INSTALL_FRONTMATTER_REQUIREMENTS=False`](/reference/env-configuration#enable_pip_install_frontmatter_requirements)，并在镜像构建阶段安装这些包：

```dockerfile
FROM ghcr.io/open-webui/open-webui:main

RUN pip install --no-cache-dir python-docx requests beautifulsoup4
```

运行时安装只适合开发或 homelab 环境。参见[外部包](/features/extensibility/plugin/tools/development#external-packages)。

## 部署最佳实践 {#deployment-best-practices}

### 更新与迁移 {#updates-and-migrations}

:::danger 关键：避免并发迁移
**升级 Open WebUI 时，只能有一个进程执行数据库迁移。**
:::

:::danger 关键：绝不能让两个版本共用同一个数据库
**新旧版本的 Open WebUI 实例绝不能同时为流量提供服务。** 在涉及 schema 变更的版本中，滚动更新、金丝雀发布以及“更新一个副本、等它健康后再扩展其余副本”这类策略都不受支持。
:::

数据库迁移会在启动时自动执行。如果多个副本同时启动新版本，它们就会并发执行迁移，从而可能损坏 schema。

请先停止所有副本，让其中一个实例完成迁移，然后再把整个集群以新版本拉起。这会带来一次短暂的全量中断；跨 schema 变更并不存在通用的零停机路径。

升级前请先备份数据库。把旧镜像换回去并不能撤销一次迁移：schema 以及被重写的行都会保持迁移之后的状态。真正的退路是恢复一份升级前制作的备份。参见[备份与恢复](/getting-started/updating#backup--restore)。

**安全更新流程：**

#### 方案 1：指定一个主迁移 Pod（推荐） {#option-1-designate-a-master-migration-pod-recommended}
1.  选一个 pod 作为迁移“主节点”。
2.  在该 pod 上保持 `ENABLE_DB_MIGRATIONS=True`（默认）。
3.  在其他所有 pod 上设置 `ENABLE_DB_MIGRATIONS=False`。
4.  更新时，由主节点迁移 schema，其他 pod 跳过迁移。

`ENABLE_DB_MIGRATIONS` 只决定**哪一个**实例执行迁移。新镜像要同时下发到每个 pod。如果你的平台无法同时替换所有 pod，请使用方案 2。

#### 方案 2：更新时先缩容 {#option-2-scale-down-during-update}
1.  **缩容：** 把副本数设为 `1`。
2.  **更新**镜像或版本。
3.  **等待**单实例启动并完成迁移。
4.  **扩容**到你期望的副本数。

### 会话亲和性（Sticky Sessions） {#session-affinity-sticky-sessions}

在配置好 Redis 并开启 WebSocket（默认开启）的情况下，任意副本都可以处理任意请求，因此并不需要粘性会话。在网络不稳定时，偶尔的抖动或重连仍可能影响流式响应或工具调用抵达浏览器的过程；如果你遇到这种情况，开启粘性会话值得一试。当 `ENABLE_WEBSOCKET_SUPPORT=false` 时，粘性会话是必需的，因为长轮询要求同一个连接的每个请求都落到同一个副本上。

- **Nginx Ingress：** `nginx.ingress.kubernetes.io/affinity: "cookie"`
- **AWS ALB：** 启用 Target Group Stickiness。

### 使用更快的 JSON 编码器 {#use-the-faster-json-encoder}

```bash
ENABLE_ORJSON=True
```

在多副本部署中，每个 Socket.IO 事件都会通过 Redis 发布，在发出时编码、在接收时解码，这使得 JSON 编码成为处理实时更新的副本上最大的开销之一。[`ENABLE_ORJSON`](/reference/env-configuration#enable_orjson)（默认 `True`）在整个应用中改用快得多的 [orjson](https://pypi.org/project/orjson/) 这个 Rust 实现。它随 Open WebUI 一同提供，因此无需安装任何东西。在小型单实例上，差异主要体现在保存和打开非常长的对话时。

orjson 无法处理的载荷（非字符串字典键、超出 64 位的整数）会自动回退到标准库，因此可用的载荷绝不会变成错误。仍然存在两处差异：

- **响应体中的 `NaN` 和 `Infinity` 浮点数会变成 `null`。** 使用标准库时，这样的响应会失败。只有自定义工具或管道输出这些值时才相关。
- **编码后的输出使用原始 UTF-8，而不是 `\uXXXX` 转义。** 两者解析结果完全相同；只有对编码后 JSON 做校验和的东西才会受影响。行分隔符字符仍会被转义，因此流式回复不会被拆开。切换该设置无需迁移。
