Open WebUI 中的 Web Search 让语言模型能够访问互联网中的实时信息。当它没有按预期工作时，本指南可以帮助你诊断并解决常见问题。

## 常见 Web Search 问题 {#common-web-search-issues}

### 1. Web Search 在 HTTP 代理后失效 {#1-web-search-fails-behind-http-proxy}

如果你把 Open WebUI 部署在 HTTP 代理后，可能会发现搜索查询本身可以成功（例如 SearXNG 能返回结果），但后续内容抓取会失败，并出现类似错误：

- `[Errno -3] Temporary failure in name resolution`
- `Connection timeout to host`
- `The content provided is empty`

这是因为网页内容抓取器默认不会使用你的 `http_proxy`/`https_proxy` 环境变量。

✅ **解决方法：**

1. 前往：**设置 > Web Search**（管理员区域）
2. 启用 **信任代理环境**
3. 保存修改

或者设置环境变量 [`WEB_SEARCH_TRUST_ENV`](/reference/env-configuration#web_search_trust_env)：

```bash
WEB_SEARCH_TRUST_ENV=True
```

:::info
这是一个 **ConfigVar** 变量，意味着它既可以在启动时通过环境变量设置，也可以通过管理面板 UI 配置。一旦你在 UI 中设置了它，数据库中的值就会优先生效。

这个设置会让 Open WebUI 的网页内容加载器遵循环境变量中的代理设置（`http_proxy`、`https_proxy`）。如果不开启，即使你的搜索引擎本身能通过代理工作，从返回 URL 抓取内容时仍然会失败。
:::

### 2. 来自 SearXNG 的 403 Forbidden 错误 {#2-403-forbidden-errors-from-searxng}

如果你使用的是 SearXNG，并在日志中看到 `403 Client Error: Forbidden`，通常说明没有启用 JSON 格式。

✅ **解决方法：**

编辑你的 SearXNG `settings.yml`，并在 formats 列表中加入 `json`：

```yaml
search:
  formats:
    - html
    - json
```

修改后重启 SearXNG。

### 3. 内容为空或结果质量差 {#3-empty-content-or-poor-results}

如果 Web Search 返回空内容或结果质量很差，问题通常与上下文窗口大小或内容提取有关。

✅ **解决方法：**

- **增大上下文长度**：网页通常包含 4,000-8,000+ token。如果你的模型限制是 2048 token，那你实际上会丢掉大部分内容。请在 **设置 > 模型 > 编辑**（管理员区域）的模型 **> 高级参数** 中将其提高到 16384+（低于这个值时，网页内容效果通常都比较差）。

- **检查结果数量**：通过调整 `WEB_SEARCH_RESULT_COUNT` 控制抓取的结果数。

  在 Native/Agentic 工具调用模式下，如果模型在 `search_web` 中省略了 `count`，Open WebUI 会默认使用 `WEB_SEARCH_RESULT_COUNT`。如果模型提供了 `count`，也会被限制在管理员配置的同一最大值以内。

- **压缩响应会被拒绝**：Open WebUI 会请求未压缩的页面和文件，并以 `The server answered with a compressed response, which is not accepted.` 拒绝压缩响应。如果主机总是以压缩方式发送文件（例如上传时带有 `Content-Encoding` 说明头的 S3 或 MinIO 对象），就无法读取。请在不带该说明头的情况下重新上传文件。

- **尝试不同 loader**：把 `WEB_LOADER_ENGINE` 改为 `playwright` 以处理 JavaScript 较重的网站，或使用 `firecrawl`/`tavily` 获得更好的提取效果。

- **设置真实的 User-Agent**：如果来自 Wikipedia、受 Cloudflare 保护的大型站点等来源的结果为空（或在日志中出现 403），说明默认的 Python `requests` / `aiohttp` UA 被反爬机制拦截了。请将 [`USER_AGENT`](/reference/env-configuration#user_agent) 设置为真实的浏览器 UA（例如 `Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/126.0 Safari/537.36`）。该设置同时影响 Web 搜索的结果抓取与 `fetch_url` 工具。

关于上下文窗口问题的更多细节，请参阅 [RAG 故障排查指南](./rag)。

### 4. Web Search 已启用但模型没有调用 `search_web` {#4-web-search-is-enabled-but-the-model-does-not-call-search\_web}

如果网页搜索引擎已经配置好（例如以 DuckDuckGo 为后端的 DDGS）、模型也启用了 Web Search、当前对话的 Web Search 开关也已打开，但助手仍然不搜索就作答，那么问题通常出在模型能力而不是搜索提供商。

在 Native/Agentic 模式下，Open WebUI 会把网页搜索暴露为 `search_web` 工具。模型必须自行决定调用该工具并返回有效的结构化工具调用。较旧、较小或较弱的本地模型可能会漏掉这个工具、无视它，或者即使 Open WebUI 的所有设置都正确也产出格式错误的工具调用。

**解决方法：**

- **为网页搜索工作流使用现代的高质量工具调用模型。** 前沿模型或近期的大型开放权重模型，在判断何时该搜索以及正确组织工具调用方面，都比老旧或较小的模型可靠得多。有关模型要求与建议，请参阅[工具调用模式：原生与旧版](/features/extensibility/plugin/tools#tool-calling-modes-default-vs-native)。
- **确认原生函数调用已启用**：在 **设置 > 模型 > 编辑**（管理员区域） 中选中模型，进入 **高级参数 > 函数调用**。内置的网页搜索工具属于原生模式工具。
- **检查三道网页搜索开关**：全局已启用网页搜索、模型上已启用网页搜索、对话中已打开网页搜索开关。
- **对于 DDGS / DuckDuckGo 配置**，请参照 [DDGS 提供商指南](/features/chat-conversations/web-search/providers/ddgs)单独确认提供商配置；但如果 DDGS 在日志中返回了结果而助手却从不调用 `search_web`，请更换模型。

### 5. 连接超时 {#5-connection-timeouts}

如果 Web Search 经常超时：

✅ **解决方法：**

- **降低并发请求数**：设置 `WEB_SEARCH_CONCURRENT_REQUESTS=1`，按顺序执行（Brave 免费层需要这样做）。

- **调整 loader 并发**：如果同时抓取很多页面，请降低 `WEB_LOADER_CONCURRENT_REQUESTS`。

- **检查网络连通性**：确认 Open WebUI 能访问搜索引擎以及搜索结果对应的 URL。

## 环境变量参考 {#environment-variables-reference}

完整的 Web Search 环境变量列表，请参阅 [环境变量配置文档](/reference/env-configuration#web-search)。

常用变量：

| 变量 | 说明 |
|----------|-------------|
| `WEB_SEARCH_TRUST_ENV` | 为内容抓取启用代理支持 |
| `WEB_SEARCH_RESULT_COUNT` | 要抓取的搜索结果数量 |
| `WEB_SEARCH_CONCURRENT_REQUESTS` | 向搜索引擎发起的并发请求数 |
| `WEB_LOADER_CONCURRENT_REQUESTS` | 页面抓取并发数 |
| `WEB_LOADER_ENGINE` | 内容提取引擎 |


以上全部都是持久化设置，因此 **Settings > Web Search**（管理员区域） 才是它们的唯一真实来源。页面抓取器会在每次搜索时从这份已保存的配置中读取代理信任、加载器并发数和 SSL 校验设置，所以你在那里保存的变更会直接作用于下一次搜索，无需重启，并且与这些设置在其他位置的行为保持一致。如果你在管理面板中做的修改看起来没有生效，请回到那里重新确认，而不要想当然地认为环境变量仍在起作用：环境变量只用于设定初始值，之后保存的设置优先。

**Web Search Engine** 只在 **Web Search** 开启期间才是必需的，因此 **Loader** 设置可以在没有它的情况下保存。

当 **Web Search** 关闭时，页面会隐藏那些仅对搜索生效的设置，但它们已保存的值会被保留。
