OAuth 和 Single Sign-On（SSO）为 Open WebUI 提供安全认证。当登录出现问题时，通常都能在下面这些常见原因中找到答案。

## 常见 OAuth/SSO 问题 {#common-oauthsso-issues}

### 1. WebUI URL 未配置 {#1-webui-url-not-configured}

大多数 OAuth 流程都需要应用的外部 URL（redirect URI），这样提供商才能在登录后把用户重定向回来。如果缺失，OAuth 无法完成。

**解决方法：**
- 前往：**Settings > General**（管理员区域）
- 确认 **WebUI URL** 已填写，并且指向你的真实部署地址（例如 `https://yourwebui.yourdomain.com`）

:::tip
注意拼写错误——OAuth 非常严格。URL 必须完全匹配，包括 `https://`。
:::

---

### 2. 环境变量配置错误 {#2-incorrect-environment-variable-configuration}

这是 OAuth 失效的**最常见原因**。环境变量拼写错误、缺失，或使用了错误名称，都会让认证无法工作。

**常见环境变量错误：**

#### ❌ 人们经常误用的不存在变量： {#non-existent-variables-people-often-use}
- `OIDC_CONFIG` → 应使用 `OPENID_PROVIDER_URL`
- `WEBUI_OIDC_CLIENT_ID` → 应使用 `OAUTH_CLIENT_ID`
- `WEBUI_ENABLE_SSO` → OAuth 由 `ENABLE_OAUTH` 默认启用。只有需要通过 SSO 创建新账户时，才需要 `ENABLE_OAUTH_SIGNUP`
- `WEBUI_AUTH_TYPE` → 这个变量不存在——请改用提供商对应的变量
- `OPENID_CLIENT_ID` → 应使用 `OAUTH_CLIENT_ID`
- `OPENID_CLIENT_SECRET` → 应使用 `OAUTH_CLIENT_SECRET`

#### ✅ 正确的 OIDC 变量： {#correct-oidc-variables}
```bash

# Required for OIDC
OAUTH_CLIENT_ID=your_client_id
OAUTH_CLIENT_SECRET=your_client_secret
OPENID_PROVIDER_URL=https://your-provider/.well-known/openid-configuration

# Needed only for SSO to create accounts that do not exist yet
ENABLE_OAUTH_SIGNUP=true

# Optional but recommended
OAUTH_PROVIDER_NAME=Your Provider Name
OAUTH_SCOPES=openid email profile
OPENID_REDIRECT_URI=https://your-domain/oauth/oidc/callback

# Optional: pass provider-specific authorize params (JSON object)
# e.g. force consent screen, prefill user/email hint
OAUTH_AUTHORIZE_PARAMS={"prompt":"consent","login_hint":"user@example.com"}
```

#### ✅ Google 特有的可选 authorize 参数： {#google-specific-optional-authorize-params}
```bash
# Optional: extra Google /authorize params as JSON
GOOGLE_OAUTH_AUTHORIZE_PARAMS={"prompt":"consent","login_hint":"user@example.com","hd":"example.com"}
```

#### ✅ 正确的 Microsoft 变量： {#correct-microsoft-variables}
```bash

# Use these for Microsoft Entra ID
MICROSOFT_CLIENT_ID=your_client_id
MICROSOFT_CLIENT_SECRET=your_client_secret
MICROSOFT_CLIENT_TENANT_ID=your_tenant_id
OPENID_PROVIDER_URL=https://login.microsoftonline.com/YOUR_TENANT_ID/v2.0/.well-known/openid-configuration
ENABLE_OAUTH_SIGNUP=true
```

**解决方法：**
- **始终以官方 [环境变量配置文档](/reference/env-configuration/) 为准**
- 逐项检查你的部署环境：
  - 确认所有必需环境变量都按文档中的精确名字设置
  - 如果你是自托管，请确认这些变量已出现在 Docker Compose、Kubernetes manifest 或 `.env` 文件中
- 修改变量后，请重启后端/应用，使新值生效

:::info
如果你的提供商在 `/authorize` 步骤需要额外参数（例如 `prompt`、`login_hint`、`domain_hint` 或 `resource`），请通过 `OAUTH_AUTHORIZE_PARAMS` 以 JSON 对象形式传入。

对于 Google 特定定制项，也可以使用 `GOOGLE_OAUTH_AUTHORIZE_PARAMS`。
:::

:::tip
大多数 OAuth 错误（循环、401 错误、无响应）都源于环境变量名称错误、完全缺失，或沿用了旧变量名。
:::

:::warning
**Kubernetes/YAML 用户注意：** 小心**环境变量名尾部的空格**。在 YAML 中，如果你把键写成 `'OAUTH_CLIENT_ID '`（引号内尾部带空格），最终设置出来的变量名就真的是 `OAUTH_CLIENT_ID `，Open WebUI **不会识别**。请确保环境变量名末尾没有任何空白字符：

```yaml
# Wrong — trailing space inside quotes:
- name: 'OAUTH_CLIENT_ID '
  value: your_client_id

# Correct — no trailing space:
- name: OAUTH_CLIENT_ID
  value: your_client_id
```
:::

### 3. 缺少必需变量 {#3-missing-required-variables}

#### OPENID_PROVIDER_URL 对 OIDC 是必需的 {#openid\_provider\_url-is-mandatory-for-oidc}
很多用户会忘记这个关键变量。缺少它时，OIDC 无法工作。

✅ **Microsoft Entra ID：**
```bash
OPENID_PROVIDER_URL=https://login.microsoftonline.com/YOUR_TENANT_ID/v2.0/.well-known/openid-configuration
```

✅ **Google：**
```bash
OPENID_PROVIDER_URL=https://accounts.google.com/.well-known/openid-configuration
```

✅ **Authentik：**
```bash
OPENID_PROVIDER_URL=https://your-authentik-domain/application/o/your-app-name/.well-known/openid-configuration
```

#### 按提供商分类的其他必需变量： {#other-required-variables-by-provider}
- **所有 OAuth 提供商：** `ENABLE_OAUTH`（默认开启）；需要通过 SSO 创建账户时，还需 `ENABLE_OAUTH_SIGNUP=true`。只有代理改变请求 URL 时，`WEBUI_URL` 才起作用
- **Microsoft：** `MICROSOFT_CLIENT_ID`、`MICROSOFT_CLIENT_SECRET`、`MICROSOFT_CLIENT_TENANT_ID`
- **Google：** `GOOGLE_CLIENT_ID`、`GOOGLE_CLIENT_SECRET`
- **OIDC：** `OAUTH_CLIENT_ID`、`OAUTH_CLIENT_SECRET`、`OPENID_PROVIDER_URL`

### 4. 持久化配置冲突 {#4-persistent-configuration-conflicts}

**重要：** Open WebUI 中有**两个**与 OAuth 相关的持久化设置：

1. **`ENABLE_PERSISTENT_CONFIG`**（默认 **`true`**）——控制*所有*设置（包括 OAuth）在写入数据库后，是否优先从数据库加载，而不是从环境变量读取。
2. **`ENABLE_OAUTH_PERSISTENT_CONFIG`**（默认 **`false`**）——这是针对 OAuth 设置的*额外*开关。当它为 `false` 时，即使 `ENABLE_PERSISTENT_CONFIG` 为 `true`，所有以 `oauth.` 开头的 OAuth 设置也**不会**从数据库加载。

默认情况下，因为 `ENABLE_OAUTH_PERSISTENT_CONFIG=false`，OAuth 环境变量**会优先于数据库值**。但如果你之前通过 Admin Panel 配过 OAuth，而后面又把 `ENABLE_OAUTH_PERSISTENT_CONFIG` 设为 `true`，那么数据库里的旧值就会重新接管。

#### 症状： {#symptoms}
- 修改环境变量后，重启仍然不生效
- 之前能登录，改了配置后突然失效
- 重新配置后出现 “No token found in localStorage”

**解决方法：**
1. **开发/测试环境：** 保持 `ENABLE_OAUTH_PERSISTENT_CONFIG=false`（默认就是如此），确保始终从环境变量读取
2. **生产环境：** 二选一：
   - 设置 `ENABLE_OAUTH_PERSISTENT_CONFIG=true`，并通过 Admin Panel 而不是环境变量来配置设置；或
   - 保持 `ENABLE_OAUTH_PERSISTENT_CONFIG=false`（默认），让环境变量在 OAuth 设置上优先生效
3. **彻底重来：** 删除数据库 volume，用正确配置重新启动

在它为 `false` 期间，Admin Panel 的 OAuth 区域是只读的，所以一次编辑不会看起来像是生效了，又在下次重启时消失。参见 [`ENABLE_OAUTH_PERSISTENT_CONFIG`](../reference/env-configuration.mdx#enable_oauth_persistent_config)。

📌 **Docker Compose 示例：**
```yaml
environment:
  - ENABLE_OAUTH_PERSISTENT_CONFIG=false  # Forces reading from env vars (this is the default)
  - OAUTH_CLIENT_ID=your_client_id
  - OAUTH_CLIENT_SECRET=your_secret
  - OPENID_PROVIDER_URL=your_provider_url
```

### 5. 提供商侧 OAuth 配置错误 {#5-oauth-misconfiguration-on-the-provider-side}

有时问题出在身份提供商（如 Google、Okta、Auth0、Azure AD）——它的应用注册与你的 WebUI 配置不一致。

**解决方法：**
- 确认你的应用已在 OAUTH 提供商端正确注册，并检查：
  - **Redirect URI 与真实部署地址完全一致**
    - OIDC: `https://your-domain/oauth/oidc/callback`
    - Microsoft: `https://your-domain/oauth/microsoft/callback`
    - Google: `https://your-domain/oauth/google/callback`
  - Client ID / secret 与环境中填写的值一致
  - Scopes 与允许的 grant types（例如 `authorization_code`）符合 Open WebUI 需求
- 查看提供商日志——很多应用注册错误会在那里给出明确原因

📌 **Redirect URI 格式示例：**
```
Correct: https://ai.company.com/oauth/oidc/callback
Wrong: https://ai.company.com/oauth/callback/oidc
Wrong: https://ai.company.com/callback
```

:::tip
如果不确定，就重新检查提供商应用注册，并在需要时重新生成 client secret。
:::

### 6. 服务端缓存问题 {#6-server-side-caching-issues}

如果你在使用 Nginx（或其他反向代理）时启用了服务端缓存，OAuth 端点可能会出现随机、间歇性的登录问题，而且通常很难排查。

**解决方法：**
- 在 NGINX（或其他代理）配置中：
  - 确认**不要缓存**以下端点：
    - `/api`、`/oauth`、`/callback`、`/login`、`/ws`、`/websocket`
  - 任何关键登录/认证端点都必须保持未缓存状态
- 修改后重新加载代理配置

**NGINX 示例：**
```nginx

# Disable caching for login / OAuth / websockets endpoints
location ~* ^/(api|oauth|callback|login|ws|websocket) {
    proxy_no_cache 1;
    proxy_cache_bypass 1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 3600s;
    proxy_send_timeout 3600s;
    proxy_set_header Accept-Encoding "";
}
```

:::warning
永远不要缓存 OAuth 或登录端点。缓存会导致旧 token 被重复返回，或破坏会话，最终引发难以预测的认证错误。
:::

### 7. Cookie 配置问题 {#7-cookie-configuration-issues}

**常见问题：** 反向代理里的 cookie 设置，尤其是 `HttpOnly` 与 `SameSite`，可能会干扰 OAuth 认证流程。

#### 症状： {#symptoms-1}
- “No token found in localStorage”
- 登录成功后却不断重定向循环
- 认证似乎成功了，但立刻又跳回登录页

**解决方法：**

#### 对于 NGINX Proxy Manager： {#for-nginx-proxy-manager}
```nginx

# Remove or adjust problematic cookie settings

# Problematic:

# proxy_cookie_path / "/; Secure; HttpOnly; SameSite=None";

# Better:
proxy_cookie_flags ~ secure samesite=lax;

# or remove cookie manipulation entirely
```

#### 环境变量中的 cookie 设置： {#environment-variable-cookie-settings}
```bash

# Recommended cookie settings for OAuth
WEBUI_SESSION_COOKIE_SAME_SITE=lax
WEBUI_AUTH_COOKIE_SAME_SITE=lax
WEBUI_SESSION_COOKIE_SECURE=true  # Set to false if using HTTP
WEBUI_AUTH_COOKIE_SECURE=true     # Set to false if using HTTP
```

### 8. 网络超时问题 {#8-network-timeout-issues}

OAuth 提供商有时响应较慢，导致认证握手阶段超时。请提高 [`OAUTH_TIMEOUT`](/reference/env-configuration#oauth_timeout) 以给它们更长的时间。

#### 症状： {#symptoms-2}
- 日志中出现 `httpcore.ReadTimeout`
- 出现 `CSRF Warning! State not equal in request and response`
- OAuth 登录偶发性失败

**解决方法：**
```bash

# Increase the OAuth handshake timeout (seconds). AIOHTTP_CLIENT_TIMEOUT does not
# affect the OAuth client, which is httpx-based.
OAUTH_TIMEOUT=60
```

### 9. Session State 不匹配（CSRF 错误） {#9-session-state-mismatch-csrf-errors}

OAuth 重定向过程中，如果 session cookie 没有被正确保留，就会出现这类错误。

#### 症状： {#symptoms-3}
- `CSRF Warning! State not equal in request and response`
- 日志中出现 `mismatching_state`
- 认证看似成功，但最后又跳回登录页

**解决方法：**

1. **检查 Cookie 域名配置：**
```bash

# Ensure cookies are set for the correct domain
WEBUI_URL=https://your-exact-domain.com  # Must match exactly - check if you have a different value set in the admin panel
```

2. **检查 Session 配置：**
```bash

# Ensure session handling is properly configured
WEBUI_SECRET_KEY=your_very_secure_random_key_here
OAUTH_SESSION_TOKEN_ENCRYPTION_KEY=another_secure_key_here
```

### 10. 负载均衡器与多实例问题 {#10-load-balancer-and-multi-instance-issues}

在多实例部署中，如果 OAuth 会话没有正确同步，就会失败。

#### 集群部署所需配置： {#required-configuration-for-clusters}
```bash

# Redis for session synchronization (required for multi-instance)
REDIS_URL=redis://your-redis:6379/0
WEBSOCKET_REDIS_URL=redis://your-redis:6379/0

# Shared secrets across all instances
WEBUI_SECRET_KEY=same_on_all_instances
OAUTH_SESSION_TOKEN_ENCRYPTION_KEY=same_on_all_instances

# WebSocket support for clusters
ENABLE_WEBSOCKET_SUPPORT=true
WEBSOCKET_MANAGER=redis
```

### 11. 提供商特定配置问题 {#11-provider-specific-configuration-issues}

#### Microsoft Entra ID 常见问题： {#microsoft-entra-id-common-issues}

**问题：** 错把通用 OIDC 变量当成 Microsoft 专属配置使用。

✅ **正确的 Microsoft 配置：**
```bash

# Use Microsoft-specific variables, not generic OIDC
MICROSOFT_CLIENT_ID=your_azure_app_id
MICROSOFT_CLIENT_SECRET=your_azure_app_secret
MICROSOFT_CLIENT_TENANT_ID=your_tenant_id
MICROSOFT_OAUTH_SCOPE=openid email profile
MICROSOFT_REDIRECT_URI=https://your-domain/oauth/microsoft/callback

# Needed only for SSO to create accounts that do not exist yet. OPENID_PROVIDER_URL is
# not required for Microsoft: login and sign-out use the tenant's own discovery URL.
ENABLE_OAUTH_SIGNUP=true
```

#### Authentik 常见问题： {#authentik-common-issues}

**问题：** provider URL 格式错误。

✅ **正确的 Authentik 配置：**
```bash
OAUTH_CLIENT_ID=your_authentik_client_id
OAUTH_CLIENT_SECRET=your_authentik_client_secret
OPENID_PROVIDER_URL=https://your-authentik-domain/application/o/your-app-slug/.well-known/openid-configuration
OAUTH_PROVIDER_NAME=Authentik
OAUTH_SCOPES=openid email profile
```

#### 在 ID 令牌中添加自有参数的提供商： {#providers-that-add-their-own-parameters-to-the-id-token}

**问题：** 登录在回调阶段失败。浏览器显示 `The email or password provided is incorrect`，而日志记录了真正的原因：

```
OAuth callback failed: Unsupported {'app_id'} in header
```

某些提供商会在 ID 令牌头部添加厂商特有的参数，旧版本会拒绝它们。参数名称因提供商而异。

**解决方案：** 更新 Open WebUI。无法识别的参数会被忽略，因此提供商一侧无需改动。签名和签名算法仍会照常校验。

### 12. 长时间未升级后已有账户无法登录 {#12-existing-accounts-cannot-sign-in-after-a-long-delayed-upgrade}

**问题：** 把一个停留在 v0.6.41 之前旧版本的实例升级之后，所有曾通过 SSO 登录过的账户都无法再登录，这些账户的密码登录也会失败。从未使用过 SSO 的账户不受影响。日志记录如下：

```
ERROR - Error during OAuth process: 1 validation error for UserModel
oauth
  Input should be a valid dictionary [type=dict_type, input_value='{"oidc": {"sub": "..."}}', input_type=str]
```

把账户的身份提供商 subject 迁移到当前字段的升级步骤把该值编码了两次，因此它保存的是 JSON 对象的文本而不是对象本身。只有在升级那一刻仍早于 v0.6.41 的数据库会受影响，而且只影响当时已存储 subject 的账户。

**解决方案：** 更新 Open WebUI。启动时会运行一个修复迁移，重写受影响的行，其他行一律不动。不需要手工操作数据库，不需要重新绑定，也不需要在提供商一侧做任何改动。`OAUTH_MERGE_ACCOUNTS_BY_EMAIL` 无法绕过这个问题，因为回退查找读取的是同一个账户，同样会失败。

## 高级排查建议 {#advanced-troubleshooting-tips}

### 检查 token 存储方式 {#check-token-storage-method}

较新的 Open WebUI 已从基于 URL 的 token 方案迁移到基于 cookie 的方案。如果你遇到认证问题：

1. **彻底清空浏览器 cookies 和缓存**
2. **打开浏览器开发者工具检查：**
   - 是否存在 `oauth_session_id` cookie（新方式）
   - 是否还残留 `oauth_id_token` cookie（旧方式）
   - cookie 的 domain 与 path 是否正确

### 调试 OAuth 流程 {#debugging-oauth-flow}

开启 debug 日志，并逐步跟踪 OAuth 流程：

```bash

# Enable detailed logging
GLOBAL_LOG_LEVEL=DEBUG

# Check logs for these key steps:

# 1. GET /oauth/{provider}/login - Should return 302 redirect

# 2. User authenticates with provider

# 3. GET /oauth/{provider}/callback?code=... - Should return 200 or redirect

# 4. User should be logged in
```

### 数据库调试 {#database-debugging}

检查用户账号是否真的被创建：

```bash

# Access your container
docker exec -it your-openwebui-container sh

# Check if users are created (adjust path to your data directory)
ls -la /app/backend/data/
```

### 不经过反向代理直接测试 {#test-without-reverse-proxy}

如果你使用了反向代理，请临时绕过它，直接针对 Open WebUI 测试 OAuth：

1. 临时直接暴露 Open WebUI 端口
2. 把 OAuth 提供商中的 redirect URI 改成这个直连地址
3. 测试认证流程
4. 如果此时可用，问题就出在你的代理配置上

## 小提示：先看日志 {#pro-tip-check-the-logs}

- 先看后端日志和浏览器网络错误。第一条错误通常就最接近根因。
- 如果你不确定到底是哪一侧有问题，可以用浏览器隐私窗口重新登录，并观察哪些请求被拦截或失败。

### 需要重点关注的日志信息： {#key-log-messages-to-watch-for}
- `OAuth callback error: mismatching_state` → Session/cookie 问题
- `httpcore.ReadTimeout` → 网络超时问题
- `Sign-in with your identity provider failed. Please contact your administrator for assistance.` → 登录在回调阶段失败，例如提供商拒绝访问、账户没有邮箱，或邮箱域不被允许。这些情况显示相同的文本，因此应查看后端日志确定真正原因。角色不匹配或禁止注册时会显示禁止访问的文本，邮箱重复时会显示已经注册的错误，其他异常则显示 `Error during OAuth process`
- `Unsupported {'app_id'} in header` → 提供商在 ID 令牌中添加了厂商特有的参数，而当前版本仍会拒绝它。参见[在 ID 令牌中添加自有参数的提供商](#providers-that-add-their-own-parameters-to-the-id-token)
- `1 validation error for UserModel`，发生在 `oauth` 字段 → 旧的升级步骤把身份提供商 subject 存成了文本。参见[长时间未升级后已有账户无法登录](#12-existing-accounts-cannot-sign-in-after-a-long-delayed-upgrade)
- 回调 URL 返回 `404` → Redirect URI 配置错误

## 总结清单 ✅ {#summary-checklist}

| 问题 | 修复方式 |
|-------------------------------|------------------------------------------------------------|
| 🔗 WebUI URL 缺失或错误 | 在 admin panel 中设置正确的 WebUI URL |
| 📝 环境变量拼写错误或缺失 | 对照官方文档逐项检查；不要使用 `OIDC_CONFIG` 这类不存在的变量 |
| 🚨 缺少 OPENID_PROVIDER_URL | OIDC 必需项，指向提供商的 `.well-known/openid-configuration` |
| 🔄 持久化配置冲突 | 设 `ENABLE_OAUTH_PERSISTENT_CONFIG=false` 以使用环境变量，或设为 `true` 以使用管理面板；为 `false` 时面板只读 |
| 🏢 提供商侧配置错误 | 核对应用注册、URI、client ID 与 secret |
| 🧊 代理缓存干扰 | 把所有 OAuth 端点排除在服务端缓存之外 |
| 🍪 Cookie 配置问题 | 检查反向代理 cookie 设置与相关 env vars |
| ⏱️ 超时问题 | 提高 `AIOHTTP_CLIENT_TIMEOUT` 等超时设置 |
| 🔐 CSRF / session 问题 | 检查 `WEBUI_SECRET_KEY` 与会话配置 |
| 🔀 多实例问题 | 配置 Redis 与共享密钥 |
| 长时间未升级后，SSO 账户在升级后立即无法登录 | 更新 Open WebUI；启动时的修复迁移会修复存储的身份数据 |
| 仍未解决？ | 开启 debug 日志、绕过代理测试、复查 provider 配置 |

---

只要同时把 OAuth 提供商和 Open WebUI 环境配置正确，并确保关键登录端点不被缓存，绝大多数 SSO/OAuth 登录问题都能被消除。

---

:::warning 退出单个会话需要 Redis
如果没有 Redis，**退出登录并不会撤销 JWT token**——它们会一直有效直到过期（默认：4 周）。对 SSO/OAuth 部署来说，这一点尤其重要，因为你可能需要在用户离职等场景下快速撤销访问权限，而 OIDC 后通道注销也需要 Redis 才能撤销令牌。没有 Redis 时，管理员仍可在用户编辑对话框中使用 **退出所有设备** 来结束该账户的全部会话。

对于生产环境中的 SSO 部署，请配置 Redis，或缩短 `JWT_EXPIRES_IN` 来降低暴露窗口。更多信息请参阅 [Token 撤销](/getting-started/advanced-topics/hardening#token-revocation) 和 [Redis 教程](/tutorials/integrations/redis)。
:::
