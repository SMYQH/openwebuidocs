## 🔐 HTTPS、TLS、CORS 与 WebSocket 问题 {#https-tls-cors--websocket-issues}

如果你在使用反向代理或 HTTPS 时遇到 Open WebUI 连接异常，问题通常与 CORS、TLS、WebSocket 或 cookie 配置不正确有关。下面是推荐的排查方式。

### 常见症状 {#common-symptoms}

如果你看到以下现象，很可能就是这一类问题：
- 聊天中返回空响应，例如 `"{}"`
- 出现类似 `"Unexpected token 'd', "data: {"id"... is not valid JSON"` 的错误
- 出现类似 `Unexpected token '<', "<!DOCTYPE "... is not valid JSON` 的错误，参见 [`Unexpected token '<'`](#unexpected-token--doctype--is-not-valid-json)
- 流式输出时 Markdown 显示混乱（例如可见的 `##`、`**`、格式断裂）——参见 [流式响应损坏](#garbled-markdown--streaming-response-corruption)
- 浏览器控制台出现 WebSocket 连接失败
- CLI 日志中出现 WebSocket 连接失败
- 登录异常或会话问题
- 浏览器开发者工具中出现 CORS 错误
- 通过 HTTPS 访问时出现 mixed content 警告

### HTTPS 与反向代理所需配置 {#required-configuration-for-https--reverse-proxies}

**关键环境变量**

当你把 Open WebUI 放在启用了 HTTPS 的反向代理后面时，必须正确配置这些设置：

```bash
# Set this to your actual domain BEFORE FIRST STARTUP (required for OAuth/SSO and proper operation)
WEBUI_URL=https://your-open-webui-domain.com
# If you already started Open WebUI, don't worry, you can set this config from the admin panel as well!

# CORS configuration - CRITICAL for WebSocket functionality
# Include ALL ways users might access your instance
# Make sure to include all IPs, hostnames and domains users can and could access Open WebUI and how requests are going to your Open WebUI instance
# e.g. localhost, 127.0.0.1, 0.0.0.0, <ip of your server/computer>, public domain - all in http and https with the correct ports
CORS_ALLOW_ORIGIN="https://yourdomain.com;http://yourdomain.com;https://yourip;http://localhost:3000"

# Cookie security settings for HTTPS
# Disable if you do not use HTTPS
WEBUI_SESSION_COOKIE_SECURE=true
WEBUI_AUTH_COOKIE_SECURE=true

# For OAuth/SSO, you will probably have to use 'lax' (strict can break OAuth callbacks)
WEBUI_SESSION_COOKIE_SAME_SITE=lax
WEBUI_AUTH_COOKIE_SAME_SITE=lax

# Live connection. Set it to false only if your reverse proxy cannot pass WebSocket upgrades:
# browsers then use HTTP long-polling, which needs sticky sessions when you run several replicas
ENABLE_WEBSOCKET_SUPPORT=true

# Only with several replicas
WEBSOCKET_MANAGER=redis
WEBSOCKET_REDIS_URL=redis://redis:6379/1
```

**WEBUI_URL 配置说明**

在使用 OAuth/SSO 之前，必须先正确设置 `WEBUI_URL`。由于它是持久化配置变量，只能通过以下方式修改：
- 临时设置 `ENABLE_PERSISTENT_CONFIG=false`
- 在设置 > 常规 > WebUI URL（管理员区域）中修改
- 在首次启动前就正确设置

**CORS 配置说明**

`CORS_ALLOW_ORIGIN` 对 WebSocket 尤其关键。如果日志中出现 `"https://yourdomain.com is not an accepted origin"` 或 `"http://127.0.0.1:3000 is not an accepted origin"`，就说明该 URL 需要加入配置。多个来源使用分号分隔，并且要覆盖用户访问实例的每一种方式（域名、IP、localhost 等）。

### WebSocket 故障排查 {#websocket-troubleshooting}

如果 WebSocket 不能正常工作：

1. **检查反向代理配置**——确认 `Upgrade` 和 `Connection` 头已正确设置
2. **确认 CORS 设置**——WebSocket 连接同样遵守 CORS 策略
3. **查看浏览器控制台**——检查具体的 WebSocket 连接错误
4. **测试直连**——尝试绕过代理直接连接 Open WebUI，以隔离问题来源
5. **检查 HTTP/2 与 WebSocket 的兼容问题**——某些代理（如 HAProxy 3.x）默认启用 HTTP/2。如果代理使用 HTTP/2 连接客户端，而后端/应用没有正确支持 RFC 8441（WebSockets over H2），实例可能会“卡住”或不响应。
   - **HAProxy 修复方式**：在配置中加入 `option h2-workaround-bogus-websocket-clients`，或强制后端连接使用 HTTP/1.1。
   - **Nginx 修复方式**：确认 location 块中使用了 `proxy_http_version 1.1;`（Open WebUI 的许多示例默认采用此设置）。

多实例部署中，请如上文所示设置 `WEBSOCKET_MANAGER=redis`。关于 Redis 配置细节，请参阅 [Redis WebSocket Support](/tutorials/integrations/redis)。完整的多实例扩缩容实践请参阅 [Scaling Open WebUI](/getting-started/advanced-topics/scaling)。如果你在多副本场景中遇到特定的 WebSocket 403 错误，请参见 [扩缩容与高可用故障排查](/troubleshooting/multi-replica#2-websocket-403-errors--connection-failures)。

### 在一个浏览器中可用、另一个浏览器中不可用 {#works-in-one-browser-but-not-another}

在默认的 `ENABLE_WEBSOCKET_SUPPORT=true` 下，浏览器只能通过 `/ws/socket.io` 上的 WebSocket 连接 Open WebUI，没有 HTTP 长轮询回退。Open WebUI 通过该连接把聊天回复和状态更新发送到浏览器。屏蔽 WebSocket 的浏览器可能在聊天时失败，而同一服务器上的其他浏览器却能正常工作。每次失败的尝试都会在该浏览器的控制台记录 `connect_error`。

在修改服务器或代理之前：

1. 在故障浏览器的隐私窗口中打开 Open WebUI。
2. 在另一个浏览器中打开它。
3. 如果其中一个能正常聊天，说明服务器没问题。请在故障浏览器中，为你的 Open WebUI 地址关闭隐私防护、广告或追踪拦截器以及严格追踪保护。然后清除该地址的站点数据并重新登录。
4. 如果所有浏览器都无法聊天，请按上文的 WebSocket 检查步骤排查。

### 测试你的配置 {#testing-your-configuration}

要验证配置是否正常：

1. **检查 HTTPS**：访问你的域名，确认浏览器能识别有效证书且没有警告
2. **测试 WebSocket**：打开浏览器开发者工具，进入 Network 标签，筛选 `WS`，确认 WebSocket 连接建立成功
3. **验证 CORS**：检查控制台是否还有 CORS 相关错误
4. **测试功能**：发送一条消息，确认流式输出正常工作

### 快速修复清单 {#quick-fixes-checklist}

- ✓ 在启用 OAuth 前把 `WEBUI_URL` 设为真实 HTTPS 域名
- ✓ 在 `CORS_ALLOW_ORIGIN` 中配置所有可能的访问 URL
- ✓ 在 HTTPS 下启用 `WEBUI_SESSION_COOKIE_SECURE=true`
- ✓ 在反向代理中加入 WebSocket 所需头
- ✓ 在 SSL 配置中使用 TLSv1.2 或 TLSv1.3
- ✓ 正确设置反向代理中的 `X-Forwarded-Proto`
- ✓ 配置 HTTP 到 HTTPS 重定向
- ✓ 配置 Let's Encrypt 自动续签
- ✓ 对 SSE 流式输出关闭 proxy buffering（见下文）

## 📝 Markdown 乱码 / 流式响应损坏 {#garbled-markdown--streaming-response-corruption}

如果流式响应时出现 Markdown 渲染错乱（例如可见 `##`、`**` 或格式断裂），但关闭流式输出后又恢复正常，这通常是 **nginx proxy buffering** 导致的。

### 常见症状 {#common-symptoms-1}

- 响应中直接显示原始 Markdown token（`##`、`**`、`###`）
- 粗体标记位置异常（例如 `** Control:**` 而不是 `**Control:**`）
- 响应中随机缺词或缺段落
- 关闭流式输出后格式恢复正常

### 原因：Nginx 代理缓冲 {#cause-nginx-proxy-buffering}

启用 nginx 的 proxy buffering 后，SSE（Server-Sent Events）流会被任意重新分块。这样会把 Markdown token 从中间切开——例如 `**bold**` 被拆成 `**` + `bold` + `**`，导致 Markdown 解析失败。

### 解决方案：关闭代理缓冲 {#solution-disable-proxy-buffering}

在 Open WebUI 的 nginx location 块中加入以下配置：

```nginx
location / {
    proxy_pass http://your-open-webui-upstream;
    
    # CRITICAL: Disable buffering for SSE streaming
    proxy_buffering off;
    proxy_cache off;
    
    # WebSocket support
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    
    # Standard proxy headers
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

:::tip
关闭代理缓冲通常也会**明显提升流式速度**，因为响应会逐字节直接发送给客户端，而不是被 nginx 延迟缓冲。
:::

### 其他反向代理 {#for-other-reverse-proxies}

- **HAProxy**：确保 SSE 端点未启用 `option http-buffer-request`
- **Traefik**：检查压缩/缓冲中间件设置
- **Caddy**：默认就能正确处理 SSE，但请检查是否装有缓冲插件

## 当模型使用工具时回复为空白 {#blank-replies-when-the-model-uses-a-tool}

### 常见症状 {#common-symptoms-2}

- 助手消息返回时**完全为空**，界面上没有任何错误，日志中在任何日志级别下也没有任何内容。
- 看起来**毫无规律**：大多数轮次都正常，同一个提示词有时成功、有时不成功。
- 服务商仍会为这个空轮次的输出 token 向你计费。
- 存储的消息中 `content: ''` 且 `output: []`，而 `usage.completion_tokens` 不为零。
- 启用工具之后情况会明显恶化，使用内置工具时尤其如此，因为模型会自行调用它们。

### 原因：服务商在流式工具调用中省略了 `index` {#cause-the-provider-omits-index-on-streamed-tool-calls}

OpenAI 的流式 schema 在每个工具调用增量上都有一个 `index` 字段，正是它让客户端能够跨数据块把一次调用的各片段拼接起来。Open WebUI 的累加器正是以该字段为键。若服务商在单个数据块中就完整发送每次工具调用、却省略了 `index`，那它就不符合 schema，这次调用会被丢弃。该轮次于是既没有文本也没有工具运行，也就是你所看到的空消息。

这并非某一家厂商的问题。任何在流式工具调用中不带 `index` 的兼容 OpenAI 端点都会受影响。**Google 在 `https://generativelanguage.googleapis.com/v1beta/openai` 的 OpenAI 兼容层是已知的案例**，而 Gemini 3 模型还额外带来了第二个问题：Google 要求在后续请求中回传一个专有的 `thought_signature`，而任何符合 OpenAI schema 的客户端都不会这样做。

### 用一条命令确认 {#confirm-it-in-one-command}

直接向端点发起请求并查看工具调用的数据块。把你自己的 URL、密钥和模型替换进去：


在 `delta.tool_calls` 条目中查找 `"index"`。如果它不存在，你就遇到了这个问题。外层 `choices` 条目上的 `index` 是另一个字段，不算数。

```bash
curl -s -N -X POST "https://your-provider.example/v1/chat/completions" -H "Authorization: Bearer $API_KEY" -H "Content-Type: application/json" -d '{"model":"your-model","stream":true,"messages":[{"role":"user","content":"What is the weather in Paris?"}],"tools":[{"type":"function","function":{"name":"get_weather","parameters":{"type":"object","properties":{"city":{"type":"string"}},"required":["city"]}}}]}'
```
### 解决方案 {#solutions}

1. **在前面加一层网关。** LiteLLM、OpenRouter 或任何与服务商原生 API 通信、同时输出符合 schema 的 OpenAI 结果的代理。这是唯一能既保留原生工具调用、又让内置工具继续工作的方案。
2. **把模型切换到 Legacy 函数调用。** 在模型的 **高级参数** 中把 **函数调用** 设为 **Legacy**。此后工具改由一次独立的非流式请求来选择，不会再经过流式累加器。不设置该值即为原生模式。代价是旧版模式下无法使用内置工具（记忆等），因为它们只为原生函数调用注入。
3. **为该模型关闭工具。** 如果你只需要普通对话，请在模型上关闭 **内置工具** 能力，使其永远不尝试调用任何东西。聊天补全本身不受此缺陷影响。
4. **使用管道。** 直接调用服务商原生 API 的[管道函数](/features/extensibility/plugin/functions/pipe)可以完全绕开兼容 OpenAI 的这条路径。

Open WebUI 遵循 OpenAI Chat Completions schema，不会为偏离该 schema 的端点添加按厂商定制的变通方案，这背后的理由与[面向协议的设计](/getting-started/quick-start/connect-a-provider/starting-with-openai-compatible#protocol-oriented-design)一节所述相同。

## 前端连接与后端连接（localhost 混淆） {#frontend-vs-backend-connections-localhost-confusion}

Open WebUI 的一些功能提供**两种连接配置方式**：**管理员／全局**连接（由 Open WebUI 后端发起）和 [Tether](/ecosystem/tether#bring-your-own-models-and-tools) 连接（由用户自己的电脑发起）。两者的网络环境完全不同，因此同一个 URL 在一种方式下可能可用，在另一种方式下却会失败。

### 核心规则 {#the-core-rule}

| 请求来源 | `localhost` 的含义 | 谁在使用 |
| :--- | :--- | :--- |
| **后端（服务端）** | 运行 Open WebUI 的机器/容器 | 全局工具服务器、管理员配置的终端、Ollama 连接 |
| **Tether（你的电脑）** | 运行 Tether 应用的电脑 | 在 Tether 中添加的连接 |

### 为什么同一个 URL 可能一边可用、一边失败 {#why-the-same-url-can-work-and-fail}

在 Tether 中添加 `https://myserver.com/api` 这样的 URL 时，你的电脑会解析 `myserver.com` 并直接连接。如果将同一 URL 添加为**管理员／全局**连接，则由 Open WebUI 后端解析此主机名。在 Docker 容器内，该主机名可能解析为 `127.0.0.1`，完全绕过反向代理。

**常见症状：**
- Tether 连接正常，但管理员配置的连接报 502 Bad Gateway
- 后端日志中出现 `Connect call failed ('127.0.0.1', ...)`
- 全局工具服务器连接超时

**修复方式：** 对于后端/管理员连接，请使用**后端实际可达的内部 URL**：
- Docker 服务名称（例如 `http://open-terminal:8000`）
- `host.docker.internal`（从 Docker 内部访问宿主机）
- 内网 IP（例如 `http://192.168.1.50:8000`）

:::tip
这适用于 Open WebUI 中**所有经后端代理的连接**，包括 Open Terminal。[工具服务器连接](/features/extensibility/plugin/tools/openapi-servers/open-webui#1-tool-servers-added-by-an-admin)、[Open Terminal 管理员连接](/features/open-terminal#enterprise-multi-user)和 Ollama/OpenAI API 端点均遵循同样的规律。
:::

## "Open WebUI backend required" / 纯前端错误 {#open-webui-backend-required--front-end-only-error}

**症状：** 页面加载时显示 *"Open WebUI backend required. Oops! You're using an unsupported method (frontend only). Please serve the WebUI from the backend."* 这通常出现在**第二个实例**、反向代理之后或通过 **SSH 隧道**访问时，而另一个实例正常工作。

**实际含义：** 页面加载时，前端从其自身源获取 `/api/config`。如果该请求失败，Open WebUI 会显示此错误。这**不**意味着你运行的是纯前端构建。官方镜像是一个同时提供 UI 和 API 的单一进程，监听容器端口 **`8080`**，因此如果页面到达了你，API 应该也在那里。此错误意味着对该源的 `/api/config` 请求未能到达后端。

两个原因几乎涵盖了所有情况：

1. **端口映射或隧道不匹配。** 你打开的源提供了页面，但未将 `/api/config` 路由到后端。请检查：
   - 每个容器将其主机端口映射到容器端口 **`8080`**，例如 `ports: ["3001:8080"]`。映射到其他内部端口会破坏 API，同时仍可能提供缓存的静态资源。
   - 你的 SSH 隧道将本地端口转发到**该实例实际发布的主机端口**。运行多个实例时容易转发到错误的端口。
   - 从浏览器机器通过隧道快速测试：`curl http://localhost:3001/api/config`。返回 JSON 表示后端可达，则查看原因 2。空回复或连接拒绝表示隧道或端口映射有问题。

2. **过期的 Service Worker 提供缓存的页面。** Open WebUI 自身不注册 Service Worker，并会在加载时注销它发现的任何 Service Worker，因此出现陈旧的外壳只能来自浏览器的 HTTP 缓存，或来自同一源上另一个应用留下的 worker——此时实时的 `/api/config` 调用失败，就会产生这个确切的错误。普通的强制刷新并不会注销 Service Worker。请在 **DevTools > Application > Service Workers > Unregister** 中为该源清除它，或用全新的隐私 / 无痕窗口打开该实例。

这是部署和网络条件问题，而非 Open WebUI 的错误。

## `Unexpected token '<', "<!DOCTYPE "... is not valid JSON` {#unexpected-token--doctype--is-not-valid-json}

**症状：** 错误提示条或浏览器控制台显示 `SyntaxError: Unexpected token '<', "<!DOCTYPE "... is not valid JSON`。当失败的请求是模型列表时，控制台的那一行以 `Failed to load models:` 开头。

**实际含义：** 浏览器向某个 Open WebUI API 路径请求 JSON，却拿回了一个 HTML 页面。这个错误不是来自模型或服务商。有两处会返回 HTML：

1. **Open WebUI 自身。** 对任何没有对应路由的路径，Open WebUI 会用自己的网页 `index.html` 和状态码 `200` 回应 `GET` 请求。添加或剥离路径前缀的反向代理会把 API 调用送到并不存在的路径，于是它们返回的是那个网页。这通常是把 Open WebUI 放在子路径下的结果，而子路径[不受支持](/faq#q-can-i-serve-open-webui-under-a-subpath-such-as-examplecomopenwebui)。
2. **Open WebUI 前面的某个组件。** 请求根本没有到达它，而是由代理、登录网关或同一域名下的其他站点用自己的页面作答，例如请求过大或耗时过长时返回的错误页。

要区分两者，请打开 **DevTools > Network**，选中失败的请求并查看其响应。Open WebUI 自己的页面标题是 `Open WebUI`。其他任何页面都会标出作出应答的代理或站点。然后按 [HTTPS 与反向代理](/reference/https) 中的说明，让 Open WebUI 从自己主机名的根路径提供服务，并把每个路径原样转发给它。

## 重新加载后长聊天中的编辑与评分丢失 {#edits-and-ratings-lost-after-reload-in-long-chats}

**症状：** 在长聊天中，编辑过的消息、评分或用**另存为副本**创建的副本在屏幕上可见，但重新加载页面后就消失了。没有出现错误。同一个聊天中的新消息和回复仍能保存，较短的聊天也能保留所有改动。

**实际含义：** Open WebUI 前面的反向代理因为请求超过了它的请求体大小上限而拒绝保存。用**保存**、**另存为副本**、评分和**合并回复**保存编辑时，都会把整个聊天一次性 `POST` 到 `/api/v1/chats/{id}`：每个分支中的每条消息，加上屏幕上那个分支的消息。该请求会随着聊天增长而变大。新消息不走这条路径，因为 Open WebUI 在回复开始时就把每一轮存到服务器上，所以聊天超过上限后它们仍能保存。

要确认这一点，请打开 **DevTools > Network**，重新做一次该改动，并选中发往 `/api/v1/chats/<id>` 的 `POST` 请求。状态码 `413` 表示代理拒绝了它。

要修复，请提高代理的请求体大小上限。在 nginx 中这是 [`client_max_body_size`](https://nginx.org/en/docs/http/ngx_http_core_module.html#client_max_body_size)，默认值为 `1m`；`0` 表示关闭该检查。参见[请求头和请求体大小限制](/reference/https/nginx#header-and-body-size-limits)，其他代理参见[关键配置注意事项](/reference/https#key-configuration-notes)。重新加载后，被代理拒绝过的改动就丢失了，因此请重新做一遍。

## 连接 Ollama 服务器 {#connection-to-ollama-server}

### 让 Open WebUI 访问 Ollama {#accessing-ollama-from-open-webui}

如果 Open WebUI 无法访问 Ollama，通常是因为 Ollama 只监听了 `127.0.0.1`（localhost）。请按下面修复：

1. **设置 `OLLAMA_HOST=0.0.0.0`**，让 Ollama 监听所有网络接口
2. **确认该变量已在你的部署环境中生效**（systemd、Docker、shell profile 等）
3. **重启 Ollama** 使变更生效

重启后再打开 WebUI 验证连通性。更详细说明见 [Ollama 文档](https://github.com/ollama/ollama/blob/main/docs/faq.mdx#setting-environment-variables-on-linux)。

**确认变更是否生效。** Ollama 默认绑定 `127.0.0.1` 的 `11434` 端口（[Ollama FAQ](https://github.com/ollama/ollama/blob/main/docs/faq.mdx#how-can-i-expose-ollama-on-my-network)）。在运行 Ollama 的机器上，查看 `11434` 端口监听在哪个地址上。在 Linux 上：

```bash
ss -tlnp | grep 11434
```

在 Windows 上：

```powershell
netstat -an | findstr 11434
```

输出中的 `127.0.0.1:11434` 表示 Ollama 仍只监听环回地址，新的 `OLLAMA_HOST` 没有生效。`0.0.0.0:11434`、`*:11434` 或 `[::]:11434` 表示它监听所有接口。如果设置没有生效，请把你的步骤与 [Ollama FAQ](https://github.com/ollama/ollama/blob/main/docs/faq.mdx#how-do-i-configure-ollama-server) 对照：

- **使用 systemd 的 Linux：** 运行 `systemctl edit ollama.service`，在 `[Service]` 下另起一行写入 `Environment="OLLAMA_HOST=0.0.0.0:11434"`。然后运行 `systemctl daemon-reload` 和 `systemctl restart ollama`。缺少 `[Service]` 行、跳过 `daemon-reload` 或跳过重启，是地址仍停留在 `127.0.0.1` 的常见原因。
- **Windows：** 从任务栏退出 Ollama，在用户环境变量中设置 `OLLAMA_HOST`，然后从开始菜单重新启动 Ollama。
- **macOS 应用：** 运行 `launchctl setenv OLLAMA_HOST "0.0.0.0:11434"`，然后重启 Ollama 应用。

:::warning 不要把 11434 端口暴露到你的网络
Open WebUI 是从其后端调用 Ollama，绝不从浏览器调用，因此用户的浏览器不需要访问 `11434` 端口。Ollama 的本地 API 不需要认证（[Ollama API 文档](https://github.com/ollama/ollama/blob/main/docs/api/authentication.mdx)），因此在 `OLLAMA_HOST=0.0.0.0` 时，任何能在 `11434` 端口访问该主机的设备都能使用它。请在主机防火墙上对除 Open WebUI 主机之外的所有来源屏蔽 `11434` 端口，或者让 Ollama 与 Open WebUI 位于同一个 Docker 网络中且不发布其端口。仓库中的 [`docker-compose.yaml`](https://github.com/open-webui/open-webui/blob/main/docker-compose.yaml) 采用了后一种做法：`ollama` 服务没有 `ports` 条目，Open WebUI 通过 `OLLAMA_BASE_URL=http://ollama:11434` 访问它。
:::

### Docker 中的连接错误 {#docker-connection-error}

如果 Docker 中的 Open WebUI 无法连接宿主机上的 Ollama：

在 Docker 命令中使用 `--network=host` 标志。这会让容器直接连接到宿主机的网络。

**示例 Docker 命令：**
```bash
docker run -d --network=host -v open-webui:/app/backend/data -e OLLAMA_BASE_URL=http://127.0.0.1:11434 --name open-webui --restart always ghcr.io/open-webui/open-webui:main
```
运行后，WebUI 应可通过 `http://localhost:8080` 访问。

使用 `--network=host` 时：

- Docker 会忽略 `-p` 和 `--publish`，并打印 `WARNING: Published ports are discarded when using host network mode.`（[Docker 文档](https://docs.docker.com/engine/network/drivers/host/)）。Open WebUI 监听 `PORT` 中的端口，默认为 `8080`。加上 `-e PORT=3000` 可以改到别的端口。
- 在 Docker Desktop 上，主机网络仅从 4.34 版本开始可用，并且需要先开启 **Settings > Resources > Network > Enable host networking**。否则容器会共用 Docker Desktop 的 Linux 虚拟机网络，你的浏览器无法连接，如[网络示意图](/reference/network-diagrams)所示。请改用 `-p 3000:8080` 发布端口，并使用 `OLLAMA_BASE_URL=http://host.docker.internal:11434`。
- 其他机器会直接访问主机上的该端口访问 Open WebUI，因此主机防火墙必须放行。

### 模型缺失或与 `ollama list` 不一致 {#models-missing-or-different-from-ollama-list}

Open WebUI 只列出**管理面板 > 设置 > 连接**中的 Ollama URL 所返回的模型。它会向每个启用的 URL 请求 `/api/tags` 并合并结果。没有响应的 URL 不会增加任何模型，并记录 `Connection error:`。当列表与 `ollama list` 不一致时，通常是 Open WebUI 与你的终端连到了不同的 Ollama 服务器或不同的模型存储：

- **两套 Ollama 安装**，例如原生安装加一个 Ollama 容器，或一个在 WSL 中、另一个在 Windows 上。它们各自拥有自己的模型。请在 URL 指向的那套安装中运行 `ollama list`，例如对名为 `ollama` 的容器运行 `docker exec ollama ollama list`。
- **Docker 卷被改名或缺失。** Ollama 把模型保存在挂载到 `/root/.ollama` 的卷中。以不同卷名启动的容器会以空的模型列表开始。
- **内置的 `:ollama` 镜像没有带 `-v ollama:/root/.ollama` 运行。** 拉取到其中的模型在容器重建后就会消失。

要发现那个过时的第二台服务器，请打开**设置 > 关于**。**Ollama 版本**显示所有启用的 Ollama 连接所报告的最低版本。比你安装的版本更旧，说明已配置的某个 URL 指向了另一台 Ollama 服务器。

### `does not support tools` {#ollama-does-not-support-tools}

如果每个使用 Ollama 模型的聊天都因 `registry.ollama.ai/library/<model> does not support tools` 而失败，说明 Ollama 拒绝了请求中的工具定义。在默认的原生模式下开启**函数调用**，并且默认开启模型的**内置工具**能力时，Open WebUI 会把它自己的内置工具加入聊天界面发出的每个请求。即使你没有在聊天中启用任何工具，请求里也会带上工具。

**解决方案：**

1. **把模型设为旧版模式。** 在**设置 > 模型**（管理员区域）中该模型的**高级参数**里，把**函数调用**设为**旧版**。旧版模式下不会发送内置工具。
2. **在模型上关闭内置工具。** 在模型编辑器中禁用**内置工具**能力。为某个聊天启用的工作区工具或 MCP 工具在原生模式下仍会被发送，并导致同样的错误。
3. **如果需要内置工具，请使用支持工具调用的模型。**

### 聊天失败但验证连接正常 {#ollama-model-fails-to-load}

**症状：** **验证连接**显示**服务器连接已验证**，Ollama 模型也出现在模型列表中，但与某个模型的聊天却以错误结束。

**原因：** 两项检查都不运行模型。**验证连接**只请求 `/api/version`，模型列表来自 `/api/tags`。只有发往 `/api/chat` 的聊天请求才会让 Ollama 运行模型。当 Ollama 返回错误时，Open WebUI 会在聊天消息中显示 Ollama 自己的错误文本，并将其记录为 `Error processing chat payload: <text>`。当 Ollama 的错误没有消息时，聊天中显示 `Open WebUI: Server Connection Error`。

**修复：**

1. 在运行 Ollama 的机器上，用终端运行同一个模型：`ollama run <model>`。对于名为 `ollama` 的 Ollama 容器，运行 `docker exec -it ollama ollama run <model>`。如果在那里同样失败，问题出在 Ollama 本身，而不是连接。
2. 查看 Ollama 的服务器日志以了解原因。[Ollama 的故障排查页面](https://github.com/ollama/ollama/blob/main/docs/troubleshooting.mdx) 列出了各系统上日志的位置，例如使用 systemd 的 Linux 上的 `journalctl -u ollama`，以及容器的 `docker logs <container-name>`。
3. 如果错误提到内存，说明模型放不进可用的 RAM 或 VRAM。请改用更小的模型或它更小的变体。`ollama ps` 会显示已加载的模型以及每个模型运行在 GPU 还是 CPU 上（[Ollama FAQ](https://github.com/ollama/ollama/blob/main/docs/faq.mdx#how-can-i-tell-if-my-model-was-loaded-onto-the-gpu)）。

## 验证连接 URL 时出现 `Network Problem` {#network-problem-when-you-verify-a-connection-url}

**症状：** **管理面板 > 设置 > 连接**中某个连接的**验证连接**显示 `Ollama: Network Problem` 或 `OpenAI: Network Problem`，该 URL 下的模型也没有出现。

**原因：** Open WebUI 不检查 URL 的格式。它会去掉一个结尾斜杠，然后追加固定路径。验证时，对 Ollama 连接请求 `<url>/api/version`，对 OpenAI 连接请求 `<url>/models`。聊天请求则发往 Ollama 的 `<url>/api/chat` 和 OpenAI 的 `<url>/chat/completions`。Azure 和 Anthropic 的 URL 遵循各自的规则。Ollama 检查的任何失败都会显示 `Ollama: Network Problem`。OpenAI 检查失败会显示 `OpenAI: Network Problem`，或者在提供方返回 JSON 错误时显示 `OpenAI:` 后接提供方的消息。

| 你填写的 | Open WebUI 为验证而请求的地址 | 请改为填写 |
| :--- | :--- | :--- |
| `192.168.1.5:11434` | 什么都没有：请求在发出前就失败了，因为该 URL 没有 `http://` | `http://192.168.1.5:11434` |
| `http://192.168.1.5` | 端口 `80`，这是 `http://` 的默认端口 | `http://192.168.1.5:11434` |
| `http://localhost:11434/api` | `http://localhost:11434/api/api/version` | `http://localhost:11434` |
| `https://api.openai.com/v1/chat/completions` | `https://api.openai.com/v1/chat/completions/models` | `https://api.openai.com/v1` |
| `https://api.openai.com` | `https://api.openai.com/models` | `https://api.openai.com/v1` |

Ollama 的 URL 形式是 `http://host:port`，端口之后不能再有内容。OpenAI 兼容的 URL 是位于 `/models` 和 `/chat/completions` 之前的基础 URL。对大多数提供方来说，它以 `/v1` 结尾，正如 **URL** 字段给出的建议值。

## 间歇性名称查找失败（常被报告为“未找到模型”） {#intermittent-name-lookup-failures-often-reported-as-model-not-found}

### 常见症状 {#common-symptoms-3}

- 对于一个已经配置好、刚刚还能正常工作的模型，对话却以**“未找到模型”**失败，之后又恢复正常。
- Ollama 的模型列表会自行清空，重启后又恢复。
- 日志中出现 `ClientConnectorDNSError` 或 `Cannot connect to host ...`，而同一个容器内的 shell 却能正常解析该主机名。
- 在某些 Windows 主机上，从第一次启动开始，对外部模型服务商的每一次请求都会失败。

### 原因 {#cause}

除非启用可选的 c-ares 解析器，Open WebUI 会让操作系统把主机名转换为地址。c-ares 在各处的表现并不一致：

- 在某些 Windows 主机上它找不到可用的名称服务器，导致所有外部名称都无法解析。
- 在 Docker 中它可能间歇性地不再解析容器名，尽管 Docker 自身的 DNS 仍在应答。结果就是模型列表被清空、进行中的对话以误导性的“未找到模型”失败——因为无法解析的名称与没有该模型的服务商看起来毫无区别。

### 解决方案 {#solution}

让 c-ares 保持关闭。默认情况下名称查找走操作系统，因此容器名、`host.docker.internal`、Compose 的 `extra_hosts` 以及 Kubernetes 的 `hostAliases` 的行为都与宿主机上的其余部分保持一致。

c-ares 作为一个可选项仍然可用，在繁忙的实例上值得一试，因为它消除了每次出站请求前的一段排队延迟：

```bash
AIOHTTP_CLIENT_ASYNC_DNS_RESOLVER=true
```

如果你启用了它，请在之后实际操作你的模型、网页搜索和各项内部服务，并注意那些并非来自 `/etc/resolv.conf` 或 hosts 文件的名称（通过 avahi/mDNS 提供的 `.local`、NIS 或 LDAP 目录、Windows NBNS）可能会停止解析。完整说明参见 [`AIOHTTP_CLIENT_ASYNC_DNS_RESOLVER`](/reference/env-configuration#aiohttp_client_async_dns_resolver)，它能带来什么参见[性能 → DNS 解析器](/troubleshooting/performance#dns-resolver)。

## ⏱️ 模型列表加载问题（UI 很慢 / 端点不可达） {#model-list-loading-issues-slow-ui--unreachable-endpoints}

如果 Open WebUI 加载模型需要很久，或者模型选择器一直转圈，常见原因是你在连接配置中保存了不可达或非常慢的 API 端点。

### 常见症状 {#common-symptoms-4}

- 模型选择器长时间显示加载状态
- `/api/models` 返回 `500 Internal Server Error`
- 打开 Settings 时 UI 明显卡顿
- Docker/服务器日志出现：`Connection error: Cannot connect to host...`

### 原因：端点不可达 {#cause-unreachable-endpoints}

当你配置多个 Ollama 或 OpenAI base URL（用于负载均衡或冗余）时，Open WebUI 会尝试从**所有**已配置端点拉取模型列表。只要其中任何一个端点不可达，系统就会一直等到超时后才返回结果。

默认情况下，Open WebUI 获取模型列表时对每个不可达端点会等待 **10 秒**。端点是并发查询的，因此总等待时间取决于最慢的端点，各端点的等待时间不会累加。

### 方案 1：缩短超时时间 {#solution-1-adjust-the-timeout}

通过 `AIOHTTP_CLIENT_TIMEOUT_MODEL_LIST` 调低模型列表请求超时：

```bash
# Set a shorter timeout (in seconds) for faster failure on unreachable endpoints
AIOHTTP_CLIENT_TIMEOUT_MODEL_LIST=3
```

这样可以缩短 Open WebUI 放弃等待每个端点并继续处理之前所用的时间。

### 方案 2：修复或删除不可达端点 {#solution-2-fix-or-remove-unreachable-endpoints}

1. 进入 **管理设置 → Connections**
2. 检查你的 Ollama 与 OpenAI base URL
3. 删除或修正不可达的 IP 地址与主机名
4. 保存配置

### 方案 3：从数据库中的错误配置中恢复 {#solution-3-recover-from-database-persisted-bad-configuration}

如果你保存了不可达 URL，导致连设置页面都进不去，那么坏配置已经写入数据库，并且会优先于环境变量生效。可以使用以下恢复方式之一：

**选项 A：启动时重置配置**
```bash
# Forces environment variables to override database values on next startup
RESET_CONFIG_ON_START=true
```

**选项 B：始终使用环境变量**
```bash
# Prevents database values from taking precedence (changes in UI won't persist across restarts)
ENABLE_PERSISTENT_CONFIG=false
```

**选项 C：手动清理数据库（高级）**

如果你使用的是 SQLite，停止容器后执行：
```bash
sqlite3 webui.db "DELETE FROM config WHERE key IN ('ollama.base_urls','openai.api_base_urls');"
```

:::warning
手动修改数据库应作为最后手段。操作前务必先备份数据库。
:::

### 相关环境变量 {#related-environment-variables}

| 变量 | 默认值 | 说明 |
|----------|---------|-------------|
| `AIOHTTP_CLIENT_TIMEOUT_TOOL_SERVER` | 继承 `AIOHTTP_CLIENT_TIMEOUT` | 执行 tool server API 调用的超时（秒） |
| `AIOHTTP_CLIENT_TIMEOUT_TOOL_SERVER_DATA` | `10` | 加载 tool server metadata/spec 数据的超时（秒） |
| `AIOHTTP_CLIENT_TIMEOUT_MODEL_LIST` | `10` | 拉取模型列表的超时（秒） |
| `AIOHTTP_CLIENT_TIMEOUT` | `300` | 通用 API 请求超时 |
| `RESET_CONFIG_ON_START` | `false` | 启动时把数据库配置重置为环境变量值 |
| `ENABLE_PERSISTENT_CONFIG` | `true` | 数据库配置是否优先于环境变量 |

更多信息请参阅 [环境变量配置](/reference/env-configuration#aiohttp_client_timeout_model_list)。

## 🐢 低配硬件上的慢性能或超时 {#slow-performance-or-timeouts-on-low-spec-hardware}

如果你在资源受限的系统上（尤其是 Raspberry Pi 等设备）遇到页面加载慢、API 超时或 UI 无响应，问题可能与数据库会话共享有关。

### 原因 {#cause-1}

数据库会话共享可能会让低配硬件（Raspberry Pi、CPU 配额极低的容器等）或并发下的 SQLite 数据库过载。

### 解决方法 {#solution-1}

关闭数据库会话共享：

```bash
DATABASE_ENABLE_SESSION_SHARING=false
```

对于硬件资源充足的 PostgreSQL 部署，启用该设置反而可能提高性能。详情请参见 [DATABASE_ENABLE_SESSION_SHARING](/reference/env-configuration#database_enable_session_sharing)。

## 🔒 与 Hugging Face 连接时的 SSL 问题 {#ssl-connection-issue-with-hugging-face}

如果你在连接 Hugging Face 时遇到 SSL 错误：

1. **检查 Hugging Face 服务状态**：确认是否是其服务端故障
2. **切换端点**：如果 Hugging Face 服务异常，请在 Docker 命令中切换端点

**示例 Docker 命令：**
```bash
docker run -d -p 3000:8080 -e HF_ENDPOINT=https://hf-mirror.com/ --add-host=host.docker.internal:host-gateway -v open-webui:/app/backend/data --name open-webui --restart always ghcr.io/open-webui/open-webui:main
```

## 🔐 内部工具的 SSL 证书问题 {#ssl-certificate-issues-with-internal-tools}

如果 Tika、Ollama（用于嵌入）、外部 reranker、模型连接或工具服务器使用自签名证书或来自私有 CA 的证书，你可能会遇到 SSL 校验错误。

### 常见症状 {#common-symptoms-5}

- 日志中出现 `[SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed: self-signed certificate`
- Tika 文档导入失败
- 嵌入生成因 SSL 报错失败
- Reranking 因 SSL 报错失败

### 解决方法 {#solution-2}

你可以通过以下环境变量，为这些内部工具连接关闭 SSL 校验：

1.  **对于同步请求（Tika、External Reranker）：**
    ```bash
    REQUESTS_VERIFY=false
    ```

2.  **对于异步请求（Ollama Embeddings）：**
    ```bash
    AIOHTTP_CLIENT_SESSION_SSL=false
    ```

:::warning
关闭 SSL 校验会降低安全性。只有在你信任所处网络及目标服务（例如在安全的内网环境中运行）时才应这样做。
:::

### 改为信任私有 CA 或自签名 CA {#trust-a-private-or-self-signed-ca-instead}

模型连接和工具服务器可以验证来自你自己的 CA 的证书，因此校验可以保持开启。给 Open WebUI 提供容器内 CA bundle 文件（PEM）的路径：

| 变量 | 覆盖的连接 | 取值 |
| :--- | :--- | :--- |
| [`AIOHTTP_CLIENT_SSL_CERT_FILE`](/reference/env-configuration#aiohttp_client_ssl_cert_file) | 下表中自身变量为 `true` 的所有连接 | CA bundle 文件的路径。默认未设置 |
| [`AIOHTTP_CLIENT_SESSION_SSL`](/reference/env-configuration#aiohttp_client_session_ssl) | Ollama 和 OpenAI 连接（模型列表、连接检查和聊天）、Ollama 嵌入、语音转文字和文字转语音、图像生成，以及 MCP 工具服务器的 OAuth 2.1 发现、注册和令牌刷新请求 | `true`（默认）、`false`，或 CA bundle 文件的路径 |
| [`AIOHTTP_CLIENT_SESSION_TOOL_SERVER_SSL`](/reference/env-configuration#aiohttp_client_session_tool_server_ssl) | OpenAPI 工具服务器（加载规范和调用工具）以及 MCP 工具服务器流量 | `true`（默认）、`false`，或 CA bundle 文件的路径 |

`true` 和 `false` 不区分大小写。其他任何取值都会被当作文件路径读取，并且该路径在对应变量的连接中优先于 `AIOHTTP_CLIENT_SSL_CERT_FILE`。要一次覆盖全部，请只设置 `AIOHTTP_CLIENT_SSL_CERT_FILE`，另外两个保持 `true`。

对于使用它的连接，bundle 会取代默认的信任库：它们只信任该文件中的 CA（[Python `ssl.create_default_context`](https://docs.python.org/3/library/ssl.html#ssl.create_default_context)）。如果同样的连接还要访问公共端点，例如 `api.openai.com`，请把你的 CA 和公共根证书放进同一个文件，例如复制容器的 `/etc/ssl/certs/ca-certificates.crt` 并在末尾追加你的 CA。

如果该文件不存在，Open WebUI 会记录 `SSL CA bundle path does not exist: '<path>', ignoring` 并回退到 `AIOHTTP_CLIENT_SSL_CERT_FILE`；当它也未设置时，回退到默认信任库，因此 `CERTIFICATE_VERIFY_FAILED` 错误会继续出现。这些变量只在启动时读取一次，因此修改后请重启 Open WebUI。

对于使用 TLS 的 Milvus，请将 [`MILVUS_SERVER_PEM_PATH`](/reference/env-configuration#milvus_server_pem_path) 指向 CA 或服务器证书。校验仍保持开启。

## 🍏 MacOS 上的 Podman {#podman-on-macos}

对于 MacOS 上的 Podman：

1. **启用宿主机访问**：Podman 5.0+ 默认使用 **pasta**，已经简化了 host loopback。旧版本请使用 `--network slirp4netns:allow_host_loopback=true`。
2. **设置 OLLAMA_BASE_URL** 为 **`http://host.containers.internal:11434`**。

**示例 Podman 命令：**
```bash
podman run -d -p 3000:8080 -e OLLAMA_BASE_URL=http://host.containers.internal:11434 -v open-webui:/app/backend/data --name open-webui --restart always ghcr.io/open-webui/open-webui:main
```

## 🔐 Web Search 中的 SSL/TLS 错误 {#ssltls-errors-with-web-search}

使用 Web Search 时遇到 SSL 错误，通常可归为两类：代理配置问题，或证书校验问题。

### 证书校验问题 {#certificate-verification-issues}

如果 Open WebUI 在抓取网页内容（Web Loader）时出现 SSL 校验错误：

- **症状**：加载搜索结果时出现 `[SSL: CERTIFICATE_VERIFY_FAILED]`
- **解决方法**：可以单独关闭 Web Loader（抓取器）的 SSL 校验
  ```bash
  ENABLE_WEB_LOADER_SSL_VERIFICATION=false
  ```
  > **注意**：该设置只作用于网页的*抓取*过程。如果你是在搜索引擎（例如本地 SearXNG）或后续步骤（Embedding/Reranking）中遇到 SSL 问题，请查看本页其他章节。

### 代理配置问题 {#proxy-configuration-issues}

如果在使用 Bocha、Tavily 等 Web Search 提供商时，看到 `UNEXPECTED_EOF_WHILE_READING` 或 `Max retries exceeded` 之类的 SSL 错误：

#### 常见症状 {#common-symptoms-6}

- `SSLError(SSLEOFError(8, '[SSL: UNEXPECTED_EOF_WHILE_READING]'))`
- `Max retries exceeded with url: /v1/web-search`
- Web Search 在独立 Python 脚本中能正常工作，但在 Open WebUI 中失败

#### 原因：对 HTTPS 流量使用了 HTTP 代理 {#cause-http-proxy-configured-for-https-traffic}

这通常说明你把**HTTP 代理**用于**HTTPS 流量**。HTTP 代理无法正确处理 TLS 连接，从而导致 SSL 握手失败。

请检查以下环境变量：
- `HTTP_PROXY` / `http_proxy`
- `HTTPS_PROXY` / `https_proxy`

如果你的 `https_proxy` 指向的是 `http://...`（HTTP）而不是 `https://...`（HTTPS），握手通常会失败，因为代理会提前终止连接。

#### 解决方法 {#solutions-1}

1. **修正代理配置**：为 HTTPS 流量使用支持 HTTPS 的代理，或让 HTTP 代理正确支持 CONNECT 隧道
2. **为特定主机绕过代理**：设置 `NO_PROXY`
   ```bash
   NO_PROXY=api.bochaai.com,api.tavily.com,api.search.brave.com
   ```
3. **如果不需要代理则禁用**：直接取消这些代理环境变量

#### 为什么独立脚本可以工作 {#why-standalone-scripts-work}

直接运行 Python 脚本时，它未必继承 Open WebUI 服务所使用的代理环境变量。该服务通常从 systemd、Docker 或 shell 的配置文件继承环境变量，因此两者的代理配置可能不同。
