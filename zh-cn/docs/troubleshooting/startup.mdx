# 启动与 Docker 故障 {#startup--docker-failures}

Open WebUI 完全无法启动？从这里开始。关于 Alembic 迁移的问题（`no such table`、`Can't locate revision`），请参阅[数据库迁移](./manual-database-migration.md)。

## 容器反复重启 {#container-keeps-restarting}

即使容器存在且已发布端口，Open WebUI 也可能仍在启动或反复退出。如果浏览器无法连接，请先检查容器状态和近期日志，再决定是否重建容器：

```bash
docker ps -a --filter name=open-webui
docker inspect --format 'status={{.State.Status}} restarts={{.RestartCount}} exit={{.State.ExitCode}} oom={{.State.OOMKilled}}' open-webui
docker logs --tail 100 --timestamps open-webui
```

将 `open-webui` 替换为容器名称。重启次数持续增加，表示进程在反复退出。如果显示 `oom=true`，请检查可用内存以及容器的内存限制。否则，请查找每次重启前的最后一条错误。如果容器仍在运行，但日志停在 Open WebUI 横幅处，请参见[访问 Hugging Face 时启动延迟](#startup-stops-after-the-banner-while-hugging-face-is-slow-or-blocked)。

## 使用 Docker 安装后无法连接 {#cannot-connect-after-docker-install}

先检查 Open WebUI 容器内部是否就绪，再通过已发布的端口检查。v0.13.4 镜像的 Docker 健康检查会在容器内部调用 `/health`。健康状态表明 Web 服务器在容器内能够响应。`/ready` 端点还会检查启动是否完成，以及数据库和已配置的 Redis 连接能否响应。

```bash
docker exec open-webui sh -c 'curl -i --max-time 5 "http://127.0.0.1:${PORT:-8080}/ready"'
curl -i --max-time 5 http://127.0.0.1:3000/ready
```

在 Docker 主机上运行这两个命令。将 `open-webui` 替换为容器名称，将 `3000` 替换为已发布的主机端口。正在监听的服务器仍可能从 `/ready` 返回 HTTP 503，并附带 `Startup not complete`、`Database not ready` 或 `Redis not ready`。结合该响应与容器日志，找出仍未就绪的部分。如果无法在容器内连接，请按上文检查容器状态及启动日志。

如果容器内的探测返回 HTTP 200 和 `{"status":true}`，但通过主机端口无法连接，请运行 `docker port open-webui` 检查端口映射。容器端口默认为 `8080`，例如 `3000:8080` 会把主机端口 `3000` 的请求转发到容器端口 `8080`。如果修改了 `PORT`，请确认映射指向对应的容器端口。

## 设备空间不足 {#no-space-left-on-device}

如果启动或上传失败并报错 `No space left on device` 或 `database or disk is full`，请检查服务器日志中的路径。在标准 Docker 镜像中，`/app/backend/data` 保存默认的 SQLite 数据库、上传文件和应用缓存。使用 S3 存储时，上传文件仍会先写入本地磁盘，再发送到存储桶。读取文件时也会下载本地副本。

确认出错路径位于哪个文件系统上。对于使用默认数据目录且正在运行的 Linux 容器，请运行：

```bash
docker inspect --format '{{json .Mounts}}' open-webui
docker exec open-webui df -h /app/backend/data
docker exec open-webui df -i /app/backend/data
```

将 `open-webui` 替换为容器名称。如果配置了不同的 [`DATA_DIR`](/reference/env-configuration#data_dir) 路径，请使用实际路径。第二条命令检查剩余空间，第三条检查剩余 inode。即使还有空间，inode 也可能耗尽。如果容器无法持续运行，请根据挂载信息检查 Docker 主机上的底层文件系统。如果错误由 Docker 本身在拉取或创建期间报告，请检查 Docker 存放数据的文件系统。

释放空间或扩展受影响的文件系统后重试。保留 Open WebUI 数据卷。从中删除文件前请参见[备份](/tutorials/maintenance/backups)。

## Apple Silicon (M1/M2/M3) 上容器启动时挂起 {#container-hangs-at-startup-on-apple-silicon-m1m2m3}

### 症状 {#symptom}

在 macOS Apple Silicon 上，容器在迁移完成后、打印出以下信息时**在启动过程中卡死**：

```text
WARNING: CORS_ALLOW_ORIGIN IS SET TO '*' - NOT RECOMMENDED FOR PRODUCTION DEPLOYMENTS.
```

没有 `Started server process`、没有 ASCII 横幅，也没有错误。容器会**无限期**卡住（一小时后仍没有响应），即使使用**全新的空数据卷**也会重现。`OFFLINE_MODE` / `HF_HUB_OFFLINE` 都不能缓解此问题。按 `Ctrl+C` 后容器仍在运行，必须用 `docker kill` 终止。

### 原因 {#cause}

此时迁移已完成，Open WebUI 自身的逻辑还未执行，也尚未发起数据库查询或网络请求。Python 正通过 `import` 加载应用及其原生依赖（`pycrdt`、嵌入或向量库、`pydub` 等）。

通常的触发原因是**架构不匹配**：主机全局设置了 `DOCKER_DEFAULT_PLATFORM=linux/amd64`，导致 Docker 拉取 **x86_64 镜像并在 ARM 主机上通过 Rosetta 仿真运行**。原生扩展在仿真环境下导入时卡住。

### 修复 {#fix}

运行**原生的 `arm64` 镜像**，不要在 Apple Silicon 上仿真 x86：

1. 让 Docker 自动选择架构，或显式指定：

   ```bash
   docker run --platform linux/arm64 ... ghcr.io/open-webui/open-webui:main
   ```

2. 检查全局覆盖设置并取消（或在每次运行时覆盖）：

   ```bash
   echo $DOCKER_DEFAULT_PLATFORM     # also check Docker Desktop → Settings
   ```

3. 确认容器实际运行的架构（Apple Silicon 上应为 `aarch64`）：

   ```bash
   docker run --rm ghcr.io/open-webui/open-webui:main uname -m
   ```

:::warning 不支持仿真
在 Apple Silicon 上通过仿真（Rosetta）运行 **x86 镜像是尽力而为且不受支持的**，可能会像这样在启动时卡住。请使用原生 `arm64` 镜像。
:::

:::tip 捕获确切的阻塞导入
如果启动挂起*不*是架构相关的问题，可以在 60 秒后转储每个线程的堆栈（无需安装，`faulthandler` 是标准库）：

```bash
docker run --rm --entrypoint python ghcr.io/open-webui/open-webui:main \
  -X faulthandler -c "import faulthandler; faulthandler.dump_traceback_later(60); import open_webui.main; print('IMPORT OK')"
```

`IMPORT OK` 表示导入没有问题，问题出在其他地方；约 60 秒后的堆栈跟踪将显示确切阻塞的导入。
:::

## Hugging Face 缓慢或被阻断时，启动在横幅之后卡住 {#startup-stops-after-the-banner-while-hugging-face-is-slow-or-blocked}

### 症状 {#symptom-1}

日志打印出 Open WebUI 横幅之后，几分钟内不再有新的输出。`Application startup complete.` 不会出现，页面也加载不了。这发生在服务器无法快速访问 Hugging Face 时，例如在公司代理或防火墙后面，或者完全没有互联网访问。

### 原因 {#cause-1}

使用**默认（SentenceTransformers）**嵌入引擎时，每次启动都会在服务器接受连接之前加载本地嵌入模型（[`RAG_EMBEDDING_MODEL`](/reference/env-configuration#rag_embedding_model)，默认为 `sentence-transformers/all-MiniLM-L6-v2`）。只要 [`RAG_EMBEDDING_MODEL_AUTO_UPDATE`](/reference/env-configuration#rag_embedding_model_auto_update) 为 `True`（默认值），这一步就会访问 Hugging Face 来检查模型并下载缺失的文件，即使本地已有缓存副本也一样。启动会一直等到该请求完成或失败。启用混合检索时，重排序模型在 `RAG_RERANKING_MODEL_AUTO_UPDATE` 下也走同样的步骤。如果模型没有缓存且请求失败，日志会显示 `Cannot determine model snapshot path`。

### 修复 {#fix-1}

任选一种：

- **模型已缓存后跳过检查。** 设置 `RAG_EMBEDDING_MODEL_AUTO_UPDATE=false`。这样 Open WebUI 会直接加载缓存副本，不再访问 Hugging Face。如果模型尚未缓存，它会记录 `Cannot determine model snapshot path` 并按 Hugging Face 名称加载模型，因此首次启动仍然需要网络。
- **完全离线运行。** 设置 [`OFFLINE_MODE=true`](/reference/env-configuration#offline_mode)，它同时会设置 `HF_HUB_OFFLINE=1` 并关闭两个自动更新变量。模型必须已经缓存，参见下一节。
- **让下载走你的代理。** Hugging Face 客户端会从 Open WebUI 进程的环境变量中读取[标准代理变量](https://www.python-httpx.org/environment_variables/) `HTTPS_PROXY`（或 `https_proxy`）和 `NO_PROXY`。请在设置其他 Open WebUI 变量的地方设置它们，例如 `docker run` 的 `-e`，或 shell 中的导出。
- **使用外部嵌入引擎。** 在 **Settings > Documents**（管理员区域）中把 **Embedding Model Engine** 设为 **Ollama**、**OpenAI** 或 **Azure OpenAI**，或设置 [`RAG_EMBEDDING_ENGINE`](/reference/env-configuration#rag_embedding_engine)。这样启动时不会加载本地嵌入模型。

## 离线模式新安装时出现 `ValueError: No embedding model is loaded` {#valueerror-no-embedding-model-is-loaded-with-offline-mode-on-a-fresh-install}

### 症状 {#symptom-2}

容器启动了，它的日志中带有下面的 `LocalEntryNotFoundError`，随后第一次文档上传或 RAG 查询会以 `ValueError` 失败：

```text
huggingface_hub.errors.LocalEntryNotFoundError: Cannot find an appropriate cached
snapshot folder ... outgoing traffic has been disabled.

ValueError: No embedding model is loaded. Set RAG_EMBEDDING_MODEL to a valid
SentenceTransformer model name, or configure an external RAG_EMBEDDING_ENGINE
(ollama, openai, azure_openai).
```

这发生在**新安装**上设置了 [`OFFLINE_MODE=true`](/reference/env-configuration#offline_mode) 和/或 [`HF_HUB_OFFLINE=1`](/reference/env-configuration#hf_hub_offline) 时。

### 原因 {#cause-2}

离线模式会屏蔽 Hugging Face 下载和版本检查。默认的 RAG 嵌入引擎使用一个**必须下载一次的本地 SentenceTransformers 模型**。在新安装上已经启用了离线模式的情况下，模型从未被缓存，因此没有可加载的内容。该错误会在第一次嵌入调用时浮现。

### 修复 {#fix-2}

选择一种方案：

- **先缓存。** **不启用** `OFFLINE_MODE` / `HF_HUB_OFFLINE`，启动一次以下载和缓存嵌入模型。之后再启用离线模式。
- **使用外部嵌入器**，这样无需下载：将 [`RAG_EMBEDDING_ENGINE`](/reference/env-configuration#rag_embedding_engine) 设置为 `ollama`（配合已拉取的 [`RAG_EMBEDDING_MODEL`](/reference/env-configuration#rag_embedding_model)）、`openai` 或 `azure_openai`。
- 对于与外网隔离的部署，**将模型缓存预先打包到镜像中，或通过卷挂载**。

有关完整的离线设置，请参阅[离线模式指南](/tutorials/maintenance/offline-mode)。

## 全新 Windows 安装时报 `WEBUI_SECRET_KEY is not set` {#webui\_secret\_key-is-not-set-on-a-fresh-windows-install}

### 症状 {#symptom-3}

`backend\start_windows.bat` 在启动时中止：

```text
WEBUI_SECRET_KEY is not set. It is a hard requirement when authentication is enabled.
```

### 原因 {#cause-3}

该脚本从 `.webui_secret_key` 读取密钥，并且只在该文件不存在时才生成一个。早期一次失败运行遗留的空 `.webui_secret_key`，会被读成空密钥。

### 修复 {#fix-3}

**删除 `backend` 文件夹中空的 `.webui_secret_key` 文件**，然后重新启动，让脚本生成一个密钥。

自己设置 `WEBUI_SECRET_KEY` 同样有效，而且这才是个人机器之外一切环境的正确配置方式。设置之后，脚本会完全跳过密钥生成。

各种启动方式如何生成并持久化该密钥，请参阅 [`WEBUI_SECRET_KEY`](/reference/env-configuration#webui_secret_key)。

## 启动时报 `Could not parse SQLAlchemy URL from given URL string` {#could-not-parse-sqlalchemy-url-from-given-url-string-at-startup}

### 症状 {#symptom-4}

Open WebUI 在加载过程中停止，堆栈跟踪的最后一行是：

```text
sqlalchemy.exc.ArgumentError: Could not parse SQLAlchemy URL from given URL string
```

### 原因 {#cause-4}

`DATABASE_URL` 被设置成了空值，例如等号后面什么都没有的 `DATABASE_URL=` 行。只有在该变量完全没有设置时，Open WebUI 才会使用它的 SQLite 默认值，因此空值会被当作数据库 URL 传下去。你的 shell 中残留的、来自另一个项目的 `DATABASE_URL` 同样会替换掉默认值，Open WebUI 随后会连到那个项目的数据库。

### 修复 {#fix-4}

删除或取消设置 `DATABASE_URL`（在启动 Open WebUI 的那个 shell 中执行 `unset DATABASE_URL`），以使用 [`DATA_DIR`](/reference/env-configuration#data_dir) 中的 SQLite 数据库；或者把它设置为完整 URL。参见 [`DATABASE_URL`](/reference/env-configuration#database_url)。

## 某个 Function 导致 Open WebUI 无法加载 {#a-function-stops-open-webui-loading}

### 症状 {#symptom-5}

在你添加或更新某个 Function 之后，Open WebUI 无法启动，或者界面加载不出来。

### 修复 {#fix-5}

1. 使用 [`SAFE_MODE=true`](/reference/env-configuration#safe_mode) 重启 Open WebUI。启动时它会关闭数据库中的每个 Function，因此它们都不会被加载。
2. 打开 **Admin Panel > Functions**，删除或修复出问题的那个 Function。
3. 移除 `SAFE_MODE` 并重启。只要它还开着，每次重启都会再次关闭所有 Function。
4. 在 **Admin Panel > Functions** 中把仍然需要的 Function 逐个重新打开。移除 `SAFE_MODE` 并不会把它们重新打开。

参见[安全模式](/getting-started/advanced-topics/hardening#safe-mode)。
