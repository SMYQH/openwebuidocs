## 概览 {#overview}

Open WebUI 可以很方便地连接并管理你的 **Ollama** 实例。本指南将带你完成连接配置、模型管理以及快速上手。

---

## 面向协议的设计 {#protocol-oriented-design}

Open WebUI 的设计是**面向协议（Protocol-Oriented）**的。当我们提到 “Ollama” 时，具体指的是 **Ollama API 协议**（通常运行在 `11434` 端口）。

尽管某些工具可能提供基础兼容，但这一连接类型针对 Ollama 服务本身的独特能力做了优化，例如原生模型管理，以及直接通过管理界面拉取模型。

如果你的后端主要遵循 OpenAI 标准（例如 LocalAI 或 Docker Model Runner），我们建议使用[兼容 OpenAI 的服务指南](/getting-started/quick-start/connect-a-provider/starting-with-openai-compatible)以获得最佳体验。

---

## 第 1 步：设置 Ollama 连接 {#step-1-setting-up-the-ollama-connection}

当 Open WebUI 安装并启动后，它会自动尝试连接你的 Ollama 实例。如果一切顺利，你可以立即开始管理和使用模型。

如果连接失败，最常见原因通常是网络配置错误。你可以参考我们的[连接故障排查指南](/troubleshooting/connection-error)来解决。

---

## 第 2 步：管理你的 Ollama 实例 {#step-2-managing-your-ollama-instance}

在 Open WebUI 中管理 Ollama 的步骤如下：

1. 在 Open WebUI 管理面板中前往 **Settings > Connections**。
2. 在 **Manage Ollama API Connections** 下找到你的实例，并点击 **Manage**（下载图标）。
   在这里，你可以下载模型、调整设置并管理 Ollama 连接。

### 连接提示 {#connection-tips}

*   **Docker 用户：** 如果 Ollama 运行在宿主机上，请使用 `http://host.docker.internal:11434` 作为 URL。
*   **负载均衡：** 你可以添加**多个** Ollama 实例。Open WebUI 会采用**随机选择**策略在它们之间分发请求，从而为并发用户提供基础负载均衡。
    *   **注意：** 要启用这一点，必须确保各实例中的 **Model ID 完全一致**。如果使用了 **Prefix ID**，它们也必须一致（或都为空），这样模型才会合并为同一条目。
    *   **在每台服务器上拉取同一个标签**：模型只按名称合并。Open WebUI 不比较版本或摘要，因此两台服务器上同名但不同构建的模型仍会显示为同一个模型，聊天请求可能落到其中任意一台。模型选择器中显示的参数规模、量化方式和文件大小，来自列表中第一个提供该模型的连接。更新之后，请在每个连接上执行 **更新所有模型**。
    *   **每个请求各自选一台服务器**：Open WebUI 会为每个请求随机选择一台提供该模型的服务器，因此同一段聊天中的消息可能发往不同服务器。
    *   **多用户共用一台服务器**：Open WebUI 收到请求就立即发给 Ollama，自己不维护队列。一台 Ollama 服务器是同时处理同一模型的多个请求，还是让它们排队等待，由 Ollama 服务器上的 `OLLAMA_NUM_PARALLEL` 决定，默认值为 `1`。内存占用会随之增长。请参阅 Ollama 的[并发请求 FAQ](https://docs.ollama.com/faq#how-does-ollama-handle-concurrent-requests)。
    *   **一台宿主机上两个 Ollama 容器**：Ollama 在容器内监听 `11434` 端口，因此要给第二个实例映射一个不同的宿主机端口，例如 `docker run -d -v ollama2:/root/.ollama -p 11435:11434 --name ollama2 ollama/ollama`，并把它添加为 `http://host.docker.internal:11435`。

### 高级配置 {#advanced-configuration}

*   **Prefix ID：** 如果你有多个 Ollama 实例都在提供相同模型名，可加上前缀（例如 `remote`）加以区分。Open WebUI 用一个点把前缀和模型名连起来，因此 `llama3` 会显示为 `remote.llama3`。

    添加、更改或移除**前缀 ID** 后，请检查使用该连接中模型的所有工作区预设。预设会保存旧的模型 ID。在**工作区 > 模型**中编辑预设，使用更新后的 ID 重新选择**基础模型（来源）**，然后保存。
*   **Model IDs (Filter)**：在此列出要显示的模型（白名单）。留空则显示全部模型。

:::tip 连接超时配置

使用多个 Ollama 实例时（尤其跨网络时），如果某个端点不可达，就可能带来连接延迟。你可以通过以下方式调整超时：

```bash
# Lower the timeout (default is 10 seconds) for faster failover
AIOHTTP_CLIENT_TIMEOUT_MODEL_LIST=3
```

如果你保存了一个不可达 URL，导致连 Settings 都打不开，请参见 [模型列表加载问题](/troubleshooting/connection-error#model-list-loading-issues-slow-ui--unreachable-endpoints) 故障排查页面。

:::

## 快速高效下载模型 {#a-quick-and-efficient-way-to-download-models}

如果你想更快开始，管理员可以直接在 **模型选择器** 中下载模型。只需输入模型名称；如果本地尚未可用，Open WebUI 会提示你直接从 Ollama 下载。

示例如下：

![Ollama 下载提示](/images/getting-started/quick-start/selector-ollama.png)

如果你不想在 Admin Settings 菜单里来回切换，而是想直接开始用模型，这种方式会非常方便。

### 从 Hugging Face 下载 GGUF 模型 {#downloading-gguf-models-from-hugging-face}

Ollama 也可以直接从 Hugging Face 下载 GGUF 模型。在 **从 Ollama.com 拉取模型** 或模型选择器中，把模型写成 `hf.co/{username}/{repository}:{quantization}`，例如 `hf.co/ggml-org/gemma-3-270m-it-GGUF:Q8_0`。量化标识要与 GGUF 文件名中的写法一致，例如 `Q4_K_M` 或 `Q8_0`。之后该模型会以这个完整名称列出。关于哪些仓库可用，请参阅 Hugging Face 的 [Ollama 指南](https://huggingface.co/docs/hub/en/ollama)。

### 上传 GGUF 文件 {#uploading-a-gguf-file}

要使用你已经有的 GGUF 文件，请打开该连接的 **管理** 对话框，点击底部 **Experimental** 徽标旁的 **显示**。**上传 GGUF 模型** 下的模式按钮用于选择来源。**文件模式** 会从你的电脑上传一个 `.gguf` 文件，**URL 模式** 则接受一个 Hugging Face resolve（下载）URL。Open WebUI 会把文件发送到那个 Ollama 服务器，并创建一个以文件名（不含扩展名）命名的模型，随后显示 **模型创建成功！**。若要给它设置系统提示词或参数，可以如[创建模型](#creating-a-model)所述以它为基础新建一个模型。

## 更新与删除模型 {#updating-and-deleting-models}

这两个操作都位于下载功能所在的同一个 **管理** 对话框中（参见[第 2 步](#step-2-managing-your-ollama-instance)）。它们只作用于你打开 **管理** 的那个连接背后的 Ollama 服务器，因此当你有多个 Ollama 连接时，需要在每个想要修改的连接上分别打开 **管理**。

### 更新所有模型 {#updating-all-models}

在 **从 Ollama.com 拉取模型** 旁边，**更新所有模型** 按钮会再次逐个拉取该服务器上的每个模型，从而把每个模型更新到其标签的最新版本。Ollama 只下载发生变化的部分，因此已经是最新的模型会很快完成。

运行期间，对话框会显示 **正在更新“模型名”** 以及一个进度条。**取消** 会停止正在下载的那个模型并跳过其余模型。如果某个模型无法被拉取——例如你自己创建而非从 Ollama.com 下载的模型——更新会跳过它并继续处理下一个。运行结束时，Open WebUI 会显示 **所有模型都是最新的**。

更新之后，已经加载的模型会继续运行旧版本，直到被卸载。参见[卸载已加载的模型](#unloading-loaded-models)。

### 删除模型 {#deleting-a-model}
1. 在 **删除模型** 下，从 **选择模型** 中选取目标模型。每个条目都会显示其在磁盘上的占用。
2. 点击 **删除模型** 并确认。

删除会从 Ollama 服务器本身移除该模型并释放其磁盘空间，因此它会从该连接的所有用户面前消失。若只想停止提供某个模型而不删除它，可以改为在连接的 **模型 ID（筛选）** 中只列出你想提供的模型（参见[高级配置](#advanced-configuration)）。

## 创建模型 {#creating-a-model}

**创建模型**（同样位于 **管理** 对话框中）会在该 Ollama 服务器上基于它已有的某个模型创建一个新模型，并带有自己的系统提示词或参数。不会下载任何新内容，因此只需几秒钟。

1. 为新模型输入一个名称，例如 `pirate-gemma`。
2. 在下方的输入框中用 JSON 描述该模型，字段参见 Ollama 的 [create API](https://docs.ollama.com/api/create)。`from` 是要基于的模型，且必须已存在于该服务器上。例如：

   ```json
   {"from": "gemma3:270m", "system": "You answer in one short sentence.", "parameters": {"temperature": 0.3, "num_ctx": 8192}}
   ```

3. 点击名称旁边的 **创建模型** 按钮。在名称和 JSON 都填写完整之前，该按钮保持禁用状态。

当 Ollama 完成后，Open WebUI 会显示 **success**，新模型会以 `pirate-gemma:latest` 出现在模型选择器中。如果 JSON 无法解析，会显示错误且不会发送任何内容。如果 `from` 模型不在该服务器上，Ollama 会尝试从 Ollama.com 下载它，并在那里不存在该模型时失败并提示 **pull model manifest: file does not exist**。

:::note 此处设置的系统提示词是兜底
Ollama 只在对话没有发送系统提示词时才使用模型自身的系统提示词。来自 **工作区** > **模型** 中模型设置的系统提示词、来自用户设置的系统提示词，或由过滤器添加的系统提示词都会取代它。若要让某个系统提示词在 Open WebUI 中始终生效，请在 **工作区** > **模型** 中设置。
:::

## 卸载已加载的模型 {#unloading-loaded-models}

Open WebUI 会在当前由运行时保持预热的 Ollama 模型旁显示一个绿色的“已加载”指示器，管理员可以在模型行上看到 **弹出** 按钮，无需重启服务器即可卸载它。在底层，Open WebUI 会调用 `POST /api/models/unload`（仅管理员），它会向每个提供该模型的 Ollama 节点转发一次带 `keep_alive=0` 的 generate 调用。

这在需要腾出 GPU/显存以在多个大模型之间切换时很有用，也可以在拉取新版本后强制重新加载。尝试卸载一个已连接提供商不支持卸载的模型时会返回错误，而不是静默失败。

### 暂停后首次回复很慢 {#slow-first-reply-after-a-pause}

当一段安静期之后的首次回复比之后的回复慢得多时，说明 Ollama 正在把模型重新加载进内存。默认情况下，Ollama 会卸载 5 分钟内没有使用过的模型。有两个设置可以改变模型保持加载的时间：

- **`OLLAMA_KEEP_ALIVE`**，在 **Ollama 服务器** 上设置，对所有模型生效。它接受 `10m` 或 `24h` 这样的时长、秒数，或者一个负数，用来让模型保持加载。请参阅 Ollama 的[keep-alive FAQ](https://docs.ollama.com/faq#how-do-i-keep-a-model-loaded-in-memory-or-make-it-unload-immediately)。
- **keep_alive (Ollama)**，是 Open WebUI 的高级参数，会作为 `keep_alive` 随每次聊天请求发给 Ollama，并在该请求中取代 `OLLAMA_KEEP_ALIVE`。可以在 **工作区** > **模型** 中按模型设置，也可以在聊天的 **控制** 或 **设置 > 通用** 中设置，后者只有管理员账号可见（参见[聊天参数](/features/chat-conversations/chat-features/chat-params)）。把它从 **默认** 改为 **自定义** 会填入 `5m`。保持 **默认** 时，Open WebUI 不发送任何内容，适用的是 `OLLAMA_KEEP_ALIVE`。

模型会在内存中停留 keep-alive 指定的时长，因此该值越大，模型在两次对话之间占用内存的时间就越长。

## 使用推理 / Thinking 模型 {#using-reasoning--thinking-models}

Ollama 会自行把模型的思考过程与它的答案分开。自 Ollama v0.9.0 起，支持思考的模型（Qwen3、DeepSeek-R1、DeepSeek-V3.1、GPT-OSS）会在单独的 `thinking` 字段中返回思考轨迹，Open WebUI 会把它显示在答案上方一个可折叠的小节中。这里不涉及任何服务端开关，`ollama serve` 也不接受此类参数。

### 控制思考级别 {#controlling-thinking}

**模型控制 > 控制 > 高级参数** 下的 **think (Ollama)** 控件（或在模型编辑器中按模型设置）会作为 `think` 参数发送给 Ollama：

| 设置 | Ollama 收到什么 |
|---|---|
| **默认** | 无。适用 Ollama 自身的默认值，即对支持思考的模型默认开启思考。 |
| **开启** | `true` |
| **自定义** | 一个思考级别：`low`、`medium`、`high` 或 `max`。GPT-OSS 只接受级别。 |
| **关闭** | `false` |

把推理直接写成 `<think>...</think>` 文本、而不使用 Ollama 思考字段的模型，由 **Reasoning Tags** 设置处理。两项设置及排查步骤请参阅[推理与思考模型指南](/features/chat-conversations/chat-features/reasoning-models)。

## 上下文长度 (`num_ctx`) 和 `OLLAMA_CONTEXT_LENGTH` {#context-length-num\_ctx-and-ollama\_context\_length}

模型实际能"看到"多少对话内容由**上下文长度**决定。对于 Ollama，它来自两个地方，其中一个会静默覆盖另一个：

- **`OLLAMA_CONTEXT_LENGTH`** 在 **Ollama 服务器**上设置，是 Ollama 用于模型的默认上下文长度。自 Ollama v0.15.5 起，Ollama 会根据可用显存选取该默认值：显存低于 24 GiB 时为 `4096`，24 到 48 GiB 之间为 `32768`，48 GiB 及以上为 `262144`（参见 [Ollama 的上下文长度文档](https://docs.ollama.com/context-length)）。
- **`num_ctx`** 是 **Open WebUI 的高级参数**（聊天中的**模型控制 > 控制 > 高级参数**，或在模型编辑器中按模型设置）。它默认**未设置**，因此默认情况下应用 Ollama 的 `OLLAMA_CONTEXT_LENGTH`。

:::warning `num_ctx` 会覆盖 `OLLAMA_CONTEXT_LENGTH`
如果在 Open WebUI 中的任何地方设置了 `num_ctx`（模型预设的参数或聊天的高级参数），Open WebUI 会在每次请求时将其发送给 Ollama，并且每次请求的 `num_ctx` **会覆盖**服务器的 `OLLAMA_CONTEXT_LENGTH`。打开 `num_ctx` 控制开关会**预填 `2048`**，这是一个非常小的值，因此很容易在不知情的情况下将模型限制在 2048 个 token，即使你在 Ollama 端提高了 `OLLAMA_CONTEXT_LENGTH`。
:::

过小的上下文会静默截断提示词。这在**原生函数调用**时最为明显，因为工具定义会被注入到提示词中：在 `2048` token 时，模型可能会空间不足并返回**空白响应**，或者输出原始的 tool-call JSON 块而不是实际调用工具。提高上下文长度可以解决这个问题。

**操作建议：**

- 要为所有 Ollama 模型设置默认值，请在 **Ollama 服务器**上设置 `OLLAMA_CONTEXT_LENGTH`，并在 Open WebUI 中**保持 `num_ctx` 未设置**，这样就不会被覆盖。
- 要按模型或按聊天设置，请将 `num_ctx` 设置为模型的合理值（例如 `8192`、`16384` 或模型的最大值），而不是 `2048` 预填值。请记住它会覆盖 `OLLAMA_CONTEXT_LENGTH`。
- 更大的上下文会使用更多 VRAM 和 RAM，请根据你的硬件容量合理设置。

## 工具调用之前写下的文字 {#text-written-before-a-tool-call}

当模型在同一次回复中先写下一句话再调用工具，例如先说 “Let me check the calendar.” 然后给出工具调用时，聊天中会同时显示两者。对于 **管理 Ollama API 连接** 下的连接所提供的模型，之后的每个请求都会把该助手轮次以空文本、只带工具调用的形式发给 Ollama。这适用于工具结果之后的追问请求，也适用于聊天中的每一条后续消息。模型的思考和工具调用会保留下来，聊天本身仍会存储并显示那段文字。

Open WebUI 之所以这样做，是为了让模型在后续轮次中看不到那句话，这是对每个带工具调用的助手轮次都生效的。
