## 插件 {#plugins}

Open WebUI 自带的功能已经很多，但它真正的力量在于它从一开始就被设计成可扩展的。人们在演示中看到的许多高级能力（自动翻译、token / 成本统计、自定义后处理、小众提供商集成）都是构建在平台之上的**插件**。理解插件生态，是新手能获得的最大一次提升。

插件分为两大家族：**工具（Tools）** 与 **函数（Functions）**。

**工具**赋予模型可以在回答过程中调用的能力：

| 来源 | 作用 | 示例 |
| :--- | :--- | :--- |
| **内置** | 随 Open WebUI 一起提供的系统工具。在管理面板中启用，无需安装。 | 网页搜索、代码解释器、图片生成、记忆、笔记、知识检索 |
| **自定义** | | |
| &nbsp;&nbsp;↳ 工具 | 你自己编写或从[社区站点](https://openwebui.com/)安装的代码。在 **Workspace > 工具** 中管理。 | Langfuse / OpenLit 可观测性、Home Assistant、arXiv / PubMed 检索、Wolfram Alpha、Jira / Linear、SQL 查询 |
| &nbsp;&nbsp;↳ 工具服务器 | 通过 **MCP** 或 **OpenAPI** 连接的外部服务。在 **设置 > 集成**（管理员区域） 中配置。 | 你自己的微服务、第三方 API、已有的 MCP 服务器 |

**函数**在平台层级运行，修改 Open WebUI 自身的行为，共有三种类型：

| 类型 | 作用 | 示例 |
| :--- | :--- | :--- |
| **管道（Pipes）** | 向模型选择器中添加一个由自定义代码支撑的新“模型” | 模型路由（按提示词选择便宜或昂贵模型）、多步智能体循环、自定义 LLM 后端 |
| **过滤器（Filters）** | 在每次对话轮次中自动修改经过的每个请求和 / 或响应 | 上下文裁剪、PII 脱敏、token / 成本统计、Langfuse 追踪、响应重排版 |
| **操作（Actions）** | 在每条消息下添加一个按钮，点击时运行自定义代码 | “重新生成追问”、“翻译回复”、“置顶消息”、“保存到知识库” |

### 安装插件 {#installing-plugins}

工具和函数都可以在 [**Open WebUI 社区站点**](https://openwebui.com/)浏览并安装，那是一个一键式的目录，收录了数千个由社区构建的插件。挑一个，点击 “Get”，粘贴到管理面板中，启用它，并配置它的 **valves**（即插件的设置）。你也可以在管理面板中从零编写自己的插件。

刚接触这个目录？[**社区插件**](/features/extensibility/community)指南就是新手地图：如何按想做的事找到插件，以及如何安全地导入。现在就记住一条规则：插件被精选或受欢迎**不等于**经过安全或质量审查，而插件会在你的服务器上运行真实代码，因此导入前请先阅读源码。

:::note 在动手编写之前，先逛一逛
每当你想到“Open WebUI 要是有 X 功能就好了”时，它几乎肯定已经通过某个插件实现了。已经有数千个现成的插件，你需要的那个通常也在其中。即使没有完全匹配的，通常也只需修改最接近的插件约 20 行代码即可。你可以直接在管理面板中为该插件创建一个分支。
:::

## 工具调用（原生与旧版） {#tool-calling-native-vs-legacy}

本页介绍的其他功能几乎都作为**工具**提供给模型，例如网页搜索、知识检索、记忆、代码解释器和 Open Terminal。模型可以在回答途中调用这些工具。一个实例级开关决定模型*如何*调用它们。

**原生模式现在是默认模式。** 任何没有显式选择模式的模型都会使用 **Native（Agentic）模式**，它依赖模型自带的函数调用能力。正因如此，模型可以自行决定何时去搜索网页、到知识库中查找或保存一条记忆，而不需要你手动逐个打开工具。它速度更快，能让 KV cache 保持热状态，并且是唯一能解锁内置系统工具（记忆、笔记、知识、频道、智能体研究）的模式。

**旧版模式是主动退出项。** 过去那种基于提示词注入的方式（此前称为 “Default”）已更名为 **Legacy**，并且不再受支持。任何依赖旧行为的模型现在都会运行在原生模式，除非你手动改回去。如果某个模型在原生模式下表现吃力，正确的解决办法是换一个更擅长工具调用的模型，而不是回到旧版。你并不需要前沿模型才能做到这一点——GPT-5.6 Luna、Gemini 3.5 Flash-Lite、MiniMax M3，或本地运行的 Muse Glimmer 30B 都足够可靠，可以作为合理下限。

更多细节，包括如何把单个模型或整个实例切换到旧版：
- [工具调用模式：原生与旧版](/features/extensibility/plugin/tools#tool-calling-modes-default-vs-native)
- [如何把所有模型切换到旧版](/features/extensibility/plugin/tools#enable-legacy-for-all-models)

## 提示词缓存（KV cache） {#prompt-caching-kv-cache}

提供商会对请求开头的 token 进行缓存，并对可复用的部分收取更低的费用，因此开头不变的一段对话既更便宜，启动回答也更快。OpenAI、Gemini 和 DeepSeek 会自动这样做；Anthropic 则只在请求明确要求时才缓存，而且每次请求都需要说明。Open WebUI 的若干功能会在每一轮重写请求的开头，这会把缓存冲掉。下面的设置可以避免这种情况。

### 推荐的缓存配置 {#recommended-caching-config}

在 **设置 > 模型**（管理员区域） 中选中模型，点击铅笔图标（**编辑**），然后进入 **能力** 与 **内置工具**：

| 设置项 | 推荐值 | 原因 |
|---------|-------------------|-----|
| **系统提示词** | 固定的文本，不随每轮重新生成 | 这是最大的一块可以保持缓存的内容 |
| **预加载文件** | **关闭**，同时保持**文件上传**开启 | 不再向每条消息注入文件内容，模型改用内置文件工具按需读取 |
| **引用** | 可选：**关闭**，并把引用规则写进系统提示词 | 在原生函数调用下引用会保持缓存完好。关闭后请求更小，同时去掉回复下方那些来源标签 |
| **内置工具** | 开启，并启用你需要的分类 | 检索仍按需触发，因此结果会追加在末尾，已缓存的开头不受影响 |
| **函数调用** | **原生** | 旧版模式下不存在内置工具 |
| **记忆** | 使用原生函数调用，每次回复时仅在用户消息之后加入一次检索到的记忆；也可以设置 `ENABLE_MEMORY_SYSTEM_CONTEXT=false`，由模型通过记忆工具自行获取 | 在旧版模式下，记忆会在每一轮追加到用户消息中，并随对话主题变化 |

工具列表本身也要保持稳定。工具定义与系统提示词相邻，同属缓存部分，因此在对话中途切换分类或打开网页搜索，会从那一刻起让缓存失效。语音模式无需特别处理：它的提示词只会前置一次，并在整个会话中保持不变。

更多细节：[提示词缓存（KV Cache）优化](/features/chat-conversations/prompt-caching)。

## 任务模型 {#task-models}

:::info 值得了解
默认情况下，后台任务（标题、标签、追问）会使用你当前的主聊天模型；自动补全在管理员启用之前处于关闭状态，并且需要在 设置 > 界面 中打开 **提示词自动补全**（可由每个用户自行打开，也可由管理员通过默认界面设置为所有人打开）。设置一个专用的任务模型，是提升速度并减少不必要 API 成本最简单的方式。
:::

每当 Open WebUI 需要为某个界面功能做一小段“思考”（为侧边栏撰写聊天的**标题**、生成**标签**、建议**追问消息**、为输入框中的**自动补全**提供动力）时，它都会调用一个**任务模型**。默认情况下，这个任务模型就是你当前正在聊天的主模型，这意味着：

- 每当你新开一个聊天只是为了写一句“购物清单”，你那昂贵的旗舰模型都会被调用一次。
- 在缓慢的本地模型上，每一次按键都会感觉卡顿，因为自动补全正在等待一个 30B 参数的模型。
- 推理模型（o1、r1、开启扩展思考的 Claude）会先花五秒*思考*，然后才给出三个词的标题。

这些任务都在后台运行，因此很容易被忽略。设置一个专用任务模型只是一个小改动，却能带来明显的差别。

**解决办法：** 在 **设置 > 界面**（管理员区域） 中设置专用的任务模型。这里有两个字段，因为正确的选择取决于你的主聊天模型：

:::tip 推荐的任务模型
- **任务模型（外部）**：设置为一个快速、便宜且*非推理*的云端模型，例如 `gpt-5.6-luna`、`gemini-3.5-flash-lite` 或 `deepseek-v4-flash`。
- **任务模型（本地）**：设置为一个小巧的本地模型，例如 `qwen3.5:2b` 或 `qwen3.5:0.8b`。生成标题和标签所需的能力极低，不要为它花上 27B 模型。

主聊天体验不会改变，只是这些后台杂务不再拖后腿。
:::

在这两个选择器下方，**任务模型参数**决定了这些后台请求被允许消耗多少资源。大多数人从不碰它，因此先放着，直到出现异常再调整：参见[任务模型](/features/administration/task-models#task-model-parameters)。

在界面设置中，如果你的机器配置较低，或只是不想要这些功能，你也可以把它们整个关掉。每一项在同一页面里既有**管理员开关**，也有对应的**环境变量**：

| 杂务 | 管理员开关（设置 > 界面） | 环境变量 |
| :--- | :--- | :--- |
| 自动补全 *（每次按键都会触发）* | **自动补全生成** | `ENABLE_AUTOCOMPLETE_GENERATION=False` |
| 追问建议 | **追问生成** | `ENABLE_FOLLOW_UP_GENERATION=False` |
| 聊天标题生成 | **标题生成** | `ENABLE_TITLE_GENERATION=False` |
| 标签生成 | **标签生成** | `ENABLE_TAGS_GENERATION=False` |

:::tip 弱硬件上的性能
自动补全默认关闭。一旦启用，它就是弱硬件上提升流畅度最有效的一个开关。它会在每次按键时触发，因此一个缓慢的任务模型会让整个输入框变得像糖浆一样黏滞。如果界面感觉迟缓，先把它关掉。
:::

更多细节：[任务模型](/features/administration/task-models)以及[性能与内存：专用任务模型](/troubleshooting/performance#1-dedicated-task-models)。

## 上下文管理 {#context-management}

来回对话足够多之后，你最终会看到：

> `The prompt is too long: 207601, model maximum context length: 202751`

:::note 这不是 Open WebUI 的 bug
这个错误来自你的模型提供商，而不是 Open WebUI。每当你发送一条消息时，*整个*对话（系统提示词、此前所有轮次、附件、工具调用结果以及你的新消息）都会作为“提示词”一起发送。当总和超出模型的上下文窗口时，提供商就会拒绝该请求。
:::

### 内置答案：上下文压缩 {#the-built-in-answer-context-compaction}

Open WebUI 正是为此提供了**上下文压缩（Context Compaction）**。一旦某个聊天的估算上下文超过某个 token 阈值，模型就会对较早的消息做摘要，对话随后从该摘要加上最近的消息继续，因此长对话可以持续下去而不是撞墙。它在服务端运行，只改变该轮发送给模型的内容。你的聊天仍被完整存储和完整显示，什么都没有被删除。一条 **Context compacted** 标记会指出较早消息被摘要的位置，点击即可查看摘要。压缩进行期间，聊天会在该位置显示 **Compacting context**，失败时则显示错误。

它**默认关闭**。管理员在 **设置 > 界面**（管理员区域） 中开启它，token 阈值（默认 `80000`）、用于撰写摘要的模型、逐字保留的近期消息比例以及可选的自定义摘要提示词都可以配置。请把阈值设得低于模型真实的上下文窗口。

在依赖它之前，有两点需要知道：

- 超过阈值并不保证一定触发。在一轮开始时，切割点必须落在用户消息上，因此如果一段对话只有一轮极其庞大的交互、没有更早的轮次，它会未经压缩就被发送。这种情况是静默发生的，并会在下一轮重试，所以压缩更像一个泄压阀，而不是硬性上限。一长串工具调用是例外情况：压缩也会在工具轮次之间运行，并且可以在那里切割。
- 在提供商没有上报真实用量之处，token 数字都是估算值，因此请把它当作仪表读数，而不是精确计数。

启用之后，在聊天输入框中输入 `/compact` 可以立即压缩对话，而不必等待阈值触发。

### 当你需要不同的策略时 {#when-you-need-a-different-policy}

压缩采用“摘要并替换”策略。如果需要给聊天长度设硬性上限、先丢弃附件再裁剪对话正文、优先裁剪工具结果，或为不同模型设置不同的上下文窗口，请改用**过滤器函数**。Open WebUI 不提供一刀切的裁剪工具，因为分词器、上下文窗口和合适的策略因模型和部署而异。

:::tip 快速解决
针对最常见策略，社区过滤器已经存在并且可以一键安装。如果没有完全合适的，代码也短到可以直接复制改写。包含一个最小化“最近 N 轮”过滤器在内的完整指南请见：[故障排除：上下文窗口 / 提示词过长](/troubleshooting/context-window)。
:::

更多细节：[上下文压缩](/troubleshooting/context-window#the-built-in-option-context-compaction)一节涵盖了检查点机制、摘要器失败时的回退方案，以及用于显示聊天距离压缩还有多近的 `context_usage` API。

## 基础 RAG {#basic-rag}

**RAG**（检索增强生成）让你可以说“这里有一份 400 页的 PDF，回答我关于它的问题”，而不必让模型每一轮都把整份文档读一遍。Open WebUI 会把你的文档切分成块、把它们嵌入为向量、存入向量数据库，并在对话时只检索相关片段传给模型。

有两种用法，按简单程度排列：

1. **一次性附件。** 把文件拖进任意聊天输入框并提问。该文件会仅为这段对话切分并嵌入。
2. **知识库。** 对于你想在多个对话中复用的文档（公司手册、代码库、研究资料库、用户手册），前往 **Workspace > 知识** 并创建一个知识库。随后你可以把整个知识库附加到某个对话（在输入框中用 `#` 快捷键），或者在 **Workspace > 模型** 中把它绑定到某个模型，让该模型始终可以取用。

默认配置对于起步已经够用。当你觉得不够用时，有三个最关键的调节项：

- **嵌入引擎。** 默认（SentenceTransformers `all-MiniLM-L6-v2`）在本地 CPU 上运行，每个副本大约占用 500 MB 内存。对于任何多用户部署，请通过 `RAG_EMBEDDING_ENGINE` 指向外部嵌入 API（OpenAI，或使用 `nomic-embed-text` 的 Ollama）。
- **内容提取引擎。** 默认使用 `pypdf`，在大量导入时会泄漏内存。如果不只是随便用用，请通过 `CONTENT_EXTRACTION_ENGINE` 切换到 **Tika** 或 **Docling**；如果你需要按文件类型路由或自定义逻辑，也可以用[外部引擎](/features/chat-conversations/rag/document-extraction/external)指向自己的服务。
- **向量数据库。** 默认使用基于本地 SQLite 的 ChromaDB（`:slim` 镜像默认改用 PGVector），不支持多副本部署。扩容时请切换到 **PGVector**，它是唯一由 Open WebUI 团队正式支持和维护的向量数据库。Milvus、Qdrant 和 MariaDB Vector 也可以使用，但它们属于非核心集成，升级时可能失效，由 Open WebUI 核心维护渠道之外的人员修复。配置方法请参阅[环境变量参考](/reference/env-configuration#vector_db)及各提供商的集成免责声明。

:::note 什么时候才需要操心这些
对于“单个用户加几份 PDF”的场景，这些都不重要。它们从你有 100 份文档或 10 个并发用户的那一刻起才开始重要。
:::

### 推荐的起始配置 {#recommended-starting-config}

如果你只想让 RAG 开箱即用地表现良好，下面的设置是一个通用的良好起点。它们并未针对每种用例做精细调优，但相比默认值，对大多数文档类型都能带来明显更好的效果。

在 **设置 > 文档**（管理员区域） 中设置：

| 设置项 | 默认值 | 推荐值 | 原因 |
|---------|---------|-------------------|-----|
| **文本切分器** | `character` | `token` | 基于 token 的切分在不同文档类型下能产生更一致的块大小 |
| **Markdown 标题切分器** | 开启 | **开启** | 按标题切分，尊重文档结构，让各部分保持连贯 |
| **块大小** | `1024` | `2000` | 更大的块在每次检索命中时能保留更多上下文 |
| **块重叠** | `100` | `200` | 更大的重叠意味着把关键句子拦腰截断的概率更低 |
| **Top K** | `10` | `15` | 检索更多候选块，为模型提供更宽泛的相关上下文池。如果你使用的是上下文长度受限的本地模型，可以降到 `5`，避免检索到的块占满上下文窗口 |
| **嵌入模型** | `all-MiniLM-L6-v2`（本地 CPU） | 外部（OpenAI 或 Ollama） | 默认方案对单个用户够用，但每个副本要占用约 500 MB 内存。任何多用户环境都应改用外部嵌入 API |

:::tip 嵌入模型
默认的 SentenceTransformers 模型在本地 CPU 上运行，对刚开始使用的单个用户完全够用。除此之外的场景，请指向外部嵌入 API：设置 `RAG_EMBEDDING_ENGINE=openai` 并提供 OpenAI API key，或设置 `RAG_EMBEDDING_ENGINE=ollama` 并搭配任意 Ollama 嵌入模型（例如 `nomic-embed-text`）。这样可以把这项工作卸载出去，释放可观的内存。
:::

:::tip 增强型智能体 RAG：启用 kb_exec
原生函数调用是默认模式，因此若想要明显更好的知识库体验，请设置 `ENABLE_KB_EXEC=True`。它为模型提供了一个面向你知识库的文件系统式接口（`ls`、`tree`、`grep`、`cat`、按行读取），能力较强的模型串联起这些接口比使用单个搜索工具更可靠，因此更常找到正确的段落。对设置为旧版的模型无效。参见[文件系统式访问](/features/workspace/knowledge#filesystem-style-access-kb_exec)。
:::

## Web 搜索 {#web-search}

模型只知道训练数据里的内容。那份数据有截止日期，也从不包含你所在世界的私密信息（今天的新闻、上个月发布的库、某样东西的当前价格）。**Web 搜索**填补了这一空白：它让模型在回答途中执行实时搜索并阅读结果，使回复引用当前来源，而不是凭陈旧记忆猜测。

它是一个内置工具，无需安装。唯一需要决定的是**使用哪个搜索提供商**，Open WebUI 支持二十多种。它们大致分为两组：

- **自托管、无需 API key。** 运行你自己的搜索后端，让每次查询都留在内部。[**SearXNG**](/features/chat-conversations/web-search/providers/searxng) 是常见选择。
- **商业 API。** [**Tavily**](/features/chat-conversations/web-search/providers/tavily)、[**Brave**](/features/chat-conversations/web-search/providers/brave)、[**Exa AI**](/features/chat-conversations/web-search/providers/exa)、[**Perplexity Search**](/features/chat-conversations/web-search/providers/perplexity_search)、[**Firecrawl**](/features/chat-conversations/web-search/providers/firecrawl) 等，用一把 API key（通常还有账单）换取质量更高、针对 AI 调优的结果。

**启用方式：** 前往 **设置 > 网页搜索**（管理员区域），打开 **启用网页搜索**，然后挑选你的提供商并粘贴对应的 key 或配置。在任意对话中，可以用提示词输入框里的 **+** 按钮为某条消息打开网页搜索。

:::tip 原生函数调用会完成剩下的事
原生模式现在是默认的工具调用模式。在对话中打开网页搜索后，模型会自行判断某个问题是否需要联网，并以工具形式执行搜索。若想让它在每个对话中都可用，请在模型设置的 **默认功能** 下勾选 **网页搜索**。
:::

## Open Terminal {#open-terminal}

如果“运行 Python”太受限，而你希望模型真正在你的机器上干活（克隆仓库、安装软件包、运行测试套件、启动网站本地预览、基于真实 CSV 迭代数据报告），那正是[**Open Terminal**](/features/open-terminal)的用途。它把一个真实的 shell（默认沙箱在 Docker 容器中，也可以按需使用裸机）作为工具连接进来，模型调用它的方式与其他工具完全一致。它还内置了聊天内文件浏览器、实时网页预览和技能定义。

:::tip 试试看
一旦你越过基础聊天阶段，这是最有“顿悟感”的功能。它把 Open WebUI 从一个聊天界面变成了一个模型真正替你构建东西的地方。如果启用了原生模式，并且给模型配了一个能力不错的终端，让它为你构建一个小应用，或者对一个文件目录做一次分析，然后看着它跑起来。
:::

## 接下来做什么 {#what-to-do-next}

你不需要一次把所有内容都做完。对于新装实例，一个合理的顺序是：

1. 挑一个合适的默认模型，聊几次，先熟悉界面。
2. 设置一个任务模型，并决定哪些后台杂务你确实想开启。这是能带来最明显“手感提升”的单项改动，而且直接针对隐藏在每次对话里的成本。
3. 启用你需要的内置工具（网页搜索、图片生成、代码执行、记忆），并安装一两个与你工作相符的社区工具。
4. 第一次看到 “prompt is too long” 时，就安装一个上下文过滤器。
5. 当你想跨多份文档提问时，搭建一个知识库。
6. 让模型接入 Open Terminal，真正替你构建东西。
7. 如果你的使用超出了单用户范围，回头再看 RAG 基础设施那一节。

## 有问题吗？ {#questions}

本页是精简版，完整文档讲得更深。如果你没有找到需要的内容：

- **[在 GitHub Discussions 提问](https://github.com/open-webui/open-webui/discussions)**：适合开放式问题、功能讨论以及“我该怎么做 X？”这类帖子。可搜索，也能让以后遇到同样问题的用户看到。
