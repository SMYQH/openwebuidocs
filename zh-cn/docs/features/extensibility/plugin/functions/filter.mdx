# 🪄 Filter 函数：修改输入和输出 {#filter-function-modify-inputs-and-outputs}

:::danger ⚠️ 关键安全警告
**Filter 函数会在你的服务器上执行任意 Python 代码。** 函数创建仅限管理员。请只从可信来源安装，并在导入前审查代码。恶意函数可能访问文件系统、窃取数据，甚至危及整套系统。完整说明请参阅 [插件安全警告](/features/extensibility/plugin/)。
:::

欢迎阅读 Open WebUI 中 Filter 函数的完整指南！Filter 是一个灵活而强大的 **插件系统**，可以在数据*发送给大语言模型（LLM）之前*（输入）或*从 LLM 返回之后*（输出）修改数据。无论你是在转换输入以获得更好的上下文，还是在清理输出以提升可读性，**Filter 函数**都能帮你完成。

本指南会拆解**Filter 是什么**、它们如何工作、它们的结构，以及构建强大又易用的自定义 Filter 需要知道的一切。我们会一步步讲清楚，并用比喻、示例和技巧让内容尽量一目了然。🌟

---

## 🌊 Open WebUI 中的 Filter 是什么？ {#what-are-filters-in-open-webui}

你可以把 Open WebUI 想象成一条在管道中流动的**水流**：

- **用户输入**和**LLM 输出**就是水。
- **Filters** 则像是**水处理工序**，在水到达最终目的地之前，先对它进行清理、修改和适配。

Filter 位于流程中间，就像检查点一样，你可以在这里决定哪些内容需要被调整。

下面快速总结一下 Filter 的作用：

1. **修改用户输入（Inlet 函数）**：在输入到达 AI 模型之前对其进行调整。你可以在这里增强清晰度、补充上下文、清理文本，或者按照特定要求重新格式化消息。
2. **修改每一次发出的调用（Request 函数）**：在载荷被交给模型提供方之前的最后一刻进行调整，每一次发送都会执行。详见下文的 [`request` 步骤](#the-request-step)。
3. **拦截模型输出（Stream 函数）**：在模型**生成回复的过程中**捕获并调整 AI 的响应。这适合实时修改，例如过滤敏感信息或调整输出格式以提高可读性。
4. **修改模型输出（Outlet 函数）**：在 AI 响应**处理完成后**、展示给用户之前进行调整。这有助于改进、记录或适配数据，为用户提供更清晰的结果。

> **核心概念：** Filter 不是独立模型，而是增强或转换数据的工具，既能处理*发给模型*的数据，也能处理*模型返回*的数据。

Filter 就像 AI 工作流里的**翻译器或编辑器**：你可以在不打断流程的情况下拦截并修改对话内容。

## 🗺️ Filter 函数的结构：骨架 {#structure-of-a-filter-function-the-skeleton}

先从最简单的 Filter 函数表示法开始。别担心，一开始有些部分看起来会有点技术化——我们会一步一步拆开讲。

### 🦴 Filter 的基本骨架 {#basic-skeleton-of-a-filter}

``` python
from pydantic import BaseModel
from typing import Optional

class Filter:
    # Valves: Configuration options for the filter
    class Valves(BaseModel):
        pass

    def __init__(self):
        # Initialize valves (optional configuration for the Filter)
        self.valves = self.Valves()

    async def inlet(self, body: dict) -> dict:
        # This is where you manipulate user inputs.
        print(f"inlet called: {body}")
        return body

    async def request(self, body: dict) -> dict:
        # This is where you manipulate the payload for each outgoing model call.
        print(f"request called: {body}")
        return body

    async def stream(self, event: dict) -> dict:
        # This is where you modify streamed chunks of model output.
        print(f"stream event: {event}")
        return event

    async def outlet(self, body: dict) -> dict:
        # This is where you manipulate model outputs.
        print(f"outlet called: {body}")
        return body
```

### `request` 步骤 {#the-request-step}

`request` 接收即将发送给模型服务商的载荷，它返回什么就发送什么。

```python
    async def request(self, body: dict, __user__: Optional[dict] = None) -> dict:
        body["metadata"] = {**body.get("metadata", {}), "department": "research"}
        return body
```

#### 它与 `inlet` 的区别 {#how-it-differs-from-inlet}

`inlet` 每个用户轮次运行**一次**。`request` 每次**调用模型**运行一次，而这两者并不是同一个次数。

如果一轮对话使用了工具，就会多次调用模型：先决定使用哪个工具，然后每返回一组工具结果就再调用一次，直到模型给出最终答案。`inlet` 只处理第一次调用前的输入。`request` 会在每次调用前运行，也包括需要用户批准的工具运行后的那次调用。用户批准后，`request` 过滤器还会在获准的工具执行之前运行，因此仍可在工具产生任何影响之前拒绝请求。

这个区别决定了你该用哪一个：

| 何时使用 `inlet` | 何时使用 `request` |
| :--- | :--- |
| 你要对用户输入的内容做出反应 | 你要对发出的请求强制执行某些约束 |
| 每轮运行多次逻辑是错误的，例如计费、限流或记录某一轮 | 每次调用都运行正是目的，例如为参数打标记、注入请求头或脱敏内容 |
| 你想修改用户的消息 | 你想修改整个请求，无论其中的消息来自用户、模型还是工具 |

在 `inlet` 中添加的内容会到达第一次调用，并且随着后续调用重建消息列表而可能被丢弃。而在 `request` 中添加的内容按其定义必然出现在每次调用中，因此强制性的约束应放在这里。

#### `request` 在流水线中的位置 {#where-request-sits-in-the-pipeline}

`inlet` 在这一轮接近开头处运行；`request` 在末尾运行，作用于即将发出的载荷。流水线所做的一切都发生在两者之间，这会改变你拿到的 `body` 里有什么。

**等到 `request` 运行时已经消失的东西。** 在 `inlet` 返回之后，流水线会把若干键从 body 中弹出：`features`、`tool_ids`、`terminal_id`、`files`、`folder_id` 和 `skill_ids`。需要其中任何一项的过滤器只能写成 `inlet`。`variables`、`regeneration_prompt` 和 `params` 被弹出的时间更早，在 `inlet` 运行之前就已移除，而 `variables` 仍可通过 `__metadata__["variables"]` 读取。（`features` 在 `request` 中仍可通过保留参数 `__features__` 取到，因为流水线在弹出该键之前会把它另存一份；其余的则不行。）

**等到 `request` 运行时才存在的东西。** 用 `<source>` 标签包裹的 RAG 检索 chunk、解析完成的 `tools` 数组（服务端工具与过滤器或调用方添加的内容合并而成）、聊天自身的系统消息与文件夹系统提示词（工作区模型自己的 System Prompt 是在 `request` 返回之后由 provider 路由添加的），以及网页搜索上下文，在旧版函数调用下还包括记忆上下文。在原生函数调用下，召回的记忆、技能列表和附加的知识列表会在 `inlet` 和第一次 `request` 调用之后以隐藏的工具结果形式加入，因此 `inlet` 永远看不到它们，而 `request` 从一次回复的第二次调用起会以工具消息的形式看到它们。如果你想读取或改写的是*检索到的 chunk 文本*而不是文件引用，`request` 原生就能看到，无需 `file_handler` 开关，也不需要自己写检索代码。这通常比[自行接管检索](#owning-retrieval-with-file_handler)更简单：当你要*替换*检索方式时用 `file_handler`，只需要转换检索结果时用 `request`。

提供商消息格式的归一化发生在 `request` 返回之后，因此你看到的仍然是 Open WebUI 的内部消息结构，而不是提供商的。

#### 幂等写法 {#write-it-to-be-idempotent}

这一点最容易踩坑。由于 `request` 在工具循环的每一跳都会再次运行，而每一跳都会把**整个对话**重新过一遍你的过滤器，因此你做的任何改动都必须能够安全地应用在一个你已经改过的 body 上。

```python
# WRONG: a three-tool-call turn ends with four copies of this line.
async def request(self, body: dict) -> dict:
    body["messages"].insert(0, {"role": "system", "content": "Be concise."})
    return body

# RIGHT: converges to the same body no matter how many times it runs.
async def request(self, body: dict) -> dict:
    marker = "Be concise."
    if not any(
        m.get("role") == "system" and marker in str(m.get("content", ""))
        for m in body["messages"]
    ):
        body["messages"].insert(0, {"role": "system", "content": marker})
    return body
```

要检查系统消息是否**包含**你的文本，而不是是否与它完全相等。每次调用模型之前，Open WebUI 会把所有系统消息合并成一条，因此在下一跳中，只要聊天里还有另一条系统消息（例如聊天自身的 system prompt、文件夹的 prompt，或另一个过滤器添加的），你那一行就会成为更长消息的一部分。等值判断在那种情况下会漏掉它，于是每一跳都会再加一遍。

天然幂等的转换不需要额外保护，例如限制数值范围、将超限图片缩小到上限以内，或遮盖处理后就不再匹配的文本。在末尾或开头添加内容、递增数值或累积数据时，则需要防止重复处理。如果必须保证每轮只运行一次，请使用 `inlet`。

#### 其它需要留意的地方 {#other-things-to-watch-for}

`request` 会在每一次提供商调用时运行，因此其中任何昂贵操作都会在同一次回答内被反复付出代价。由于每次调用都要重新扫描完整历史，成本会随对话长度和工具调用次数一起增长。如果这部分工作很重，可以按内容哈希做缓存。

抛出异常的后果取决于所在的钩子。从 `inlet` 抛出，或从一轮中的第一次 `request` 调用抛出，会中止这一轮；从工具循环后续某跳的 `request` 抛出，则会以错误结束循环，而已经流式输出的内容保留；从 `stream` 抛出，在 WebUI 路径中会丢掉那一个事件，但对直接调用 API 流式接口的调用方则会结束整个流；从 `outlet` 抛出，只会在 debug 级别记录日志并被忽略，只有经由 `/api/chat/completed` 时才会变成 HTTP 400。如果你的过滤器在遇到格式错误的输入时可能失败，而你更希望降级而不是毁掉整个回答，请自己捕获异常并原样返回 body。

`file_handler` 对 `request` 过滤器无效；参见[下面的说明](#owning-retrieval-with-file_handler)。

`inlet`、`stream` 和 `outlet` 都没有变化，未定义 `request` 的过滤器行为与之前完全一致。

### 🧲 可切换 Filter：让用户掌控 Filter 是否启用（`self.toggle`） {#toggleable-filters-making-filters-user-controllable-selftoggle}

默认情况下，只要 Filter **处于激活状态且在作用范围内**（全局，或附加到当前模型），它就会在每次请求时执行——用户对此没有控制权。这在很多场景下正是你想要的（PII 清洗、日志、强制的安全护栏）。但有时你希望反过来：让用户自己决定某个 Filter 是否在本次会话中运行。

把 `self.toggle = True` 设置上，就能让 Filter **变成可由用户控制**。随后它会作为聊天输入框 **+** 菜单中的一个开关出现，并且只在用户选中它的请求上运行。

```python
from pydantic import BaseModel, Field
from typing import Optional

class Filter:
    class Valves(BaseModel):
        pass

    def __init__(self):
        self.valves = self.Valves()
        self.toggle = True   # Make this filter user-controllable (see notes below)
        # TIP: Use a hosted URL for your icon instead of base64 to avoid API payload bloat.
        # See the Action Function docs for details on why base64 icons are not recommended.
        self.icon = "https://example.com/icons/lightbulb.svg"

    async def inlet(
        self, body: dict, __event_emitter__, __user__: Optional[dict] = None
    ) -> dict:
        # This method ONLY runs when the filter is currently selected by the user.
        # You do NOT need to branch on self.toggle inside here. See the note below.
        await __event_emitter__(
            {
                "type": "status",
                "data": {"description": "Running!", "done": True, "hidden": False},
            }
        )
        return body
```

#### `self.toggle = True` 到底做了什么 {#what-selftoggle--true-actually-does}

它是一个**可见性 / 门控标志**，在请求分发时读取一次——**并不是**运行时由 UI 翻转的 Python 对象状态。具体来说：

- **可见性：** 只有当 `self.toggle = True` **并且** Filter 是全局 Filter 或已附加到当前选中的模型时，该 Filter 才会出现在聊天 UI（**+** 菜单条目及其标签）中。没有 `self.toggle`，Filter 仍会运行（如果处于激活且在作用范围内），但没有 UI 入口——用户无法关闭它。
- **门控：** 在请求时，后端会检查用户当前的 `filter_ids` 选择。如果 Filter 在该列表中，则 `inlet()` / `request()` / `stream()` / `outlet()` 会被调用；否则，**Filter 根本不会被调用**。
- **`self.toggle` 永远不会被 UI 修改。** 在 `inlet()` 内部，它始终是你在 `__init__` 中设置的值——对于每次实际运行的调用，它都是 `True`，因为如果用户禁用了该 Filter，`inlet()` 就不会执行。不要在运行时读取 `self.toggle` 来做逻辑判断；它不是实时的开关信号。

:::warning 从 0.9.0 之前的 Filter 升级
一些旧版 Filter 使用了类似 `if self.toggle: enable_feature() else: disable_feature()` 这样的模式放在 `inlet()` 内，期望在每次请求时读取 UI 状态。**该模式从未可靠，在 0.9.0+ 上实际上已失效。** 当 UI 中禁用了 Filter，`inlet()` 根本不会被调用，因此不会有 "else" 分支。正确的迁移方式是完全停止对 `self.toggle` 的分支判断，直接无条件地执行逻辑——用户通过开启/关闭该 Filter 来控制 `inlet()` 是否运行。如果你需要用户驱动的配置（数字阈值、目标语言等），请通过 [`UserValves`](#filter-administration--configuration) 暴露；用户可以从该 Filter 的 **Valves** 按钮打开它。
:::

#### 用户如何与可切换 Filter 交互 {#how-users-interact-with-a-toggleable-filter}

当一个可切换 Filter 在当前聊天的作用范围内时，它会出现在两个地方：

- **聊天输入栏的 + 菜单。** 列出作用范围内的每个可切换 Filter，并显示它的 `self.icon`、名称以及开/关**开关**。如果该 Filter 定义了 `UserValves` 类，菜单里还会有一个 **Valves** 按钮。
- **+ 按钮旁边的标签**，仅当用户在 **设置 > 界面** 中开启了 **Show Input Selections** 时才会显示（默认关闭）。它会为每个被选中的 Filter 显示一个。点击它：如果该 Filter 定义了 `UserValves` 就打开用户 valves 模态框，否则把它从选中列表中移除；悬停时出现的 **x** 始终会移除它。

开关处于开启状态的 Filter 会在下一次请求时运行。

#### 选中状态存储在哪里 {#where-the-selection-lives}

- 以**浏览器 sessionStorage 草稿状态**形式存储，按聊天区分。
- 在同一浏览器会话中页面刷新后仍然存在，但**不会持久化到服务器上的聊天记录**。
- 初始状态来自模型的 `defaultFilterIds`（Settings > Models → 编辑模型 → **Filters** → **在新对话中默认启用**（管理员区域））——管理员决定每个模型的哪些可切换 Filter 默认**开启**或**关闭**。
- 切换模型时会应用新模型的默认 Filter，并保留用户自己开启或关闭的那些。

![Toggle Filter](/images/features/plugin/functions/toggle-filter.png)

`self.icon` 接受一个 URL（强烈推荐）或 base64 data URI，并同时渲染在 **+** 菜单条目和标签上。关于为何更推荐托管 URL 而不是 base64，请参阅 [Action Function icon_url 警告](/features/extensibility/plugin/functions/action#example-specifying-action-frontmatter)。

### 🛠️ 通过 file_handler 接管检索 {#owning-retrieval-with-file\_handler}

当用户在聊天中挂载知识库或上传文件，并且模型的 **Preload files** 能力处于开启状态（使用 Legacy function calling 时默认开启）时，Open WebUI 会在**所有 inlet filter 全部返回之后**才运行内置 RAG 流程：chat-completion 处理程序会基于用户的最后一条消息在向量库中查询相关 chunk，把它们包进 `<source>` 标签，再追加到最后一条用户消息（或者，根据 `RAG_SYSTEM_CONTEXT`，追加到系统消息）中，最后才调用 LLM。

这一点对 filter 编写者来说很关键：在 `inlet()` 时刻，`body["metadata"]["files"]` 和 `body["files"]` 里只有文件和知识库的*引用*（ID、名称、类型）。**真正的 chunk 文本此刻还不存在**：检索还没发生。因此，如果你想检查或改写这些 chunk 本体（PII / PHI 脱敏、重排序、自定义混合打分、翻译、chunk 级访问控制、匿名化），标准的 inlet 契约还不够，因为此时没有所需数据。

**`file_handler = True`** 正是为这种场景准备的“自助”开关。它声明在 `Filter` 实例上——可以是在 `__init__` 中写成 `self.file_handler = True`，也可以写成类属性——含义是告诉 Open WebUI：“我自己来处理检索和 chunk 注入——请跳过内置 RAG 步骤。”一旦开启，后端会在你的 `inlet()` 返回后剥离 `body["metadata"]["files"]` 和 `body["files"]`，于是 chat-completion 处理程序找不到可检索的文件，就会带着你注入的内容直接调用 LLM。

``` python
from pydantic import BaseModel
from typing import Optional

class Filter:
    class Valves(BaseModel):
        pass

    def __init__(self):
        self.valves = self.Valves()
        # Read from the instance before each inlet() call.
        self.file_handler = True

    async def inlet(
        self,
        body: dict,
        __request__=None,
        __user__: Optional[dict] = None,
        __model__: Optional[dict] = None,
    ) -> dict:
        # body["metadata"]["files"] still contains the file and knowledge base REFERENCES here.
        # After this method returns, Open WebUI strips them and does NOT run its own RAG.
        # Therefore: it is YOUR job to retrieve, transform, and inject chunks below.
        return body
```

:::warning 它是实例属性，不是模块级变量
Open WebUI 从 `Filter` 实例上读取 `file_handler`，读取方式与读取 `toggle` 和 `icon` 完全一样。在文件顶部裸露地写 `file_handler = True` 会被静默忽略。请在 `__init__` 中写 `self.file_handler = True`，或者像上面示例那样声明为类属性。
:::

:::note `file_handler` 只对 `inlet` 生效
这个标志只会在 `inlet` 这一遍被读取，文件引用也只会在所有 `inlet` filter 运行完之后才被剥离。如果你的模块里定义的 filter 只实现了 `request`（或 `stream` / `outlet`），那么声明 `file_handler = True` 完全不起作用：内置 RAG 照样运行，也不会剥离任何键。如果你的目标是转换检索到的 chunk 而不是替换检索本身，其实并不需要这个标志——`request` filter 本来就能拿到注入之后的 chunk。参见[`request` 在流水线中的位置](#where-request-sits-in-the-pipeline)。
:::

#### 适用场景 {#when-to-use-it}

- **按模型脱敏。** 只有当请求目标是远端模型时才对 PII / PHI 做脱敏，让自托管模型看到原始 chunk。可以在 inlet 内根据 `__model__["owned_by"]`（或其他信号）分支判断后再改写 chunk。
- **自定义检索逻辑。** 混合 BM25 + dense 打分、查询改写、多集合路由、用与 Open WebUI 默认不同的模型做重排序、基于改写后查询做结果缓存。
- **注入前变换。** 翻译、摘要、去重，或任何需要*实际 chunk 文本*而不仅仅需要引用的转换。
- **chunk 级访问控制。** 根据源文档上附带的元数据，过滤掉当前用户不应看到的 chunk。

#### 完整步骤 {#the-recipe}

1. 按上方示例，将 `file_handler = True` 设为实例属性或类属性，不要设为模块级变量。
2. 在 `inlet()` 中，从 `body["metadata"]["files"]`（以及临时挂载的 `body["files"]`）读取文件引用。
3. 自行检索 chunk。两种方式：
   - **HTTP 方式**：调用 `POST /api/v1/retrieval/query/doc`（单集合）或 `POST /api/v1/retrieval/query/collection`（多集合），把用户最后一条消息作为查询串，并传入请求里的 bearer token，使权限仍受用户范围限制。
   - **进程内方式**：`from open_webui.retrieval.utils import get_sources_from_items`，并使用与核心代码相同的参数直接调用。这样可省去一次网络往返，且返回结构更干净（一个 list，每个元素是包含 `document` chunk 数组与平行 `metadata` 数组的 dict）。
4. 按需转换 chunk。如果转换是条件式的（例如“只对远端模型脱敏”），则按 `__model__` / `__user__` 分支处理。
5. 把转换后的 chunk 重新注入到 `body["messages"]`。若希望 UI 中保留可点击的引用，请使用与 Open WebUI 内部一致的格式：

   ```html
   <source id="1" name="filename.pdf" resource-id="<collection_id>" resource-type="collection">
   ...chunk text...
   </source>
   ```

   如果你不在意 UI 中的引用是否可点击，纯 Markdown 也能用——只有结构化的 `<source>` 形式才会把引用的弹出框接上。
6. 返回 `body`。由于 `file_handler` 引发了文件引用被剥离，内置 RAG 步骤被跳过，LLM 调用会带着你清洗过的 chunk 直接发出。

#### 注意：它对 filter 是“静态、全有或全无”的 {#caveat-its-static-all-or-nothing-per-filter}

`file_handler` 是在每次 `inlet()` 调用之前从缓存的 `Filter` 实例中读取的。它不是 per-request 信号：在 `inlet()` 内部改动的值会从下一次请求开始生效，而不是作用于当前正在处理的那一次；你也不能根据当前请求的 model、user 或 chat 来翻转它。一旦设置，只要这个 filter 被调用，对应的请求就**总会**跳过内置 RAG——无论你那次 `inlet()` 是否真的执行了检索逻辑。

实际含义是：只要你用了 `file_handler = True`，你的 filter 就必须**穷尽**内置路径会处理的所有检索场景，包括那些你本来觉得用默认行为就行的场景。检索调用本身在两种路径下是相同的；只有“条件式的*转换*”（例如“只对远端模型脱敏”）按上下文分支。

如果确实需要按请求切换检索方式，例如让同一模型的部分用户使用内置 RAG，其他用户使用自定义检索，可为实现自定义 RAG 的 Filter 设置 `self.toggle = True`。它只在用户选中时运行。未选中时，它不会运行，`file_handler` 也不生效，请求仍由内置 RAG 正常处理。不要在 `inlet()` 中动态修改 `file_handler`，因为调用该方法之前就会从模块对象读取此标志。

#### 与“在 inlet 中改 `body["files"]`”相比，这为什么重要 {#why-this-matters-compared-to-mutating-bodyfiles-in-inlet}

另一种朴素做法是直接在 `inlet()` 里清空 `body["metadata"]["files"] = []` 和 `body["files"] = []` 来动态抑制内置 RAG。这在实践中是有效的，但很脆弱：未来 Open WebUI 版本可能会在新的键上挂更多文件/知识库相关逻辑，而“我自己处理”的官方契约就是 `file_handler`。请优先使用文档化的开关。

## ⚙️ Filter 管理与配置 {#filter-administration--configuration}

### 🌐 全局 Filter 与模型专属 Filter {#global-filters-vs-model-specific-filters}

Open WebUI 提供了一个灵活的多层级 Filter 系统，可让你控制哪些 Filter 处于激活状态、如何启用它们，以及谁可以切换它们。理解这个系统对高效管理 Filter 至关重要。

#### Filter 激活状态 {#filter-activation-states}

Filter 在数据库中由两个布尔标志控制，可以处于四种状态之一：

| 状态 | `is_active` | `is_global` | 影响 |
|-------|------------|------------|--------|
| **全局启用** | ✅ `True` | ✅ `True` | 自动应用于 **所有** 模型，且无法在单个模型上禁用 |
| **全局禁用** | ❌ `False` | `True` | 不会应用到任何地方——尽管它被设为全局，Filter 本身仍处于禁用状态 |
| **模型专属** | ✅ `True` | ❌ `False` | 只应用到管理员明确启用它的模型 |
| **未激活** | ❌ `False` | ❌ `False` | 不会应用到任何地方，即便管理员已在模型上启用它——Filter 本身处于关闭状态 |

:::tip 全局 Filter 的行为
当某个 Filter 被设为**全局**（`is_global=True`）且**激活**（`is_active=True`）时，它会对所有模型**强制启用**：
- 它会在每个模型的 Filter 列表中显示为**已勾选且灰显**
- 管理员**无法**在模型设置中取消勾选它
- 无论模型是什么，它都会在**每一次**聊天补全请求中运行
:::

#### 管理面板：将 Filter 设为全局 {#admin-panel-making-a-filter-global}

**位置：** 管理面板 → Functions

要将 Filter 设为全局：
1. 打开管理面板
2. 点击侧边栏中的 **Functions**
3. 在列表中找到你的 Filter
4. 点击该 Filter 旁边的 **三点菜单（⋮）**
5. 切换该菜单中的 **全局** 开关
6. 确保该 Filter 也处于**激活**状态（绿色开关）

**API 端点：**
```http
POST /api/v1/functions/id/{filter_id}/toggle/global
```

**视觉标识：**
- 🟢 绿色开关 = `is_active=True`（Filter 处于激活状态）
- 列表本身不会显示该 Filter 是否为全局。打开 ⋮ 菜单查看 **全局** 开关。

### 🎛️ 双层 Filter 系统 {#the-two-tier-filter-system}

Open WebUI 使用一个复杂的双层系统来按模型管理 Filter。乍看可能有点绕，但它的设计目标是同时支持**始终启用的 Filter**和**用户可切换的 Filter**。

#### 第一层：FiltersSelector（哪些 Filter 可用？） {#tier-1-filtersselector-which-filters-are-available}

**位置：** 模型设置中的 **Filters** 行

它控制某个特定模型有哪些 Filter **可用**。

**行为：**
- 打开可搜索的选择器，列出**所有** Filter（全局与模型专属）
- **全局 Filter** 标记为 **Global**，不可点击
- **普通 Filter** 可通过点击来添加或移除
- 保存到数据库中的 `model.meta.filterIds`

**示例：**
```json
{
  "meta": {
    "filterIds": ["filter-uuid-1", "filter-uuid-2"]
  }
}
```

#### 第二层：DefaultFiltersSelector（哪些可切换 Filter 默认启用？） {#tier-2-defaultfiltersselector-which-toggleable-filters-start-enabled}

**位置：** 模型设置中的 **Filters** 行，使用 **Start enabled in new chats** 开关

每个已选中或全局启用且可切换的 Filter 下方都会显示此开关。

**用途：** 控制哪些可切换 Filter 在新聊天中**默认启用**。

**什么是“可切换” Filter？**

当某个 Filter 的 Python 代码包含以下内容时，它就变成可切换的：
```python
class Filter:
    def __init__(self):
        self.toggle = True  # This makes it toggleable!
```

**行为：**
- 只显示 `toggle=True` 的 Filter
- 只显示以下两类 Filter：
    - 在 `filterIds` 中（该模型已选中），或者
    - `is_global=true`（全局启用）
- 控制聊天 UI 中该 Filter 默认是**开启**还是**关闭**
- 保存到：`model.meta.defaultFilterIds`

**示例：**
```json
{
  "meta": {
    "filterIds": ["filter-uuid-1", "filter-uuid-2", "filter-uuid-3"],
    "defaultFilterIds": ["filter-uuid-2"]
  }
}
```

**解读：**
- 这三个 Filter 都对该模型可用
- 只有 `filter-uuid-2` 会默认启用
- 如果 `filter-uuid-1` 和 `filter-uuid-3` 的 `toggle=True`，用户就可以在聊天 UI 中手动启用它们

---

### 🔄 可切换的过滤器与始终启用的过滤器 {#toggleable-filters-vs-always-on-filters}

理解这两类 Filter 的差异，是高效使用 Filter 系统的关键。

#### 始终启用的 Filter（没有 `toggle` 属性） {#always-on-filters-no-toggle-property}

**特点：**
- 只要该 Filter 对某个模型处于激活状态，就会自动运行
- 在聊天界面中**没有用户控制**
- 模型的 **Filters** 行中没有 **Start enabled in new chats** 开关
- **不会**显示在聊天输入框的 **+** 菜单中

**适用场景：**
- **内容审核** —— 过滤脏话、仇恨言论或不当内容
- **PII 清理** —— 协助隐藏邮箱、电话号码、SSN、信用卡号
- **提示注入检测** —— 阻止试图操纵系统提示的行为
- **输入/输出日志** —— 跟踪所有对话以便审计或分析
- **成本跟踪** —— 估算并记录 token 使用量，便于计费
- **限流** —— 对单个用户或全局执行请求限制
- **语言约束** —— 确保回复使用指定语言
- **公司政策执行** —— 注入法律免责声明或合规通知
- **模型路由** —— 根据内容将请求重定向到不同模型

**示例：**
```python
class ContentModerationFilter:
    def __init__(self):
        # No toggle property - this is an always-on filter
        pass

    async def inlet(self, body: dict) -> dict:
        # Always scrub PII before sending to model
        last_message = body["messages"][-1]["content"]
        body["messages"][-1]["content"] = self.scrub_pii(last_message)
        return body
```

#### 可切换的 Filter（`toggle=True`） {#toggleable-filters-toggletrue}

**特点：**
- 在聊天输入框的 **+** 菜单中显示为**开关**。开启 **Show Input Selections** 时，它还会在 **+** 按钮旁显示为标签。
- 用户可在各个聊天的当前会话中将其加入或移出启用列表。选中状态保存在浏览器的 sessionStorage 中，不会写入服务器上的聊天记录。
- 模型的 **Filters** 行中有 **Start enabled in new chats** 开关。
- 模型上的 `defaultFilterIds` 控制**初始选中状态**（哪些可切换 Filter 在新聊天开始时默认开启）。
- `self.toggle` 本身**永远不会被运行时改写**——它只是一个在请求分发时读取一次的可见性/门控标志。`inlet()` 只会在 Filter 当前被选中时执行，没有“else”分支可写。详见上面的[说明](#what-selftoggle--true-actually-does)。

**适用场景：**
- **Web 搜索集成** —— 由用户决定何时搜索网页以获取上下文
- **引用模式** —— 由用户控制何时在回复中要求来源
- **详细/啰嗦模式** —— 用户在简洁和详细回复之间切换
- **翻译 Filter** —— 用户启用特定语言之间的翻译
- **代码格式化** —— 用户决定何时应用语法高亮或 lint
- **思考/推理开关** —— 用户通过启用/禁用 Filter 来切换底层模型的思考模式（在 `inlet()` 中无条件执行即可；用户通过开关来关闭）
- **Markdown 渲染** —— 在原始文本与格式化输出之间切换
- **匿名化模式** —— 用户在讨论敏感话题时启用
- **专家模式** —— 注入领域上下文（法律、医疗、技术）
- **创意写作模式** —— 为创意任务调整 temperature 和风格

**示例：**
```python
class WebSearchFilter:
    def __init__(self):
        self.toggle = True  # Make user-controllable
        self.icon = "https://example.com/icons/web-search.svg"

    async def inlet(self, body: dict, __event_emitter__) -> dict:
        # This only runs when the user has this filter selected.
        # Do NOT branch on self.toggle here; it's always True when this runs.
        await __event_emitter__({
            "type": "status",
            "data": {"description": "Searching the web...", "done": False}
        })
        # ... perform web search ...
        return body
```

**可切换 Filter 出现的位置：**

1. **模型设置 → Filters → 在新聊天中默认启用**
   - 管理员决定哪些可切换 Filter 在使用该模型的新聊天中默认处于选中状态。
2. **聊天输入栏 → + 菜单**
   - 列出当前模型作用范围内所有可切换的 Filter，每个都有一个正式的开/关**开关**；当该 Filter 定义了 `UserValves` 时还会显示一个 **Valves** 按钮。
3. **聊天输入栏 → + 按钮旁边的标签**
   - 仅当 **设置 > 界面** 中的 **Show Input Selections** 开启时，才会为用户选中列表中的每个可切换 Filter 显示标签。
   - 点击标签会**打开用户 valves 模态框**（若该 Filter 定义了 `UserValves`），否则**将该 Filter 从当前选中状态中移除**。
   - `self.icon` 会作为标签图片渲染。

### 📊 Filter 执行流程 {#filter-execution-flow}

下面是从管理员配置到 Filter 执行的完整流程：

**1. 管理面板（Filter 创建与全局设置）**
- 管理面板 → Functions → 创建新的 Function
- 设置 type="filter"
- 切换 is_active（全局启用/禁用该 Filter）
- 切换 is_global（应用到所有模型）

**2. 模型配置（按模型选择 Filter）**
- 模型设置 → **Filters** 行
- Filters 选择器：选择该模型要使用的 Filter
- **在新会话中默认启用**开关：设置默认启用状态（仅对可切换的 Filter 有效）

**3. 聊天界面（用户交互，仅限可切换的 Filter）**
- 聊天输入框 → **+** 菜单 → 逐个切换可切换的 Filter
- 聊天输入框 → 打开 **Show Input Selections** 时，每个已选 Filter 都会显示一个标签（点击标签会打开 UserValves 弹窗；若没有定义，则移除该 Filter）
- 前端在 sessionStorage 中跟踪 `selectedFilterIds`（按聊天、按会话分别保存）
- 初始选中项由模型的 `defaultFilterIds` 播种
- 始终启用的 Filter（没有 `self.toggle`）会自动运行，没有任何界面控件

**4. 请求处理（Filter 编译）**
- 前端会随请求发送当前的 `selectedFilterIds`
- 后端：`get_sorted_filter_ids(request, model, filter_ids)`
- 获取全局 Filter（`is_global=True`、`is_active=True`）以及来自 `model.meta.filterIds` 的模型专属 Filter
- 按 `is_active` 状态过滤
- **对于可切换的 Filter：** 只保留 ID 出现在请求 `filter_ids` 中的那些。其余的会被完全丢弃（不会被调用，`self.toggle` 也不会被读取）
- 按优先级排序（来自 valves）

**5. Filter 执行**
- 执行 inlet() Filter（每轮开始时执行一次）
- 执行 request() Filter（紧接在请求负载发往提供商之前）
- 把修改后的请求发送给 LLM
- 执行 stream() Filter（在流式传输过程中）
- 该轮后续的每一次调用（例如工具结果返回之后）都重复执行 request() 与 stream()
- 执行 outlet() Filter（在最终响应之后执行一次）

:::note 后台任务调用会跳过 Filter 函数
过滤器只在聊天请求中运行。Open WebUI 的后台调用，例如在 [task model](/features/administration/task-models) 上进行的标题、标签、后续提示、查询、自动补全、表情和图像提示词生成，以及上下文压缩、记忆复核和 **Legacy** 工具选择，都不会运行任何 Filter 函数的 `inlet()`、`request()`、`stream()` 或 `outlet()`，全局过滤器也不例外。过滤器无法读取或修改这些提示词及其回复。

若要介入任务调用，请把 [Pipe](/features/extensibility/plugin/functions/pipe) 设为 task model。它从 `__task__` 读取任务名称。另一个选择是 Pipelines 过滤器：标题、标签、后续提示、查询、自动补全、表情和图像提示词调用会为 task model 运行 Pipelines 的 inlet 过滤器，但不会运行 outlet 过滤器。上下文压缩、记忆复核和 **Legacy** 工具选择两者都不会运行。
:::

### 📡 Filter 在 API 请求中的行为 {#filter-behavior-with-api-requests}

当你直接使用 Open WebUI 的 API 端点（例如通过 `curl` 或外部应用）时，`inlet()`、`request()` 和 `stream()` 的执行模型与 WebUI 请求相同。真正不同的是 `outlet()`：它在直接 API 调用时的行为会有明显差异，下面会详细说明。

#### 关键行为差异 {#key-behavioral-differences}

| 函数 | WebUI 请求 | 直接 API |
|----------|--------------|------------|
| `inlet()` | 始终调用 | 始终调用 |
| `request()` | 在每次调用提供商之前执行 | 在每次调用提供商之前执行 |
| `stream()` | 在流式传输期间调用 | 在流式传输期间调用 |
| `outlet()` | 在响应之后调用 | 默认运行，由 `ENABLE_API_OUTLET_FILTERS` 控制（见下文） |
| `__event_emitter__` | 显示界面反馈 | 在 `inlet()` 和第一次 `request()` 中是一个真实但不可见的可调用对象，在 `stream()` 和 `outlet()` 中为 `None` |

:::info 直接 API 调用时的 outlet()
对于直接调用 `/api/chat/completions` 的客户端，`outlet()` **默认会运行**，在**非流式和流式两条路径上**都会运行，由 [`ENABLE_API_OUTLET_FILTERS`](/reference/env-configuration#enable_api_outlet_filters) 控制（默认 `True`）。在流式路径上，服务端会先累积完整响应，等流结束后再运行一次 `outlet()`。把 `ENABLE_API_OUTLET_FILTERS=False`，即可在直接 API 流量中跳过 outlet 过滤器。

**响应可见性：** `outlet()` 的副作用会执行（更新数据库、调用 `__event_emitter__`、发起诸如日志/追踪之类的外部调用），但它**不会**改写 HTTP 响应体；而且在流式路径上，`outlet()` 触发时流式客户端早已收到了流内容。要观察 `outlet()` 的输出，请回读聊天记录、订阅 `chat:outlet` WebSocket 事件，或者改用 `/api/chat/completed`。对于纯 API 调用方，`outlet()` 中的 `__event_emitter__` 为 `None`。
:::

#### 通过 `__metadata__` 实现 Inlet ↔ Outlet 关联 {#inlet--outlet-correlation-via-\_\_metadata\_\_}

`__metadata__` 是贯穿请求生命周期的可变字典。在 `inlet()` 中存入的值可在*同一请求*的 `outlet()` 中读取。这适合记录开始时间、关联 ID 或单次调用的 valves，*前提是 `outlet()` 确实运行*。这适用于 WebUI 请求和直接调用 `/api/chat/completions` 时的内联 outlet：同一个字典对象从 `inlet()` 传到 `outlet()`。但这不适用于 `/api/chat/completed`，该端点会新建一个 metadata 字典，其中只有 `chat_id`、`message_id`、`filter_ids`、`session_id` 和 `user_id`。

```python
import time
from pydantic import BaseModel, Field

class Filter:
    class Valves(BaseModel):
        priority: int = Field(default=0)

    def __init__(self):
        self.valves = self.Valves()

    async def inlet(self, body: dict, __metadata__: dict = None) -> dict:
        if __metadata__ is not None:
            __metadata__["_my_started_at"] = time.monotonic()
        return body

    async def outlet(self, body: dict, __metadata__: dict = None) -> dict:
        if __metadata__ is not None and "_my_started_at" in __metadata__:
            duration = time.monotonic() - __metadata__["_my_started_at"]
            print(f"request took {duration:.3f}s")
        return body
```

:::warning 在 `inlet()` 中伪造 `chat_id` / `message_id` 并不可靠
在 `inlet()` 内部设置一个编造的 `chat_id` 和 `message_id`，并不会把 `outlet()` 的输出返回给纯 API 调用方。聊天归属检查在 Filter 管道之前执行，而内联 outlet handler 也不会改写 HTTP 响应体。如果你需要通过 HTTP 把 `outlet()` 的输出交给 API 调用方，请改用 `/api/chat/completed`。
:::

#### 为 API 调用方运行 outlet()：`/api/chat/completed` {#running-outlet-for-api-callers-apichatcompleted}

为直接 API 集成可靠地执行 `outlet()` 的做法是：在 `/api/chat/completions` 之后再发起一次 `POST /api/chat/completed`，把完整对话（包括助手回复）放在 `messages` 中传递。请求体还必须携带 `id`（助手消息 ID）以及 `chat_id` 和 `session_id` 键（它们的值可以为空，但非空的 `chat_id` 必须是你拥有的聊天）。该端点会无条件执行 pipeline 的 outlet Filter 和 Function 的 `outlet()` handler，并把过滤后的负载作为返回结果。错误以 HTTP 400 返回。

``` bash
# Step 2: run outlet() after /api/chat/completions returned a response.
curl -X POST http://localhost:3000/api/chat/completed \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen3.6:27b",
    "messages": [
      {"role": "user", "content": "Hello"},
      {"role": "assistant", "content": "Hi there! How can I help you?"}
    ],
    "id": "the-assistant-message-id",
    "chat_id": "a-chat-id-you-own",
    "session_id": ""
  }'
```

:::info
该端点已被标记为 deprecated，倾向于内联执行；但由于内联执行并不会把过滤后的负载通过 HTTP 返回给纯 API 调用方，所以在今天的多数 API 集成中，`/api/chat/completed` 仍然是正确的选择。
:::

#### 区分 API 请求与 WebUI 请求 {#detecting-api-vs-webui-requests}

没有任何字段会直接标明调用方，因此要改用聊天上下文来判断。来自 WebUI 的请求总是带着 `chat_id` 和 `session_id`；而普通的 API 调用拿到的是空的 `chat_id` 和 `null` 的 `session_id`。这两个键总是存在，所以要判断的是它们的值，而不是它们是否存在：

``` python
async def inlet(self, body: dict, __metadata__: dict = None) -> dict:
    metadata = __metadata__ or {}

    if metadata.get("chat_id") and metadata.get("session_id"):
        print("Request from a chat session")
    else:
        print("No chat context, likely a direct API call")

    return body
```

#### 示例：对所有请求做限流 {#example-rate-limiting-for-all-requests}

由于 `inlet()` 始终会被调用，因此可以借助它实现对 WebUI 和 API 请求都生效的限流：

```python
from pydantic import BaseModel, Field
from typing import Optional
import time

class Filter:
    class Valves(BaseModel):
        requests_per_minute: int = Field(default=60, description="Max requests per minute per user")
    
    def __init__(self):
        self.valves = self.Valves()
        self.user_requests = {}  # Track requests per user
    
    async def inlet(self, body: dict, __user__: dict = None) -> dict:
        if not __user__:
            return body
        
        user_id = __user__.get("id")
        current_time = time.time()
        
        # Clean old entries and count recent requests
        if user_id not in self.user_requests:
            self.user_requests[user_id] = []
        
        # Keep only requests from the last minute
        self.user_requests[user_id] = [
            t for t in self.user_requests[user_id] 
            if current_time - t < 60
        ]
        
        if len(self.user_requests[user_id]) >= self.valves.requests_per_minute:
            raise Exception(f"Rate limit exceeded: {self.valves.requests_per_minute} requests/minute")
        
        self.user_requests[user_id].append(current_time)
        return body
```

#### 示例：记录所有 API 调用 {#example-logging-all-api-usage}

对 WebUI 与直接 API 调用的 token 用量和请求进行记录：

```python
from pydantic import BaseModel, Field
from typing import Optional
import logging

class Filter:
    class Valves(BaseModel):
        log_level: str = Field(default="INFO", description="Logging level")
    
    def __init__(self):
        self.valves = self.Valves()
        self.logger = logging.getLogger("api_usage")
    
    async def inlet(self, body: dict, __user__: dict = None, __metadata__: dict = None) -> dict:
        user_email = __user__.get("email", "unknown") if __user__ else "anonymous"
        model = body.get("model", "unknown")
        chat_id = (__metadata__ or {}).get("chat_id")
        
        self.logger.info(
            f"Request: user={user_email}, model={model}, "
            f"chat_id={chat_id or 'none'}"
        )
        
        return body
```

:::note 事件发射器的行为
使用 `__event_emitter__` 的 Filter 在 API 请求中也会执行，但既然没有 WebUI 来展示这些事件，状态消息就不会显示。在 `inlet()` 和第一次 `request()` 中，发射器是一个真实可调用的对象，因此 await 它不会有任何副作用。在 `stream()` 和 `outlet()` 中，对于纯 API 调用方它是 `None`，因此在 await 之前请先用 `if __event_emitter__:` 做保护。
:::

### ⚡ Filter 优先级与执行顺序 {#filter-priority--execution-order}

当多个 Filter 同时激活时，它们会按照 **priority** 的值顺序执行。理解这一点，对于构建 Filter 链——即后一个 Filter 需要依赖前一个 Filter 修改结果——的场景至关重要。

#### 设置 Filter 优先级 {#setting-filter-priority}

通过 `Valves` 类中的 `priority` 字段来配置：

```python
class Filter:
    class Valves(BaseModel):
        priority: int = Field(
            default=0,
            description="Filter execution order. Lower values run first."
        )
    
    def __init__(self):
        self.valves = self.Valves()
    
    async def inlet(self, body: dict) -> dict:
        # This filter's execution order depends on its priority value
        return body
```

#### 优先级排序规则 {#priority-ordering-rules}

| 优先级值 | 执行顺序 |
|---------------|----------------|
| `0`（默认值） | 最先执行 |
| `1` | 在 priority 为 0 的之后执行 |
| `2` | 在 priority 为 1 的之后执行 |

:::tip 数值越小 = 越先执行
Filter 按 priority **升序**排列。`priority=0` 的 Filter **先于** `priority=1` 执行，后者又先于 `priority=2` 执行，依此类推。多个 Filter 的 priority 相同时，**按函数 ID 的字母顺序**排序，以保证执行顺序一致。
:::

---

### 🔗 Filter 之间的数据传递 {#data-passing-between-filters}

当多个 Filter 同时启用时，链中的每个 Filter 都会收到**上一个 Filter 修改后的数据**。按优先级依次执行时，上一项的返回值就是下一项的输入。

```
User Input
    ↓
Model Router Filter (priority=0) → changes parts of the body
    ↓
Context Manager Filter (priority=1) → receives modified body ✓
    ↓
Logging Filter (priority=2) → receives body with all previous changes ✓
    ↓
LLM Request (sends final modified body to OpenAI/Ollama API)
```

:::warning 重要：务必返回 body
如果你的过滤器修改了 `body`，你**必须**将其返回。返回值会传递给下一个过滤器。如果返回 `None`，后续过滤器将会失败。

```python
async def inlet(self, body: dict, __event_emitter__) -> dict:
    body["messages"].append({"role": "system", "content": "Hello"})
    return body  # Don't forget this!
```
:::

### 🔌 注入额外的 API 请求体参数 {#injecting-extra-api-body-parameters}

Inlet Filter 可以向请求体中注入 **额外字段**，并将其转发给外部 LLM API。这对于 Open WebUI UI 中没有暴露出来、但 API 需要的特定参数非常有用。

请求体会从你的 inlet Filter 流向 LLM API，过程中不会剔除未知字段——只有 `metadata`、`features`、`tool_ids`、`files` 和 `skill_ids` 这类内部键会被移除。你添加的其他字段都会被序列化为 JSON，并发送给 API 提供方。

#### 示例：OpenAI 安全标识符 {#example-openai-safety-identifier}

OpenAI 建议在每个请求中发送 `safety_identifier` 以便进行滥用检测。你可以通过 Filter 自动注入它：

```python
import hashlib

class Filter:
    async def inlet(self, body: dict, __user__: dict = None) -> dict:
        if __user__ and __user__.get("id"):
            body["safety_identifier"] = hashlib.sha256(
                __user__["id"].encode()
            ).hexdigest()
        return body
```

哈希化后的用户 UUID 会作为顶层 body 参数被添加，并直接转发到 OpenAI 的 API——不会发送任何 PII，只会发送一个不可读的哈希值。

:::warning 不能注入 HTTP 标头
Filter 只能修改 **请求体**（`form_data`）。出站 HTTP 标头是单独构造的，不能由 Filter 影响。若要为 API 请求添加自定义标头，请使用 **Settings → Connections → OpenAI API**（管理员区域） 中的 headers 配置。
:::

#### 通过 Filter 注入 OpenAI 风格的 `tools` {#injecting-openai-style-tools-from-a-filter}

Inlet Filter 还可以向 `body["tools"]` 中追加 OpenAI 风格的函数调用工具。追加的工具会**合并到现有列表**，而不会取代 Open WebUI 在服务端根据 `tool_ids`、MCP 服务器和模型内置工具解析出的工具。

```python
class Filter:
    async def inlet(self, body: dict) -> dict:
        body.setdefault("tools", []).append({
            "type": "function",
            "function": {
                "name": "lookup_user_tier",
                "description": "Return the caller's billing tier.",
                "parameters": {
                    "type": "object",
                    "properties": {"user_id": {"type": "string"}},
                    "required": ["user_id"],
                },
            },
        })
        return body
```

行为：

- **原生函数调用**（默认）。在 chat completion 发送前，由 Filter 注入的工具会被追加到服务端解析出的工具列表后。同一请求中，两套工具对模型都可见。
- **由原始 API 调用方提供的工具。** 如果*进入* Filter 管道的请求中已经带有 `body["tools"]`（例如外部客户端在调用 `/api/chat/completions` 时自带 `tools` 数组），那么这些由调用方提供的工具会优先，Open WebUI 会**完全跳过服务端的工具解析**。此时，Filter inlet 同样应追加工具。调用方提供的工具和你追加的工具都会发送给 LLM。
- **非原生函数调用。** 服务端工具解析仍会走 Open WebUI 提示驱动的工具处理流程；由 Filter 注入的工具会被转发给 LLM，但这些工具的运行时执行者取决于你在上游调用中接入的实现。

这种能力适合那些在 workspace 中没有对应 Tool 的工具——例如，你希望只在特定用户的某些聊天里临时告诉模型它的能力。

### 🔍 解析基础模型（`__model__`） {#resolving-the-base-model-\_\_model\_\_}

当用户选择 workspace 或自定义模型时，`body["model"]` 里保存的是自定义模型 ID（例如 `"my-custom-gpt5"`），而不是底层的基模型。要获取真正的基模型，请使用 `__model__` dunder 参数：

```python
class Filter:
    async def inlet(self, body: dict, __model__: dict = None) -> dict:
        custom_model_id = body["model"]  # e.g. "my-custom-gpt5"

        base_model_id = None
        if __model__ and "info" in __model__:
            base_model_id = __model__["info"].get("base_model_id")
            # e.g. "gpt-5.6-sol"

        if base_model_id:
            print(f"Workspace model '{custom_model_id}' → base model '{base_model_id}'")
        else:
            print(f"Direct base model: '{custom_model_id}'")

        return body
```

如果没有 `base_model_id`，说明用户是直接选择了基模型（没有 workspace 包装层）。

#### 可用的 Dunder 参数 {#available-dunder-parameters}

Filter 可以在函数签名中声明以下任意参数，以自动接收它们：

| 参数 | 提供什么 |
|-----------|-----------------|
| `__model__` | 完整的模型字典（对 workspace 模型还包含 `info.base_model_id`） |
| `__user__` | 完整的用户记录（`UserModel.model_dump()`），如果 Filter 定义了 `UserValves`，则额外带上 `valves` |
| `__metadata__` | 请求元数据（`chat_id`、`session_id`、`user_id`、`files`、`features`、`params` 等） |
| `__event_emitter__` | 向客户端发送状态更新、嵌入等内容的函数 |
| `__event_call__` | 发送事件并等待浏览器回应的函数 |
| `__chat_id__` | 聊天会话 ID。不会传给 `outlet()`，后者从 `body["chat_id"]` 中读取 |
| `__message_id__` | 正在生成的助手消息的 ID。不会传给 `outlet()` |
| `__oauth_token__` | 用户的 OAuth token 数据，或者 `None`。不会传给 `outlet()` |
| `__id__` | 该 Filter 自身的函数 ID |
| `__body__` | 仅 `stream()`：正在回应的请求体，因为 `stream()` 接收到的分片是 `event` |
| `__request__` | 原始的 FastAPI `Request` 对象 |

只有你在函数签名中声明的参数才会被注入——Open WebUI 会在运行时检查签名，决定该传入什么。

在一轮对话的第一次调用中，`request()` 拿到的参数集合与 `inlet()` 相同，因此这里的 `__model__` 同样能正确解析 workspace 模型；另外还会多一个 `__features__`，其中携带的是流水线从请求体中弹出之后的 `features` 字典。在后续的工具循环跳转中 `__features__` 不存在，所以请为它设置默认值。

### 💡 Filter 配置最佳实践 {#best-practices-for-filter-configuration}

#### 1. 何时使用全局 Filter {#1-when-to-use-global-filters}

✅ **适合使用全局 Filter 的场景：**
- 安全与合规（PII 清理、内容审核）
- 全局格式统一（统一所有输出样式）
- 日志与分析（跟踪所有请求）
- 组织级策略（执行公司规范）

❌ **不建议使用全局 Filter 的场景：**
- 可选功能（改用可切换 Filter）
- 模型特定行为（改用模型专属 Filter）
- 用户偏好类功能（让用户通过开关控制）

#### 2. 何时使用可切换 Filter {#2-when-to-use-toggleable-filters}

✅ **当满足以下情况时，应将 Filter 设为可切换（`toggle=True`）：**
- 用户应该控制它何时启用（网页搜索、翻译）
- 它是一个可选增强功能（引用模式、详细输出）
- 它提供的功能并非用户每次都需要（代码格式化）
- 它会带来性能成本，应该允许按需启用

❌ **以下情况不应将 Filter 设为可切换：**
- 它用于安全/合规（始终开启更合适）
- 用户不应该能够关闭它（改用始终开启）
- 它是系统级转换（全局更合适）

#### 3. 为你的组织组织 Filter {#3-organizing-filters-for-your-organization}

**推荐结构：**

```
Global Always-On Filters:
├─ PII Scrubber (security)
├─ Content Moderator (compliance)
└─ Request Logger (analytics)

Model-Specific Always-On Filters:
├─ Code Formatter (for coding models only)
├─ Medical Terminology Corrector (for medical models)
└─ Legal Citation Validator (for legal models)

Toggleable Filters (User Choice):
├─ Web Search Integration
├─ Citation Mode
├─ Translation Filter
├─ Verbose Output Mode
└─ Image Description Generator
```

### 🎯 关键组件详解 {#key-components-explained}

#### 1️⃣ **`Valves` 类（可选设置）** {#valves-class-optional-settings}

把 **Valves** 看作过滤器的旋钮和滑块。如果你想为用户提供可配置选项来调整过滤器的行为，就在这里定义它们。

```python
class Valves(BaseModel):
    OPTION_NAME: str = "Default Value"
```

例如：
如果你正在创建一个把响应转为大写的过滤器，可以允许用户通过类似 `TRANSFORM_UPPERCASE: bool = True/False` 的 valve 来配置是否将输出完全大写。

##### 使用下拉菜单（枚举）配置 Valves {#configuring-valves-with-dropdown-menus-enums}

你可以为 `Valves` 的部分选项提供下拉菜单，替代自由文本输入，从而让过滤器更易用。在 Pydantic `Field` 定义中，将 `enum` 关键字放入 `json_schema_extra` 即可。

`enum` 关键字允许你指定一组预定义值，供 UI 以下拉选项的形式呈现。

**示例：** 在过滤器中创建用于配色主题的下拉菜单。

```python
from pydantic import BaseModel, Field
from typing import Optional

# Define your available options (e.g., color themes)
COLOR_THEMES = {
    "Plain (No Color)": [],
    "Monochromatic Blue": ["blue", "RoyalBlue", "SteelBlue", "LightSteelBlue"],
    "Warm & Energetic": ["orange", "red", "magenta", "DarkOrange"],
    "Cool & Calm": ["cyan", "blue", "green", "Teal", "CadetBlue"],
    "Forest & Earth": ["green", "DarkGreen", "LimeGreen", "OliveGreen"],
    "Mystical Purple": ["purple", "DarkOrchid", "MediumPurple", "Lavender"],
    "Grayscale": ["gray", "DarkGray", "LightGray"],
    "Rainbow Fun": [
        "red",
        "orange",
        "yellow",
        "green",
        "blue",
        "indigo",
        "violet",
    ],
    "Ocean Breeze": ["blue", "cyan", "LightCyan", "DarkTurquoise"],
    "Sunset Glow": ["DarkRed", "DarkOrange", "Orange", "gold"],
    "Custom Sequence (See Code)": [],
}

class Filter:
    class Valves(BaseModel):
        selected_theme: str = Field(
            "Monochromatic Blue",
            description="Choose a predefined color theme for LLM responses. 'Plain (No Color)' disables coloring.",
            json_schema_extra={"enum": list(COLOR_THEMES.keys())}, # KEY: This creates the dropdown
        )
        custom_colors_csv: str = Field(
            "",
            description="CSV of colors for 'Custom Sequence' theme (e.g., 'red,blue,green'). Uses xcolor names.",
        )
        strip_existing_latex: bool = Field(
            True,
            description="If true, attempts to remove existing LaTeX color commands. Recommended to avoid nested rendering issues.",
        )
        colorize_type: str = Field(
            "sequential_word",
            description="How to apply colors: 'sequential_word' (word by word), 'sequential_line' (line by line), 'per_letter' (letter by letter), 'full_message' (entire message).",
            json_schema_extra={
                "enum": [
                    "sequential_word",
                    "sequential_line",
                    "per_letter",
                    "full_message",
                ]
            }, # Another example of an enum dropdown
        )
        color_cycle_reset_per_message: bool = Field(
            True,
            description="If true, the color sequence restarts for each new LLM response message. If false, it continues across messages.",
        )
        debug_logging: bool = Field(
            False,
            description="Enable verbose logging to the console for debugging filter operations.",
        )

    def __init__(self):
        self.valves = self.Valves()
        # ... rest of your __init__ logic ...
```

**这里发生了什么？**

*   **`json_schema_extra`**：`Field` 中的这个参数允许你注入 Pydantic 没有显式支持、但下游工具（例如 Open WebUI 的 UI 渲染器）可以使用的任意 JSON Schema 属性。
*   **`"enum": list(COLOR_THEMES.keys())`**：这告诉 Open WebUI，`selected_theme` 字段应该提供一组可选值，具体来说就是 `COLOR_THEMES` 字典中的键。随后 UI 会把下拉菜单渲染为“Plain (No Color)”“Monochromatic Blue”“Warm & Energetic”等可选项。
*   `colorize_type` 字段也演示了另一种用于不同着色方式的 `enum` 下拉菜单。

为 `Valves` 选项使用 `enum` 可以让 Filter 更易用，并防止无效输入，从而带来更顺滑的配置体验。

#### 2️⃣ **`inlet` 函数（输入预处理）** {#inlet-function-input-pre-processing}

`inlet` 函数就像 **烹饪前的备菜**。想象你是一位厨师：在食材进入菜谱（这里相当于 LLM）之前，你可能会清洗蔬菜、切洋葱或给肉类调味。如果没有这一步，最后的菜品可能味道不足、食材没洗干净，或者风味不稳定。

在 Open WebUI 的世界里，`inlet` 函数会在**用户输入**发送给模型之前完成这项重要准备工作。它能确保输入尽可能干净、带有上下文，并且对 AI 来说更有帮助。

📥 **输入**：
- **`body`**：Open WebUI 传给模型的原始输入。它采用 chat-completion 请求的格式（通常是一个字典，包含对话消息、模型设置和其他元数据等字段）。你可以把它看作做菜时的食材。

🚀 **你的任务**：
修改并返回 `body`。LLM 处理的是修改后的 `body`，所以这是你为输入补充清晰度、结构和上下文的机会。

:::info 想转换 RAG chunk？`inlet()` 在检索**之前**运行
在 `inlet()` 时刻，`body["metadata"]["files"]` 和 `body["files"]` 里只有文件和知识库的*引用*。所有 inlet filter 返回后，才会检索并注入实际 chunk 文本。有两种方式可以获取 chunk 文本（例如用于 PII 脱敏、重排序、翻译或 chunk 级 ACL）：

- **[`request()`](#the-request-step)** 在检索之后运行，因此 body 中已有注入的 chunk。用它来*转换*内置 RAG 的结果。这是最简单的选项，无需开启额外设置。
- **[`file_handler`](#owning-retrieval-with-file_handler)** 会完全跳过内置 RAG，把引用交给你。用它以自定义实现*替换*检索方式。
:::

##### 🍳 为什么要使用 `inlet`？ {#why-would-you-use-the-inlet}
1. **添加上下文**：自动为用户输入补充关键信息，尤其是在文本模糊或不完整时。例如，你可以添加“你是一位友好的助手”或“帮助用户排查软件 bug”。

2. **格式化数据**：如果输入需要特定格式，比如 JSON 或 Markdown，你可以在发送给模型前先做转换。

3. **清理输入**：去掉不需要的字符，删除可能有害或令人困惑的符号（如多余空白或表情符号），或者替换敏感信息。

4. **简化用户输入**：如果模型在获得额外指引后表现更好，你可以利用 `inlet` 自动注入澄清指令！

5. **限流**：跟踪每个用户的请求，并拒绝超出配额的请求（WebUI 和 API 请求都适用）。

6. **请求日志**：记录所有进入的请求，用于分析、调试或计费。

7. **语言检测**：检测用户语言，并注入翻译指令，或路由到对应语言的模型。

8. **Prompt Injection 检测**：扫描用户输入中是否存在试图操纵系统提示词的行为，并阻止恶意请求。

9. **成本估算**：在发送给模型前估算输入 token，便于预算追踪。

10. **A/B 测试**：根据用户 ID 或随机选择，将用户路由到不同的模型配置。

##### 💡 示例用法：继续沿用“备菜”比喻 {#example-use-cases-build-on-food-prep}

###### 🥗 示例 1：添加系统上下文 {#example-1-adding-system-context}
假设 LLM 是一位厨师，要为意大利料理准备菜品，但用户没有说明“这是意大利菜”。你可以在把数据发送给模型之前附上这段上下文，让信息更明确。

```python
async def inlet(self, body: dict, __user__: Optional[dict] = None) -> dict:
    # Add system message for Italian context in the conversation
    context_message = {
        "role": "system",
        "content": "You are helping the user prepare an Italian meal."
    }
    # Insert the context at the beginning of the chat history
    body.setdefault("messages", []).insert(0, context_message)
    return body
```

📖 **会发生什么？**
- 任何类似“晚餐有什么好点子？”的用户输入，现在都会带上意大利主题，因为我们已经设置了系统上下文！芝士蛋糕也许不会出现，但意面大概率会。

###### 🔪 示例 2：清理输入（移除奇怪字符） {#example-2-cleaning-input-remove-odd-characters}
假设用户输入看起来很乱，或者包含 `!!!` 之类的不需要的符号，这会让对话效率变低，也让模型更难解析。你可以在保留核心内容的前提下把它清理干净。

```python
async def inlet(self, body: dict, __user__: Optional[dict] = None) -> dict:
    # Clean the last user input (from the end of the 'messages' list)
    last_message = body["messages"][-1]["content"]
    body["messages"][-1]["content"] = last_message.replace("!!!", "").strip()
    return body
```

📖 **会发生什么？**
- 之前：`"How can I debug this issue!!!"` ➡️ 发送给模型后变成 `"How can I debug this issue"`

:::note

注意：用户体验没有变化，但模型处理的是更干净、更容易理解的查询。

:::

##### 📊 `inlet` 如何帮助优化 LLM 输入： {#how-inlet-helps-optimize-input-for-the-llm}
- 通过澄清含糊查询来提升 **准确性**。
- 通过移除表情、HTML 标签或多余标点等噪音，让 AI **更高效**。
- 通过把用户输入格式化为模型预期的模式或 schema（例如某个特定场景下的 JSON），来确保**一致性**。

💭 **可以把 `inlet` 想象成厨房里的二厨**——它负责确保送进模型（你的 AI“菜谱”）的一切都已经被备好、清理好并调味到位。输入越好，输出通常也越好！

#### 🆕 3️⃣ **`stream` 钩子（Open WebUI 0.5.17 新增）** {#stream-hook-new-in-open-webui-0517}

##### 🔄 什么是 `stream` 钩子？ {#what-is-the-stream-hook}
**`stream` 函数** 是 Open WebUI **0.5.17** 中新增的功能，允许你实时 **拦截并修改流式模型响应**。

与处理完整响应的 `outlet` 不同，`stream` 会在收到模型发来的**每个片段**时立即处理。

##### 🛠️ 什么时候使用 stream 钩子？ {#when-to-use-the-stream-hook}
- **实时内容过滤** —— 在内容流式输出时屏蔽脏话或敏感内容
- **实时词语替换** —— 替换品牌名、竞品名或过时术语
- **流式分析** —— 实时统计 token 并跟踪响应长度
- **进度指示** —— 检测特定模式以显示加载状态
- **调试** —— 记录每个片段，排查流式问题
- **格式修正** —— 在常见格式问题出现时立即修复

##### 📜 示例：记录流式片段 {#example-logging-streaming-chunks}

下面演示如何检查并修改流式 LLM 响应：
```python
async def stream(self, event: dict) -> dict:
    print(event)  # Print each incoming chunk for inspection
    return event
```

> **流式事件示例：**
``` jsonl
{"id": "chatcmpl-B4l99MMaP3QLGU5uV7BaBM0eDS0jb","choices": [{"delta": {"content": "Hi"}}]}
{"id": "chatcmpl-B4l99MMaP3QLGU5uV7BaBM0eDS0jb","choices": [{"delta": {"content": "!"}}]}
{"id": "chatcmpl-B4l99MMaP3QLGU5uV7BaBM0eDS0jb","choices": [{"delta": {"content": " [redacted]"}}]}
```
📖 **会发生什么？**
- 每一行都代表模型流式响应中的一个**小片段**。
- **`delta.content` 字段**包含逐步生成的文本。

##### 🔄 示例：从流式数据中过滤标记 {#example-filtering-out-markers-from-streamed-data}
```python
async def stream(self, event: dict) -> dict:
    for choice in event.get("choices", []):
        delta = choice.get("delta", {})
        if "content" in delta:
            delta["content"] = delta["content"].replace(" [redacted]", "")  # Strip the marker
    return event
```
📖 **之前：** `"Hi [redacted]"`
📖 **之后：** `"Hi"`

##### Responses API 连接上的流式事件 {#streamed-events-on-responses-api-connections}

上面的事件是 **Chat Completions** 数据块，除了 **API 类型** 设为 `Responses` 的连接之外，其他一切都提供这种形式。Responses 连接会原样转发服务商自己的事件流，因此 `stream()` 收到的是带类型的 Responses API 事件。该流以若干不携带文本的记账事件开头，裁剪后只保留携带文本的部分：

```jsonl
{"type": "response.output_text.delta", "delta": "Hi"}
{"type": "response.output_text.delta", "delta": " [redacted]"}
{"type": "response.output_text.done", "text": "Hi [redacted]"}
{"type": "response.content_part.done", "part": {"type": "output_text", "text": "Hi [redacted]"}}
{"type": "response.output_item.done", "item": {"type": "message", "content": [{"type": "output_text", "text": "Hi [redacted]"}]}}
{"type": "response.completed", "response": {"output": [{"type": "message", "content": [{"type": "output_text", "text": "Hi [redacted]"}]}], "usage": {"input_tokens": 9, "output_tokens": 3}}}
```

:::warning 只改写 delta 是不够的
delta 是用户看着逐条到达的内容，但后续事件会重复**完整文本**，而 Open WebUI 会据此重建消息并把重建结果推送给浏览器。只在 `response.output_text.delta` 上做的编辑，会在 `response.output_text.done` 到达的瞬间被屏幕上的内容撤销；随后 `response.content_part.done` 会用服务商的副本替换整个内容块，`response.output_item.done` 替换整个输出项，`response.completed` 替换整个响应，而回复结束时保存的正是这份副本。反过来同样成立：有些服务商以空的 `output` 收尾，此时 Open WebUI 会保留此前事件构建的内容，而只在 `response.completed` 中做的编辑永远到不了被保存的消息中。请编辑每一个携带文本的事件。

下面的示例覆盖的是助手消息文本。推理是另一种输出项类型，拥有自己的文本；拒答则位于 `refusal` 字段而非 `text` 字段，因此两者都不会被它触及。
:::

##### 示例：在 Responses API 连接上过滤标记 {#example-filtering-out-markers-on-responses-api-connections}

```python
async def stream(self, event: dict) -> dict:
    def clean(value):
        # Non-string values turn up, and raising here would drop the whole event
        return value.replace(" [redacted]", "") if isinstance(value, str) else value

    def clean_message(item):
        if (item or {}).get("type") != "message":
            return
        for part in item.get("content") or []:
            if "text" in part:
                part["text"] = clean(part["text"])

    # Chat Completions chunks
    for choice in event.get("choices") or []:
        delta = choice.get("delta") or {}
        if "content" in delta:
            delta["content"] = clean(delta["content"])

    # Responses API events
    event_type = event.get("type", "")
    if event_type == "response.output_text.delta" and "delta" in event:
        event["delta"] = clean(event["delta"])
    elif event_type == "response.output_text.done" and "text" in event:
        event["text"] = clean(event["text"])
    elif event_type == "response.content_part.done":
        part = event.get("part") or {}
        if "text" in part:
            part["text"] = clean(part["text"])
    elif event_type == "response.output_item.done":
        clean_message(event.get("item"))
    elif event_type == "response.completed":
        for item in (event.get("response") or {}).get("output") or []:
            clean_message(item)

    return event
```

如果 `stream()` 抛出异常，Open WebUI 会丢掉整个事件，而丢失 `response.completed` 会让这条回复失去 token 用量数据和响应 id。

:::note Valves 是每次响应解析一次，而不是每个数据块一次

`stream()` 会为每个片段运行，因此它的 valves 是在响应开始时从数据库读取一次、并在其余部分中复用，而不是被反复读取上千次。于是 `self.valves` 和 `__user__["valves"]` 在一次流式回复的整个过程中都是稳定的：在回复流式输出期间修改某个 valve，会在下一次回复中生效，而不是在当前回复中途生效。`inlet()` 和 `outlet()` 不受影响，因为它们本来就各只运行一次。

:::

#### 4️⃣ **`outlet` 函数（输出后处理）** {#outlet-function-output-post-processing}

`outlet` 函数就像一位 **校对员**：它在 *LLM 处理完成后*整理 AI 的回复或进行最后修改。

📤 **输入**：
- **`body`**：这里包含聊天中的**所有当前消息**（用户历史 + LLM 回复）。

每条消息都带有 `id`、`role`、`content`、`info` 和 `timestamp`，如果存在还会带有 `output`、`usage` 和 `sources`。只有刚刚结束的那条回复会带有 **`finish_reason`**：这是提供商给出的结束原因，例如 `stop`、`length`（回复触及 token 上限）或 `tool_calls`。当回复涉及工具调用时，它是该轮最后一次模型调用返回的值。

对于 OpenAI 兼容模型和 Ollama 模型，无论是否流式，`finish_reason` 都会被设置。Ollama 在回复被 token 上限截断时报告 `length`。使用 OpenAI Responses API 的连接只在非流式回复上设置它，取值为 `stop` 或 `tool_calls`。

🚀 **你的任务**：修改这个 `body`。你可以清理、追加或记录变更，但要注意每一次调整对用户体验的影响。

💡 **最佳实践**：
- 在 outlet 里，优先记录日志而不是直接修改内容（例如用于调试或分析）。
- 如果需要大幅改写（例如格式化输出），可以考虑改用 **pipe 函数**。

##### 🛠️ `outlet` 的使用场景： {#use-cases-for-outlet}
- **响应日志** —— 跟踪所有模型输出，用于分析或合规
- **Token 使用跟踪** —— 在完成后统计输出 token，用于计费
- **Langfuse / 可观测性集成** —— 把 trace 发送到监控平台
- **引用格式化** —— 重新整理最终输出中的引用链接
- **免责声明注入** —— 追加法律声明或 AI 披露语句
- **响应缓存** —— 将响应存储以便后续检索
- **质量评分** —— 对模型输出执行自动化质量检查

:::info Outlet 与 API 请求
对于直接调用 `/api/chat/completions` 的客户端，`outlet()` 在流式和非流式路径上默认运行，由 [`ENABLE_API_OUTLET_FILTERS`](/reference/env-configuration#enable_api_outlet_filters) 控制。关闭后，直接集成 API 的客户端必须在请求结束后调用 `POST /api/chat/completed`。无论哪种情况，过滤后的内容都不会写回 HTTP 响应。详见 [API 请求中的 Filter 行为](#filter-behavior-with-api-requests)。
:::

一个会修改回复的 outlet，同时会改动该消息的 `content` 以及 `output` 里的文本——因为聊天界面展示的回复正是取自 `output`。

💡 **示例用法**：把不希望用户看到的敏感 API 响应内容去掉：
``` python
async def outlet(self, body: dict, __user__: Optional[dict] = None) -> dict:
    for message in body["messages"]:
        message["content"] = message["content"].replace("<API_KEY>", "[REDACTED]")
        for item in message.get("output") or []:
            if item.get("type") == "message":
                for part in item.get("content") or []:
                    if part.get("type") == "output_text":
                        part["text"] = part["text"].replace("<API_KEY>", "[REDACTED]")
    return body
```

### 📚 示例 #2：高亮输出，便于阅读 {#example-2-highlight-outputs-for-easy-reading}

``` python
class Filter:
    async def outlet(self, body: dict, __user__: Optional[dict] = None) -> dict:

```

### 📚 示例 #3：流式可观测性提示（概念性模式） {#example-3-streaming-observability-hints-conceptual-pattern}

管理员有时希望在模型流式输出时，直接在**界面中显示简短提示**，例如估算的**首 token 延迟**、**流式输出总时长**或**粗略的 tokens/s**。借助前面介绍的 **`stream`** 钩子，Filter 无需另建仪表盘或修改前端即可做到。

本节描述的是**行为与注意要点**，不是开箱即用的完整脚本。Filter 会执行**任意 Python**；请把任何你拼出来的片段都当作**特权服务端代码**对待。部署前请仔细审查，只通过可信渠道共享，并参考本页面顶部的**关键安全警告**。

#### 这种 Filter 应当观察什么 {#what-such-a-filter-would-observe}

流式过程中，Filter 会收到一连串 **`event`** 对象（来自上游 provider / Open WebUI 栈的 chunk）。典型字段包括 **`choices[].delta`**（assistant 增量文本）、可选的 **`choices[].finish_reason`**（完成后的回复也会交给 `outlet`，参见 [`outlet`](#outlet-function-output-post-processing)）、**`usage`**（通常只在终止 chunk 上出现），或合成的终止标志（一个 **`done`** 标志位、**`type`** 哨兵值）——具体形状会因 connector 与协议而异。

计时最简单的方式是用**单调时钟**（Python 里用 `time.perf_counter()`）：记录第一次看到 assistant 回复流片段的时刻，对包含可打印模型文本（包括一些 API 暴露的 reasoning / 音频转写字段）的 delta 累加计数，并在你判定流**已结束**时对比时间戳。

#### 关联一条流（"这条流属于哪条消息？"） {#correlating-one-stream-which-message-is-this}

每个请求的 **`__metadata__`**（`stream` 的保留参数）都包含 **`chat_id`**、**`message_id`** 等标识。在内存映射中使用**复合键**，避免并发聊天之间发生冲突。该键对应的流结束后，清除保存的状态，防止映射不断增长。

#### 在 Web UI 中展示提示（`status`） {#surfacing-hints-in-the-web-ui-status}

界面可以通过 **`status`** 负载显示与助手消息关联的简短进度。Filter 会收到 **`__event_emitter__`**。用它发出一个字典，指定 **`type`: `"status"`**，并在 **`data`** 中至少包含 **`description`**（可读文本）和 **`done`**（该状态是否已结束）。若要在工具中识别此插件，可选用一个固定的 **`data.action`** 字符串。

流中段发提示的粗略模式：

```python
await __event_emitter__(
    {"type": "status", "data": {"done": False, "description": "First model text observed.", "hidden": False}}
)
```

在生成**真正结束**时，再发一条 **`done: True`** 的 status 来汇总统计值并停止加载指示器。

#### 如何判定流真的结束了 {#knowing-when-the-stream-really-ended}

判断时应谨慎：**只包含 `usage` 的 chunk** 可能在流式输出中途出现。看到 **`finish_reason`**、显式的 **`stop`**、**`event["done"]`** 或协议特定的 **DONE** 标记时，再将回复视为结束。然后发出最终的 **`status`** 并清除保存的状态。

#### 大致吞吐 {#rough-throughput}

如果最后一个 chunk 提供了合理的 **`usage.completion_tokens`** 值（或等效字段），可计算 **tokens ÷ 所用秒数**，从首次收到正文时开始计时。

如果对某个 provider 来说 **`usage`** 要到末尾才出现——或者根本不会出现，许多 Filter 的**兜底方案**是按流式字符数粗略估算 token（经验法则做除法；很粗略且依赖模型）。**不要把**启发式得到的数字当作计费级别或科学基准使用。

## 🚧 容易混淆的地方：清晰 FAQ 🛑 {#potential-confusion-clear-faq}

### **问：Filter 和 Pipe 函数有什么区别？** {#q-how-are-filters-different-from-pipe-functions}

Filter 会修改**进入模型**和**从模型返回**的数据，但不会明显介入这些阶段之外的逻辑。另一方面，Pipe：
- 可以集成 **外部 API**，或者显著改变后端处理操作的方式。
- 可以把自定义逻辑暴露成全新的“模型”。

### **问：我可以在 `outlet` 里做很重的后处理吗？** {#q-can-i-do-heavy-post-processing-inside-outlet}

可以，但 **这不是最佳实践**：
- **Filter** 适合做轻量修改或日志记录。
- 如果需要大幅改写，建议改用 **Pipe Function**。

## 🎉 总结：为什么要构建 Filter 函数？ {#recap-why-build-filter-functions}
到目前为止，你已经了解了：
1. **Inlet** 每轮对话处理一次，用于操纵**用户输入**（前处理）。
2. **Request** 在每次调用提供方之前调整**发出的载荷**，包括工具循环中的每一跳。它应当写成幂等的。
3. **Stream** 拦截并修改**流式模型输出**（实时）。
4. **Outlet** 微调**AI 输出**（后处理）。
5. Filter 最适合对数据流进行轻量级的实时改动。
6. 借助 **Valves**，你可以让用户动态地配置 Filter，以获得定制化的行为。
