# 什么是 Tools？ {#what-are-tools}

:::danger ⚠️ 重要安全警告
**Workspace Tools 和 Functions 在你的服务器上执行任意 Python 代码。** 只从受信任的来源安装，导入前审查代码，并将 Workspace 访问限制为受信任的管理员。授予用户创建或导入 Tools 的能力等同于给予他们服务器的 shell 访问权限。详情参见[插件安全警告](/features/extensibility/plugin/)。
:::

Tools 是你扩展 LLM 能力、超越简单文本生成的各种方式。启用后，它们允许你的聊天机器人做惊人的事情——比如搜索网络、抓取数据、生成图像、使用 AI 语音回应等。

由于在 Open WebUI 中有几种集成"Tools"的方式，了解你使用的是哪种类型非常重要。

---

## 工具分类：你使用的是哪种"Tool"？ {#tooling-taxonomy-which-tool-are-you-using}

🧩 用户经常在不同上下文中遇到"Tools"这个术语。以下是区分它们的方法：

![工作区中已安装的工具](/images/workspace/tools-list.png)

| 类型 | 在 UI 中的位置 | 最适合…… | 来源 |
| :--- | :--- | :--- | :--- |
| **Native Features** | Admin/Settings | 平台核心功能（即[内置系统工具](#built-in-system-tools-nativeagentic-mode)） | 内置于 Open WebUI |
| **Workspace Tools** | `Workspace > Tools` | 用户自建或社区 Python 脚本——**最强大、限制最少的选项** | [社区库](https://openwebui.com/search) |
| **Native MCP (HTTP)** | `Settings > Connections` | 通过 HTTP/SSE 可达的标准 MCP 服务器 | 外部工具服务器 |
| **MCP via Proxy (MCPO)** | `Settings > Connections` | 基于 stdio 的本地 MCP 服务器（例如 Claude Desktop 工具） | 外部工具服务器（通过 [MCPO Adapter](https://github.com/open-webui/mcpo)） |
| **OpenAPI Servers** | `Settings > Connections` | 标准 REST/OpenAPI Web 服务 | 外部工具服务器 |

最后三项（**MCP HTTP**、**MCPO**、**OpenAPI**）都是**外部工具服务器**：工具代码运行在独立进程或机器上，Open WebUI 通过 HTTP 调用它。**Native Features** 是 Open WebUI 自带的内置系统工具。**Workspace Tools** 是进程内运行的 Python——对于最苛刻的使用场景，它们是能力最强、限制最少的选项（见下文）。

### 1. 原生功能（内置） {#1-native-features-built-in}
这些深度集成在 Open WebUI 中，通常不需要外部脚本。
- **网络搜索**：通过 SearXNG、Google 或 Tavily 等引擎集成。
- **URL 获取**：使用 `#` 或原生工具直接从网站提取文本内容。
- **图像生成**：与 DALL-E、ComfyUI 或 Automatic1111 集成。
- **记忆**：模型在对话之间记住关于你的事实的能力。
- **RAG（知识）**：查询上传文档的能力（`#`）。

在[**原生模式**](#built-in-system-tools-nativeagentic-mode)下，这些功能作为模型可独立调用的 **Tools** 暴露。

### 2. Workspace Tools（自定义插件） {#2-workspace-tools-custom-plugins}
这些是直接在 Open WebUI 环境中运行的 **Python 脚本**。**对于高要求场景，Workspace Tools 是最强大、限制最少的选项** —— 它们以进程内方式运行，能完整访问 Python、`open_webui` 源码以及请求上下文，因此几乎没有什么是它们做不了的（完整能力可参阅 [Under the Hood](../development/under-the-hood)）。上面列出的外部工具服务器限制更多：它们只能看到你通过 HTTP 传过去的内容，触碰不到 Open WebUI 自身。
- **能力**：可以做 Python 能做的任何事情（网络抓取、复杂数学、API 调用），并且可以完全在服务端持有密钥（API key），用户和模型都看不到。
- **访问**：通过 `Workspace` 菜单管理。
- **安全**：始终在导入前审查代码，因为这些在你的服务器上运行。
- **⚠️ 安全警告**：普通或不受信任的用户**不应**被授予访问 Workspace Tools 部分的权限。此访问允许用户在你的服务器上上传和执行任意 Python 代码，可能导致全系统被入侵。

### 3. MCP（模型上下文协议） {#3-mcp-model-context-protocol}

🔌 MCP 是一个允许 LLM 与外部数据和工具交互的开放标准。
- **原生 HTTP MCP**：Open WebUI 可以直接连接到任何暴露 HTTP/SSE 端点的 MCP 服务器。
- **MCPO（代理）**：大多数社区 MCP 服务器使用 `stdio`（本地命令行）。要在 Open WebUI 中使用这些，你可以使用 [**MCPO 代理**](../../plugin/tools/openapi-servers/mcp.mdx)来桥接连接。

### 4. OpenAPI / 函数调用服务器 {#4-openapi--function-calling-servers}
提供 OpenAPI（`.json` 或 `.yaml`）规范的通用 Web 服务器。Open WebUI 可以摄取这些规范并将每个端点视为工具。

:::info Open Terminal —— 一项独立的代码执行集成
除了上面列出的工具类型，Open WebUI 还集成了 **[Open Terminal](/features/open-terminal)**：一个常驻、隔离的 Docker 容器，为模型提供真正的 shell 和文件系统。一旦连接，它会暴露自己的一组**内置工具**（`run_command`、`read_file`、`write_file`、`grep_search`、`glob_search`、进程管理等），模型可以直接调用——它本质上是一个沙箱化的代码执行与文件处理环境，区别于每条消息粒度的 [Code Interpreter](#built-in-system-tools-nativeagentic-mode) 工具。配置、多用户与安全方面的注意事项请参阅 [Open Terminal 文档](/features/open-terminal)。
:::

## 如何安装与管理工作区工具 {#how-to-install--manage-workspace-tools}

📦 Workspace Tools 是用社区功能扩展你的实例最常见的方式。

1. 前往[社区工具库](https://openwebui.com/search)
2. 选择一个工具，点击 **Get** 按钮。
3. 输入你的 Open WebUI 实例 URL（例如 `http://localhost:3000`）。
4. 点击 **Import to WebUI**。

:::warning 安全提示
切勿导入你不认识或不信任的工具。这些都是 Python 脚本，可能在你主机系统上运行不安全的代码。**关键是，请确保仅向受信任用户授予"工具"权限**，因为创建或导入工具的能力等同于在服务器上运行任意代码的能力。
:::

---

### 关闭工具 {#turning-a-tool-off}

**工作区 > 工具** 中某个工具所在行上的开关用于启用或停用它。该开关只出现在你有权限编辑的工具上。已停用的工具不会出现在对话中，包括已选中它的对话，并且其 Python 依赖不会被安装。

### 共享工具 {#sharing-a-tool}

**工作区 > 工具** 中某个工具的 **⋯** 菜单里有一个 **访问** 项，可直接从列表打开该工具的[访问设置](/features/authentication-access/rbac/groups#resource-access-rbac)，无需进入编辑器。该项只出现在你有权限编辑的工具上；非管理员还需要 **工具共享** 权限才能看到。工具编辑器中的 **访问** 按钮遵循同样的权限规则。

### 版本历史 {#version-history}

每次改变工具名称、描述、翻译或代码的保存都会保留为一个版本，同时保留 **保存** 旁 **描述此次变更** 中填写的内容。工具编辑器顶部 **返回** 旁的版本选择器默认停在 **生产环境**，即对话使用的版本。展开它可查看已保存的版本，按时间倒序排列，每页 20 条，每条附带作者和描述（若描述为空则显示一个简短的版本 ID）。任何能编辑该工具的人都可以使用它。

- **打开版本**：选择某个版本即可，编辑器会以只读方式显示其名称、描述、翻译和代码。
- **与当前版本对比** 显示该版本与生产环境之间的差异：并排展示发生变化的字段，然后以差异形式展示代码。布局菜单可在 **分栏** 和 **统一** 之间切换，浏览器会记住选择。只涉及行尾符的改动会显示为 **仅行尾符发生变化**。任一版本中超过 5000 行的代码无法比较（`Diff is limited to 5000 lines per version`）。
- **设为生产环境** 会让当前打开的版本成为对话使用的版本。其代码的加载和检查方式与保存时相同。如果编辑器中有未保存的改动，会先要求你确认，因为这些改动将被丢弃。
- **删除** 位于某个版本的 **⋯** 菜单中。生产环境版本无法删除。在被删除版本之上保存的版本会重新链接到其父版本，从而保持版本链完整。

一个版本包含名称、描述、翻译和代码。阀门和访问权限设置属于工具本身，切换版本时它们会保持当前值。出现下列情况时，将某个版本设为生产环境会被拒绝：

- 当前的阀门与该版本的代码不匹配（**当前阀门与此代码不兼容**）。请先调整阀门（参见[在已有代码中修改阀门](/features/extensibility/plugin/development/valves#changing-valves-in-existing-code)）。
- 该版本的代码与生产环境不同，而你既没有[**工具访问**也没有**导入工具**权限](/features/authentication-access/rbac/permissions#1-workspace-permissions)。缺少其中任一权限时，写入权限只覆盖工具的名称、描述和翻译，保存和版本变更均是如此。

每个已有工具在升级时都会自动创建一个版本。

同样的操作也可以通过 API 完成：`GET /api/v1/tools/id/{id}/history`（通过 `?page=` 分页）、`GET /api/v1/tools/id/{id}/history/{history_id}`、`GET /api/v1/tools/id/{id}/history/diff?from_id=...&to_id=...`、`DELETE /api/v1/tools/id/{id}/history/{history_id}` 以及 `POST /api/v1/tools/id/{id}/update/version` 搭配 `{"version_id": "..."}`。通过 `POST /api/v1/tools/id/{id}/update` 保存时，还可以附带可选的 `commit_message`。

### 翻译工具 {#translating-a-tool}

工具编辑器中的地球图标选择器可按语言存储名称、描述和阀门标签。优先翻译用户阀门标签，因为普通用户看到的正是 **模型控件** 菜单中 **控件** 下的这些标签。参见[翻译](/features/administration/translations)。

## 如何在对话中使用 Tools {#how-to-use-tools-in-chat}

🔧 安装或连接后，以下是为对话启用它们的方法：

### 选项 1：即时启用（特定对话） {#option-1-enable-on-the-fly-specific-chat}
聊天时，点击输入区域中的 **➕（加号）** 图标。你将看到可用 Tools 列表——你可以专门为该会话启用它们。

### 选项 2：默认启用（全局/模型级别） {#option-2-enable-by-default-globalmodel-level}
1. 前往 **Workspace ➡️ 模型**。
2. 选择你使用的模型并点击 ✏️ 编辑图标。
3. 滚动到 **Tools** 部分。
4. ✅ 勾选你希望此模型默认始终访问的 Tools。
5. 点击**保存**。

对于支持的模型，**原生工具调用模式**（见下方[工具调用模式](#tool-calling-modes-default-vs-native)）让模型自己决定每轮调用哪些附加工具。这取代了旧的基于提示注入的"auto-tool"过滤方法，是让模型自动选择工具的推荐方式。

:::caution 附加的 Tools 仍然需要用户访问权限
将 Workspace Tool 附加到模型**不会**绕过访问控制。当用户与模型聊天时，Open WebUI 会检查**该特定用户**是否有每个附加工具的读取权限。用户无法访问的工具会被静默跳过——模型将无法调用它们。

**示例场景**：管理员创建一个私有工具并将其附加到与所有用户共享的模型。与此模型聊天的普通用户将**无法使用**该工具，因为他们没有工具本身的读取权限。

**解决方案**：确保需要模型工具的用户也对每个工具有读取权限（通过访问授权、组权限或将工具设为公开）。"Workspace → Tools"权限控制用户是否可以*创建和管理*工具——它**不影响**模型附加的工具是否对他们有效。
:::

## 工具调用模式：Native 模式与 Legacy 模式 {#tool-calling-modes-default-vs-native}

:::danger Native 是 v0.10.0 起的默认值；"Legacy"（原名 "Default"）是不受支持的选择退出选项
**Native（Agentic）模式现在是默认值。** 从 **v0.10.0** 起，每个未明确选择工具调用模式的聊天和模型都会运行 **Native** 模式，该模式依赖于模型内置的函数调用支持。旧的提示注入方法，之前称为 **Default**，现已更名为 **Legacy**。它是一个明确的选择退出选项，并且仍然**不受支持**：没有功能更新、没有错误修复、没有内置系统工具，并且与现代 Open WebUI 功能不兼容（Agentic Research、交错思考、内置 Memory/Notes/Knowledge/Channels 工具、网络搜索/图像生成/代码解释器工具注入）。

**重大变更：** 如果你的任何模型依赖于旧的基于提示的行为，它们现在将运行 Native 模式，除非你将其切换回 **Legacy** 模式，[按对话、按模型或在全局模型参数中设置](#enable-legacy-for-all-models)。如果某个模型在 Native 模式下有问题，正确的解决方法是选择更好的工具调用模型，而不是回退到 Legacy。
:::

Open WebUI 在**模型设置 → 高级参数 → 函数调用**中提供两种模式：**Native 模式（Agentic 模式）**——唯一受支持的模式——以及 **Legacy 模式（原名 Default）**，仅为向后兼容性保留在 UI 中。

### 🔴 Legacy 模式（基于提示，原名 Default）— 遗留/不受支持 {#legacy-mode-prompt-based}

:::warning 不受支持
Legacy 模式**已过时且不再受支持**。此处仅供参考。新部署必须使用 Native 模式；现有部署应迁移。关于 Default 模式行为的错误报告、功能请求和支持问题将不会被处理。
:::

在 Legacy 模式下，Open WebUI 通过注入一个长提示模板来管理工具选择，引导模型以定制格式输出工具请求。这在 2023 年是合理的方法；自主流提供商和开放权重模型获得适当的函数调用 API 以来，它已经过时了。

为什么它已过时：
- **破坏 KV 缓存。** 注入的提示每轮都会改变，阻止 LLM 引擎重用缓存的键值对。每条消息都要再次支付完整的预填充成本。
- **更高的延迟和令牌成本。** 每轮都有大量工具描述提示。
- **对多步骤链接不可靠。** 解析自然语言工具请求比结构化工具调用更脆弱。
- **无法访问内置系统工具。** 记忆、笔记、知识、频道、Agentic Research、交错思考以及工具注入的网络搜索/图像生成/代码解释器功能都是**仅 Native 模式**可用的。
- **不支持现代能力。** 2024 年以来发布的每个新功能都针对 Native 模式。

#### 如何将所有模型切换到 Legacy 模式 {#enable-legacy-for-all-models}

由于 v0.10.0 起 Native 是默认值，你永远不需要"开启 Native"。你可能需要的唯一工具调用切换是相反的：为那些依赖于旧的提示注入行为且无法迁移到更强的支持 Native 的模型的模型强制重新开启 **Legacy**。在你需要的任何作用域将**函数调用**设置为 `Legacy`（与下方 [Native 模式的控制方式](#how-to-enable-native-mode-agentic-mode) 相同）：

1.  **一次性应用于所有模型（全局默认值，最快）**：
    *   导航到**设置 → 模型**（管理员区域）。
    *   点击模型列表**右上角**的**设置**按钮，打开**全局模型参数**（适用于*每个*模型，包括当前和未来的，除非特定模型覆盖它们）。
    *   在**模型参数**下，将**函数调用**设置为 `Legacy`，然后保存。每个未设置自己值的模型现在都将运行 Legacy。你**不需要**逐一编辑它们。
2.  **按模型覆盖**：在**设置 → 模型**（管理员区域）中编辑特定模型，并在**模型参数**下将**函数调用**设置为 `Legacy`。仅覆盖该模型的全局默认值。
3.  **按对话覆盖**：在对话中，打开**聊天控制 → 高级参数**，将**函数调用**设置为 `Legacy`。仅适用于该对话。

:::info 更喜欢环境变量？使用 `DEFAULT_MODEL_PARAMS`
要通过环境变量将整个实例切换到 Legacy，请使用以下方式设置相同的全局默认值：

```yaml
DEFAULT_MODEL_PARAMS: '{"function_calling": "legacy"}'
```

`function_calling` 是 `DEFAULT_MODEL_PARAMS` 内部的一个键；没有独立的 `FUNCTION_CALLING_MODE`（或类似）变量。唯一能改变行为的值是 `"legacy"`；不设置（或设置为 `"native"`）则保持默认的 Native 模式。
:::

### 🟢 Native 模式（Agentic 模式/系统函数调用）— 唯一受支持的模式 {#native-mode-agentic-mode--system-function-calling-the-only-supported-mode}
Native 模式（也称为 **Agentic 模式**）利用模型内置的能力处理工具定义并返回结构化工具调用（JSON）。从 v0.10.0 起它是**默认值**，也是所有支持它的模型的**推荐模式**——包括绝大多数现代模型（2024+）。

:::warning 模型质量很重要
**Agentic 工具调用需要高质量模型才能可靠工作。** 虽然小型本地模型在技术上可能支持函数调用，但它们通常难以完成多步骤工具使用所需的复杂推理。为获得最佳结果，使用前沿模型如 **GPT-5**、**Claude 4.5 Sonnet**、**Gemini 3 Flash** 或 **MiniMax M2.5**。小型本地模型可能产生格式错误的 JSON 或无法遵循 Agentic 行为所需的严格状态管理。
:::

#### 为什么使用 Native 模式（Agentic 模式）？ {#why-use-native-mode-agentic-mode}
- **速度与效率**：避免大量基于提示的工具选择，延迟更低。
- **KV 缓存友好**：工具定义作为结构化参数发送（而不是注入提示中），因此不会使轮次间的 KV 缓存失效。这可以显著降低延迟和令牌成本。
- **可靠性**：遵循工具模式的准确性更高（使用质量模型）。
- **多步骤链接**：对于需要连续调用多个工具的 **Agentic Research** 和**交错思考**至关重要。
- **自主决策**：模型可以决定何时搜索、使用哪些工具以及如何组合结果。
- **系统工具**：只有 Native 模式才能解锁[内置系统工具](#built-in-system-tools-nativeagentic-mode)（记忆、笔记、知识、频道等）。

#### 如何启用 Native 模式（Agentic 模式） {#how-to-enable-native-mode-agentic-mode}

Native 模式是**默认值**，因此新模型和现有模型都会使用它，除非明确设置为 Legacy。你仍然可以在以下层级显式设置 `Function Calling`（以固定为 Native，或将某个模型切换为 Legacy）：

1.  **为所有模型固定 Native（可选，因为 Native 已经是默认值）**：
    *   导航到 **设置 → 模型**（管理员区域）。
    *   点击模型列表顶部的 **模型默认值** 按钮。这会打开**全局模型参数**，它适用于实例中的*每个*模型（当前和未来），除非特定模型覆盖它们。
    *   在 **模型参数**下，将 **函数调用** 设置为 `Native`。
    *   保存。这只会重申既有的默认值；通常你无需设置它。只有在希望显式固定该值而不是依赖默认值时才使用它。
2.  **按模型覆盖**：
    *   在 **设置 → 模型**（管理员区域）中，选择特定模型并点击其编辑按钮。
    *   打开 **高级参数** 一行，将 **函数调用** 设置为 `Native`。此值仅覆盖该模型的全局默认值。
    *   当特定模型需要不同参数时使用此选项——否则优先使用全局设置。
3.  **按对话覆盖**：
    *   在对话中，打开消息输入框旁的 **模型控件** 菜单并展开 **控件**。
    *   在 **高级参数** 下，将 **函数调用** 设置为 `Native`。仅适用于该对话。

:::tip 一次性、全局地设置任意参数
**设置 → 模型**（管理员区域） 中的 **模型默认值** 可一次性为每个模型（当前和未来）设置任意模型参数（`function_calling`、temperature、top_p、max_tokens 等），除非特定模型覆盖它。对应的环境变量是 `DEFAULT_MODEL_PARAMS`（参见[如何将所有模型切换到 Legacy 模式](#enable-legacy-for-all-models)）。
:::
#### 工具调用标签 {#tool-call-labels}

已完成的工具调用会在对话中显示为 **查看来自** 加工具名称。在 **设置 > 界面**（管理员区域） 中开启 **工具调用标签**（[`ENABLE_TOOL_CALL_LABELS`](/reference/env-configuration#enable_tool_call_labels)），可以让模型用用户的语言为每次调用写一段简短标签：调用进行中显示一个，完成后再显示一个。Open WebUI 会为每个工具添加一个必需的 `__labels__` 参数，并在工具运行前将其移除。隐藏的工具以及参数不是纯 JSON 对象的工具仍使用默认行。

#### 模型要求与注意事项 {#model-requirements--caveats}

:::tip 最低模型档位（并非持续维护的清单）
可靠的 Agentic 工具调用需要的是一个*当前*的模型，而不一定是前沿模型。下面这些都是一个可靠的**下限**：

- **GPT-5.6 Luna** (OpenAI)：便宜、快速且工具调用能力强
- **Gemini 3.5 Flash-Lite** 或 **Gemini 3.1 Flash-Lite** (Google)
- **MiniMax M3**
- **DeepSeek V4 Flash**
- **Muse Glimmer 30B** 或 **Qwen 3.6 27B**（本地，开放权重）

**这份清单不会持续更新。** 请使用你的服务商当前提供的任何模型。
:::

- **能力足够的本地模型**：为 Agentic 工作而生的开放权重模型（如 **Muse Glimmer 30B**、**Qwen 3.6 27B**、**Gemma 4 12B**、**gpt-oss 120B**）与 Native 模式配合良好。Muse Glimmer 尤其出色：Apache 2.0 许可，单张 24 GB 显卡即可稳定运行 Agentic 循环，是本地工具调用的一个不错的默认选择。
- **小型本地模型**：小型本地模型（约 30B 参数以下）即使在 Native 模式下，也经常输出格式错误的 JSON，或无法完成多步骤工具链。**正确的解决方法是为工具调用场景使用更强的模型**，而不是退回到 Legacy 模式——Legacy 已属遗留方案且不再受支持。如果你的硬件条件迫使你使用小模型，就需要接受该层级下工具调用不稳定的现实，或只把需要调用工具的对话卸载给云端模型。

#### 已知的模型特定问题 {#known-model-specific-issues}

:::caution DeepSeek V3.2 的函数调用问题
**DeepSeek V3.2** 在原生函数调用方面存在已知问题，并且会导致**可稳定复现的失败**。尽管它是 600B+ 参数级别的大模型，却经常输出格式错误的工具调用。

**问题根源**：DeepSeek V3.2 在训练时使用了一种名为 **DSML（DeepSeek Markup Language）** 的专有工具调用格式。使用原生函数调用时，模型有时会输出原始 DSML/XML 风格语法，而不是标准 JSON：
- `<functionInvoke name="fetch_url">`，而不是合法的 JSON
- 内容中出现 `<function_calls>` / `</function_calls>` 标签
- 类似 `prominentfunction_cinvoke name="search_parameter` 的乱码混合文本

**为什么会这样**：这是一种高度**依赖模型本身**的行为，由 DeepSeek 的微调过程引入。DeepSeek 选择让模型学习 DSML，而不是标准 OpenAI 风格的 JSON 工具调用。尽管一些推理服务商（如 VertexAI、OpenRouter 等）会尝试拦截 DSML 片段并转换成 OpenAI 风格 JSON，但在某些条件下（流式输出、高温度、高并发、多轮对话）这层转换并不可靠。**主要责任在 DeepSeek**，因为它采用了需要脆弱翻译层支撑的非标准格式。

**已知诱因**：
- 较高的 temperature 往往会带来更多格式错误输出
- 多轮对话（6-8 轮以上）可能导致模型完全停止调用函数
- 复杂的多步骤工作流（15-30 次工具调用）可能导致“schema drift”，即参数格式逐渐劣化

**临时规避方案**：
- **为 Agentic 工作负载换用其他模型。** Claude 4.5 Sonnet、GPT-5、Gemini 3 Flash 和 MiniMax M2.5 在 Native 模式下都更可靠，是 DeepSeek V3.2 表现异常时的推荐替代。
- 在 DeepSeek V3.2 上使用工具调用时，适当降低 temperature。
- 限制多轮工具调用会话的长度。

即使针对 DeepSeek，Legacy 模式**也不是**受支持的规避方案——它已是遗留模式，未来也不会为此扩展支持。这是 DeepSeek 模型/API 的问题，而不是 Open WebUI 的问题。Open WebUI 已按标准 OpenAI 格式正确发送工具定义；格式错误输出源自 DeepSeek 内部的非标准 DSML 格式。
:::

| 特性 | Legacy 模式（遗留 / 不受支持） | Native 模式（唯一受支持的模式） |
|:---|:---|:---|
| **状态** | ❌ 遗留模式，已不再支持 | ✅ 必需 —— 所有模型都应使用它 |
| **延迟** | 中 / 高 | 低 |
| **KV 缓存** | ❌ 每轮都会破坏缓存 | ✅ 对缓存友好 |
| **模型兼容性** | 任意文本模型（已不再重要） | 2024 年以来的所有主流模型 |
| **执行逻辑** | 由 Open WebUI 解析提示注入 | 由提供商 API 处理结构化工具调用 |
| **系统工具** | ❌ 不可用 | ✅ 完整访问（Memory、Notes、Knowledge、Channels、Web Search、Image Gen、Code Interpreter） |
| **Agentic Research / 交错思考** | ❌ 不支持 | ✅ 支持 |
| **复杂链式调用** | ⚠️ 不可靠 | ✅ 表现优秀 |
| **未来开发方向** | ❌ 无 | ✅ 所有新功能都只面向此模式 |

#### Native 模式下的畸形工具调用 {#malformed-tool-calls-in-native-mode}

Open WebUI 在执行调用前会修复常见的参数问题：

- 被代码块包裹、被双重编码或写成 Python 字面量的参数都会被接受。
- 文本值会转换为工具 schema 中声明的类型，例如 `"5"` 转换为 `5`，`"true"` 转换为 `true`。
- 非 MCP 工具未声明的参数会被丢弃。
- 粘合在同一组参数中的多次调用会被拆分成独立调用。
- 只由可用工具的 `<tool_call>` 或 `<function=...>` 块组成的回复会作为工具调用执行。与其他文本混合的此类标记仍按纯文本处理。

出现以下情况时循环会停止：

- 模型重复了连续两次失败的调用（相同工具、相同参数）。重复调用会返回错误，并要求模型基于已有结果作答。
- 回复被截断，例如触发 token 上限或内容过滤器。其中的工具调用不会执行。
- 达到迭代上限（[`CHAT_RESPONSE_MAX_TOOL_CALL_ITERATIONS`](/reference/env-configuration#chat_response_max_tool_call_iterations)）。模型会在不使用工具的情况下给出最终答案。

对话历史中较早的、参数无法读取的工具调用，会以空参数发送给 Ollama。

### 工具审批 {#tool-approval}

默认情况下，模型一旦发起工具调用就会立即执行。管理员可以在 **设置 > 界面**（管理员区域） 中开启 **工具权限**（[`ENABLE_TOOL_PERMISSIONS`](/reference/env-configuration#enable_tool_permissions)）来提供更多模式。该功能为**实验性**功能，默认关闭。

开启后，对话输入框的 **+** 菜单会新增 **工具权限** 项，包含两种选择；开启 **自动权限** 时则包含三种：

| 模式 | 行为 |
| :--- | :--- |
| **完全访问**（未提供 **自动** 时的默认项） | 工具调用会立即执行，一如既往。 |
| **请求审批** | 回复会在第一次工具调用处暂停。待处理的调用会在消息中显示 **允许** 和 **拒绝**，只有在你作答后模型才会继续。等待期间，对话侧边栏中的条目会显示一个黄色圆点并标注 **等待审批**。如果模型一次请求了多个工具，你需要逐个批准，其余的按顺序等待。 |
| **自动** | 每个工具调用都会对照审批策略进行检查。需要审批的调用会像 **请求审批** 一样等待 **允许** 或 **拒绝**，其余则立即执行。没有选择模式的用户将获得 **自动**。 |

你也可以用键盘作答：**允许工具调用**（`Cmd+Alt+Enter`）和 **拒绝工具调用**（`Cmd+Alt+Backspace`），两者都可在[快捷键](/features/chat-conversations/chat-features/keyboard-shortcuts)中重新绑定。

你的选择会保存到用户设置中，因此会延续到新的对话，直到你改回为止。它也会存储在该对话上，所以重新打开该对话时会保留其模式。被拒绝的调用会作为错误反馈给模型以便其作出反应，同时该工具调用会在消息中被标记为已拒绝。对等待审批的回复按下 **停止** 会将其定稿，并拒绝所有仍待处理的调用。

**频道**回复始终以完全访问运行，且频道对话中无法选择 **自动**。**自动化**没有选定的模式，因此在提供 **自动** 时以 **自动** 运行，否则以完全访问运行。“询问用户”工具提出的问题永远不需要审批。

#### 自动 {#auto}

管理员在 **设置 > 界面**（管理员区域） 的 **工具权限** 下方开启 **自动权限**（[`ENABLE_TOOL_PERMISSIONS_AUTO`](/reference/env-configuration#enable_tool_permissions_auto)），并选择决定哪些调用需要审批的 **引擎**：

| 设置 | 默认值 |
| :--- | :--- |
| **引擎**（[`TOOL_PERMISSIONS_AUTO_ENGINE`](/reference/env-configuration#tool_permissions_auto_engine)） | **默认** |
| **审批策略**（[`TOOL_PERMISSIONS_AUTO_PROMPT`](/reference/env-configuration#tool_permissions_auto_prompt)） | 空（使用内置策略） |
| **API 基础 URL**（[`TOOL_PERMISSIONS_AUTO_DECISIONS_API_BASE_URL`](/reference/env-configuration#tool_permissions_auto_decisions_api_base_url)） | `https://api.openai.com/v1` |
| **API 密钥**（[`TOOL_PERMISSIONS_AUTO_DECISIONS_API_KEY`](/reference/env-configuration#tool_permissions_auto_decisions_api_key)） | 空 |
| **模型**（[`TOOL_PERMISSIONS_AUTO_DECISIONS_MODEL`](/reference/env-configuration#tool_permissions_auto_decisions_model)） | `gpt-6-luna` |
| **审批阈值**（[`TOOL_PERMISSIONS_AUTO_DECISIONS_THRESHOLD`](/reference/env-configuration#tool_permissions_auto_decisions_threshold)） | `0.5` |

两种引擎都会使用 **审批策略**。后四项设置仅适用于 **决策 API** 引擎。

使用 **默认** 引擎时，由对话模型作出决定。Open WebUI 会把审批策略加入系统提示词，并为每个工具添加一个必需的 `__approval__` 参数，并在工具运行前将其移除。只有当模型在该参数中恰好发送 `{"required": false}` 时，调用才会不经审批直接执行；其他任何情况（包括完全省略）都会请求审批。参数不是纯 JSON 对象的工具，或自行定义了 `__approval__` 参数的工具，不会获得 `__approval__` 参数，因此它们的调用始终会请求审批。在[旧版模式](#legacy-mode-prompt-based)中，没有任何工具会获得该参数，因此每次调用都会请求审批。决定随调用一同返回，所以该引擎无需额外服务。由于对话模型评判自己的调用，能够引导模型的内容（例如工具结果中的指令）同样会影响它的决定。

使用 **决策 API** 引擎时，Open WebUI 会在每次工具调用时向 `<API 基础 URL>/decisions` 发送一个 `POST` 请求，其中包含 **模型**、审批策略、你最近的请求和最后四条消息、工具的定义和名称、调用的参数，以及工具类型和开放终端 ID。该服务会返回这次调用需要审批的概率。当该概率达到或超过 **审批阈值** 时，调用会请求审批。当审查服务在 5 秒内没有响应、失败或返回无效结果时，调用也会请求审批；当 **审批阈值** 不是 0 到 1 之间的数字时同样如此；当除模型和审批策略之外的数据超过 64 KB 时也会如此。审查服务必须实现与[工具搜索](#tool-search) **决策 API** 引擎相同的 `/decisions` 端点。

[工具搜索](#tool-search)中的 `search_tools` 调用不会经过审查。如果关闭 **自动权限**，此前使用 **自动** 的对话会切换为 **请求审批**。

:::info 已保存的对话与临时对话
在已保存的对话中，待处理的调用会存储在助手消息上，因此审批提示在刷新页面后依然存在。在[临时对话](/features/chat-conversations/chat-features/url-params#8-temporary-chat-sessions)中，每次调用都会打开一个实时的 **工具权限** 对话框，显示工具名称及其参数，并提供 **允许** 和 **拒绝**。当标签页中打开的并非该对话时，调用会立即被拒绝。浏览器标签页关闭、或 120 秒内无人应答时也会被拒绝；若 [`WEBSOCKET_EVENT_CALLER_TIMEOUT`](/reference/env-configuration#websocket_event_caller_timeout) 设置得更低，则以该值为准。
:::

### 工具搜索 {#tool-search}

启用大量工具后，仅工具定义就可能占据每个请求的很大一部分。**工具搜索** 会把庞大的工具定义排除在请求之外，直到模型主动索取。该功能为**实验性**功能，默认关闭，仅适用于原生模式下的对话。

管理员在 **设置 > 界面**（管理员区域） 的 **对话** 部分开启它。这些设置适用于所有模型和所有用户：

| 设置 | 默认值 | 作用 |
| :--- | :--- | :--- |
| **工具搜索**（[`ENABLE_TOOL_SEARCH`](/reference/env-configuration#enable_tool_search)） | 关闭 | 开启该功能。开启后才会出现下面的设置。 |
| **搜索引擎**（[`TOOL_SEARCH_ENGINE`](/reference/env-configuration#tool_search_engine)） | **BM25** | 搜索如何匹配到被延迟的工具：**BM25**、**嵌入** 或 **决策 API**。参见[搜索引擎](#search-engines)。 |
| **延迟内置工具**（[`TOOL_SEARCH_DEFER_BUILTIN_TOOLS`](/reference/env-configuration#tool_search_defer_builtin_tools)） | 开启 | 把内置工具与其他工具同等对待。关闭后始终完整发送内置工具。 |
| **延迟阈值（字符数）**（[`TOOL_SEARCH_DEFER_THRESHOLD`](/reference/env-configuration#tool_search_defer_threshold)） | `400` | 定义（名称、描述和参数 schema，以 JSON 表示）超过该字符数的工具会被延迟。设为 `0` 会延迟所有工具。 |
| **始终加载的工具**（[`TOOL_SEARCH_ALWAYS_LOADED`](/reference/env-configuration#tool_search_always_loaded)） | 空 | 以逗号分隔的工具名称或通配模式，例如 `jira_create_issue, github_*`，这些工具始终完整发送。匹配区分大小写。 |

![设置 > 界面中的对话部分（管理员区域），已开启工具搜索，延迟内置工具，延迟阈值（字符数）设为 400，始终加载的工具为空](/images/features/plugin/tools/tool-search-settings.webp)

工作原理：

- **哪些工具会被延迟。** 每次请求都会检查为该对话启用的所有工具：工作区工具、MCP 与 OpenAPI 工具服务器、开放终端工具以及内置工具。当工具定义长于阈值且不匹配任何始终加载模式时，它会被延迟。内置工具只在开启 **延迟内置工具** 时才会被延迟。较小的工具照常完整发送，而没有任何工具符合条件时，请求会与之前完全一样发送。
- **模型看到什么。** 系统提示词末尾会有一段简短的 `<available_tools>` 指令，告诉模型用 `search_tools` 查找工具。它不会列出被延迟的工具。工具列表中会新增两个内置工具：`search_tools` 和 `call_tool`。
- **模型如何加载工具。** 模型用若干关键词或确切的工具名调用 `search_tools`，并可附带可选的 `count`（默认 `5`，最多 `20`）。它会拿回最佳匹配项的完整定义。传入确切工具名时只返回该工具；否则每个被延迟的工具会按所选搜索引擎排序。要运行找到的工具，模型调用 `call_tool` 并传入 `calls` 数组。每一项包含 `tool_name`（工具的确切名称）和 `params`（以 JSON 编码对象字符串表示的工具参数），例如 `call_tool(calls=[{"tool_name": "get_weather", "params": "{\"city\":\"Dubai\"}"}])`。一次 `call_tool` 调用可以运行多个彼此独立的工具。Open WebUI 会把每一项都当作模型直接调用了该工具来执行，因此审批、结果、引用和对话显示都按工具分别进行。
- **提示词缓存。** 通过搜索加载工具时，发送给服务商的工具列表保持不变。工具列表和 `<available_tools>` 块只会在启用的工具集合发生变化时才改变，因此缓存的前缀可以在多轮工具调用和多轮对话中保持有效。参见[提示词缓存](/features/chat-conversations/prompt-caching)。
- **工具审批。** 开启 **请求审批** 时，`search_tools` 会像其他工具一样请求审批，因此使用一个被延迟的工具通常需要两次审批：一次用于搜索，一次用于工具本身。在 **自动** 下，`search_tools` 不经过审查。`call_tool` 调用所运行的每个工具都会以其自身名称单独审批。
- **后端支持。** 模型发起的每次调用都会进入发送给服务商的工具列表中的某个工具，因此工具搜索在只接受对已列出工具调用的后端上同样有效，例如 OpenAI API（Chat Completions 和 Responses 两种）、xAI 以及 llama.cpp 服务器。

2. **或者为该模型禁用 Native Function Calling**，恢复自动 RAG 注入。
3. **或者把附件切换为“全文上下文”模式**（点击附件并选择 “Use Entire Document”），这样会始终直接注入全文内容。

详情参见 [Native Function Calling 下的知识范围控制](/features/workspace/knowledge#scoped-access-keeps-things-organized)。
:::

**为什么要使用这些工具？** 因为它们能支持 **深度研究**（多次搜索网页或反复查询知识库）、**上下文感知**（查阅历史对话或笔记）、**动态个性化**（保存事实）以及 **精确自动化**（基于既有笔记或文档生成内容）。

#### 搜索引擎 {#search-engines}

| 引擎 | 排序方式 |
| :--- | :--- |
| **BM25**（默认） | 将查询与每个工具的名称、描述和参数名做关键词匹配。 |
| **嵌入** | 使用[文档](/features/chat-conversations/rag)嵌入模型计算查询与每个工具定义之间的相似度。工具嵌入按 worker 在内存中缓存（总计最多 2048 条，按用户分别保存），不做持久化。重启后或嵌入模型变更时会重新计算。 |
| **决策 API** | 由服务为每个工具与查询的相关性打分。达到或超过 **相关性阈值**（[`TOOL_SEARCH_DECISIONS_THRESHOLD`](/reference/env-configuration#tool_search_decisions_threshold)，默认 `0.5`）的工具会被返回，相关性高的排在前面。 |

**决策 API** 引擎拥有自己的 **API 基础 URL**（[`TOOL_SEARCH_DECISIONS_API_BASE_URL`](/reference/env-configuration#tool_search_decisions_api_base_url)，默认 `https://api.openai.com/v1`）、**API 密钥**（[`TOOL_SEARCH_DECISIONS_API_KEY`](/reference/env-configuration#tool_search_decisions_api_key)）、**模型**（[`TOOL_SEARCH_DECISIONS_MODEL`](/reference/env-configuration#tool_search_decisions_model)，默认 `gpt-6-luna`）和 **提示词**（[`TOOL_SEARCH_DECISIONS_PROMPT`](/reference/env-configuration#tool_search_decisions_prompt)，留空表示使用内置指令）。每次搜索都会向 `<API 基础 URL>/decisions` 发送一个 `POST` 请求，其中包含 **模型**、模型的搜索查询，以及每个被延迟工具对应的一个问题（该问题包含 **提示词** 和该工具的定义），按每批最多 400 个工具分批，总计 30 秒内完成。服务会为每个工具返回一个概率。搜索失败时，模型会收到一条错误消息而不是结果。

请针对[模型看到的工具名称](/features/extensibility/mcp#tool-names-the-model-sees)来编写始终加载的模式。MCP 工具带有其服务器 ID 作为前缀（服务器 ID 为 `github` 的 `get_issue` 工具名为 `github_get_issue`），因此 `github_*` 会让该服务器的所有工具保持加载。

#### 对话附带文件 {#attached-chat-files}

**文件** 类别是把上传文件的文本直接放进提示词之外的智能体式替代方案。只有当模型上传了文件但 **预加载文件** 关闭时，它才会被注入。开启 **预加载文件** 时，内容已经存在于对话中，工具就会显得多余，而且仅在该对话确实带有附件时才有意义。

随后模型会像处理知识库那样处理这些文件：用 `list_chat_files` 查看有哪些文件，用 `query_chat_files` 查询含义，用 `grep_chat_files` 查找字面字符串和行号，用 `view_file` 阅读段落。`query_chat_files` 返回的文本块会像知识库结果一样渲染为引用。每个文件在被读取前仍会对照用户自身的访问权限重新检查，因此用户已无法打开的附件会被跳过，而不会被检索。
#### 工具结果中的图片 {#images-in-tool-results}

工具除了返回文本也可以返回图片，`generate_image` 和 `edit_image` 就是如此，自定义工具同样可以。图片以何种方式送达模型取决于服务商：

- 在 **Responses API** 上，图片随工具结果一起返回，位置恰到好处。
- 在 **Chat Completions** 上，工具消息只能携带文本。因此图片会被拆分出来：工具结果以纯文本形式送达，随附的图片则通过一条简短的用户消息跟进，交给模型分析。

这样一来，运行在 Chat Completions 服务商上的模型就能真正看到工具产出的内容，先生成一张图片再对它点评或编辑，而不是收到一个打不开的结果。对话中不会额外显示任何内容；这些图片本来就已经从工具结果中渲染出来了。

快速规则：`list_knowledge` 和 `list_knowledge_bases` 是互斥的。

"附加的知识"不只是模型自身携带的那些。上面的矩阵会把以下三个来源汇总、去重，并一视同仁地处理：

- 在模型编辑器中附加给模型的知识；
- 附加到该对话所属[文件夹](/features/chat-conversations/chat-features/conversation-organization)的知识；
- 附加到对话本身的知识库和笔记——只有在模型的 **预加载文件** 能力关闭时才会计入，因为开启时内容已经在对话里了。

[范围访问](/features/workspace/knowledge#scoped-access-keeps-things-organized)解释了原因，以及如何选择模型获得哪些内容。

当 **知识库** 类别已启用且上述内容存在时，用户消息之后会附带一条隐藏的 `list_attached_knowledge` 工具结果，其中包含一个 `<attached_knowledge>` 块，列出每一项的类型、ID 和名称，以及它来自模型还是文件夹。对话附件不会被列出，因为每条用户消息本身都会指明自己的附件。如果没有任何附加内容，或回复是延续上一轮，该结果会被跳过。这只是一份目录而不是内容本身：它告诉模型可以取用哪些东西，并把 ID 提供给 `list_knowledge` 和 `search_knowledge_files` 等工具，使模型能够翻页或搜索某个知识库。

:::info 启用后 `kb_exec` 会取代这张矩阵
设置 [`ENABLE_KB_EXEC`](/reference/env-configuration#enable_kb_exec) 后，Open WebUI 会用 `kb_exec` 取代上面列出的面向文件的工具。仍然与它一同注入的有：`query_knowledge_files` 和 `display_file`（始终注入）、`view_note`（附加了笔记时），以及 `query_knowledge_bases` + `search_knowledge_bases`（什么都没附加时）。模型通过熟悉的 shell 命令与文件交互。详情参见[知识功能页面](/features/workspace/knowledge#filesystem-style-access-kb_exec)。
:::

在 `view_file` 和 `view_knowledge_file` 的按行模式中，只给 `end_line` 而不给 `start_line` 时从第 1 行开始读取；只给 `start_line` 而不给 `end_line` 时返回 100 行。行范围会在最后一整行能装进 [`VIEW_FILE_MAX_CHARS`](/reference/env-configuration#view_file_max_chars) 的位置停下（行号前缀也计入长度）。此时响应中会带有 `truncated: true` 和 `next_start_line`，可据此继续读取。开启 `line_numbers` 的按字符分页会保证每个字符恰好出现一次：逐页跟随 `next_offset` 即可无缝读完整个文件。

:::warning 在附加笔记的对话中，内置工具的行为有所不同

从笔记打开的对话是一种类型为 `note` 的内部对话，内置工具在那里的门控规则不同。有两项独立的覆盖规则生效：

**笔记工具始终注入。** 无论 `notes.enable` 配置、模型的 **Notes** 类别以及用户的 `features.notes` 权限如何，`search_notes`、`view_note`、`write_note` 和 `replace_note_content` 都会加载。通过这三项控制中的任意一项关闭笔记，都不会在那种对话中移除它们。

**整个内置工具集合被强制启用。** 笔记对话会激活内置工具，即使按常规判断本次请求并不满足条件：没有 UI 会话、`function_calling` 被设为 legacy，**甚至当模型的 `builtin_tools` 能力被关闭时也是如此**。因此，一个管理员刻意配置为不使用内置工具的模型，在笔记对话中仍然会收到这些工具（记忆、网页搜索、代码解释器、图像生成等，仍受各自类别的门控约束）。如果你依赖该能力开关来阻止模型使用工具，那么在这个特定场景中它并不起作用。

另外，`view_note` 和 `replace_note_content` **对管理员绕过了访问控制**：管理员可以读取或改写任何笔记，无需经过其他用户必须遵守的所有者或授权检查。这与管理员在其他地方相当于 root 的定位一致，但如果你依赖的是之前的行为（管理员也和其他人一样被检查），需要注意这一点。

笔记附件同样会被注入：用户当前打开页面上的每个文件，都会作为检索上下文加入该对话中的**每一条**消息。

:::

:::info 自动时区检测
Open WebUI 在你登录时自动检测并存储你的时区。这允许与时间相关的工具和功能提供准确的本地时间，无需任何手动配置。你的时区由浏览器设置确定。
:::

:::warning 知识工具注入取决于附件
知识工具的可用性根据知识是否附加到模型、文件夹或对话而变化。使用上面的**知识工具可用性**矩阵作为参考依据。

- 有附件时：模型获得范围限定的知识工具。
- 无附件时：模型获得知识库发现工具。
- `list_knowledge` 和 `list_knowledge_bases` 是互斥的。
:::

:::caution 附加的知识仍然需要用户访问权限
将知识库或笔记附加到自定义模型**不会**绕过访问控制。当用户与模型聊天时，`query_knowledge_files` 会检查**该特定用户**是否有权访问每个附加的知识库和笔记。用户无法访问的项目会被静默排除在搜索结果之外。单个文件则不同：直接附加到模型的文件会与所有能使用该模型的人共享，并且模型作者在附加时必须能够读取它。

**按知识类型的访问要求：**

| 附加类型 | 用户所需权限 |
|---------------|-----------|
| **知识库** | 所有者、管理员，或显式的读取访问授权 |
| **单个文件** | 任何能使用该模型的人（附加时会以模型作者的身份校验） |
| **笔记** | 所有者、管理员，或显式的读取访问授权 |

**示例场景**：管理员创建一个私密知识库，并把它附加到一个与所有用户共享的自定义模型上。普通用户与该模型聊天时，`query_knowledge_files` 会返回**空结果**，因为他们没有该知识库本身的读取权限——尽管他们可以使用这个模型。

**解决方案**：确保需要访问模型知识的用户，同时对底层知识库拥有读取权限（通过访问授权或知识设置中的群组权限）。
:::

:::info 推荐的 KB 工具工作流
**有附加知识时：**
1. 首先调用 `list_knowledge` 发现附加的 KB、文件和笔记
2. 使用 `query_knowledge_files` 搜索文件内容（自动范围限定为附件）
3. 使用 `view_file` 或 `view_knowledge_file` 读取特定文件；对大文件使用 `offset` 和 `max_chars`

**无附加知识时：**
1. 首先调用 `list_knowledge_bases` 发现可用的知识
2. 然后使用 `query_knowledge_files` 在相关 KB 中搜索文件内容
3. 如果仍然为空，文件可能尚未嵌入，或者你可能启用了**始终使用全文**（它会绕过向量存储）

**不要将始终使用全文或使用整篇文档与知识工具一起使用。** 全文会直接注入文件内容且不存储嵌入，因此 `query_knowledge_files` 将返回空。基于工具的访问请使用聚焦检索（默认）。
:::

:::tip 知识库工具和混合搜索
当在管理设置中启用 `ENABLE_RAG_HYBRID_SEARCH` 时，原生 `query_knowledge_files` 工具使用**混合搜索 + 重排序**，为你提供与标准 RAG 管道相同的搜索质量。当混合搜索禁用时，它回退到简单的向量搜索。
:::

:::warning Native 模式下知识不会自动注入
**重要：** 使用 Native 函数调用时，附加知识**不会自动注入**到对话里。模型必须主动调用知识工具来搜索并检索信息。

**如果你的模型没有使用附加知识：**
1. **在系统提示词中加入明确指令**，要求模型先发现再查询知识库。例如：*“当用户提问时，先使用 list_knowledge 查看可用知识，再用 query_knowledge_files 搜索相关知识库后再回答。如果该模型未附加知识，请先调用 list_knowledge_bases 来发现可用 KB。”*
2. **或者为该模型关闭 Native 函数调用**，恢复自动的 RAG 注入行为。
3. **或者在聊天中以"使用整篇文档"模式附加一个小文档**（点击附件并切换其模式），同时开启模型的 **预加载文件** 能力，这样会注入其完整内容。附加到模型或文件夹上的知识在原生模式下永远不会被注入。

更多细节请参见[使用原生函数调用时的知识限定范围](/features/workspace/knowledge#scoped-access-keeps-things-organized)。
:::

**为什么要用这些工具？** 它们可以带来**深度研究**（多次搜索网页或查询知识库）、**上下文感知**（查阅之前的对话或笔记）、**动态个性化**（保存事实）以及**精确自动化**（基于已有笔记或文档生成内容）。

#### 禁用内置工具（按模型） {#disabling-builtin-tools-per-model}

**Builtin Tools** 能力可以在 **Workspace > Models** 编辑器的 **Capabilities** 区域按模型开启或关闭。启用时（默认状态），使用 Native 模式会自动注入上面列出的所有系统工具。

**何时适合禁用 Builtin Tools：**

| 场景 | 禁用原因 |
|----------|-------------------|
| **模型不支持函数调用** | 较小的或较老的模型可能无法正确处理 `tools` 参数 |
| **需要更简单 / 可预期的行为** | 希望模型只使用预注入的上下文，不进行自主工具调用 |
| **出于安全 / 管控考虑** | 防止模型主动查询知识库、搜索聊天记录、访问记忆等 |
| **节省 token** | 工具定义会消耗 token；禁用后可以节省上下文窗口空间 |

**禁用 Builtin Tools 后会发生什么：**

1. **不注入工具**：即使在 Native 模式下，模型也不会收到任何内置系统工具。
2. **RAG 仍然有效**（前提是启用了预加载文件）：附加的文件仍会经过 RAG 处理并作为上下文注入。
3. **无法自主检索**：模型不能自行决定搜索知识库或获取额外信息；它只能使用预先提供的内容。
#### 细粒度内置工具分类（按模型） {#granular-builtin-tool-categories-per-model}

当 **Builtin Tools** 能力已启用时，你还可以进一步控制模型可用的内置工具**类别**。在模型编辑器中，这会显示为 **Builtin Tools** 下的一组开关，每个类别一个。

![模型编辑器中的内置工具类别](/images/features/plugin/tools/builtin_tools.png)

| 类别 | 包含的工具 | 说明 |
|----------|----------------|-------------|
| **时间与计算** | `get_current_timestamp`、`calculate_timestamp` | 获取当前时间并进行日期 / 时间计算 |
| **询问用户** | `ask_user` | 暂停回复，向用户提出一个澄清问题 |
| **记忆** | `search_memories`、`list_memory_paths`、`read_memory_path`、`list_memories`、`update_memory`、`add_memory`、`replace_memory_content`、`delete_memory` | 搜索并管理用户记忆 |
| **聊天历史** | `search_chats`、`view_chat` | 搜索并查看用户的聊天历史 |
| **笔记** | `search_notes`、`view_note`、`write_note`、`replace_note_content` | 搜索、查看并管理用户笔记 |
| **知识库** | `list_knowledge`、`list_knowledge_bases`、`search_knowledge_bases`、`query_knowledge_bases`、`search_knowledge_files`、`query_knowledge_files`、`grep_knowledge_files`、`view_file`、`view_knowledge_file`、`display_file`，附加了笔记时还有 `view_note`（或启用 [`ENABLE_KB_EXEC`](/reference/env-configuration#enable_kb_exec) 后按需使用 `kb_exec` + `query_knowledge_files` + `display_file` + `view_note`/`query_knowledge_bases`/`search_knowledge_bases`） | 浏览并查询知识库 |
| **网页搜索** | `search_web`、`fetch_url` | 搜索网页并抓取 URL 内容 |
| **图像生成** | `generate_image`、`edit_image` | 生成和编辑图像 |
| **代码解释器** | `execute_code` | 在沙箱环境中执行代码 |
| **频道** | `search_channels`、`search_channel_messages`、`view_channel_message`、`view_channel_thread` | 搜索频道和频道消息 |
| **任务管理** | `create_tasks`、`update_task` | 创建结构化的任务 / 待办清单，并在当前对话中更新单个任务的状态 |
| **自动化** | `create_automation`、`update_automation`、`list_automations`、`toggle_automation`、`delete_automation` | 在对话中创建并管理定时自动化 |
| **日历** | `search_calendar_events`、`create_calendar_event`、`update_calendar_event`、`delete_calendar_event` | 搜索、创建、更新和删除日历事件 |
| **技能** | `view_skill`、`read_skill_file`、`grep_skill_files`、`update_skill_files`、`create_skill` | 查找、读取、搜索、编辑和创建技能 |
| **工具创建** | `create_tool` | 在对话中创建 Python 工作区工具。需要 [`ENABLE_TOOLS`](/reference/env-configuration#enable_tools)，非管理员还需要 **Tools Access** 权限 |

所有类别**默认启用**。禁用某个类别后，该类别下的工具不会被注入，其他类别仍然保持可用。

:::info 技能
当该对话的内置工具处于启用状态，且模型的 **Skills** 类别已打开时：

1. 为对话选中的技能会在模型回答之前加载，每个对话只加载一次，形式是隐藏的 `view_skill` 结果。每个新对话都会预先选中该模型的技能
2. 模型会通过 `<available_skills>` 标签，在隐藏的 `list_available_skills` 工具结果中收到**用户可读的每个生效技能**的摘要（名称 + 描述），其中包括未附加到模型的技能，以及用户在对话中关闭的技能
3. 只要列出了至少一个技能，就会注入 `view_skill`、`read_skill_file` 和 `grep_skill_files`，模型便可按需加载、读取和搜索说明与文件。只要列出了至少一个工作区技能，就会注入 `update_skill_files`，用于编辑用户有权写入的技能；管理员和拥有 Skills Access 权限的用户还会得到 `create_skill`
4. 当用户读不到任何生效技能时，或回复是延续上一轮时，`<available_skills>` 块会被省略

过长的 `SKILL.md` 会在 **技能读取上限** 处截断，模型可以用 `read_skill_file` 继续读取。没有技能工具时，被选中的技能会按其前 100,000 个字符注入。参见[技能](/features/workspace/skills#model-attached-skills)。

:::

**使用细粒度控制的场景：**

| 场景 | 推荐配置 |
|----------|---------------------------|
| **注重隐私的模型** | 禁用记忆和聊天历史，避免访问个人数据 |
| **只读助手** | 禁用笔记（防止创建 / 修改笔记），但保留知识库 |
| **最小化 token 消耗** | 只启用模型真正需要的类别 |
| **以知识为核心的机器人** | 除知识库和时间之外全部禁用 |

:::note
这些类别级开关只会在主 **Builtin Tools** 能力启用时出现。如果你完全关闭 Builtin Tools，那么无论类别设置如何，都不会注入任何工具。
:::

:::info 全局功能开关优先
启用某个模型级类别开关**不会**覆盖全局功能开关。比如，如果 `ENABLE_NOTES` 在全局（管理面板）被关闭，那么即便模型启用了 "Notes" 类别，笔记工具也仍然不可用。模型级开关只能在已可用的基础上**进一步收紧**，不能开启全局已禁用的功能。
:::

:::warning 用户级权限同样生效
凡是对应某个 RBAC 功能权限的内置工具，还会受到用户 **Features** 权限的限制。即使某类工具在模型上已启用、全局功能开关也已打开，只要用户缺少相应的 `features.*` 权限，该工具就**不会**被注入。管理员始终通过这些检查。

| 工具类别 | 需要的 `features.*` 权限 |
|---------------|----------------------------------|
| 记忆 | `features.memories` |
| 网页搜索 | `features.web_search` |
| 图像生成 | `features.image_generation` |
| 代码解释器 | `features.code_interpreter` |
| 笔记 | `features.notes` |
| 频道 | `features.channels` |
| 自动化 | `features.automations` |
| 日历 | `features.calendar` |

这确保了 RBAC 权限得到端到端的尊重：为某个用户禁用某项功能，会阻止模型代其调用这些工具，而不只是隐藏界面。

`features.memories` 的影响还不止于工具列表。它同时控制着[记忆系统上下文](/features/chat-conversations/memory#memory-system-context)，因此没有该权限的用户，其提示词中同样不会被注入任何已保存的记忆，无论对话请求如何要求。
:::
:::tip 对话级功能开关（网页搜索、图像生成、代码解释器）
**网页搜索**、**图像生成**和**代码解释器**这三个内置工具还有一层控制：聊天输入栏中的**对话级功能开关**。要在 Native 模式下注入这些工具，必须**同时满足三个条件**：

1. **全局配置已启用**：该功能在管理面板中已打开（例如 `ENABLE_WEB_SEARCH`）
2. **模型能力已启用**：模型在 Workspace > Models 中勾选了相应能力（例如 "Web Search"）
3. **对话级开关已启用**：用户通过输入栏的开关为这个具体对话激活了该功能

这意味着即便某个功能在全局和模型上都已启用，用户仍可按对话关闭网页搜索（或图像生成、代码解释器）。这对于必须保持离线的对话，或想避免意外调用工具的场景非常有用。
:::

:::tip 完整的 Agentic 体验
如果希望用户开箱即拥有完整的 Agentic 体验，管理员可以把**网页搜索**、**图像生成**和**代码解释器**设为某个模型的默认功能。在 **设置 > 模型**（管理员区域） 中点击目标模型的铅笔图标（**编辑**），并在 **Default Features** 下打开这三项。这样它们默认在每个新对话中生效，用户无需逐一手动开启。若有需要，用户仍然可以按对话将其关闭。
:::

:::tip 内置工具与预加载文件的区别
**Builtin Tools** 控制的是模型是否获得用于自主检索的*工具*。它**不**控制文件内容是否通过 RAG 注入——那是由独立的**预加载文件**能力控制的。

- **预加载文件** = Open WebUI 是否提取并注入文件内容（RAG 处理）
- **Builtin Tools** = 模型是否获得可自主搜索 / 检索额外内容的工具

详细对比请参见[预加载文件与内置工具的区别](/features/chat-conversations/rag#preload-files-vs-builtin-tools)。
:::

### 交错思考 {#interleaved-thinking}

使用 **Native 模式（Agentic 模式）** 时，高端模型可以进行**交错思考**。这是一个强大的"思考 → 行动 → 思考 → 行动 → 思考 → ..."循环：模型可以先推理任务，再执行一个或多个工具，评估结果，然后决定下一步。

:::info 需要高质量模型
交错思考要求模型能在多次工具调用之间保持上下文，并能合理地选择工具。当前具备推理能力的模型都能胜任；GPT-5.6、Claude Sonnet 5、Gemini 3.6 Flash 或 MiniMax M3 是一个合理的下限。较老或非常小的模型则不行。
:::

在交错工作流中，模型遵循以下循环：
1.  **推理**：分析用户意图，找出信息缺口。
2.  **行动**：调用工具（例如对内部文档使用 `query_knowledge_files`，或对网络研究使用 `search_web` 和 `fetch_url`）。
3.  **思考**：读取工具输出并更新自己的理解。
4.  **迭代**：如果答案还不清晰，就调用另一个工具（例如用 `view_knowledge_file` 读取特定文档，或用 `fetch_url` 读取特定页面），或者细化搜索。
5.  **定稿**：只有完成这一轮"深度研究"循环后，模型才会给出有依据的最终答案。

正是这种行为把普通聊天机器人变成了能够自主解决复杂多步问题的 **Agentic AI**。

对于长时间运行的工作流，可以把交错的工具使用与 `create_tasks`（提前列出计划）和 `update_task`（随工作推进标记每一步完成）结合起来，让模型能够显式地规划、跟踪进度，并让用户始终清楚下一步该做什么。
