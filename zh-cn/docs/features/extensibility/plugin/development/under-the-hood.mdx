# 🔧 底层机制：插件加载器实际做了什么 {#under-the-hood-what-the-plugin-loader-actually-does}

:::danger 关键安全警告
**Tools、Functions、Pipes、Filters 和 Actions 会在你的服务器上执行任意 Python 代码。** Function 的创建仅限管理员，Workspace Tool 的创建则受 `workspace.tools` 权限管控——授予该权限等同于授予用户对服务器的外壳访问权限。请仅从受信来源安装、导入前审阅代码，并将创建权限限制在受信管理员范围内。恶意插件可能访问你的文件系统、窃取数据，甚至危及整个系统。完整细节请参见 [插件安全警告](/features/extensibility/plugin/)。
:::

Open WebUI 的插件（Tools、Functions = Filters / Pipes / Actions）并不是在某个受限运行时中运行的沙箱脚本。它们是**在你的 Open WebUI 进程中执行的 Python 模块**，对标准库、任何 pip 包、整个 `open_webui` 代码库、实时 FastAPI 应用以及数据库都拥有完全访问权限。文档中列出的钩子（`inlet`、`outlet`、`stream`、`pipe`、`action`）只是利用这种访问权限的*一种*方式，并不是唯一的方式。

本文档会说明加载器实际做了什么，以及这为你打开了哪些可能性——这样你就可以构建（或审计）超出各类型文档中所展示的模式之外的插件。它也会列出这条路上必然踩到的坑。

---

## 插件是如何被加载的 {#how-a-plugin-is-loaded}

[`backend/open_webui/utils/plugin.py`](https://github.com/open-webui/open-webui/blob/main/backend/open_webui/utils/plugin.py) 中有**一个**加载器负责处理所有插件类型：

1. 从数据库读取插件的 Python 源码。
2. 创建一个全新的 `types.ModuleType`，并在加载期间以当前源码版本的唯一名称注册到 `sys.modules`，即 `function_{id}_<32 hex characters>`（或 `tool_{id}_<32 hex characters>`）。这个唯一名称就是插件的 `__name__`，因此 `logging.getLogger(__name__)` 也会用到它。
3. 源码被送入 `exec(content, module.__dict__)`。模块顶层（top level）的任何代码都会在这一刻执行。
4. 加载器会查找**一个**入口点类：`Tools`、`Pipe`、`Filter`、`Action` 或 `Event`。这个类就成为 Open WebUI 调用的句柄。
5. 加载成功后，该模块会以「唯一名称 + 稳定别名 `function_{id}`（或 `tool_{id}`）」的形式发布到 `sys.modules`，同时移除上一个版本的条目。加载失败则不发布任何内容。已发布的模块会一直存在，直到更新的版本替换它或进程重启。第 3 步产生的任何副作用（import、monkey-patch、后台任务、路由注册）都会安装到正在运行的应用中。

入口点类是 Open WebUI 唯一关心的事物。文件中的其他内容都归你自由发挥。

:::tip 读取插件自身的 id
`__name__` 返回的是附带 32 个十六进制字符的 id，因此插件无法从中取得自己的 id。请在处理函数内部改为读取 [`__id__`](./reserved-args.mdx#__id__) 参数（Pipes 不会收到它）。在模块加载时、任何处理函数被调用之前运行的代码，可以自行去掉前缀和后缀，这对新旧两种名称都适用：

```python
import re

PLUGIN_ID = re.sub(r"^(?:function|tool)_|_[0-9a-f]{32}$", "", __name__)
```

:::

### 模块何时被重新执行 {#when-the-module-is-re-executed}

`inlet` / `outlet` 钩子会传 `load_from_db=True`。如果源码没有变化，加载器仍会从缓存中服务调用，但它会在每次调用时都去查询数据库以判断是否需要重新加载。`stream` 钩子则传 `load_from_db=False`，直接从缓存中读取。

| 钩子 | 每次调用都查数据库？ | 何时重新执行模块？ |
|---|---|---|
| `inlet` / `outlet`（Filter） | 是 | 调用之间源码发生变化时 |
| `stream`（Filter） | 否 | 只有当其他钩子重新加载时 |
| Tools、Pipes、Actions | 分发时是 | 调用之间源码发生变化时 |

实际影响：

- **通过编辑器修改 Filter 会在下一次聊天时对 `inlet` / `outlet` 生效。** `stream` 则要等到下一次某个 `inlet` 或 `outlet` 触发重新加载后才会拿到新代码。
- **重新执行并不是按请求进行的**，因此模块顶层的工作只会按内容版本各执行一次，而不是按聊天各执行一次。顶层的 import、patch 和单例都这样做没有问题。
- **禁用或删除插件** 会将其从激活集合中移除，但**不会**撤销其模块顶层所做的任何事情。该模块会继续留在 `sys.modules` 中，而它对其他模块所做的任何 monkey-patch 也会一直保留，直到进程重启才会消失。

## 你实际拥有哪些访问权限 {#what-you-actually-have-access-to}

从任何钩子（以及模块顶层）都可以访问：

- 完整的 `open_webui.*` 包。示例：`from open_webui.models.chats import Chats`、`from open_webui.utils.middleware import process_chat_payload`、`from open_webui.models.config import Config`。
- 通过 `__request__` 拿到实时 FastAPI `Request`，它携带 `__request__.app`（FastAPI 应用）、`__request__.app.state`（配置、缓存、处理器）以及 `__request__.state`（按请求的临时数据）。
- [保留参数](./reserved-args.mdx) 文档中列出的保留双下划线参数：`__user__`、`__metadata__`、`__model__`、`__request__`、`__event_emitter__`、`__event_call__`、`__features__`、`__body__`、`__id__`、`__oauth_token__`，以及仅 stream 可用和按钩子附加的参数。
- [事件](./events.mdx) 中文档化的所有事件：可以向前端发送任意事件，也可以通过 `event_call` 向用户征求响应。
- 通过 `requirements:` 前言（frontmatter）声明的任何 pip 包，会在加载时安装（受 [`ENABLE_PIP_INSTALL_FRONTMATTER_REQUIREMENTS`](/reference/env-configuration#enable_pip_install_frontmatter_requirements) 开关控制）。
- Python 标准库，以及容器中 pip 安装的所有内容。

这里没有沙箱、没有白名单、没有能力（capability）系统。执行模型就是 **"这就是 Python，你在服务器进程里"**。

## 常用模式 {#patterns}

### 1. 在 `inlet` 中修改按请求的 model dict {#1-mutate-the-per-request-model-dict-from-inlet}

你拿到的 `__model__` **就是**本次请求后续流程中读取的那个 dict 对象。在 `inlet` 中修改它的键，会影响本次请求后续管线的行为。示例（针对 DeepSeek / Kimi / MiMo 的 reasoning-content 修复）：

```python
class Filter:
    async def inlet(self, body: dict, __model__: dict = None) -> dict:
        # 把按请求的 model 切换到那条会在原生工具调用循环中
        # 将 reasoning_content 作为 assistant 消息顶层字段
        # 发出的代码路径上。
        if __model__ and __model__.get("provider") not in ("ollama", "llama.cpp"):
            __model__["provider"] = "llama.cpp"
        return body
```

同样的手法也适用于中间件从 model dict 中读取的任何其他字段：`params`、`meta`，以及你自己放进去、然后从另一个钩子里读取的自定义键。

### 2. Monkey-patch 一个后端函数 {#2-monkey-patch-a-backend-function}

因为插件模块可以 `import open_webui.*` 并重新绑定模块属性：

```python
import open_webui.utils.middleware as _mw

_original = _mw.process_chat_payload

async def _patched(request, form_data, user, metadata, model):
    # …… 你的包装逻辑，然后委托给原函数 ……
    return await _original(request, form_data, user, metadata, model)

_mw.process_chat_payload = _patched
```

这段代码会在模块加载时运行（按源码版本各执行一次）。该 patch 会在 `sys.modules` 中持续存在，覆盖进程的整个生命周期。删除或禁用插件**不会**回滚这个 patch。唯一干净的回滚方式是重启进程。

请谨慎使用。跨插件干扰是一个真实存在的风险：如果两个插件 patch 了同一个函数，结果取决于加载顺序，而加载顺序并不是确定性的。

:::tip 先确认 `request` 过滤钩子是否已经够用
人们最初去 patch `generate_chat_completion` 或 `process_chat_payload`，最常见的原因是需要在**每一次**提供商调用时都拿到请求体，而不只是第一次——因为 `inlet` 每个用户轮次只运行一次，永远看不到工具循环的后续调用。[`request` 过滤钩子](/features/extensibility/plugin/functions/filter#the-request-step) 正是作为受支持的钩子提供这一能力的：无需 patch，没有加载顺序隐患，回滚也不需要重启进程。

如果你使用的是 0.11.2+ 并且你的 patch 目的是拦截发往外部的请求体，请把它迁移到 `request` 并删除该 patch。注意，由旧版本插件安装的 patch 会一直存活在加载过它的每个 worker 进程中，因此要真正移除它，仍然需要对整个集群执行一次重启。
:::

### 3. 在加载时添加新的 HTTP 路由 {#3-serve-a-page-or-asset-from-a-route}

```python
from fastapi.responses import HTMLResponse, Response

def _ensure_routes(app):
    if any(getattr(r, "path", None) == "/my/tool" for r in app.routes):
        return  # idempotency guard: the loader may re-exec on edits

    async def page():
        return HTMLResponse(
            "<html><head><link rel=stylesheet href=/my/tool.css></head>"
            "<body><div id=app></div><script src=/my/tool.js></script></body></html>"
        )

    async def script():
        return Response(MY_JS, media_type="application/javascript")

    async def style():
        return Response(MY_CSS, media_type="text/css")

    app.add_api_route("/my/tool", page, methods=["GET"])
    app.add_api_route("/my/tool.js", script, methods=["GET"])
    app.add_api_route("/my/tool.css", style, methods=["GET"])
```

在第一个能拿到 `__request__.app` / `__app__` 的钩子中调用（也可以挂在 `system.startup.completed` 事件上）。幂等性保护很重要：加载器可能会因编辑而重新执行，而 `add_api_route` 会毫无顾虑地把同一条路径注册两次。

`__app__` 是**真正的** FastAPI 应用对象，因此路由可以返回任何 HTTP 能承载的内容：JSON、`HTMLResponse`、JavaScript、CSS、图片，甚至是一整个打包好的 SPA。你可以把自己的独立工具以插件形式发布在自己的 URL 上，**无需重新构建前端**。插件正是用这种方式提供 ToS/同意页面、审批界面、OAuth 回调、状态面板或一键安装界面的。

**不要越过的界线：** 路由是你*自己的*页面。你的页面可以引用你自己的 `/my/tool.js` 和 `/my/tool.css`，它们能正常加载。但它**不会**注入到 Open WebUI 的聊天界面中。注册 `/my/tool.js` 并不会让 Open WebUI 自己的 `index.html` 去加载它；只有当用户访问*你的*路由时，他才会拿到你的资源。

若要把你的 JS/CSS 放进**真正的** Open WebUI SPA 中（例如在真实消息上加一个按钮、给真实应用套一层主题、在真实界面上做首次使用引导），前端就必须引用你的资源。这意味着要在启动时写入 custom-CSS / custom-JS 加载器这一接缝，属于间接且脆弱的路径。要让多个插件都能安全地做到这件事，需要一个专门的资源注入原语来把这个接缝正式化。仅仅注册路由给你带来的是**页面**，而不是**注入**。

:::warning
已注册的路由运行在真实应用上，并且**默认不带鉴权**，除非你自己加上鉴权依赖。你在某个路径上暴露的任何内容，任何能访问该服务器的人都能访问到，因此请显式地对敏感路由加以限制（管理员校验、签名令牌等）。
:::


### 4. 启动一个后台任务 {#4-spawn-a-background-task}

```python
import asyncio

async def _loop(app):
    while True:
        # …… 周期性工作 ……
        await asyncio.sleep(60)

def _start_once(app):
    if getattr(app.state, "_my_plugin_started", False):
        return
    app.state._my_plugin_started = True
    asyncio.create_task(_loop(app))
```

`app.state` 上的标志使其成为"每进程一次"而不是"每源码版本一次"。在干净重启时会重新启动。

### 5. 在 `app.state` 中存放状态 {#5-stash-state-in-appstate}

```python
async def inlet(self, body, __request__):
    cache = __request__.app.state.__dict__.setdefault("my_cache", {})
    # …… 读写缓存 ……
    return body
```

跨请求以及**同一进程中的多个插件**共享。没有命名空间：请取一个唯一的 key。

### 6. 使用 `event_emitter` 在 UI 中实现任意副作用 {#6-use-event\_emitter-for-arbitrary-side-effects-in-the-ui}

`event_emitter` 接受前端能处理的任何事件形态：状态横幅、来源引用、文件附件、聊天消息更新、toast 通知等。你并不局限于各类型文档中列出的那些事件。完整目录请参见 [事件](./events)。

### 7. 在 handler 中途通过 `event_call` 提示用户 {#7-prompt-the-user-mid-handler-with-event\_call}

`event_call` 是会**等待响应**的 `event_emitter`。显示一个表单、一个确认框、一个输入对话框，然后阻塞直到用户作答。在需要人参与的 Tool 方法中、或在执行前需要确认的 Action handler 中都很有用。

### 8. 将 Pipe 用作完整的 provider 替代品 {#8-pipes-as-full-provider-replacements}

`Pipe` 会替换整个 LLM 调用。Open WebUI 把请求交给你，然后等你返回一个响应。中间件对你在该响应中放什么没有任何约束，因此你可以：

- 包装一个外部 API（任意 provider，任意协议），
- 根据请求形态在 provider 之间路由，
- 在 `pipe()` 内运行整个 agent，并把该 agent 的输出流式回传，
- 跳过任何模型，直接返回预设内容。

Pipe 是最强大的入口点，原因恰恰在于中间件会让出控制权。

### 9. 不止于 docstring 所描述的 Tool {#9-tools-that-do-more-than-their-docstring-says}

`Tools` 类的方法会以可调用工具的形式暴露给模型（其 docstring 会成为 JSON schema）。方法体可以**做任何事**：调用外部 API、用 `__event_emitter__` 发送 UI 事件、在 `app.state` 中存放数据、首次调用时进行 monkey-patch。docstring 仅仅决定了工具向模型如何自描述其自身；实现本身不受任何限制。

### 10. 将 Action 用作任意一次性操作 {#10-actions-as-arbitrary-one-shot-operations}

`Action` 会在 assistant 消息上渲染一个按钮。handler 在服务器端运行，拥有与 Filters 和 Tools 相同的双下划线参数表，运行上下文是消息所属的聊天。可用于"批准这条"、"用……重新跑一遍"、"发送到外部系统"，或任何应当允许用户从特定消息触发的一次性操作。

## 并发与多实例 {#concurrency-and-multiple-instances}

**Open WebUI 不会串行化插件代码，也不提供恰好一次执行保证。** Hook 和 handler 在异步事件循环中运行，可能相互重叠；在多副本部署中，同一逻辑工作也可能同时在多个 worker 上运行。需要*至多*执行一次的副作用必须由插件通过共享状态、分布式锁或幂等键自行协调，平台不负责这件事。

这里有两个不同层级：

- **同一个进程内部。** 异步 hook 会相互交错。如果两个请求并发命中同一个 hook，而它对共享状态（模块全局变量、`app.state` 缓存、某个文件）做读-改-写，就会产生竞态。`asyncio.Lock`（用于协程）或 `threading.Lock`（用于卸载到线程池的工作）可以把它们串行化，但那只在*那一个进程内部*有效。
- **跨副本。** 每个副本都是独立进程，拥有各自的 `sys.modules` 和各自的 `app.state`。模块全局变量或进程内锁在它们之间什么都协调不了。两个 worker 可以在同一时刻为同一事件运行同一个 handler。任何必须全局只触发一次的事情（发送邮件、开通资源、写入一条审计记录、调用非幂等的外部 API）如果没有共享状态守护，就会**每个副本各触发一次**。

Open WebUI 自己使用的共享状态原语是 **Redis**。在配置正确的多实例部署中，`REDIS_URL` 本来就已经设置好了（必须如此，WebSocket 和共享缓存才能跨副本工作）。你可以用它来获取分布式锁，或强制实施幂等键：

```python
from open_webui.utils.redis import get_redis_connection
from open_webui.env import REDIS_URL, REDIS_KEY_PREFIX

# decode_responses=True 让取值返回 str 而不是 bytes。
_redis = get_redis_connection(REDIS_URL, decode_responses=True) if REDIS_URL else None


def run_once(key: str, ttl: int = 300) -> bool:
    """True for exactly one caller across all replicas within `ttl` seconds.

    Backed by Redis `SET key value NX EX ttl` — an atomic "set if not exists"
    with expiry, so exactly one worker gets the key and the rest get nothing.
    """
    if _redis is None:
        # 没有 Redis 意味着是单进程部署：没有其它副本需要协调，
        # 所以这个调用者就是唯一的那个。
        return True
    return bool(_redis.set(f"{REDIS_KEY_PREFIX}:plugin:{key}", "1", nx=True, ex=ttl))
```

然后用返回值来守护副作用：

```python
if run_once(f"signup-log:{event['actor']['id']}"):
    await log_signup(event)   # runs on exactly one replica
```

请有意识地选择 `ttl` 和 key。key 代表「同一份工作」的含义（用户 ID、事件 ID、某个日期区间）；`ttl` 决定这条声明被记住多久，因此窗口内的重试或慢速重复会被抑制，但同一个 key 之后仍可以合法地再次出现。

对于耗时超过单次原子声明的工作，Open WebUI 自带一个可续期的锁辅助工具：`backend/open_webui/socket/utils.py` 中的 `RedisLock`（`aquire_lock()` / `renew_lock()` / `release_lock()`），WebSocket 层正是用它来做清理任务的。它很方便，但属于内部 API，适用下文「容易踩的坑」中的稳定性提醒；而上面直接调用 `set(..., nx=True, ex=...)` 则是纯粹的 redis-py 调用，不会变动。

## 容易踩的坑 {#footguns}

- **没有沙箱。** Tools 和 Functions 在你的后端进程中、以后端用户的身份执行 Python 代码。安全策略（[Rule 9](/security/security-policy#reporting-guidelines)）将这种行为视为预期行为：授予 Tool 或 Function 创建权限等同于授予主机的 shell 访问权限。请把插件作者当作管理员来对待。
- **Stream 钩子使用的是陈旧的缓存。** 对 `stream` 方法的编辑只有在另一个钩子（或一次进程重启）刷新了模块后才会生效。如果你修改了 stream filter 但变更似乎没生效，请触发一次 `inlet` / `outlet` 重新加载或重启进程。
- **跨插件干扰不会被检测。** 两个插件 patch 同一个函数、注册同一条路由，或写入同一个 `app.state` key，会发生冲突。加载顺序不是确定性的。请优先采用加法式（additive）的模式（你自己的命名空间、会委托的包装器），而不是破坏性的模式。
- **禁用不会卸载。** 模块会一直留在 `sys.modules` 中，所有模块级别的副作用也都会一直保留。要完全回滚请重启进程。
- **`requirements:` 会在每个副本加载时运行 `pip install`。** 在多副本部署中，请将 [`ENABLE_PIP_INSTALL_FRONTMATTER_REQUIREMENTS=False`](/reference/env-configuration#enable_pip_install_frontmatter_requirements) 关闭，并在镜像中预装依赖；运行时的安装会在多个 worker 之间产生竞态并导致崩溃。参见 [Scaling → Function/Tool Dependency Installation Crashes](/troubleshooting/multi-replica#9-functiontool-dependency-installation-crashes)。
- **内部 API 并不是稳定的公共接口。** `open_webui.utils.*`、内部 model 类、middleware 辅助函数，以及文档化的双下划线参数和事件类型之外的所有内容，在不同版本之间都可能被重命名、移位或更改签名。如果你的 monkey-patch 在升级后挂了，修复责任在你。

---

## 何时该选择其他方案 {#when-this-is-the-wrong-tool}

对于能通过文档化的钩子表达的任何事情（修改 `body` 的 filter、调用 API 并返回结果的 tool、发送事件的 action），**请留在文档化的钩子里**。上面的模式虽然强大，但持久性较差：一旦你开始 patch 模块内部，跨插件交互、升级兼容性和回滚都会变差。

如果你的插件需要一个还不存在的接口，那么提一个上游 PR 会比 monkey-patch 更持久。

如果你针对被你的插件 monkey-patch 过的代码路径提交了一个 bug 报告，请做好被关闭的准备。报告必须能在未经修改的 Open WebUI 上复现（[Rule 5](/security/security-policy#reporting-guidelines)）。
