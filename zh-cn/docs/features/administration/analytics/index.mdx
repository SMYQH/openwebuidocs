# Analytics（分析） {#analytics}

Open WebUI 中的 **Analytics** 功能为管理员提供了关于实例使用模式、Token 消耗和模型性能的全面洞察。这一强大工具帮助您了解用户与 AI 模型的交互方式，并基于数据做出资源分配和模型选择决策。

:::info 仅管理员可用
Analytics 仅供拥有 **admin** 角色的用户访问。通过 **Settings > Admin > Analytics** 进入。
:::

:::tip 禁用 Analytics

如果您不需要 Analytics 标签，可以通过将 [`ENABLE_ADMIN_ANALYTICS`](/reference/env-configuration#enable_admin_analytics) 环境变量设置为 `False` 来完全隐藏它。这会阻止挂载分析 API 路由，并从管理员导航中移除该标签。此更改需要重启才能生效。

:::

## 概述 {#overview}

Analytics 仪表板为您提供 Open WebUI 实例活动的全局视图，包括：

- 不同模型和时间段的**消息量**
- 用于费用估算和资源规划的 **Token 使用量**跟踪
- 了解参与度的**用户活动**模式
- 展示小时、天或月趋势的**时间序列数据**

所有分析数据均来源于实例数据库中存储的消息历史记录。启用 Analytics 功能后，Open WebUI 会自动跟踪和索引消息，以提供快速、可查询的洞察。

---

## 访问 Analytics {#accessing-analytics}

1. 使用 **admin** 账户登录
2. 点击个人资料图标并打开 **Settings**
3. 打开 **Admin** 区域并选择列在 **Quality** 之下的 **Analytics**

![Analytics 仪表板](/images/admin/admin-analytics.png)

该仪表板不再是独立页面。它会在设置窗口中紧邻你的个人设置打开，而旧的 `/admin/analytics` URL 会重定向到那里。如果 [`ENABLE_ADMIN_ANALYTICS`](/reference/env-configuration#enable_admin_analytics) 关闭，该 URL 会改为重定向到管理面板的用户列表，并且不会列出 Analytics 条目。

## 个人使用情况 {#personal-usage}

这里描述的仪表板是实例范围的管理员视图。另外，**每位用户都有属于自己的个人使用情况视图**，位于 **Settings > Usage**。它既不需要 admin 角色，也不需要任何配置。

它的范围严格限定为已登录用户自己的数据：

- Token 总量（输入与输出），既有累计值，也有所覆盖时间段的值
- 消息数和对话数，以及有活动的天数
- 活动热力图，可按天、按周或以累计总量查看
- 当前连续活跃天数和最长连续活跃天数
- 使用最多的模型和工具

所覆盖的时间段为过去两年（最近 730 天），无论账户何时创建都是同一个窗口，数据按用户自己所在时区分桶。由于它始终只报告请求者自己的活动，因此不会泄露任何关于他人的信息。

## 仪表板功能 {#dashboard-features}

**Overview** / **Sessions** 开关用于选择视图。两者遵循相同的时间段和分组筛选条件。[Sessions](#sessions) 列出单个对话。

### 时间段选择 {#time-period-selection}

在 Analytics 仪表板右上角，您可以按时间段筛选所有数据：

- **最近 24 小时**
- **最近 7 天**
- **最近 30 天**
- **最近 90 天**
- **年初至今** - 从当年 1 月 1 日到现在
- **最近 12 个月**
- **全部时间** - 完整历史数据
- **自定义范围** - 由你选择的开始日期和结束日期

选择**自定义范围**会在时间段下拉框旁放置两个日期字段。在两者都填写完整之前不会发起任何查询，因此在你还在挑选时，仪表板会保持空闲而不是显示加载动画，并在第二个日期设定后立即加载。结束日期是包含在内的，因此覆盖该日期一整天。

您选择的时间段会**自动保存**，并在浏览器会话之间持久存储，自定义日期也包含在内。如果您在 **Custom range** 上离开 Analytics 时日期尚未填写完毕，之后再回来，仪表板会显示空的数据，而不是一直加载。

### 用户组过滤 {#group-filtering}

如果您配置了[用户组](/features/authentication-access/rbac/groups)，Analytics 仪表板支持按组过滤：

- 使用时间段选择器旁边的**组下拉菜单**
- 选择特定组，仅查看**该组用户**的分析数据
- 选择"所有用户"查看全实例分析

适用场景：
- **部门级报告** - 跟踪特定团队的使用情况
- **成本分摊** - 将 Token 消耗归因于业务单元
- **试点项目** - 监控测试组的推广情况

更改时间段或组过滤器时，页面上的所有指标会自动更新，使用情况图表也包括在内。

### 汇总统计 {#summary-statistics}

仪表板标题显示所选时间段的关键指标：

- **Token** - 处理的所有输入和输出 Token 之和
- **输入** 与 **输出** - 分别列出的输入和输出 Token
- **消息数** - 生成的 AI 助手响应数量
- **对话数** - 独立对话的数量
- **用户数** - 发送过消息的用户数量

Token 数字会做缩写处理，例如 `1.2m`。将鼠标悬停在任意数字上即可查看确切值。

:::note 消息计数
Analytics 统计的是 **AI 助手响应**而非用户消息。这能更准确地衡量 AI 模型使用情况和 Token 消耗。
:::

### 消息时间线图表 {#message-timeline-chart}

使用情况图表按模型展示随时间变化的活动情况。其上方的 **Tokens** / **Messages** 开关用于选择统计对象，默认显示 **Tokens**。同一个开关也决定下方表格的排序方式，参见[模型使用表格](#model-usage-table)。

图表有两种视图：

- **Volume** - 每个时间步一份堆叠柱状图，每个模型一种颜色
- **Activity** - 每行一个模型的热力图。每个单元格的深浅相对于该模型最繁忙的时间步，空白单元格表示没有记录到使用

点击图表下方图例中的模型，或 **Activity** 视图中的行名，即可只显示该模型。再次点击它或点击 **All models** 即可显示全部模型。悬停某个时间步会显示各模型在该时刻的数值。图表上的时间是服务器时间。

时间间隔下拉框用于设置每个时间步的大小。它的默认值和可选项跟随所选时间段：

| 时间段 | 默认值 | 可选项 |
|-------------|---------|---------|
| **最近 24 小时** | **10 分钟** | **10 分钟**、**每小时**、**每天** |
| **最近 7 天** | **每小时** | **每小时**、**每天** |
| **最近 30 天** | **6 小时** | **每小时**、**3 小时**、**6 小时**、**每天** |
| 更长的时间段 | **每天** | **每天** |

**Compare** 会在 **Volume** 视图中把上一时间段显示在当前时间段旁边。上一时间段是紧接在所选时间段之前的等长时间窗口。此时图表会把当前时间段画成实线，把上一时间段画成虚线。悬停某个时间步会同时显示两个数值、对应日期以及百分比变化。**全部时间** 不支持 **Compare**，因为该时间段之前没有任何内容。

此图表帮助您：
- 识别容量规划的繁忙时段
- 跟踪部署后的模型推广情况
- 检测异常活动峰值
- 监控变更或公告的影响

### 模型使用表格 {#model-usage-table}

图表下方的模型使用和用户活动共用同一张表格。其上方的 **Models** / **Users** 开关用于选择显示哪份列表，默认显示 **Models**。两份列表默认都按 **Total** Token 排序。在图表上方的开关中选择 **Messages**，则会按消息数排序，并把占比列变为 **Message share**。

每个模型的使用情况细分如下：

| 列 | 说明 |
|--------|-------------|
| **#** | 当前排序中的名次 |
| **模型** | 带图标的模型名称 |
| **消息数** | 生成的 AI 助手响应总数 |
| **用户数** | 不同用户数 |
| **对话数** | 不同对话数 |
| **输入** | 输入 Token |
| **输出** | 输出 Token |
| **总数** | 输入与输出 Token 之和 |
| **Token 占比** | 占全部 Token 的百分比。当图表统计消息时显示为 **Message share** |

**功能：**
- **可排序列** - 点击任意列标题即可排序，三个 Token 列也包括在内
- **模型图标** - 通过头像图片进行视觉识别
- **Token 跟踪** - 查看哪些模型消耗资源最多
- **可点击行** - 点击任意模型打开[模型详情模态框](#model-details-modal)

**使用场景：**
- 识别最受欢迎的模型
- 计算每个模型的费用（将 Token 数乘以提供商价格）
- 决定保留或移除哪些模型
- 根据使用情况规划基础设施升级

### 模型详情模态框 {#model-details-modal}

点击任意模型行即可打开包含两个标签的详细模态框：

#### 概览标签 {#overview-tab}

概览标签提供：

- **反馈活动图表** - 用户反馈（点赞/踩）随时间变化的可视化历史记录
  - 在 **30D**、**1Y** 或 **All** 视图之间切换
  - 较长时间范围使用周粒度聚合
- **标签** - 与此模型关联的最常见对话标签（前 10 个）

这有助于您了解：
- 用户对模型质量的感知随时间的变化
- 模型处理的主题/使用场景
- 用户满意度趋势

#### 对话标签 {#chats-tab}

:::info 需要管理员对话访问权限
只有在实例设置中启用了 [**`ENABLE_ADMIN_CHAT_ACCESS`**](/reference/env-configuration#enable_admin_chat_access) 时，对话标签才会可见。
:::

对话标签显示使用过该模型的对话：

- **用户信息** - 是谁发起了每个对话
- **预览** - 每个对话的第一条消息
- **时间戳** - 对话最后更新的时间
- **点击打开** - 直接导航到共享对话视图

适用于：
- 了解用户如何与特定模型交互
- 审计模型使用情况以确保质量
- 寻找用于培训或文档的示例对话

### 用户活动表格 {#user-activity-table}

在表格上方的开关中选择 **Users**，即可按用户跟踪参与度和 Token 消耗：

| 列 | 说明 |
|--------|-------------|
| **#** | 当前排序中的名次 |
| **用户** | 带头像的用户名 |
| **消息数** | 该用户发送的总消息数 |
| **输入** | 该用户的输入 Token |
| **输出** | 该用户的输出 Token |
| **总数** | 输入与输出 Token 之和 |
| **Token 占比** | 占全部 Token 的百分比。当图表统计消息时显示为 **Message share** |

**功能：**
- **可排序列** - 可按名称、消息数、占比或三个 Token 列中的任意一个排序。表格显示所选时间段内 Token 最多的 50 位用户；当图表统计消息时，则显示消息最多的 50 位用户。API 的 `limit` 参数可以调高这个数量
- **用户识别** - 头像和显示名称。悬停或点击头像可打开该人的资料卡
- **Token 归因** - 查看每个用户的资源消耗

**使用场景：**
- 监控高级用户及其 Token 消耗
- 识别非活跃或低使用率账户
- 规划用户配额或速率限制
- 计算账单用途的每用户费用

## 会话 {#sessions}

:::info 需要管理员对话访问权限
只有在启用了 [**`ENABLE_ADMIN_CHAT_ACCESS`**](/reference/env-configuration#enable_admin_chat_access) 时才会显示 **Sessions** 视图。它会显示其他用户对话中的对话标题、工具调用和错误。
:::

**Sessions** 为所选时间段内有消息的每个对话列出一行，并按组筛选。子 agent、定时任务和笔记对话都包含在内并带有标注。摘要显示会话、提示词、Token 和响应错误的总数。点击其下方的某个 Token 区间即可筛选列表。

| 列 | 说明 |
|--------|-------------|
| **会话** | 对话标题，附其所在文件夹或模型 |
| **用户** | 对话的所有者 |
| **最近活跃** | 最后一条已保存消息的时间 |
| **响应数** | 该时间段内的助手响应数 |
| **Token** | 记录到的输入和输出 Token。`-` 表示没有记录，`*` 表示部分记录 |
| **响应错误** | 以错误结束的响应数 |
| **跨度** | 从第一条到最后一条已保存消息的时间，包含空闲时间 |

**未记录** 表示缺少时间戳。可以按对话标题、用户或文件夹搜索，按模型筛选，或在 **Session options** 菜单中隐藏子 agent 对话。

### 会话详情 {#session-details}

点击某个会话即可查看其 Token 与缓存总量、每次响应的图表（**Tokens** 或 **Timeline**）以及执行轨迹：每次响应及其工具调用、结果与错误、它们的结果与耗时。**All**、**Tools** 和 **Errors** 可用于筛选轨迹。**Open chat** 会在新标签页中打开该对话。耗时信息只为新的回复保存。

标题会被截断为 10 个单词。链接、文件路径、长标识符，以及位于 token 或 password 等词之后的值都会被移除。

## Token 使用量跟踪 {#token-usage-tracking}

### 什么是 Token？ {#what-are-tokens}

Token 是语言模型处理文本的单位。**输入**（您的提示词）和**输出**（模型的响应）都消耗 Token。大多数 AI 提供商按 Token 使用量收费，因此 Token 跟踪对于费用管理至关重要。

### Token 跟踪的工作原理 {#how-token-tracking-works}

Open WebUI 自动从模型响应中捕获 Token 使用量，并与每条消息一起存储。Analytics 功能汇总这些数据以显示：

- **输入 Token** - 用户提示词和上下文中的 Token
- **输出 Token** - 模型响应中的 Token
- **总 Token** - 输入和输出之和

Token 数据在不同模型提供商（OpenAI、Ollama、llama.cpp 等）之间进行标准化，无论使用哪个后端都能提供一致的指标。

每次对提供商的调用只计一次，即使提供商在每个流式数据块中都重新发送其用量。当一次回复因为模型使用工具而发起多次调用时，它们的用会被累加。没有用量数据的回复不会被记录，而只有部分调用上报用量的回复会被标记为部分。

这些数字就是提供商所报告的数字，而大多数 OpenAI 兼容提供商在流式回复中除非被询问否则什么都不报告。**Workspace > Models > Edit** 中的 **Usage** 能力正是用来提出这一请求的，因此一个没有该能力的模型可能完全不显示 Token。参见[能力与绑定](/features/workspace/models#capabilities-and-bindings)。

:::info 定时运行和委派运行同样会被计入
获取 Token 计数的请求是在服务端添加的，因此启用了 **Usage** 的模型会在它运行的每个对话中报告 Token，包括 Open WebUI 通过[自动化](/features/chat-conversations/chat-features/automations)、[定时任务](/features/chat-conversations/chat-features/timers)、[子 agent](/features/chat-conversations/chat-features/subagents) 和 [channels](/features/channels) 代用户发起的那些运行。这些运行与用户手动输入的对话计入同一批总数。
:::

### Token 使用量指标 {#token-usage-metrics}

**Token 使用量**部分（可通过 Tokens 端点或仪表板访问）提供：

- **按模型的 Token 明细** - 每个模型的输入、输出和总 Token
- **总 Token 消耗** - 全实例 Token 使用量
- **每消息 Token 数** - 用于效率分析的每消息 Token 数

:::tip 费用估算
要估算费用，将 Token 数乘以您的提供商定价：
```
费用 = (输入_token 数 × 输入单价) + (输出_token 数 × 输出单价)
```

GPT-5.6 示例：
- 输入：1,000,000 token × $0.03/1K = $30
- 输出：500,000 token × $0.06/1K = $30
- **合计：$60**
:::

## 使用场景 {#use-cases}

### 1. 资源规划 {#1-resource-planning}

**场景：** 您为团队运行 Open WebUI，需要规划基础设施容量。

**Analytics 的帮助：**
- 查看**消息时间线**识别高峰使用时段
- 检查**模型使用**了解哪些模型需要更多资源
- 监控 **Token 使用量**估算未来费用
- 跟踪**用户活动**为团队增长做规划

### 2. 模型评估 {#2-model-evaluation}

**场景：** 您已部署多个模型，想了解用户更喜欢哪些。

**Analytics 的帮助：**
- 比较各模型的**消息数**查看推广率
- 检查 **Token 效率**（每消息 Token 数）识别冗长模型
- 引入新模型后在时间线图表中监控**趋势**
- 结合 [Evaluation 功能](/features/administration/evaluation/)获取质量洞察

### 3. 费用管理 {#3-cost-management}

**场景：** 您使用付费 API 提供商，需要控制费用。

**Analytics 的帮助：**
- 按模型和用户跟踪**总 Token 消耗**
- 识别**高使用量用户**以进行配额讨论
- 比较不同模型提供商的 **Token 费用**
- 使用时间段过滤器定期审查

### 4. 用户参与 {#4-user-engagement}

**场景：** 您想了解团队如何使用 AI 工具。

**Analytics 的帮助：**
- 监控**活跃用户**与注册账户的对比
- 识别可能需要支持或培训的**高级用户**
- 随时间跟踪**推广趋势**
- 将使用情况与团队计划或培训活动关联

### 5. 合规与审计 {#5-compliance--auditing}

**场景：** 您的组织需要使用报告以满足合规要求。

**Analytics 的帮助：**
- 生成特定时间段的**活动报告**
- 跟踪所有 AI 交互的**用户归因**
- 监控已批准与未批准模型的**模型使用**
- 通过 API 导出数据用于外部报告工具

## 技术详情 {#technical-details}

### 数据存储 {#data-storage}

Analytics 数据存储在 `chat_message` 表中，包含：

- **消息内容** - 用户和 AI 助手的消息
- **元数据** - 模型 ID、用户 ID、时间戳
- **Token 使用量** - 输入、输出和总 Token
- **关联关系** - 与父消息和对话的链接

升级时，无论是否设置该开关，每个实例上 Open WebUI 都会：
1. 创建带有优化索引的 `chat_message` 表
2. **回填**您对话历史中的现有消息
3. **双写**新消息到对话 JSON 和消息表

这种双写方式确保：
- **向后兼容** - 现有功能继续正常工作
- **快速查询** - Analytics 不影响对话性能
- **数据一致性** - 所有消息均被捕获

### 数据库索引 {#database-indexes}

以下索引优化分析查询：

- `chat_id` - 快速查找对话中的所有消息
- `user_id` - 快速用户活动报告
- `model_id` - 高效的模型使用查询
- `created_at` - 时间范围过滤
- 常用查询模式的复合索引

### API 端点 {#api-endpoints}

对于高级用户和集成，Analytics 提供 REST API 端点：

**仪表板端点：**
```
GET /api/v1/analytics/summary
GET /api/v1/analytics/models
GET /api/v1/analytics/users
GET /api/v1/analytics/messages
GET /api/v1/analytics/daily
GET /api/v1/analytics/tokens
```

**模型详情端点：**
```
GET /api/v1/analytics/models/{model_id}/chats    # 获取使用此模型的对话
GET /api/v1/analytics/models/{model_id}/overview # 获取反馈历史和标签
```

**会话端点**（仅限管理员，关闭 `ENABLE_ADMIN_CHAT_ACCESS` 时返回 `403`）：
```
GET /api/v1/analytics/sessions                                          # 每个对话一个会话
GET /api/v1/analytics/sessions/{chat_id}                                # 会话的消息，附带缩短并脱敏的预览
GET /api/v1/analytics/sessions/{chat_id}/messages/{message_id}/events   # 某次响应已保存的步骤，附带脱敏片段
GET /api/v1/analytics/sessions/{chat_id}/trace                          # 会话的执行轨迹
```
这四个端点都接受下面的常用查询参数，以及 `skip` 和 `limit`（最多 50）。

**个人使用情况端点**（任何已登录用户，只返回其自己的数据）：
```
GET /api/v1/users/usage
```
它接受 `days`（7-732）或显式的 `start_date` / `end_date` 范围，并按请求者所在时区分桶。不带任何参数调用时（正如 **Settings > Usage** 页面所做的），它返回截至当前时刻的最近 730 天。这个端点不受管理员权限限制，因为它不报告调用者自身活动之外的任何内容。

**常用查询参数：**

| 参数 | 类型 | 说明 |
|-----------|------|-------------|
| `start_date` | int | Unix 时间戳（秒）- 范围开始 |
| `end_date` | int | Unix 时间戳（秒）- 范围结束 |
| `group_id` | string | 过滤到特定用户组（可选） |

**`/api/v1/analytics/daily` 参数：**

| 参数 | 类型 | 说明 |
|-----------|------|-------------|
| `granularity` | string | 每个时间桶的大小：`10m`、`hourly`、`3h`、`6h` 或 `daily`（默认）。按服务器时间分桶 |
| `metric` | string | `messages`（默认）统计助手响应数，`tokens` 汇总输入和输出 Token |
| `compare` | bool | 为 `true` 时，为每个桶添加一个 `previous` 对象，其中包含紧接在范围之前的等长窗口的数值，以及两者的 `start` 和 `end`。它需要同时提供 `start_date` 和 `end_date`，且 `start_date` 不得晚于 `end_date`，否则请求会以 `400` 失败 |

**`/api/v1/analytics/users` 参数：**

| 参数 | 类型 | 说明 |
|-----------|------|-------------|
| `metric` | string | `messages`（默认）按助手响应数对用户排名，`tokens` 按输入与输出 Token 总量排名 |
| `skip` | int | 跳过排名靠前的用户数量，默认 `0`。与 `limit` 一起使用可以翻页浏览排名 |
| `limit` | int | 返回排名靠前的用户数量，默认 50 位用户 |

响应中除 `users` 列表外还带有 `total`，即该范围内有活动的用户数。

:::tip API 访问
所有 Analytics 端点均需要管理员身份验证。包含您的管理员 Bearer 令牌：
```bash
curl -H "Authorization: Bearer YOUR_ADMIN_TOKEN" \
  "https://your-instance.com/api/v1/analytics/summary?group_id=abc123"
```
:::

## 隐私与数据注意事项 {#privacy--data-considerations}

### 哪些数据会被跟踪？ {#what-gets-tracked}

Analytics 跟踪：
- 消息时间戳和计数
- 每条消息的 Token 使用量
- 模型 ID 和用户 ID
- 对话 ID 和消息关联关系
- 响应和工具调用的开始与结束时间

Analytics **不会**跟踪：
- 仪表板中的消息内容。[Sessions](#sessions) 显示的是缩短后的对话标题和工具名称
- 外部分享或导出
- 数据库之外的单条消息内容

### 数据保留 {#data-retention}

Analytics 数据遵循实例的对话保留策略。当您删除：
- **一个对话** - 所有相关消息会从分析中移除
- **一个用户** - 他的对话及其中每一条消息都会被删除，因此其历史会从分析中彻底消失，而不是被匿名保留
- **消息历史** - 分析数据也会被一并清除

## 常见问题 {#frequently-asked-questions}

### 为什么消息计数与我的预期不同？ {#why-are-message-counts-different-from-what-i-expected}

Analytics 统计的是 **AI 助手响应**，而非用户消息。如果一个对话有 10 条用户消息和 10 条助手响应，计数为 10。这能更准确地衡量 AI 使用量和 Token 消耗。

### Token 跟踪的准确性如何？ {#how-accurate-is-token-tracking}

Token 准确性取决于您的模型提供商：
- **OpenAI/Anthropic** - 来自 API 响应的精确计数
- **Ollama** - 对支持 token 上报的模型准确
- **llama.cpp** - 在可用时上报 token
- **自定义提供商** - 取决于具体实现

没有 token 数据的响应不会为总数增加任何数值。

### 可以导出分析数据吗？ {#can-i-export-analytics-data}

可以，通过 API 端点。使用 `curl`、Python 脚本或 BI 工具来抓取和导出数据：

```bash
curl -H "Authorization: Bearer TOKEN" \
  "https://instance.com/api/v1/analytics/summary?start_date=1704067200&end_date=1706745600" \
  > analytics_export.json
```

## 总结 {#summary}

Open WebUI 的 Analytics 功能通过以下能力把实例升级为数据驱动的平台：

- 模型和用户活动的**实时洞察**
- 用于成本管理和优化的 **Token 跟踪**
- 帮助理解使用模式随时间变化的**趋势分析**
- 用于社区建设的**用户参与度**指标
- 注重隐私的设计，所有数据均保留在您的实例内

无论您管理的是个人实例还是大型组织部署，Analytics 都能为您提供优化性能、控制成本、更好地服务用户所需的可见性。
