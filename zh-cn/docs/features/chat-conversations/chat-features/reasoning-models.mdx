# 推理与 Thinking 模型 {#reasoning--thinking-models}

Open WebUI 原生支持具备思考（thinking）或推理（reasoning）能力的模型，如 DeepSeek R1 和 OpenAI o1。这类模型通常会在给出最终答案之前，先生成内部思维链。

## Thinking 标签的工作方式 {#how-thinking-tags-work}

当模型生成推理内容时，通常会把这些内容包裹在特定的类 XML 标签中（例如 `<think>...</think>` 或 `<thought>...</thought>`）。

Open WebUI 会自动：
1.  **检测** 模型输出流中的这些标签
2.  **提取** 标签之间的内容
3.  **渲染** 提取出的内容，并以可折叠 UI 区块形式展示，标题通常为 “Thought” 或 “Thinking”

这样既能保持主聊天界面简洁，也能让你在需要时查看模型的内部推理过程。

## `reasoning_tags` 参数 {#the-reasoning\_tags-parameter}

你可以使用 `reasoning_tags` 参数，自定义 Open WebUI 应该识别哪些标签。该参数可按**聊天级**或**模型级**设置。

### 默认标签 {#default-tags}

默认情况下，Open WebUI 会识别以下常见推理标签对：
- `<think>`, `</think>`
- `<thinking>`, `</thinking>`
- `<reason>`, `</reason>`
- `<reasoning>`, `</reasoning>`
- `<thought>`, `</thought>`
- `<|begin_of_thought|>`, `<|end_of_thought|>`

### 自定义 {#customization}

如果你的模型使用的是不同标签，你可以在 `reasoning_tags` 中提供一组标签对。每一对都是一个 tuple 或 list，包含开始标签与结束标签。

## 配置与行为 {#configuration--behavior}
- **从 Payload 中剥离**：`reasoning_tags` 参数本身是 Open WebUI 特有控制项，在发送给 LLM 后端（如 OpenAI、Ollama 等）前会被**剥离**，从而确保与不识别该参数的提供商兼容
- **聊天历史**：推理内容会保留在聊天历史中。是否会被发回给模型，取决于具体连接；参见[推理内容是如何被重新发回的](#how-reasoning-is-sent-back)
- **UI 渲染**：内部上，推理块会通过专门 UI 组件进行处理与渲染。保存或导出时，它们可能表现为 HTML `<details type="reasoning">` 标签

## Open WebUI 设置 {#open-webui-settings}
Open WebUI 提供多项内置设置，用于配置推理模型行为。你可以在以下位置找到：

- **Model controls**（消息输入框旁）→ **Controls** → **Advanced Params** —— 按聊天设置
- **Workspace** → **Models** → **Edit Model** → **Advanced Parameters** —— 按模型设置（仅管理员）
- **Settings** → **Models** → 选择某个模型 → **Advanced Parameters**（管理员区域） —— 另一个按模型设置入口

### 推理标签设置 {#reasoning-tags-setting}

该设置控制 Open WebUI 如何解析并显示 thinking / reasoning 区块：

| 选项 | 说明 |
|--------|-------------|
| **Default** | 使用系统默认行为 |
| **Enabled** | 显式启用推理标签检测，默认按 `<think>...</think>` 解析 |
| **Disabled** | 完全关闭推理标签检测 |
| **Custom** | 允许你指定自定义开始和结束标签 |

#### 使用自定义标签 {#using-custom-tags}

如果你的模型使用非标准推理标签（如 `<reasoning>...</reasoning>` 或 `[思考]...[/思考]`），请选择 **Custom**，并填写：

- **Start Tag**：开始标签（例如 `<reasoning>`）
- **End Tag**：结束标签（例如 `</reasoning>`）

这适用于：
- 使用本地化思考标签的模型
- 使用独特标签格式的自定义微调模型
- 使用 XML 风格 reasoning marker 的模型

### `think`（Ollama） {#think-ollama}
这是一个 Ollama 专属设置，用于控制模型内置的 reasoning 功能。自 v0.9.0 起，Ollama 已原生将 thinking 与答案分离，因此无需设置任何服务端开关：

| 选项 | 发送内容 | 说明 |
|--------|--------------|-------------|
| **Default** | 不发送 | 使用 Ollama 的默认行为，即对支持的模型默认开启 thinking |
| **On** | `think: true` | 显式为模型开启 thinking mode |
| **Custom** | `think: "low"`、`"medium"`、`"high"` 或 `"max"` | 指定 thinking 等级。GPT-OSS 只接受等级，不接受 `true` |
| **Off** | `think: false` | 关闭 thinking mode |

:::note
该设置会把 `think` 参数直接发送给 Ollama，由它在独立的 `thinking` 字段中返回推理轨迹，Open WebUI 将其作为 reasoning 读取（参见[推理内容是如何被重新发回的](#how-reasoning-is-sent-back)）。这与 Open WebUI 解析文本中 `<think>` 标签的机制相互独立，后者只对把推理直接写在正文里的模型才有影响。
:::

### 推理力度 {#reasoning-effort}
对于支持可变推理深度的模型（如某些 API 提供商模型），该设置用于控制模型投入多少“推理力度”：

- 常见值：`low`、`medium`、`high`
- 某些提供商也接受数值型参数

Open Terminal 中的[智能体](/features/open-terminal/agents#options)也会收到此设置。

:::info
Reasoning Effort 仅适用于支持该参数的特定提供商模型。在原生 Ollama 连接上不会透传该参数——上面提到的 `think` 设置已经覆盖了同样的需求。如果把 Ollama 作为 OpenAI 连接接入，则 Ollama 的 OpenAI 兼容端点确实接受 `reasoning_effort`。
:::

### 在 vLLM 和 llama.cpp 上关闭 Thinking {#turning-thinking-off-on-vllm-and-llamacpp}

由 vLLM 或 llama.cpp 的 `llama-server` 提供的模型，通常通过聊天模板来开关 thinking，模板会从请求中读取 `chat_template_kwargs`。Open WebUI 没有对应设置，所以可以在 OpenAI 连接上把它作为自定义参数发送：

1. 进入 **Workspace → Models**，编辑该模型。
2. 展开 **Advanced Params**。
3. 在底部点击 **Add Custom Parameter**，并填写：
   - **Name**：`chat_template_kwargs`
   - **Value**：`{"enable_thinking": false}`
4. 保存模型。

Open WebUI 将该值解析为 JSON，并添加到请求正文的顶层。模板读取的键取决于模型。Qwen3 使用 `enable_thinking`，其他一些模型读取 `thinking`。请查阅模型卡或 [vLLM 推理输出页面](https://docs.vllm.ai/en/latest/features/reasoning_outputs.html)，以及 [llama.cpp 服务器 README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md) 中的 `chat_template_kwargs`。如果要关闭所有请求的思考，也可在启动 vLLM 时传入 `--default-chat-template-kwargs`。

## 工具调用中的交错式思考（Interleaved Thinking） {#interleaved-thinking-with-tool-calls}

当模型在单轮对话中使用 **native function calling**（工具调用）时，Open WebUI 会保留推理内容，并在该轮的后续调用中重新发回给 API。这使得真正的“交错式思考”成为可能：

1. 模型生成推理 → 发起工具调用
2. 工具执行并返回结果
3. 模型收到：原始消息 + 先前推理 + 工具调用 + 工具结果
4. 模型继续推理 → 可能继续调用更多工具，或给出最终答案
5. 这个过程会持续，直到本轮完成

### 工作原理 {#how-it-works}
在多步骤工具调用轮次中，Open WebUI 会：

1. **捕获** 模型响应中的推理内容——来自 `<think>` 风格的标签，或来自 `reasoning_content`、`reasoning`、`thinking` 字段
2. **将其存储** 在内容块中，并与工具调用并列保存
3. **在下一次调用时按连接所期望的格式把它发回**；参见[推理内容是如何被重新发回的](#how-reasoning-is-sent-back)

### 推理内容是如何被重新发回的 {#how-reasoning-is-sent-back}
无论模型是用 `<think>` 风格的标签写入推理，还是通过单独的字段发送推理，Open WebUI 都会把推理与答案分开存储。当消息被重放时——无论是在工具调用循环内部，还是在下一轮——推理都会按照连接的 `Provider` 设置所指定的格式发回（**设置 → 连接 → OpenAI → 高级 → Provider**（管理员区域），参见 [Provider 设置](/getting-started/quick-start/connect-a-provider/starting-with-openai-compatible#the-provider-setting)；Ollama 连接会被自动识别）。同一轮内和跨轮次适用相同的规则。参见[提供商兼容性](#provider-compatibility)。关闭 **Stream Chat Response** 时，模型在回复中写入的 `<think>` 标签会作为回复正文存储，因此会随回复一起发回给模型。

大多数 Chat Completions API 会拒绝 assistant 消息上的未知字段，因此推理文本在那里会被略去。Pipe 函数和过滤器可以按提供商特定的形式把它加回去。

如果提供商（例如 OpenRouter）在 `reasoning_details` 字段中返回推理详情，工具调用循环和后续轮次都会在同一字段中原样回传该详情。对于使用 Responses API 的连接，提供商返回的加密推理也会以同样的方式回传，方便模型保留先前的推理。换用另一个模型继续聊天时，两者都会被丢弃。

除非组织使用零数据保留，否则 OpenAI 只在请求明确要求时返回加密推理。要为模型启用此功能，请执行以下步骤。

1. 转到**工作区 → 模型**并编辑模型。
2. 展开**高级参数**。
3. 点击底部的**添加自定义参数**，然后设置：
   - **名称**：`include`
   - **值**：`["reasoning.encrypted_content"]`
4. 保存模型。

要为每个模型启用此功能，请在管理区域的**设置 → 模型**下的**模型默认值**中添加同一参数。

使用 [LiteLLM](https://docs.litellm.ai/) 代理时，在每个模型的 `litellm_params` 中配置一次 `include`，并且不要在 Open WebUI 中添加该自定义参数。Open WebUI 发送的自定义参数会覆盖 LiteLLM 的值。如果在两处都设置，请保留其中的 `reasoning.encrypted_content`。

```yaml
- model_name: gpt-5.5
  litellm_params:
    model: openai/gpt-5.5
    api_key: os.environ/OPENAI_API_KEY
    include: ["reasoning.encrypted_content"]
```

通过 LiteLLM 的 Responses 端点访问的 Anthropic 模型无需配置。LiteLLM 默认会以加密推理形式返回它们的思考。

### 提供商兼容性 {#provider-compatibility}
| 提供商 | 重放时的 reasoning 处理 |
| :--- | :--- |
| Ollama | 通过 `thinking` 字段发回 |
| llama.cpp（*Provider* 设为 `llama.cpp`） | 以 `reasoning_content` 发回。DeepSeek thinking 模式需要此设置 |
| vLLM 和 OpenRouter（*Provider* 为 `vLLM` 或 `OpenRouter`） | 以 `reasoning` 发回 |
| OpenAI Responses API | 已存储的 reasoning item 会被发回。启用 `ENABLE_RESPONSES_API_STATEFUL` 后，状态由 `previous_response_id` 携带 |
| OpenAI / Azure / Vertex AI（Chat Completions，*Provider* 为 `Default`） | 会被略去（可用 pipe 或 filter 加回去） |
| Anthropic（extended thinking） | 不原生支持；请使用 [pipe function](/features/extensibility/plugin/functions/pipe) |

## 流式与非流式 {#streaming-vs-non-streaming}

### 流式模式（默认） {#streaming-mode-default}
在 streaming 模式（`stream: true`）下，Open WebUI 会边接收 token 边处理，因此能够实时检测 reasoning 区块。通常情况下无需额外配置即可良好工作。

对于那些把 reasoning 元数据与答案一并发送（而非置于答案之前）的提供商，同样可以正确处理：在响应已经开始之后到达的 reasoning 会被折叠进答案上方的 thinking 区块，而不是显示在其下方。只有元数据、没有 reasoning 文本时则不会打开 thinking 区块。

### 非流式模式 {#non-streaming-mode}
在 non-streaming 模式（`stream: false`）下，整段响应会一次性返回。**大多数解析问题都发生在这里**，因为：

1. 响应作为单一文本块整体到达
2. 只有在完整文本中检测到相应标签时，`<think>` 内容才会被分离出来
3. 原始响应会直接原样显示

:::info 重要
如果你正在使用 non-streaming 请求（通过 API 或某些配置发起），那么 **thinking 区块能否分离，取决于能否在完整响应中检测到相应标签**，或者后端是否把 reasoning 作为独立字段返回。
:::

## API 使用示例 {#api-usage}

使用 Open WebUI API 调用 reasoning 模型时：

``` json
{
  "model": "qwen3.6:27b",
  "messages": [
    {"role": "user", "content": "Solve: What is 234 * 567?"}
  ],
  "stream": true
}
```

**建议：** 使用 `"stream": true`，以获得最稳定的 reasoning 区块解析效果。

## 故障排查 {#troubleshooting}

### 推理内容与最终答案混在一起 {#thinking-content-merged-with-final-answer}

**症状：** 使用推理模型时，整段响应（包括 `<think>...</think>` 区块）被直接显示为最终答案，而不是被拆分到隐藏 / 可折叠的 thinking 区域中。

**错误示例：**

``` text
<think>
Okay, the user wants a code snippet for a sticky header using CSS and JavaScript.
Let me think about how to approach this.
...
I think that's a solid approach. Let me write the code now.
</think>

Here's a complete code snippet that demonstrates a sticky header using CSS and JavaScript...
```

**期望行为：** thinking 内容应该隐藏或可折叠，只显示最终答案。

### 对于 Ollama 用户 {#for-ollama-users}
Ollama 不接受 parser 开关参数。`ollama serve` 没有命令行选项，某些指南中提到的 `--reasoning-parser` 其实是 vLLM 的参数。只要 `think` 参数打开，Ollama 就会自行把 thinking 与答案分离，Open WebUI 无需任何服务端配置即可呈现这种分离。

#### 第 1 步：检查 Ollama 版本 {#step-1-check-the-ollama-version}
Thinking 支持自 Ollama v0.9.0 起提供。请确认你正在运行的版本：

``` bash
ollama --version
```

#### 第 2 步：为模型开启 Thinking {#step-2-turn-thinking-on-for-the-model}
打开 **Model controls > Controls > Advanced Params**（或在模型编辑器中打开该模型的 **Advanced Params**），把 **think (Ollama)** 设为 **On**；对于只接受等级的模型（如 GPT-OSS 这类模型），也可以设为 **Custom** 并指定等级（`low`、`medium`、`high` 或 `max`）。**Default** 则交由 Ollama 自行决定，对支持的模型它会开启 thinking。

#### 第 3 步：在 Open WebUI 中验证 {#step-3-verify-in-open-webui}
1. 前往 Open WebUI，并使用 reasoning model 新建一个聊天
2. 提出一个需要推理的问题（例如数学题或逻辑题）
3. 现在回复应该会把 thinking 内容显示在答案上方的可折叠区块中

如果模型把推理直接以 `<think>...</think>` 文本形式写在回复里，而不是使用 Ollama 的 thinking 字段，请检查上面的 **Reasoning Tags** 设置；对于其他标签对，请使用 **Custom**。

### 故障排查清单 {#troubleshooting-checklist}

#### 1. 确认 Ollama 已分离 thinking {#1-verify-ollama-separates-the-thinking}
在开启 thinking 的情况下，用 Ollama CLI 运行模型。受支持的模型会把推理轨迹和答案分作两部分输出：

```bash
ollama run your-model:tag --think "Explain step by step: What is 15 + 27?"
```

如果 Ollama 提示该模型不支持 thinking，那么这个模型根本没有 thinking 模式，Open WebUI 只能从正文中提取模型写出的标签。

#### 2. 检查模型兼容性 {#2-check-model-compatibility}
并非所有模型都用相同格式输出推理内容。请查看模型文档，确认：

- 它使用什么标签表示 thinking 内容（如 `<think>`、`<reasoning>` 等）
- 是否需要特殊提示词才能启用 thinking mode

#### 3. 测试开启 Streaming {#3-test-with-streaming-enabled}
如果 non-streaming 模式表现异常，尝试在聊天中启用 streaming：

1. 打开消息输入框旁的 **Model controls > Controls > Advanced Params**
2. 确保已启用 streaming（默认即开启）
3. 再次测试该模型

#### 4. 检查 Open WebUI 版本 {#4-check-open-webui-version}

请确认你使用的是 Open WebUI 最新版本，因为 reasoning model 支持仍在持续改进：

``` bash
docker pull ghcr.io/open-webui/open-webui:main
```

#### 5. 验证模型响应格式 {#5-verify-the-model-response-format}

直接用 Ollama CLI 检查模型实际输出格式：

``` bash
ollama run your-model:tag "Explain step by step: What is 15 + 27?"
```

检查输出中是否出现 `<think>` 标签。如果没有，可能说明模型需要额外的 system prompt 才会启用 thinking mode。

### 工具调用后推理内容丢失 {#reasoning-lost-between-tool-calls}

**症状：** 工具调用完成后，模型似乎“忘记了”自己先前在想什么。

**可能原因：**
1. 模型没有通过可捕获格式输出推理内容（如 `reasoning_content`、`reasoning` 或 `thinking` delta 字段）
2. 模型使用了基于文本的 thinking 标签，但这些标签没有被解析为 reasoning block

**解决方案：** 检查你的模型是否通过以下方式输出推理内容：
- 结构化 delta 字段（`reasoning_content`、`reasoning`、`thinking`）
- Open WebUI 能识别的基于文本的标签（并确保已启用 reasoning tag detection）

### DeepSeek：`reasoning_content` 必须回传 {#deepseek-reasoning_content-must-be-passed-back}

**症状：** 处于思考模式的 DeepSeek 模型会报下面的错误，即使在聊天的第一条消息上也可能发生：

```
The `reasoning_content` in the thinking mode must be passed back to the API.
```

**原因：** 该错误来自 DeepSeek，它要求把之前的推理内容随请求一起回传。当连接的 **Provider** 保持 **Default** 时，Open WebUI 不会把推理内容放进它发送的历史记录（参见[推理内容是如何被重新发回的](#how-reasoning-is-sent-back)）。可用的技能、附加的知识和召回的记忆都会以工具调用的形式进入模型的历史记录，因此即使你从未调用过工具，用到其中任何一项的聊天也含有工具调用轮次。

**修复：**

1. 在 **Settings → Connections → OpenAI**（管理员区域）中编辑 DeepSeek 连接，打开 **Advanced**，把 **Provider** 设为 **llama.cpp**。这样 Open WebUI 会把已保存的推理内容以 `reasoning_content` 回传，而没有推理内容的工具调用轮次则会带上空的 `reasoning_content`。
2. 如果错误仍然出现，例如通过其他服务访问的 DeepSeek 模型，请为该模型关闭 thinking：在 **Advanced Params** 中把 **Reasoning Effort** 切换为 **Custom** 并填入 `none`。Open WebUI 会把它作为 `reasoning_effort: "none"` 转发。

在 **API Type** 设为 **Responses** 的连接上，同样的要求表现为 ``The `reasoning_text` in the thinking mode must be passed back to the API.``。请把 **API Type** 切换为 **Chat Completions**、**Provider** 切换为 **llama.cpp**，或者把 **Reasoning Effort** 设为 `none`。

### 在其他模型下生成的加密推理内容 {#encrypted-reasoning-produced-under-a-different-model}

**症状：** 通过 OpenRouter 或其他返回 `reasoning_details` 的服务访问的推理模型会报下面的错误：

```
Your request contains encrypted reasoning or compaction content that was produced under a different model.
```

**原因：** 无论 **Provider** 设置为什么，Open WebUI 都会在后续轮次回传 `reasoning_details`。它会把这些内容从由另一个模型写出的回复中移除，并通过 Open WebUI 模型 ID 区分模型。一个模型 ID 如果现在指向了不同的上游模型（例如基础模型被改动过的工作区模型），仍然会收到早前那些回复的推理详情。

**修复：** 开始一个新聊天，或者用写出早前回复的那个上游模型继续当前聊天。修改 **Provider** 不会改变这一点。

### Anthropic 扩展思考与工具调用不兼容 {#anthropic-extended-thinking-not-working-with-tool-calls}

**症状：** 使用 Anthropic Claude 模型，并开启 extended thinking 时，工具调用报错，例如：

```
Expected `thinking` or `redacted_thinking`, but found `text`. When `thinking` is enabled, 
a final `assistant` message must start with a thinking block.
```

**原因：** 这是一个底层架构差异。Open WebUI 遵循 **OpenAI Chat Completions API 标准**，并不原生支持 Anthropic 的专有 API 格式。Anthropic 的 extended thinking 需要结构化内容块（`{"type": "thinking"}` 或 `{"type": "redacted_thinking"}`），而这些属于 Anthropic 特有的格式，并不存在于 OpenAI 标准中。

Open WebUI 不会把 Anthropic 风格的 thinking block 发回，因此无法满足 Anthropic 对结构化 thinking block 的要求。

**为什么 Open WebUI 不原生支持这一点：**

目前没有一个跨提供商通用的标准，可在 API payload 中统一存储 reasoning 内容。如果 Open WebUI 针对某一个提供商格式实现支持，就可能破坏许多其他推理后端部署。鉴于 Open WebUI 支持的后端种类非常广泛，我们选择遵循 OpenAI Completions API 作为共同标准。更多背景可参阅 **[FAQ on protocol support](/faq#q-why-doesnt-open-webui-natively-support-provider-xs-proprietary-api)**。

**可行替代方案：**

1. **使用 Pipe Function**：创建一个自定义 [pipe function](/features/extensibility/plugin/functions/pipe)，在请求发送给 Anthropic API 前，把 Open WebUI 的文本型 thinking 格式转换成 Anthropic 所需的结构化 thinking block

2. **关闭 Extended Thinking**：如果你的工具调用工作流并不需要 extended thinking，可以关闭它，以避免格式不匹配

:::note
这一限制只出现在 Anthropic extended thinking + tool calls 的组合场景中。单独使用 extended thinking 没问题，单独使用 tool calls 也没问题——只有两者一起通过 Anthropic API 使用时才会出错。
:::

### 有状态推理模型（GPT-5.6 等） {#stateful-reasoning-models-gpt-56-etc}

**症状：** 你使用的模型会隐藏其推理内容（stateful / internal reasoning），因此推理无法被保留。

**原因：** 某些较新的模型（如 GPT-5.6）会把 reasoning 保持在内部，不会通过 API 响应暴露出来。Open WebUI 只能保留模型实际返回的推理内容。

**行为：** 如果模型返回的是推理摘要而非完整推理内容，那么被保留并重新发送的就是该摘要。

## 常见问题 {#frequently-asked-questions}

### 为什么 thinking 区块显示成了原始文本？ {#why-is-the-thinking-block-showing-as-raw-text}
如果模型使用的标签不在默认列表中，且你也没有在 `reasoning_tags` 中显式配置它们，那么 Open WebUI 会将其视作普通文本。你可以在 Model Settings 中，或在聊天的 **Model controls > Controls** 下，把正确标签加入 `reasoning_tags` 参数来解决这一问题。

### 模型能看到它自己之前的 thinking 吗？ {#does-the-model-see-its-own-thinking}
这取决于具体连接。Ollama、llama.cpp 以及 OpenAI Responses API 会在工具调用循环内部以及跨轮次时，把模型先前的 reasoning 发回给它。其他 Chat Completions 连接则不会。参见[推理内容是如何被重新发回的](#how-reasoning-is-sent-back)。
