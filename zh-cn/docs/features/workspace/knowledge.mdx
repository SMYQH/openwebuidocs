# 📚 知识库 {#knowledge}

**让您的 AI 访问文档，并找到最相关的内容。**

知识库是您存储 AI 可以搜索、阅读和推理的文件和集合的地方。上传 PDF、电子表格、代码或任何基于文本的文档。围绕项目、团队或主题构建集合。当模型需要答案时，它会从您的知识库中提取，而不是靠猜测。文档内容在哪里被处理，取决于你使用的提取引擎、嵌入模型和模型提供商；参见[对话数据隐私与加密](/security/chat-data-privacy-and-encryption)。

与将全部内容注入每条消息的[笔记](/features/notes)不同，知识库使用检索（RAG）按需找到相关片段。这使其成为注入所有内容会超出上下文窗口的大型文档集的正确选择。

## 提出第一个文档问题 {#ask-your-first-document-question}

先准备好三样东西：一个正在运行的 Open WebUI 实例、一个已连接的模型，以及创建知识库和上传文件的权限。要使用专注检索，请选择支持[原生函数调用](/features/extensibility/plugin/tools#tool-calling-modes-default-vs-native)的模型，并启用 **Builtin Tools** 和 **Knowledge Base** 工具类别。原生是默认模式；模型必须调用自己的工具来检索已附加的知识。

1. 点击**Workspace > Knowledge**，然后点击**Create**。为知识库起一个名称并填写描述。
2. 上传一个小的纯文本 PDF 或文本文件。在提问之前等待处理完成。
3. 把知识库附加到该聊天，或附加到某个模型并用该模型开始对话。[附加知识与笔记](#attaching-knowledge-and-notes)说明了可以附加的位置。
4. 提出一个答案就在文件里的问题，例如："使用附加的手册查找办公时间。引用相关段落。"
5. 将回答和任何来源引用与原始文档比对。如果模型找不到内容，请参阅[知识库故障排查](/troubleshooting/rag#13-knowledge-base-attached-to-model-not-working)。

## 选择如何处理文件 {#choose-how-to-work-with-files}

| 需求 | 使用 |
| :--- | :--- |
| 在一次对话中询问某一个文件 | [把文件上传到对话](/features/chat-conversations/data-controls/files#using-files-in-open-webui) |
| 在多次对话中复用一组文档 | 知识库，按照上面的步骤操作 |
| 分析电子表格或通过代码创建文件 | [开放终端的文件分析指南](/features/open-terminal/use-cases/file-analysis) |

一条[笔记](/features/notes)以完整文本的形式到达模型，而知识库可以按需检索相关段落。这使知识库适合那些如果完整发送就会超出模型上下文窗口的文档集合。知识库和笔记的附加位置相同，本页所说的“知识”同时涵盖两者，以及单个文件。若要纯本地地进行文档对话，请同时遵循[离线运行 Open WebUI](/tutorials/maintenance/offline-mode)。

## 附加知识与笔记 {#attaching-knowledge-and-notes}

知识库、笔记和单个文件可以附加到聊天、附加到[文件夹](/features/chat-conversations/chat-features/conversation-organization#attached-knowledge)（对该文件夹中的每个聊天都生效），或附加到[模型](/features/workspace/models)。有些选择器把知识库标为 **Collections**（单个条目上标为 **Collection**）；这个标签指的就是知识库。

**在聊天中：**

- 在消息输入框中键入 `#`。列表会提供 **Folders**、**Collections**（知识库）和 **Files**（知识库中的单个文件），并接受网页或 YouTube URL。
- 或点击 **+**（**More**）并打开 **Add Context**。**Attach Knowledge** 列出你的知识库，其中的 **Show Files** 可以从某个知识库中挑选单个文件。**Attach Notes** 列出你的笔记。同一个菜单还有 **Attach Webpage**、**Attach Files**（你之前上传的文件）和 **Reference Chats**。
- 或把笔记、文件夹或聊天从侧边栏拖入消息输入框。

**在模型或文件夹上：** 打开 **Knowledge** 字段，在模型编辑器中（**Workspace > Models**，或 **Settings > Models > Edit**（管理员区域）），或在文件夹的 **Edit** 对话框的 **Advanced** 下。其搜索会列出 **Notes**、**Collections**（知识库）和 **Files**（知识库中的单个文件），而 **Upload Files** 可以直接从你的电脑上添加文件。

**Workspace > Knowledge** 只列出知识库。笔记在[笔记](/features/notes)中。

## 为什么使用知识库？ {#why-knowledge}

---

### 您的文档变得可由 AI 搜索 {#your-documents-become-searchable-by-ai}

上传一批合同、技术规格或研究论文。AI 按语义而非仅仅关键词搜索它们，并引用答案的来源。

### 满足不同需求的两种检索模式 {#two-retrieval-modes-for-different-needs}

选择**专注检索**（RAG）让 AI 高效搜索大型文档集，或选择**全文上下文**在精度重要时逐字注入整个文档。

### 通过原生函数调用自主探索 {#autonomous-exploration-with-native-function-calling}

启用[原生函数调用](/features/extensibility/plugin/tools#tool-calling-modes-default-vs-native)后，模型不只是搜索。它们可以浏览您的知识库、逐页阅读文件，并在没有手动提示的情况下跨多个文档综合内容。

### 有序范围访问 {#scoped-access-keeps-things-organized}

当你把知识附加到模型、文件夹或聊天时，就等于精确指定了该模型要搜索哪些知识。它的知识工具随后只列出并搜索已附加的条目。这样答案会保持聚焦且可预测，因为模型只依据你挑选的来源作答。这也让你能决定每个模型搜索哪些文档：云端提供商上的模型可以只拿到一份公开手册，而跑在你自有硬件上的模型还能拿到内部文档。用户自身的访问权限在此之上仍然生效。

会收窄知识工具范围的有：

- 模型 **Knowledge** 字段中的任何内容（知识库、笔记和文件），
- 聊天所在文件夹的 **Knowledge** 字段中的任何内容，
- 在模型 **Preload files** 能力关闭时，聊天中直接附加的知识库和笔记；开启该能力时，它们会被注入对话。

在聊天中，上传的文件、从知识库中挑选的单个文件、文件夹、被引用的聊天和网页都以各自的方式到达模型，而不会改变知识工具的范围。

要让模型浏览用户能读取的所有知识库，就什么都不要附加。要限制它，就精确附加它应当使用的内容，包括你希望它读取的笔记。笔记还可以通过独立的 **Notes** 工具类别访问，无论附加了什么，该类别都能覆盖用户的全部笔记；在模型的 **Builtin Tools** 下关闭 **Notes**，即可让它只使用已附加的笔记。[工具表](#agentic-knowledge-tools)显示了每种情况会得到哪些工具。

## 检索模式 {#retrieval-modes}

将文件或知识库附加到模型时，点击已附加项在两种模式之间切换：

![知识库列表](/images/workspace/knowledge-list.png)

在打开的预览中，知识库的名称会在工作区中打开它，文件或链接名称会打开对应的文件或页面。两者都在新标签页中打开。

### 🔍 专注检索（默认） {#focused-retrieval-default}

使用 RAG 根据用户查询找到并注入最相关的片段。当启用混合搜索（`ENABLE_RAG_HYBRID_SEARCH`）时，检索结合了 BM25 关键词搜索和向量搜索，以及用于准确性的重排序。

最适合只有特定部分相关的大型文档集。

### 📄 全文上下文 {#full-context}

将文件的完整内容注入每条消息。无分块，无语义搜索。对于在聊天中附加的文件和知识库，只要模型的 **Preload files** 能力开启，无论函数调用模式如何都会注入。而附加到模型上的知识库只在旧版函数调用模式下才注入：在原生函数调用下，模型通过知识工具访问附加到模型上的知识，无论是否使用全文上下文。

最适合简短的参考文档、风格指南，或始终相关的上下文。

**Settings** > **Documents**（管理员区域）中不超过 **Full Text Threshold (Characters)** 的文件和文本附件无需选择该模式即完整包含，而 **Always Use Full Text** 会把它应用到每个文档。知识库附件不受该阈值影响。

## 智能体知识工具 {#agentic-knowledge-tools}

![知识库内的文件，带搜索和排序](/images/workspace/knowledge-detail.png)

启用[原生函数调用](/features/extensibility/plugin/tools#tool-calling-modes-default-vs-native)后，模型使用 **Knowledge Base** 工具类别中的内置工具与您的知识库（下文简称 KB）交互。显示哪些工具取决于是否附加了知识，详见[范围访问](#scoped-access-keeps-things-organized)。

| 工具 | 已附加知识 | 未附加任何内容 | 说明 |
|------|:-----------:|:--------------:|-------------|
| `list_knowledge` | ✅ | ❌ | 列出已附加的知识库（带文件数量）、单个文件和笔记；传入 `knowledge_id`（含 `skip`/`count`，最多 200）可分页查看单个知识库的文件 |
| `list_knowledge_bases` | ❌ | ✅ | 浏览可用知识库（带文件数量） |
| `search_knowledge_bases` | ❌ | ✅ | 按名称或描述查找知识库 |
| `query_knowledge_bases` | ❌ | ✅ | 通过语义相似度搜索知识库名称/描述 |
| `search_knowledge_files` | ✅（仅已附加） | ✅（全部） | 按文件名搜索文件 |
| `query_knowledge_files` | ✅（仅已附加） | ✅（全部） | 使用 RAG 流水线搜索文件内容；已附加的笔记会以完整文本返回 |
| `grep_knowledge_files` | ✅（仅已附加） | ✅（全部） | 在知识库文件中进行精确文本/正则搜索（返回带行号的匹配行；自动检测正则如 `error\|warn`） |
| `view_file` | 附加了知识库或文件时 | ❌ | 分页读取文件内容（`offset`/`max_chars`）或按行号范围（`start_line`/`end_line`，可选 `line_numbers`）读取 |
| `view_knowledge_file` | 附加了知识库或文件时 | ✅ | 从任何可访问的知识库读取文件内容 |
| `display_file` | 附加了知识库或文件时 | ✅ | 在聊天中以inline 方式向用户展示某个文件，可选择展示到某一页或某一张幻灯片 |
| `view_note` | 附加了笔记时 | ❌ | 读取一条笔记 |

模型会被告知附加了什么：你的消息之后会附带一个隐藏的 `list_attached_knowledge` 工具结果，其中以 `<attached_knowledge>` 列表给出模型和文件夹的条目及其 ID，每条消息也会列出附加给它的条目。模型用这些 ID 分页查看某个知识库的文件清单，或把文件名搜索限制在单一知识库内。使用 `query_knowledge_files` 的内容搜索会在一次排序中覆盖所有已附加的知识，并返回其中得分最高的分块，因此来自不同知识库的分块会争夺同一批结果位次。

`list_knowledge` 和 `list_knowledge_bases` 互斥：附加了知识时，模型列出已附加的内容；什么都没附加时，它会发现用户能读取的每个知识库。

**笔记工具。** **Notes** 工具类别与知识工具是分开的。只要用户启用了笔记，并且模型的 **Notes** 类别开启，模型就会在每个聊天中获得 `search_notes`、`view_note`、`write_note` 和 `replace_note_content`，无论是否附加了知识，而且这些工具能覆盖用户能读取的每一条笔记。这就是为什么在什么都没附加的聊天中 `view_note` 也会出现。参见[智能体笔记管理](/features/notes#agentic-note-management)。

#### 何时优先使用 `grep_knowledge_files` 而非 `query_knowledge_files` {#when-to-prefer-grep\_knowledge\_files-over-query\_knowledge\_files}

两个搜索工具互为补充：

| | `query_knowledge_files` | `grep_knowledge_files` |
|---|---|---|
| **匹配方式** | 语义/向量检索（启用 [`ENABLE_RAG_HYBRID_SEARCH`](/reference/env-configuration#enable_rag_hybrid_search) 时可叠加 BM25 + 重排序） | 精确字符串匹配——自动检测正则（如 `error\|warn`、`version \d+`） |
| **返回内容** | 相关内容片段 | 带文件 ID、文件名和 1 起始行号的匹配行 |
| **适用场景** | “文档里关于 X 怎么说的？”——改写后的问题、概念性查找 | “找出所有提到 `OPENAI_API_KEY` 的地方”——字面标识符、错误字符串、版本号 |
| **结果上限** | 工具自身的 `count` 参数，由模型设置（默认 5）。管理员的 Top K 设置在此不适用 | 50 条匹配（[`KNOWLEDGE_GREP_MAX_MATCHES`](/reference/env-configuration#knowledge_grep_max_matches)） |
| **标志** | — | `case_insensitive`、`count_only`、`file_id`（单文件模式）|

在智能体流程中，典型的模式是：用 `query_knowledge_files` 定位相关文档，然后用 `grep_knowledge_files` 精确定位具体行，再用 `view_file`（下方行号范围模式）阅读周边上下文。

#### 用 `view_file` 读取 {#reading-with-view\_file}

`view_file` 支持两种寻址模式：

- **字符分页**： `offset` + `max_chars`（默认 `10000`，硬上限 `100000`；两者都可以通过 [`VIEW_FILE_DEFAULT_MAX_CHARS`](/reference/env-configuration#view_file_default_max_chars) 和 [`VIEW_FILE_MAX_CHARS`](/reference/env-configuration#view_file_max_chars) 配置）。最适合流式浏览长文档；当文件被截断时响应中会包含 `next_offset`。
- **行号范围**： `start_line` 和 / 或 `end_line`（1 起始，包含两端）。设置后覆盖 `offset`/`max_chars`；与 `grep_knowledge_files` 的行号天然搭配。传 `line_numbers: true` 还会在每行前加上 `<n>: <line>` 前缀。

行号范围响应包含 `total_lines` 和 `showing_lines`。范围会在最后一整行能装进 [`VIEW_FILE_MAX_CHARS`](/reference/env-configuration#view_file_max_chars) 的位置停下；`truncated` 和 `next_start_line` 会说明从哪里继续。

### 类文件系统访问（`kb_exec`） {#filesystem-style-access-kb\_exec}

设置 [`ENABLE_KB_EXEC=True`](/reference/env-configuration#enable_kb_exec) 后，Open WebUI 会暴露一个 `kb_exec` 工具，为模型提供对知识库的类文件系统接口。

**被移除的工具**（其功能已被 `kb_exec` 命令覆盖）：

- `list_knowledge` —— 由 `ls` 替代
- `search_knowledge_files` —— 由 `find "<glob>"` 替代
- `grep_knowledge_files` —— 由 `grep "<pattern>"` 替代
- `view_file` 和 `view_knowledge_file` —— 由 `cat`、`head`、`tail`、`sed -n '<a>,<b>p'` 替代

**仍然与 `kb_exec` 并存注入的工具**（因其能做 `kb_exec` 做不到的事）：

- **`query_knowledge_files`** —— 语义/RAG 搜索（始终保留）
- **`display_file`** —— 始终保留
- **`view_note`** —— 当附加了笔记时（`kb_exec` 只处理文件，所以笔记需要自己的读取器）
- **`query_knowledge_bases`** 和 **`search_knowledge_bases`** —— 当什么都没附加时，让模型仍能按名称/描述发现并搜索知识库

`kb_exec` 遵循同样的[范围划分](#scoped-access-keeps-things-organized)。什么都没附加时，`ls` 列出用户能读取的知识库。附加了知识时，`ls` 只列出已附加的知识库，随后在 **Attached Files** 下列出已附加的单个文件。笔记永远不会出现在 `kb_exec` 中：附加的笔记用 `view_note` 读取，或通过 `query_knowledge_files` 找到；当只附加了笔记时，`ls` 会回答 `No knowledge bases found.`

该功能**默认关闭**且仍处于实验阶段，但为了获得增强的智能体 RAG 体验，我们建议为运行原生函数调用的强模型启用它（`ENABLE_KB_EXEC=True`）。它面向的是那些已经“用 Shell 思考”的前沿模型：相比编排一系列专用工具的扇出，它们往往更可靠地串联 `ls`、`grep` 和 `cat`。它只在使用原生函数调用时生效；对于设为 Legacy 的模型，它不会产生任何效果。

**支持的命令**

| 命令 | 用途 |
|---------|---------|
| `ls`、`ls <dir>/`、`ls -a` | 列出当前层级 / 子目录 / 包含完整路径的扁平文件视图 |
| `ls -t`、`ls -S`、`ls -r` | 排序列表：最新优先、最大优先，或将当前顺序反转 |
| `tree`、`tree <dir>/` | 递归目录树 |
| `cat -n <file>` | 读取文件（可选带行号） |
| `head -N <file>` / `tail -N <file>` | 前 N 行或后 N 行 |
| `sed -n '<a>,<b>p' <file>` | 输出第 `<a>` 到 `<b>` 行 |
| `grep "<pattern>" [<dir>/\|<file>\|*.ext]` | 精确/正则搜索；标志 `-i`（不区分大小写）、`-l`（仅文件名）、`-c`（计数） |
| `find [<dir>/] "<glob>"` | 按 glob 查找文件，支持与 `ls` 相同的排序标志 |
| `wc <file>` | 行/词/字符计数 |
| `stat <file>` | 文件元数据 |

**管道**

`kb_exec` 解析单个流水线，因此命令可以组合：

```text
grep "auth" | head -5
grep -l "TODO" docs/
find docs/ "*.md" | head -10
```

**文件引用**

文件可以用三种方式寻址——选择最明确的那种：

- **路径** —— `docs/api/auth.md`（相对于知识库根目录；可穿透目录树解析）
- **文件名** —— `auth.md`（当多个目录或知识库中存在同名文件时，会以“模糊的文件名”提示报错）
- **文件 ID** —— `ls`、`find` 或 `grep` 返回的 UUID

**排序**

`ls`、`find` 和 `tree` 按路径列出文件，因此列表在多次调用之间是稳定且可比较的。有三个标志会改变这一点：`-t` 把最近更新的排在最前，`-S` 把最大的排在最前，`-r` 则反转当前适用的顺序，因此 `ls -tr` 就是最旧优先。它们可以与其他标志组合使用，例如 `ls -a -t` 或 `find docs/ "*.md" -S`。

在几千个文件的知识库里询问“最近改动了什么”，应该用 `ls -a -t | head -20`，而不是读取整份列表。

**行为说明**

- `kb_exec` 遵循与其他知识工具相同的访问控制——用户无法读取的文件会被静默地从结果中排除。
- **每次调用的输出都有上限。** 一条命令最多返回 30,000 个字符（[`KB_EXEC_MAX_OUTPUT_CHARS`](/reference/env-configuration#kb_exec_max_output_chars)），无论这些字符由什么产生；当触达上限时，模型会被告知收窄命令范围。这是整条链路的单次预算，因此对大文件执行 `cat` 与执行范围很宽的 `grep` 受到同样的限制。
- **范围过宽的 `grep` 会被拒绝而不是执行。** 搜索超过 200 个文件（[`KB_EXEC_MAX_GREP_FILES`](/reference/env-configuration#kb_exec_max_grep_files)）会返回提示，要求把搜索限定到某个目录或 glob；`grep` 最多返回 50 行匹配（[`KNOWLEDGE_GREP_MAX_MATCHES`](/reference/env-configuration#knowledge_grep_max_matches)），与 `grep_knowledge_files` 和 `grep_chat_files` 使用相同的上限。
- 模型仍保留 `query_knowledge_files` 用于语义搜索；在字面命令无法找到改写后的概念时使用。
- 构建于目录模型之上——`kb_exec` 是唯一完整体现 UI 中创建的目录结构的工具。

自主探索在能够智能链接搜索、浏览和综合的前沿模型上效果最佳。较小的模型可能难以处理多步检索。管理员可以在**Settings > Models > Edit > Builtin Tools**（管理员区域）中按模型禁用 **Knowledge Base** 工具类别（对自己的模型则使用 **Workspace > Models**）。

#### 在混合知识库之间引导工具选择 {#guiding-tool-choice-across-mixed-knowledge-bases}

启用 `kb_exec` 后，模型需要在两个互补的工具间选择。最简单的做法是写一段简短的**系统提示词**，按知识库指明应优先使用哪个工具：

- **散文与 PDF** 适合用 `query_knowledge_files`（语义搜索）。它按意义匹配，对改写后的问题和文档处理得很好，且不依赖干净的文本提取。
- **文本文件、代码、配置和日志** 适合用 `kb_exec`（`ls`、`tree`、`grep`、`cat`、按行号读取）。模型可以遍历目录树并拉取确切行，在字面标识符、错误字符串和结构方面胜过语义搜索。

一个按知识库明确这一划分的提示词能引导模型做出正确选择，同时仍允许它对每次调用做判断：

> 附加了两个知识库。**Handbook** 是 PDF 文档：有关它的问题请用 `query_knowledge_files`。**Codebase** 是源代码：使用 `kb_exec`（`grep`、`cat`、`ls`）查找并读取精确代码。一般来说，对精确字符串、标识符和文件结构优先用 `kb_exec`，对概念性问题优先用 `query_knowledge_files`。

没有 `kb_exec` 时，同样的区分也适用于 [`grep_knowledge_files` 和 `query_knowledge_files`](#when-to-prefer-grep_knowledge_files-over-query_knowledge_files)。

有关所有内置智能体工具的完整列表，请参阅[原生/智能体模式工具指南](/features/extensibility/plugin/tools#built-in-system-tools-nativeagentic-mode)。

:::warning 原生函数调用时知识库不会自动注入

启用原生函数调用时，附加的知识库**不会自动注入**。模型必须调用知识工具来搜索和检索。如果您的模型未使用附加的知识库：

1. **添加系统提示词指令**，告诉模型使用 `list_knowledge` 和 `query_knowledge_files`。
2. **用[知识库故障排查](/troubleshooting/rag#13-knowledge-base-attached-to-model-not-working)检查模型的工具能力和检索设置**。保持原生模式开启，并使用能可靠调用工具的模型。
3. **对于小文档，在聊天中以全文上下文模式附加它**，并开启模型的 **Preload files** 能力，这样它的完整文本会被注入。附加到模型或文件夹上的知识在原生函数调用下永远不会被注入。
:::

## 设置知识库 {#setting-up-a-knowledge-base}

关于最初的创建、上传和对话步骤，参见[提出第一个文档问题](#ask-your-first-document-question)。下面的章节介绍的是设置完成之后的知识库管理。

当知识库超过几个之后，可以通过点击 **Title** 或 **Updated at** 列标题对列表重新排序。点击当前正在排序的那个标题会反转方向。列表默认按 **Updated at** 排序，最新的在前。

要更改谁可以查看或编辑某个知识库，请打开其所在行的三点菜单并选择**访问**。这会直接打开访问设置，无需先进入知识库，而且每次改动都会立即保存。管理员在每个知识库上都能看到该菜单；其他用户只在可以编辑的知识库上看到它，并且需要[**知识库共享**](/features/authentication-access/rbac/permissions#2-sharing-permissions)权限。知识库内部的**访问**按钮遵循同样的规则。在拥有写入权限的情况下保存知识库名称或描述不会改变它的共享设置，包括你本人无权设置的**公开**选项。[资源访问](/features/authentication-access/rbac/groups#resource-access-rbac)解释了可见性与访问授权。

### 文件数量上限 {#file-limits}

管理员在 **Settings > Documents**（管理员区域）中设置全局上限：**知识库批量上传上限**（每次上传的文件数）、**知识库文件大小上限**（每个文件的 MB 数）和**知识库文件数量上限**（每个知识库的文件总数）。留空表示不限制。相同的值也可以通过 [`KNOWLEDGE_MAX_UPLOAD_COUNT`](/reference/env-configuration#knowledge_max_upload_count)、[`KNOWLEDGE_MAX_FILE_SIZE`](/reference/env-configuration#knowledge_max_file_size) 和 [`KNOWLEDGE_MAX_FILE_COUNT`](/reference/env-configuration#knowledge_max_file_count) 设置。

知识库的所有者或管理员可以为单个知识库设置更低的**文件数量上限**和**文件大小上限（MB）**，在创建时的**高级**选项中设置，或之后通过知识库页面上的三点菜单 > **设置**设置。当全局上限和局部上限同时存在时，适用较低的那个。外部知识库没有局部上限。

超出上限的上传会被拒绝，并提示类似 `Knowledge base file limit exceeded (N files maximum).` 或 `You can only upload a maximum of N file(s) per batch.` 的错误。

### 浏览与预览文件 {#browsing-and-previewing-files}

打开知识库后，文件以树形结构显示在左侧，右侧是预览面板。点击文件即可在预览中打开；在小屏幕上，预览会滑入覆盖列表。拖动分隔线可以调整文件列表的宽度。

预览有两种视图，通过其上方的按钮切换：

- **预览**：显示文件本身——PDF、图片、音频、视频、Word 文档、Excel 工作簿（带工作表选择器）、PowerPoint 幻灯片，以及 Markdown、代码、CSV、JSON、HTML 和 SVG 等文本类文件。文本类文件和 SVG 显示其索引文本；其他格式显示原始文件。对于 Markdown、CSV、JSON、HTML 和 SVG 这类有渲染视图的格式，**⋯** 菜单可在**查看源文件**和**渲染预览**之间切换。
- **索引文本**：显示 Open WebUI 从文件中提取的文本。检索和知识工具搜索的正是这部分内容，因此当答案遗漏了文档中确实存在的内容时，应该到这里来查看。

![左侧是知识库中的文件夹和文件，右侧预览视图打开了一个 PDF](/images/workspace/knowledge-browser-preview.webp)

![同一份 PDF 的索引文本视图，显示带行号的提取文本](/images/workspace/knowledge-browser-indexed-text.webp)

如果原始文件不可用（例如只保存了文本），文件会在**索引文本**中打开，且**预览**按钮会被隐藏。

**编辑索引文本**

拥有写入权限时，点击**编辑**即可修改索引文本，然后点击**保存**（或**取消**）。保存会重新处理新的文本，并更新所有包含该文件的知识库，使检索使用你修正后的文本。原始文件保持不变，而[重新索引](/features/chat-conversations/rag#what-does-re-indexing-do)会再次提取它，从而覆盖你的修改。文本不能为空。如果处理失败，会提示错误；再次保存即可重试。

在你有未保存的修改时，打开另一个文件、关闭预览、删除条目、同步、重置或离开页面，都会先询问**放弃未保存的修改？**。

**下载**

**下载**位于预览的**⋯** 菜单以及每个文件行的三点菜单中，它保存原始文件。对于因原始文件不可用而只在**索引文本**中打开的文件，下载会把索引文本保存为 `.txt` 文件。

**搜索、筛选与排序**

文件树上方的**搜索集合**输入框按文件名搜索整个知识库，文件夹内的结果会在名称旁显示文件夹路径。其旁边的筛选按钮提供：

- **搜索文件内容**：同时匹配文件内部的索引文本。超大文件会按字符上限搜索（[`RAG_FILE_CONTENT_SEARCH_MAX_CHARS`](/reference/env-configuration#rag_file_content_search_max_chars)）。
- **全部**、**由你创建** 或 **与你共享**：按文件的添加者筛选列表。
- **名称**、**创建时间** 或 **更新时间**，以及**升序** 或 **降序**：排序方式。默认是**更新时间**，最新的在前。
### 组织为目录 {#organizing-into-directories}

知识库支持嵌套的**目录**，让大型文档集保持可导航。从**添加内容**菜单（**+ 新建目录**）创建，然后自由重组。

**创建与导航**

- **+ 新建目录** 位于**添加内容**菜单中，与文件上传并列。同一父目录下强制名称唯一——两个同级不能同名，但不同父目录下可以重用名称。
- 点击目录可进入下一层；视图顶部的**面包屑导航**始终反映当前路径，可一键跳回任意上级。
- 目录可以**重命名**或**移动到其他父目录**，里面的文件不受影响。

**拖放**

你可以通过拖放来移动条目：

- **文件** 可以拖到目录行上、打开目录的空白区域上，或任意面包屑上（包括根面包屑，可将文件送回顶层）。
- **目录** 可以拖到另一个目录上以嵌套，或拖到面包屑上以向上移动。把目录移入自身或其后代会被服务端阻止。

**删除语义**

删除非空目录时会提示如何处理其中的内容：

- **将文件移到父目录**（默认）—— 目录被移除，但其文件和子目录会上移一层。
- **删除全部** —— 永久删除该目录及其下所有文件和子目录。

**对检索和工具的影响**

- **检索与标准 RAG** 仍然覆盖整个知识库。目录不会切分向量索引；任意子目录中的片段在单次搜索中仍然可达。
- **智能体工具** 具有目录感知能力：
  - `kb_exec`（启用时）把子目录当作文件系统：`ls docs/`、`tree`、`grep "x" docs/`、以及路径式引用（`docs/api/auth.md`）都可用——参见下方的[类文件系统访问（`kb_exec`）](#filesystem-style-access-kb_exec)。
  - 其他知识工具（`query_knowledge_files`、`grep_knowledge_files`、`search_knowledge_files`）忽略目录边界，从整个知识库返回匹配结果。

### 重命名文件 {#renaming-files}

单个文件可以在工作区中通过文件项菜单原地重命名——无需重新上传。新名称会在所有引用该文件的地方（知识库列表、智能体工具输出、引用）反映出来。

### 同步本地目录 {#syncing-a-local-directory}

**添加内容 → 同步目录** 操作会**增量地**把本地文件夹镜像到知识库：客户端对每个本地文件做哈希（SHA-256），服务端将哈希和路径与已存储内容对比，只处理**新增**、**修改**和**已删除**的文件。未修改的文件（通常是大多数）原样保留——不会重新上传或重新嵌入。本地文件夹的子目录结构会镜像到知识库中；缺失的子目录会被创建，本地不再存在的子目录会被移除。

:::tip 同步大量文件？改用 oikb
应用内的**同步目录**运行在浏览器中：它在客户端枚举、哈希并上传每个文件。对中等规模的文件夹没问题，但面对**大量**文件（数千个文件或数 GB 的资料库）时会变慢且进度反馈很少，常常要等很久才开始报告文件数。对于大型或频繁变化的资料库，我们**强烈推荐**使用官方的 [**Knowledge Base Sync (oikb)**](/ecosystem/knowledge-base-sync) 工具：它以原生方式运行，带进度条、并行上传和重试，正是为这种场景设计的。把入口指向文件夹根，它会同步整棵树（每个子目录，递归）到一个知识库。
:::

需要了解的行为：

- 隐藏文件和文件夹（以 `.` 开头的任何内容）会被跳过。
- 本地修改过的文件会以新的内容哈希上传；旧的文件条目会从知识库中移除并替换。
- 本地删除的文件会在清理步骤中从知识库中删除。
- 该操作对未修改的文件是**非破坏性**的。早期版本中的相同菜单操作曾会清空并重新上传所有内容——自 v0.9.6 起已不再如此。

对于编程使用，相同的工作流通过下方的[API 访问](#api-access)中两个端点暴露。

:::tip 同步远程源或按计划同步
应用内的**同步目录**操作处理的是你机器上的本地文件夹。要镜像**远程**源（GitHub 仓库、Confluence 空间、S3 桶以及[更多](/ecosystem/knowledge-base-sync#sources-and-connectors)），或按计划/在每次推送时**自动**保持知识库最新，请使用官方的 [**Knowledge Base Sync (oikb)**](/ecosystem/knowledge-base-sync) 配套工具。它会驱动这些相同的端点来完成任务。
:::

### 导出 {#exporting}

管理员可以通过条目菜单（三点）> **导出** 把整个知识库导出为 zip 文件。文件会被转换为 `.txt` 以保证通用兼容性。普通用户看不到导出选项。

### API 访问 {#api-access}

知识库可以通过编程方式管理：

**文件**

- `POST /api/v1/files/` — 上传文件（注意[文件数量上限](#file-limits)）。在上传元数据中传入 `knowledge_id`（可选 `directory_id`）会让后端**在服务端自动关联并处理该文件到指定知识库**——等价于随后调用 `POST /api/v1/knowledge/{id}/file/add`，但不依赖上传后客户端保持连接。这是推荐的单次调用路径（v0.9.6 引入，修复了上传者中途断开导致文件未关联的问题）。服务端会将上传字节做 SHA-256 哈希存入 `file.meta.file_hash`；客户端可以预先计算并通过元数据传入 `file_hash` 以跳过服务端哈希（增量同步流程会用到）。
- `GET /api/v1/files/{id}/process/status` — 检查处理状态。`completed` 表示索引以及任何知识库关联都已完成。
- `POST /api/v1/files/{id}/rename` — 重命名文件
- `GET /api/v1/files/{id}/content` — 下载原始文件。对于仅以文本形式存储的文件，返回 404 和 `Original file is unavailable.`。
- `GET /api/v1/files/{id}/content/{file_name}` — 以附件形式下载文件。当原始上传已不存在时，会以纯文本返回已索引的文本。
- `GET /api/v1/files/{id}/data/content` — 读取已索引的文本
- `POST /api/v1/files/{id}/data/content/update` — 替换已索引的文本（body：`content`），并在包含该文件的每个知识库中重新处理。空的 `content` 会以 `400` 拒绝。
- `POST /api/v1/knowledge/{id}/file/add` — 向知识库添加文件。提取文本已存在于该知识库中的文件会被拒绝，并提示 `Duplicate content detected. Please provide unique content to proceed.`
- `POST /api/v1/knowledge/{id}/files/batch/add` — 一次添加多个文件。重复检查同样适用：重复的文件会被报告为失败，其余文件仍会被添加。
- `POST /api/v1/knowledge/{id}/files/validate` — 在发送上传之前，按[文件数量上限](#file-limits)检查一次上传（body：`count`，可选的 `file_size`（字节）和 `removed_file_ids`）。返回 `{"status": true}`，或返回该上传本会遇到的同一个错误。
- `GET /api/v1/knowledge/{id}/files` — 列出知识库中的文件，按 `page` 分页。添加或更新文件的调用只在 `files` 中返回那些文件；而删除文件、重命名知识库或更改其访问权限时返回空的 `files` 列表，因此请从这里读取完整列表。
- `POST /api/v1/knowledge/{id}/file/move` — 在同一知识库内移动文件到其他目录（body：`file_id`、`directory_id`——`null` 表示移到知识库根目录）

**目录**

- `POST /api/v1/knowledge/{id}/dirs/create` — 创建目录（body：`name`，可选 `parent_id`）
- `POST /api/v1/knowledge/{id}/dirs/{dir_id}/update` — 重命名或重新归属目录（body：`name` 和/或 `parent_id`）
- `DELETE /api/v1/knowledge/{id}/dirs/{dir_id}/delete?move_files=true` — 删除目录。`move_files=true`（默认）时，目录内文件会上移；`move_files=false` 时，连同目录一起被删除。

**增量目录同步**（v0.9.6 引入）

- `POST /api/v1/knowledge/{id}/sync/diff` — 提交本地清单（`manifest: [{path, filename, checksum}]`，其中 `checksum` 是文件字节的 SHA-256），返回 `{added, modified, deleted, mkdir, rmdir, unmodified_count}` 描述要上传、替换、删除的内容，以及要创建/移除的目录。只读——不会修改知识库。不到一小时前上传到该知识库、且仍处于待处理或处理中的文件，在其路径、名称和校验和都匹配时会被计为未修改，因此第二次同步不会重复上传它；满一小时后它会再次被提供上传。
- 在按 diff 操作后（创建 `mkdir` 路径，通过 `POST /api/v1/files/` 上传 `added` + `modified` 文件并附带哈希），调用：
- `POST /api/v1/knowledge/{id}/sync/cleanup` — body：`{file_ids: [...], dir_ids: [...]}`。移除陈旧的文件（从知识库、向量存储和每文件集合中）以及 `sync/diff` 返回的现已为空的目录。请最后运行，避免删除赶在上传之前。

文件处理是异步的。在将文件添加到知识库之前，必须轮询状态端点直到处理完成，否则会收到“内容为空”错误。有关工作流示例，请参阅 [API 端点](/reference/api-endpoints#retrieval-augmented-generation-rag)。

## 使用场景 {#use-cases}

### 项目文档 {#project-documentation}

将团队的技术规格、架构文档和操作手册上传到知识库。将其附加到“项目助手”模型。AI 根据您的实际文档回答问题，而不是通用的训练数据。

### 法律和合规审查 {#legal-and-compliance-review}

加载合同、政策和监管文件。让 AI 查找特定条款、比较协议间的条款，或标记不一致之处。

### 研究综合 {#research-synthesis}

将数十篇论文添加到知识库。AI 在所有论文中搜索以回答问题、找到支持证据，或识别研究之间的矛盾。

## 局限性 {#limitations}

### 全文上下文模式的上下文窗口 {#context-window-with-full-context-mode}

“使用整个文档”会注入全文。将大型文档附加到上下文窗口较小的模型，将会挤占对话历史。

### API 上传的处理延迟 {#processing-delay-for-api-uploads}

通过 API 上传的文件是异步处理的。在处理完成之前尝试使用文件将会静默失败或返回空结果。请注意，使用 `knowledge_id` 上传（见上）只是让关联在服务端完成、且对客户端断开更具鲁棒性，但并**不**意味着内容可以即时查询——提取和嵌入仍在后台运行，所以在依赖检索之前请轮询 `GET /api/v1/files/{id}/process/status`。

### 原生函数调用改变行为 {#native-function-calling-changes-behavior}

启用原生函数调用会改变知识库的工作方式。如果你的知识库突然停止产出结果，请检查全局模型默认值中是否设置了 `function_calling: native`。详情请参阅[知识库故障排查](/troubleshooting/rag#13-knowledge-base-attached-to-model-not-working)。
